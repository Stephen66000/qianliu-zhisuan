# 仟流智算通知体系与熔断模块位置

- 收集时间：2026-07-31（Asia/Shanghai）
- 个人定向通知复核：2026-08-01（Asia/Shanghai）
- 目标：明确熔断模块在管理后台的位置，并为当前单公司内部试验提供最小通知闭环。

## Owner 范围纠正（2026-08-01）

当前产品只供一家公司约 10 名内部人员试验，不建设多租户、多企业配置或企业间隔离能力。第一版只做个人定向通知：通过企业微信自建应用按 `userid` 直接发送给人员本人／项目负责人，不建立通知群，不使用群机器人 Webhook。本文后续涉及通用通知平台、多渠道编排和多公司扩展的内容均作为远期调研，不进入本次开发计划。正式实施以《仟流智算“运行保障”一级模块开发计划》为准。

## 一、现有产品盘点

### 已有能力

1. 管理后台已有独立“异常告警”入口 `/alerts`。
2. 数据库已有 `alert_event` 事实表，包含：告警域、技术信号、严重度、资源／主体／请求关联、首次与最后出现时间、处置状态和恢复时间。
3. 告警生命周期已支持 `OPEN → INVESTIGATING → RESOLVED/IGNORED`，源事实恢复时进入 `AUTO_RESOLVED`。
4. 同一活跃 `alert_key` 有唯一约束，可以作为通知去重的基础。
5. 后台支持查看历史、标记处理中／已处理／忽略，并写入操作日志。

### 现有缺口

1. 当前 PRD 明确规定一期告警只在管理后台展示，不发送外部渠道。
2. `GET /alerts` 才会调用 `AlertEventRepository.evaluate()`；Worker 没有主动评估任务。因此如果没人打开异常中心，系统不会及时生成并推送这些派生告警。
3. 当前没有通知策略、通知渠道、接收人、发送队列、失败重试、送达记录、升级和确认机制。
4. `principal` 只有姓名、类型和部门，没有企业微信 `userid`、手机号、邮箱或通知偏好；`admin_user` 也没有通知联系方式。
5. 项目主体没有明确的负责人绑定，无法确定项目异常应该通知谁。
6. WorkBuddy、Claude Code、ZCode 只持有主体 Key。Gateway 可以在当前失败请求里返回可读错误，但这只能通知正在调用的人，不能替代主动通知。

结论：现有“异常中心”可以保留并扩展，但现有系统还不存在完整通知体系。

## 二、模块位置建议

新增一级导航“运行保障”，替代当前单独的“异常告警”入口。其下设置：

1. 运行态势：当前资源健康、正在熔断、无备用资源和未处置重要事件；
2. 可用性规则：上游信号规则、计划熔断规则和故障预警规则；
3. 熔断事件：每次触发、影响范围、恢复条件、命中规则版本和恢复记录；
4. 异常中心：复用并扩展现有 `alert_event`；
5. 通知策略：事件级别、接收角色、渠道、升级、去重和恢复通知。

各业务页面保留状态和快捷入口：

- 厂商资源：显示当前是否被熔断，并可跳转到对应事件；
- 使用主体：维护通知身份、负责人和订阅偏好；
- 系统设置：维护企业微信应用、群机器人 Webhook 等渠道凭证；
- Gateway：对当前受影响请求返回标准错误、恢复时间和替代模型信息。

边界：通知“策略”属于运行保障；通知“渠道凭证”属于系统设置；通知“接收人身份”属于使用主体／管理员。避免把所有配置塞进同一页面。

## 三、统一通知体系

### 事件来源

- 熔断触发、恢复和恢复时间变化；
- 额度预计耗尽、主体用量异常；
- 凭证失效、账本异常和安全事件；
- 配置发布、计划熔断开始／结束；
- 后续其他业务模块的重要事件。

事件源不直接调用企业微信。事件先进入统一通知内核，由策略决定是否发送、发给谁、通过什么渠道发送。

### 核心对象

1. `notification_policy`：事件类型、严重度、接收角色、渠道、去重窗口、升级和恢复通知；
2. `notification_channel`：后台站内信、企业微信自建应用、企业微信群机器人，以及后续邮件／短信／通用 Webhook；
3. `notification_recipient_binding`：主体／管理员／资源负责人到企微 `userid`、群或其他地址的映射；
4. `notification_delivery`：每次发送的幂等键、状态、重试次数、发送时间和厂商返回结果；
5. Worker Outbox：异步发送，业务事务只写事件和 Outbox，不在 Gateway 请求热路径同步调用外部渠道。

### 谁应该收到

- 技术管理员／值班群：凭证、资源、路由、全池不可用、账本和安全事件；
- 资源负责人：对应资源的额度、套餐、权限和熔断事件；
- 受影响员工：只有本人当前无法使用或即将无法使用，且没有透明切换成功时通知；
- 项目负责人：项目额度、费用或模型可用性异常；
- 普通未受影响人员：不发送。

### 去重与升级

通知以“事件”而不是“失败请求”为单位：首次触发发送一次，后续请求只累计影响数；恢复时间或严重度变化时更新；持续未恢复按策略升级；恢复后发送关闭通知。计划熔断属于通知，不进入故障报警统计。

## 四、企业微信渠道选择

### 企业微信群消息推送／机器人

- 优点：接入最简单，只有一个群 Webhook；适合作为管理员和值班群通知。
- 能力：支持文本、Markdown、模板卡片等消息，并可按 `userid` 或手机号在群内提醒成员。
- 限制：只能发到配置它的群，不能替代面向每位员工的个人消息；官方限制每个消息推送不超过 20 条／分钟；Webhook 本身是敏感凭证，必须加密保存和轮换。

### 企业微信自建应用消息

- 优点：可按成员 `userid`、部门或标签定向发送个人应用消息，适合通知具体员工和负责人。
- 前提：企业配置 CorpID、应用 AgentID／Secret，接收成员在应用可见范围内，并完成 `principal → wecom_userid` 身份映射。
- 限制：配置和权限比群机器人复杂；需要管理 token、可见范围、接口许可、频率限制和无效成员返回。

### 当前试验版选择

1. 个人受影响事件：企业微信自建应用按 `userid` 直接发送给本人／项目负责人；
2. 当前请求即时反馈：Gateway 标准错误体和 `Retry-After`；
3. 所有事件与发送结果：后台异常中心留痕；
4. 群机器人 Webhook 明确不采用，因为它只能向配置群推送，不能实现本次要求的个人直达。

若仟流 AI 现有企业微信平台应用已经具备可用的 CorpID／AgentID／Secret、应用可见范围和成员 `userid` 映射，优先通过通知渠道适配器复用；否则为仟流智算创建独立自建应用。无论复用还是独立，通知内核都不能直接依赖某个具体企业微信应用。

## 五、建议实施顺序

### 第一阶段：个人定向通知闭环

1. 将告警评估从 `GET /alerts` 副作用中拆出，改为事件触发 + Worker 周期兜底；
2. 建人员 `userid` 绑定、Outbox 和发送记录；
3. 接入企业微信自建应用消息和 token 生命周期；
4. Gateway 返回统一的受影响用户提示；
5. 熔断触发、恢复、无备用资源接入通知内核。

### 第二阶段：远期增强（不进入本次计划）

1. 增加确认、认领、升级和恢复闭环；
2. 增加通知偏好和免打扰；
3. 评估其他渠道，但不得影响当前个人企微通知主链。
