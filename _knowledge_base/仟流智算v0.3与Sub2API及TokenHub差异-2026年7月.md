# 仟流智算 v0.3 与 Sub2API、TokenHub 差异

- 收集时间：2026-07-26（Asia/Shanghai）
- 对照版本：
  - 仟流智算：本工作区 PRD／TRD v0.3
  - TokenHub：本地提交 `1f4e7fe2bf25084f1a525e3ba2392be1e6bc49d2`，并复核 GitHub `main`
  - Sub2API：本地源码快照（目录未包含 Git 元数据），并复核 GitHub `main`
- 产品口径修订（佳哥，2026-07-26）：
  - API、Coding Plan 和账号池在仟流内部统一以 Token 为基础用量事实；
  - 最终客户是企业用户及其团队，内部单企业仅为首期 Pilot；
  - 正文零留存是当前默认策略，未来可按明确企业需求增加受控留存；
  - TokenHub／Sub2API 的成熟优势应进入仟流目标架构，只在实现顺序上分期。

## 一、结论

三者已经有明显交集，但不是同一类产品：

- **TokenHub** 是“企业 AI Gateway”：重点是统一模型入口、团队／项目治理、身份权限、路由、审计和成本归因。
- **Sub2API** 是“订阅账号池与配额分发平台”：重点是多账号接入、账号调度、API Key 分发、计费、支付和对外运营。
- **仟流智算 v0.3** 是“企业级 AI Token 管理与算力权益平台”：Gateway 是核心数据面；API、Coding Plan 和账号池在底层统一产生 Token 用量事实，再形成企业的分配、持续供给、计量和经营调度。目标客户是企业用户及其团队，仟流内部使用只是首期 Pilot。

因此，v0.3 与两者的关系是：

> 把 TokenHub 的企业 Gateway 与治理能力、Sub2API 的账号池、多因子调度、多协议和流式执行能力纳入仟流目标架构，再以统一 Token 事实、供给预测、逐次账本和经营调度形成自己的产品闭环。

## 三、v0.3 的产品闭环

### 1. 统一 Token 是基础，算力权益是上层表达

API、Coding Plan 和账号池的采购、结算方式不同，但员工和项目最终消耗的基础事实都是输入、输出、缓存等 Token。仟流先保存 Token，再根据资源、模型、Token 类型和版本化规则派生厂商扣减与费用。

### 2. 四项原则成为系统约束

v0.3 不再把“持续生产、按量消耗、存在峰谷差异、必须计量和调度”当口号，而是落实为：

- 供给快照与耗尽／恢复预测；
- 请求前经营调度；
- 请求后的逐 Attempt 计量；
- 策略、决策、执行和节省证据闭环。

TokenHub 与 Sub2API 都覆盖其中若干能力，Sub2API 甚至已经有复杂调度，但两者的公开产品定义都没有把四项原则组织为与仟流相同的企业经营契约。

### 3. “请求结算”和“真实消耗”分层

发生故障切换时，一个员工请求可能实际消耗多个上游账号。v0.3 明确：

- 一个 `ai_request` 对应一个 `ledger_transaction`；
- 每个真实消耗 Attempt 对应一个 `usage_event` 和 `ledger_line`；
- 失败 Attempt 的真实消耗不能因最终请求成功或失败而丢失；
- 原始 Token、厂商实际扣减和实际费用分别保存。

这是比普通“每请求一条 UsageLog”更严格的财务与审计模型。

### 4. 从“资源可用”推进到“资源还能生产多久”

v0.3 的 `resource_supply_snapshot` 同时保存：

- 1 小时／24 小时／7 天消耗速度；
- `forecast_exhaust_at`；
- `next_recover_at`；
- `coverage_duration`；
- `confidence`。

它回答的是经营问题，而不仅是网关健康问题。

### 5. 调度结果必须可解释、可证明

v0.3 要冻结 `dispatch_policy_version` 和 `dispatch_decision`，并保存：

- 当时的峰／谷状态；
- 成本、额度余量和剩余周期；
- 候选资源与最终动作；
- 选择理由；
- 反事实基线；
- 只有证据完整时才计算的 `dispatch_saving`。

这使“智能调度”不仅能跑，还能向企业解释为什么这样跑、到底省了多少钱。

### 6. 正文零留存是当前策略

TokenHub 已提供请求／响应正文审计能力；仟流当前先选择“只留经营和技术元数据，不留员工提示词、代码、文件与回答正文”。这不是永久产品边界。未来如企业明确需要内容审计或质检，可以独立增加，但必须默认关闭，并落实加密、权限、访问审计、留存期限和可验证删除。

## 四、仟流当前的实现差距

不能因为 v0.3 文档定义得更完整，就判断产品已经超过两者。当前客观差距是：

1. **工程成熟度**：仟流仍是设计目标；TokenHub、Sub2API 已有运行代码和大量测试。
2. **协议广度**：目标协议矩阵已经纳入 v0.3，但 Sub2API、TokenHub 已实现；仟流仍需按 PoC 开发和启用。
3. **账号池与流式执行**：账号池生命周期、多因子评分、粘性、并发、WebSocket 和故障处理已经纳入目标架构，但 Sub2API 已有成熟代码，仟流尚未实现。
4. **企业身份治理**：企业团队、成本中心、OAuth／OIDC、RBAC 已进入产品路线，但 TokenHub 当前实现更完整。
5. **验证证据**：仟流的逐 Attempt 账本、供给预测和峰谷经营调度仍需 PoC、契约测试和一个自然月验证。

## 五、产品边界判断

### 已纳入目标架构的 TokenHub 能力

- Provider／Resource／Route 分层；
- 企业项目 Key、身份、RBAC 和成本归因；
- 能力注册、协议适配、路由日志；
- Session Affinity、流式故障边界和多实例部署。

### 已纳入目标架构的 Sub2API 能力

- OAuth／API Key 账号池；
- 账号评分、冷却、配额余量、并发与限流；
- Claude Code／Codex／Gemini 等客户端兼容；
- SSE／WebSocket 长连接与故障切换测试；
- 复杂上游差异的 Adapter 工程经验。

### 必须保持仟流自有定义

- 企业级 Token 管理与算力权益表达；
- API、Coding Plan 和账号池统一产生 Token 事实，再分别派生扣减和费用；
- 请求结算＋逐 Attempt 不可变账本；
- 供给耗尽／恢复预测；
- 版本化峰谷经营调度和节省证据；
- 当前默认正文零留存及未来受控留存的安全边界；
- 面向企业客户及其团队，而非把内部 Pilot 写成永久产品边界。
