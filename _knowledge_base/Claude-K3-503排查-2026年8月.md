# Claude 使用 K3 出现 503 的根因排查

- 收集时间：2026-08-01 08:25（Asia/Shanghai）
- 排查范围：Claude Desktop / Claude Code、CC Switch 3.19.0、仟流 Gateway、Kimi K3

## 结论

截图中的 `503 无可用上游资源` 是末端结果，不是第一现场。实际故障链为：

1. Claude 完成 Web Search 后，下一轮请求携带 Anthropic Messages 协议的 `tool_use` / `tool_result` 历史；
2. 仟流 Gateway 把请求转向 Kimi 的 OpenAI-compatible Chat Completions 接口，但当前协议转换只转换了工具定义，没有转换工具调用历史和 `tool_choice`；
3. Kimi 上游因此返回请求格式错误，仟流 Gateway 又把非 429 的上游错误统一包装成可重试的 HTTP 502；
4. 连续失败后资源池或 CC Switch 熔断，最终返回 HTTP 503 `无可用上游资源`；
5. Claude 客户端只显示最后的 503，所以表面上看起来像 K3 或本机代理随机不可用。

K3 模型本身和本机 `127.0.0.1:15721` 监听服务都不是本次主因。纯文本对话通常正常，进入 Web Search、MCP 或其他工具调用的第二轮后更容易复现。

## 关键证据

### 1. 截图对应时段的原始错误顺序

`~/.cc-switch/logs/cc-switch.log` 在 2026-08-01 00:03:18–00:03:39 记录：

- 三次 `上游 HTTP 502: invalid_request_error`；
- 随后连续出现 `上游 HTTP 503: 无可用上游资源`；
- 请求目标始终为 `https://gw.qianliuai.com/v1/messages (model=Kimi)`。

这与截图中“刚完成 Searched the web，随后报 503”的顺序一致。

### 2. 协议转换存在确定缺口

`packages/provider-adapters/src/openai-compatible-caller.ts` 当前行为：

- Anthropic 工具定义会转换为 OpenAI `tools[].function`；
- Anthropic 消息内容的 `tool_use` / `tool_result` 被原样放进 OpenAI `messages[].content`；
- Anthropic `tool_choice: {type: "tool", name: ...}` 被原样传给 OpenAI 上游；
- 没有转换成 OpenAI 所需的 assistant `tool_calls`、`role: "tool"`、`tool_call_id` 和 function tool choice。

最小诊断载荷已经稳定复现上述错误转换结果。

### 3. 错误分类会放大故障

`apps/gateway/src/pipeline/real-pipeline.ts` 当前会把除 429 外的上游错误统一返回为 HTTP 502 且标记 `retryable: true`。因此原本应归类为客户端请求格式错误的 400，会被 CC Switch / 资源池当成上游临时故障，连续重试并触发熔断。资源池没有健康候选后，Gateway 返回 503 `no_healthy_candidate`。

### 4. 另有独立的额度/限流故障

2026-07-31 15:16:43–15:17:02，日志还记录了三次 `429 上游套餐暂时限流`，随后触发熔断并返回 503。2026-07-28 也出现过 Kimi 官方 `403 usage limit for this billing cycle`。

因此同一个 503 外观至少有两条前因：

- 工具协议转换错误：`invalid_request_error → 502 → 熔断 → 503`；
- 套餐额度或并发限流：`403/429 → 熔断 → 503`。

## 修复优先级

1. P0：完整实现 Anthropic Messages 与 OpenAI Chat Completions 的工具历史双向转换，并增加 Web Search / MCP 多轮回归测试。
2. P0：保留上游 HTTP 400 的客户端错误语义，禁止包装为可重试 502，也禁止这类错误污染资源健康状态。
3. P0：生产日志保留上游稳定错误码、request id 和失败阶段，不能只剩 `invalid_request_error`。
4. P1：429 按 `engine overloaded`、并发限制、周期额度耗尽分类处理；只有临时过载才短退避重试。
5. P1：K3 至少配置第二个健康资源或明确降级路由，避免单资源故障直接变成全局 503。

## 当前配置的旁支问题

当前 CC Switch 数据库中 Claude 的 current provider 已变为 `default`，但该 Provider 缺少 `base_url`，新请求会直接报 400。它是切换配置后产生的独立问题，不是截图时 K3 503 的原始原因。
