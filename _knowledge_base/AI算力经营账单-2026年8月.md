# AI 算力经营账单产品分析

- 收集时间：2026-08-02（Asia/Shanghai）
- 背景：围绕“买了什么、谁在用、产生了什么价值”重新审视仟流智算核心产品闭环
- 当前性质：讨论记录与产品分析，尚未进入 PRD、开发计划或代码调整

## 一、核心判断

仟流智算当前已经拥有资源、主体、请求、Token、扣减和 API 费用等基础事实，但这些事实分散在首页看板、厂商资源和用量账本中，尚未形成老板可以直接阅读的月度经营结论。

产品缺失的不是另一张厂商发票，而是“AI 算力月度经营账单”：

1. 资产账：企业买了哪些厂商、账号、API 余额和套餐权益；
2. 消耗账：谁使用了哪些资源，消耗多少，是否用满、闲置、超额或提前耗尽；
3. 价值账：业务负责人对项目或用例产生的价值进行人工记录和确认；
4. 经营结论：把投入、使用和人工确认价值放在同一期间、同一主体或项目下对照。

账单负责提供可信事实和归因，不替代人判断价值。产品可以计算投入、利用率、分摊和比率，但不得根据 Token 数自动推断业务价值或员工能力。

## 二、现有系统已经具备的数据

### 买了什么

- Provider、API／Coding Plan 资源和上游账号；
- API 充值金额、余额、本期费用经营快照；
- 套餐费用、总额度、有效期和重置周期；
- 历史资源经营快照。

### 谁在使用

- 员工／项目主体；
- 独立 Key；
- 请求时间、客户端、统一模型、实际上游资源；
- 输入、输出、缓存 Token；
- 套餐实际扣减额度和 API 请求费用。

### 当前已有的经营信号

- 本月 API 费用和套餐费用；
- 资源耗尽预测；
- 超额、异常和调度节省；
- 请求级账本筛选与下钻。

## 三、当前真正缺失的产品能力

### 1. 没有月度结账对象

当前首页只展示当月实时指标，没有“待结账／已结账／重开”的期间状态，也没有冻结当期购买、账单、使用和分摊结果。历史月份无法作为一份稳定经营报告复核。

### 2. 没有按主体／项目汇总的月账单

用量账本能够筛选某个主体并查看单次请求，但没有直接输出：

- 每个人／项目用了哪些厂商和模型；
- 使用次数、Token、套餐扣减和 API 费用合计；
- 占企业总使用的比例；
- 活跃天数、是否闲置或异常；
- 分摊到该主体／项目的采购成本。

### 3. API 与固定套餐还没有统一但不混淆的成本口径

API 请求可以按实际 Token 和价格规则精确归因到主体。

Coding Plan 是固定采购费用，不能伪造成每次调用的厂商实际费用。月账单应同时展示：

- 厂商实际支出：套餐固定费用；
- 权益利用：总额度、已用、剩余和利用率；
- 管理分摊：按实际扣减额度或已确认规则把固定费用分摊给主体／项目；
- 未使用权益：单独展示，不能强行分摊给使用者。

“管理分摊成本”必须与“厂商实际账单”明确区分。

### 4. 没有人工价值确认入口

价值不应由系统根据 Token 自动生成，但系统需要允许业务负责人记录：

- 价值事项名称；
- 关联项目／用例和账单期间；
- 价值类型：新增收入、节省成本、节省时间、提升质量、降低风险或其他；
- 价值说明和证据；
- 金额或非金额指标（均可为空）；
- 提报人、确认人和确认时间；
- 关联的 AI 使用主体、资源和成本范围。

系统只对人工确认的数据计算投入产出比，并明确标注“人工确认价值”，不得冒充自动测量事实。

### 5. 没有一页式老板视图

当前数据虽然存在，但需要在多个页面之间筛选、加总和解释。只要仍需老板或技术负责人自己拼表，就不能算产品已经回答了“买了什么、谁在用、产生了什么价值”。

## 四、建议的月度经营账单结构

### 账单总览

- 账单期间、状态和数据完整度；
- 采购／充值现金流；
- API 实际消耗成本；
- 套餐固定费用；
- 当前余额和未使用权益；
- 活跃人员／项目数量；
- 人工确认价值；
- 调度节省；
- 待确认或无法归因金额。

### 厂商账

| 厂商／资源 | 采购或充值 | 当期实际消耗 | 期末余额／剩余额度 | 利用情况 | 使用主体 |
|---|---:|---:|---:|---|---:|
| DeepSeek API | 充值现金流 | 厂商／内部账本费用 | 当前余额 | 消耗趋势 | 人／项目数 |
| 智谱套餐 | 固定套餐费 | 套餐扣减额度 | 剩余额度 | 用满／闲置／超额 | 人／项目数 |
| Kimi 套餐 | 固定套餐费 | 套餐扣减额度 | 剩余额度 | 用满／闲置／超额 | 人／项目数 |

### 主体／项目账

| 员工／项目 | 厂商与模型 | 调用／活跃 | Token／扣减 | API 实际费用 | 套餐管理分摊 | 关联价值 |
|---|---|---:|---:|---:|---:|---|

### 价值确认

由业务负责人填写并确认。例如：“某项目使用智谱套餐，账单分摊成本 500 元；负责人确认缩短交付周期并产生约 10 万元业务价值。”系统保存确认人、说明、证据和口径，并据此展示投入与价值，不负责替人证明 10 万元是否成立。

## 五、关键会计口径

### 充值不等于费用

DeepSeek 当月充值 1,000 元，但当月只消耗 300 元时：

- 现金流出：1,000 元；
- 当期 AI 消耗成本：300 元；
- 剩余资产：700 元（暂不考虑赠金等调整）。

经营账单必须同时展示三者，不能把充值金额直接当成本。

### 固定套餐费用不等于单次真实费用

套餐费用是企业采购支出；员工占用比例是管理分摊。二者可以关联，但不能混为厂商逐次计费事实。

### 使用量不等于价值

用量只能证明采用、消耗和归因。价值由项目或业务负责人确认；系统负责留下可复核证据并计算比率。

## 六、产品定位推论

“AI 算力经营账单”不应只是一个报表功能，而应成为仟流智算的主要老板入口：

> 每个月告诉企业：买了什么，谁用了，钱和权益落到了哪里，业务负责人认为产生了什么价值。

Gateway、资源管理、账本、预测和调度都是这张经营账单的数据采集与执行底座。

## 七、外部方法参考

FinOps Foundation 将 Unit Economics 定义为把技术支出与组织获得的价值连接起来，并明确区分资源效率指标（如每 Token 成本、每席位成本）和业务指标（如每个完成事项、每个业务结果成本）。对生成式 AI，成熟路径通常从 Token 成本开始，再逐步扩展到每次辅助、每个 Agent 动作或每个业务结果的成本。

这支持本文的产品方向：仟流先提供准确账单和归因，价值指标由业务侧提供，再逐步形成稳定的单位经济口径。
