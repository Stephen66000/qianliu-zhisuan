# Spec Delta

## Purpose

使员工分配额度成为按企业时区自然月运行、按厂商池可追溯、按既有超额策略执行的内部用量控制，区分真实 Token、套餐折算额度和 API 金额，使月初重置、跨月请求和历史月报能够相互核对。

## ADDED Requirements

### Requirement: 内部额度与厂商计费分开计量

系统 SHALL 对 API 员工额度计入真实输入加输出 Token，对 Coding Plan 员工额度计入请求时冻结规则计算的扣减量。系统 MUST 保留真实 Token、套餐扣减、API 金额各自事实，不将 API 额度计量写成套餐扣减或虚构现金费用。

#### Scenario: API 有用量而无套餐扣减
- **WHEN** API Attempt 上报输入 1000、输出 200 Token，API 套餐扣减字段为空
- **THEN** 员工所属厂商池当月已用增加 1200，套餐扣减仍为空，API 金额按原价格规则记录

#### Scenario: Coding Plan 按冻结倍率扣减
- **WHEN** Coding Plan Attempt 实际使用 1200 Token，冻结的额度倍率为 0.5
- **THEN** 真实用量为 1200 Token，员工额度扣减为 600，事后改倍率不重算这条历史事实

### Requirement: 额度以企业时区自然月独立运行

系统 SHALL 使用企业时区的每月 1 日 00:00 至下月 1 日 00:00 的半开区间作为额度周期；进入新月时建立独立额度账并令新月已用与预占为零。旧月用量、余额和超额 MUST 留存，不通过清零旧记录实现重置，不结转上月未用额度。

#### Scenario: 月初重置并保留上月
- **WHEN** Asia/Shanghai 企业从 11 月 30 日 23:59:59 进入 12 月 1 日 00:00:00
- **THEN** 新请求使用 12 月额度，上月未用额度不转入 12 月，11 月额度账仍可读取

#### Scenario: 跨年与不同月长
- **WHEN** 系统进入下一年 1 月或闰年 3 月
- **THEN** 周期由自然月边界确定，不以固定 30 天或服务器时区代替

#### Scenario: 初始化任务暂时未运行
- **WHEN** 月初 Worker 尚未完成额度初始化，但新月请求或额度查询已经到达
- **THEN** 同一新月额度账被建立或读取，请求不继续使用旧月剩余量，也不重复获得多份额度

### Requirement: 月度额度继承已生效分配且月内调整留痕

系统 SHALL 在月初从该时点有效的员工厂商授权初始化月额度，月中首次授权从生效时开始可用且不按天折减。月内“设置总额度”改变本月上限，“追加额度”增加本月上限，均保留本月已用与预占；后续月份继承最新已生效配置。

#### Scenario: 月内追加不重置已用
- **WHEN** 本月总额 1 亿、已用 6000 万，管理员追加 2000 万
- **THEN** 本月总额为 1.2 亿、已用仍为 6000 万，变更原因与前后额度可追溯

#### Scenario: 下调额度至已用以下
- **WHEN** 本月已用 6000 万，管理员把总额设为 5000 万
- **THEN** 已用保留，报告超额 1000 万；后续准入遵守该授权的允许超额开关

#### Scenario: 月内停用再启用
- **WHEN** 同一员工厂商池在本月被停用后重新启用
- **THEN** 既有本月用量不消失；系统不通过更换授权标识赠送一份新月额度

### Requirement: 允许超额与额度使用事实独立

系统 SHALL 保留每条授权的允许超额策略。允许超额时继续记录全部已用及超过总额的部分；禁止超额时对预计超出可用额度的请求在访问上游前拒绝。系统 MUST NOT 把允许超额解释为“不计量”或在本次修复中批量改为禁止超额。

#### Scenario: 保留当前允许超额配置
- **WHEN** 一条允许超额的 API 授权分配 1 亿，当月实际用量达到 1.89 亿
- **THEN** 该授权仍按策略可用，已用显示 1.89 亿、剩余可用为零、超额约 0.89 亿，而非已用为零

#### Scenario: 禁止超额的 API 额度不足
- **WHEN** API 员工授权禁止超额且剩余额度不足以覆盖本次预占
- **THEN** 返回主体额度耗尽错误，本次不访问上游；原有 Key 限制和厂商余额判定仍独立执行

### Requirement: 预占与实耗遵守相同月份和额度基础

系统 SHALL 在访问上游前按目标厂商池和该次额度基础预占，并在结算时多退少补。真实有消费的失败 Attempt SHALL 计量；确认未访问上游的拒绝 SHALL 释放未消费预占。未知用量 MUST 保留未知标记，不能冒充零消费或准确余额。

#### Scenario: 失败 Attempt 仍有真实用量
- **WHEN** 上游 Attempt 失败但上报 1200 个 API Token
- **THEN** 其当月内部额度增加 1200，不因终态失败退成零；成功请求次数可另行统计

#### Scenario: 上游前拒绝
- **WHEN** 预占后授权被撤销，且能够确认本次未访问上游
- **THEN** 撤销阻断仍有效，未消费预占释放，内部额度不会产生虚构实耗

#### Scenario: 已访问上游但用量未知
- **WHEN** Attempt 已访问上游且未获得可信用量
- **THEN** 保留保守预占并标记待核，报表不把该余额显示为完整确定值

### Requirement: 跨月请求结算回原预占月份

系统 SHALL 以每次 Attempt 访问上游前的预占时间确定额度月份，并将该 Attempt 的实际结算写回该月。请求重试产生新的 Attempt 时独立确定其月份；实际用量报表仍按原有结算时间口径统计，并说明跨月归属差异。

#### Scenario: 旧月开始新月完成
- **WHEN** Attempt 在 11 月 30 日 23:59 预占并在 12 月 1 日 00:02 完成
- **THEN** 实耗校正写入 11 月额度账，不扣 12 月；11 月报告若仍在途则显示暂未结清

#### Scenario: 同一请求跨月换 Attempt
- **WHEN** 一个请求的首个 Attempt 在 11 月执行，另一个实际 Attempt 在 12 月开始
- **THEN** 两个 Attempt 的额度分别归属对应月份，不把整条请求的全部实耗强行归到一个月

### Requirement: 额度终态结算只发生一次且与账本一致

系统 SHALL 使同一 Attempt 的内部额度事实及对应预占释放在正式终态流程中只生效一次。重试结算、重启和失败回滚 MUST NOT 重复增加已用或只更新账本未更新额度；其他员工、项目、Key 或厂商池不能分担本次额度。

#### Scenario: 重复终态提交
- **WHEN** 同一 Attempt 的结算重复执行
- **THEN** 实际用量、额度已用和预占释放与第一次成功提交一致

#### Scenario: 结算事务失败
- **WHEN** 正式结算在额度与账本提交过程中失败
- **THEN** 不产生部分成功，重试后仍只形成一次消费事实

### Requirement: 每个厂商池的额度单位可解释

系统 SHALL 明确标识额度基础为实际 Token 或套餐折算额度；不同基础的数值不能相加为统一可用 Token。存在 API 与套餐混用且无法证明同一授权额度基础时，系统 SHALL 在切换预检中指出歧义，禁止无说明切换计数基础或悄悄调整路由。

#### Scenario: API 与套餐分别展示
- **WHEN** 报告同时包含 DeepSeek API、智谱 Coding Plan 和 Kimi Coding Plan
- **THEN** 分厂商列出额度单位和状态，不提供 `22 亿−27.1 亿` 这样的混算余额

#### Scenario: 混合模式厂商池未明确基础
- **WHEN** 拟切换厂商池同时含不同计量基础的可用路径且配置未明确
- **THEN** 预检标记该池待决策并阻止本批切换，不自动停用原路由或构造新的跨单位预算
