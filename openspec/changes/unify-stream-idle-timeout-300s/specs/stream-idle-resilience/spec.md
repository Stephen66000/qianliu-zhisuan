# Spec Delta

## Purpose

为所有正式流式模型调用建立一致、可验证的上游空闲等待与失败合同，使长推理请求获得最长 300 秒的连续空闲恢复机会，并让客户端在超时后收到准确提示而不发生重复调用或错误结算。

## ADDED Requirements

### Requirement: 正式流式调用统一使用 300 秒空闲门限

系统 SHALL 对所有厂商、通用兼容资源、API 和 Coding Plan 模式的正式流式模型调用使用 300,000 毫秒连续上游空闲门限。厂商或模式级旧空闲配置 MUST NOT 改变该门限；管理探针和非流式调用 MUST 保持各自独立时限。

#### Scenario: 所有正式资源解析为统一门限
- **WHEN** Gateway 为任一正式流式资源解析空闲门限
- **THEN** 解析结果为 300,000 毫秒，与厂商和资源模式无关

#### Scenario: 旧覆盖值存在
- **WHEN** 环境中仍存在厂商级或模式级流式空闲配置
- **THEN** 该配置不改变正式调用的 300,000 毫秒门限，并产生不含敏感值的弃用提示

#### Scenario: 管理探针不继承正式调用门限
- **WHEN** 系统执行模型发现、权限探针或模型验证
- **THEN** 该管理操作继续使用自身显式配置的时限

### Requirement: 只有有效上游活动才能刷新空闲窗口

系统 SHALL 在收到第一个有效非空上游原始数据块后启动流式空闲计时，并在每个后续有效非空原始数据块到达时重置计时。系统 MUST NOT 使用下游心跳、客户端活动或零长度块刷新上游空闲窗口。

#### Scenario: 299 秒内恢复
- **WHEN** 已开始的流在连续空闲未满 300 秒时收到有效上游数据
- **THEN** 请求继续执行，并从该数据到达时重新计算完整空闲窗口

#### Scenario: 多次短空闲累计超过 300 秒
- **WHEN** 请求总历时超过 300 秒，但相邻有效上游数据块的间隔均小于 300 秒
- **THEN** 系统不因累计历时触发流式空闲超时，但仍遵守总调用时限

#### Scenario: 零长度块不能续期
- **WHEN** 上游在 300 秒窗口内仅产生零长度传输块或空读取
- **THEN** 这些活动不重置空闲计时，请求按连续空闲时间终止

#### Scenario: 上游心跳或注释等非空原始块是有效活动
- **WHEN** 上游返回包含 SSE 注释或心跳的非空原始数据块（判定在原始块层进行，`byteLength > 0` 即刷新，不要求先解析出合法事件）
- **THEN** 系统将其视为上游连接活动并重置空闲窗口，即使没有可展示正文

### Requirement: 业务超时必须先于基础设施超时生效

系统 MUST 使上游 HTTP 客户端、可控反向代理和运行时资源租约的时限覆盖业务空闲窗口及错误发送余量。底层 HTTP 超时 MUST NOT 与业务 300 秒空闲门限设为相同值并竞争终止。

#### Scenario: 真实 HTTP 流连续空闲 300 秒
- **WHEN** 真实上游 HTTP 流在首次数据后连续 300 秒无有效数据
- **THEN** 业务层首先产生 `STREAM_IDLE_TIMEOUT`，而不是底层 body timeout 或普通网络错误

#### Scenario: 总调用时限先到
- **WHEN** 总调用时限早于剩余空闲窗口到期
- **THEN** 系统以 `REQUEST_TIMEOUT` 结束请求，并保持与空闲超时不同的机器码和用户提示

#### Scenario: 并发租约覆盖长请求
- **WHEN** Coding Plan 调用跨越 300 秒空闲窗口且仍未达到总调用时限
- **THEN** 该请求的并发租约保持有效，不会被过期回收或允许重复占用

### Requirement: 可控下游链路必须覆盖协议实际等待时间

系统 SHALL 根据 Chat Completions、Messages 和 Responses 的真实输出方式配置并验证下游等待。可控代理 MUST NOT 在 Gateway 能够返回成功或约定错误之前终止连接。

#### Scenario: Messages 等待期间保活
- **WHEN** Messages 流已建立且上游处于允许的空闲窗口
- **THEN** Gateway 继续发送协议兼容的下游 ping，同时该 ping 不刷新上游空闲计时

#### Scenario: Responses 聚合超过 330 秒
- **WHEN** Responses 流式请求的上游持续产生有效数据但 Gateway 聚合等待超过 330 秒
- **THEN** 可控代理和已验证客户端保持连接，直至请求在总调用时限内成功完成或返回明确失败；330 秒仅为验收测试下限，可控代理的配置目标 MUST 覆盖 600 秒总调用时限及至少 60 秒错误发送余量，即不低于 660 秒

#### Scenario: 第三方客户端提前断开
- **WHEN** 第三方客户端存在不可调整且短于所需等待时间的限制
- **THEN** 系统记录该入口的业务验收未通过，且不得宣称该客户端支持完整 300 秒合同

### Requirement: 流式空闲超时返回专属提示

系统 SHALL 仅对 `failureLayer=STREAM_IDLE_TIMEOUT` 返回“上游模型响应中断，等待超时。请稍后重试，或切换其他模型。”，并保留 `upstream_timeout`、`STREAM_IDLE_TIMEOUT` 和真实请求 ID。

#### Scenario: 已提交流发生空闲超时
- **WHEN** Chat 或 Messages 已向客户端提交响应后发生流式空闲超时
- **THEN** 系统通过对应协议的流内错误发送规定提示和真实请求 ID，然后结束流

#### Scenario: 未提交响应发生空闲超时
- **WHEN** 北向响应尚未提交时发生流式空闲超时
- **THEN** 系统返回 HTTP 504 兼容错误包，包含规定提示、机器码、故障层和真实请求 ID

#### Scenario: 其他失败层
- **WHEN** 请求因首字节超时、总时长超时、客户端取消、限流、鉴权、异常 EOF或传输错误结束
- **THEN** 系统保留对应错误语义，不使用流式空闲超时提示

### Requirement: 空闲超时后不得继续切换上游

某个 Attempt 一旦以 `STREAM_IDLE_TIMEOUT` 结束，系统 MUST NOT 为该请求启动新的上游 Attempt。该限制 MUST NOT 改写在空闲超时前已完成的合法 Attempt 事实。

#### Scenario: 第一个 Attempt 空闲超时
- **WHEN** 第一个 Attempt 以 `STREAM_IDLE_TIMEOUT` 结束
- **THEN** 请求终止且不启动第二个 Attempt

#### Scenario: 第二个 Attempt 空闲超时
- **WHEN** 第一个 Attempt 已按现有策略合法切换，第二个 Attempt 随后发生 `STREAM_IDLE_TIMEOUT`
- **THEN** 请求保留两个 Attempt 的事实，并且不启动第三个 Attempt

### Requirement: 超时结算与清理保持事实一致

系统 MUST 在空闲超时后释放上游连接、并发租约和未消耗的额度预占，并按照已收到的厂商用量及其质量状态结算。系统 MUST NOT 将未知用量强制解释为零消耗，也不得用后续成功覆盖原请求失败事实。

#### Scenario: 部分用量后超时
- **WHEN** 流在返回部分用量或部分输出后发生空闲超时
- **THEN** 系统保留可用的估算事实，完成一次且仅一次结算，并释放全部运行时资源

#### Scenario: 没有最终用量
- **WHEN** 流式空闲超时前没有收到可信的最终用量
- **THEN** 系统保持未知或估算语义，不伪造精确零用量
