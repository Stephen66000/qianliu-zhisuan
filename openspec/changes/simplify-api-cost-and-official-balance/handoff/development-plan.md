需求以 [proposal](../proposal.md)、[三份规格](../specs/) 和 [design](../design.md) 为依据；本计划细化执行顺序，不新增产品范围。具体接口命名及工程参数在 WP0 固化后更新本文，变更需求须同时更新对应 spec 和验收用例。

用户已指定执行方式：每个工作包单独新开任务，GLM 5.3 作为总指挥负责计划、指挥、审核与验收，具体开发由指定的 GLM 5.3 Flash 子 Agent 执行；实际可用模型名在 zcode 中核实，不自动替换。总指挥必须遵守[执行指令](zcode-commander-instructions.md)，不能凭子 Agent 自报通过作验收。下表为需要覆盖的责任，可由对应总指挥、子 Agent 及业务验收人承担，不要求配齐三名同事。

## 2. 范围固定

必须交付：API费用估算同源读取、官方余额独立同步、API 资金操作和 readiness 依赖退出、套餐/员工额度保留、全部受影响页面和导出、历史兼容、迁移和回退演练。

不在本期：新增厂商余额适配、自动官方价格抓取、自动充值/换厂商、新账户管理体系、汇率系统、重开旧账、批量历史重算或消息补发。复用既有代码，不以 finance 命名为删除依据。

业务边界已在聊天中认可；以下为工程建议，不能在交付报告中写成用户已确认：

| 项目 | 建议值/方案 | 固化时点 |
|---|---|---|
| 自动同步周期 | 15 分钟，可配置 | WP0，核实厂商限制 |
| 数据过期阈值 | 30 分钟，可配置 | WP0 |

仅参数待确认时，可以继续当前工作包内不依赖该参数的读取或测试夹具工作；不得越包，不得把未确认参数硬编码或把未确定契约合并为最终接口。

| 工作包 | 对应 tasks | 主责 | 必交产物 | 退出条件 |

### WP1 修改入口与具体交付

- 主要代码：`apps/gateway/src/pipeline/billing.ts`、`packages/domain/src/billing-rule.ts`；Database 的 `monthly-operating-cost.ts`、`operating-bill-finance-projection.ts`、`dashboard-home-costs.ts`、`usage-cost-disposition-projection.ts`；Control API 的 `provider-finance/dashboard-projection.ts`、`providers/finance-usage-overview.ts`。这些是研究入口，接手时继续追踪全部调用方。
- 将按请求分项计价的读取从资金账户键、期初状态和旧余额差算法中分离。Gateway 已有正确计价时只复用，不无故重写。
- 同一范围的费用至少返回：按币种已知金额、是否完整、缺口原因/条数、统计期间/范围、价格依据状态；保持原始用量、计价快照和历史处置。
- 新增/调整消费聚合测试应覆盖资金开关与账户是否存在的组合、未知费用、失败重试、多币种和价格版本。不得通过补零期初让测试“通过”。

### WP2 修改入口与具体交付

- 主要代码：Control API 的 `provider-finance/routes.ts`、`activation-routes.ts`、`providers/routes.ts` 及实际存在的旧采购/经营数据入口；Database 的 `resource-pool-repository.ts`、`provider-finance-activation-*` 及新迁移。
- 产出 API 写入口表：方法、路径、资源模式、旧行为、退役响应、是否可能写候选或资金、对应负向测试。包括共享冲销、对账和旧候选应用路径，不只处理充值按钮。
- 按 API/Coding Plan 切分现有合同；不关闭整个企业资金开关，不删除套餐严格写、周期、幂等和自动续订。
- 移除仅 API 资金 PENDING 引起的候选排除与结算前提；不批量改 ACTIVE，不自动解除凭证、停用、套餐窗口或真实余额耗尽状态。
- 新迁移只改必要合同/索引/函数，保留旧迁移和历史数据。新库及从既有迁移升级的库都应通过相同用例。

### WP3 修改入口与具体交付

- 主要代码：`packages/provider-adapters/src/provider-operating-facts.ts`、`apps/worker/src/provider-operating-sync/runner.ts`、`apps/worker/src/main.ts`、Database 的 `provider-operating-repository.ts`、`resource-pool-repository.ts`、`supply-forecast-repository.ts`。
- 定期与手动操作共用一次查询流程；来源过滤、最近成功值和最近失败尝试分离；解除每日唯一尝试和内部充值记录依赖。
- 返回总余额及原币组成、采集时间、支持能力、状态、失败原因、下次可刷新时间。官方可用标记不能被“金额大于零”单一条件替代。
- 无官方账户标识时不建设账户系统，本期不显示跨资源官方余额总计。既有正余额恢复只接受晚于隔离的新证据。
- 现有供给预测/告警增加来源与时效判断；缺有效数据则不可算，不新建基于估算费用的硬拒绝。

### WP4 页面清单与具体交付

| 位置 | 必须看到 | 必须移除/保留的边界 |
|---|---|---|
| 厂商资源 API 列表/详情 | Token、API费用估算、官方余额、最近同步及刷新 | 移除 API 充值/内部余额和资金就绪提示；接入管理保留 |
| 用量总览/请求明细 | 输入/输出/缓存、估算及依据/缺口 | 不将货币余额塞入 Token 剩余额度 |
| 套餐与订阅 | 套餐采购、续订、周期、实付、额度 | API 不参与初始化；旧 API 资金仅只读入口 |
| 首页/账单/年度/CSV | 同源 API 金额、币种及完整性 | 新口径不含 API 期初/充值/内部月末余额；综合费用注明含估算 |

## 5. 建议的接口合同草案

以下是实现讨论基准，不宣称接口已存在。WP0 应填写实际路由和确切字段，并在前后端测试中共用样例；不得让前端解析中文文案判断状态。

| 合同 | 必需语义 | 验收约束 |
|---|---|---|
| API费用估算读取 | 范围/期间、按币种金额、完整性、缺口与价格依据 | 不依赖余额/资金状态；未知不等于零 |
| 官方余额读取 | 是否支持、来源、币种、总额/组成、可用标记、成功时间、最近尝试状态、是否过期 | 成功时间与失败尝试时间分开；过期与失败可同时表达 |
| 手动刷新 | 现有认证/写权限、资源模式检查、刷新中/成功/失败/冷却、下次可刷新时间 | 可复用在途操作；不返回凭证；失败不覆盖上次成功值 |
| 旧 API 资金写 | 原认证/权限先执行，合法 API 请求返回停用码 | 不接受成功空操作，不写资金或候选 |
| 套餐写/历史读 | 保持已有套餐合同和历史来源 | 与 API 退役独立；旧版本金额不变 |

旧客户端兼容期若保留既有字段，必须明确其语义和弃用说明；不能同一字段在某些页面代表官方余额、另一些页面代表内部余额。任何新必填字段或状态调整须同步 API 和前端。

## 6. 测试入口与记录方式

接手前核实 Node/Corepack 与 lockfile。研究时仓库脚本使用 `corepack pnpm@11.11.0`。下列命令仅作为已核实脚本入口，不表示本轮已执行或其现有用例覆盖新增行为：

```sh
# 仓库根目录；按实际改动范围选择包
corepack pnpm@11.11.0 --filter @qianliu/domain run test
corepack pnpm@11.11.0 --filter @qianliu/provider-adapters run test
corepack pnpm@11.11.0 --filter @qianliu/database run test:integration
corepack pnpm@11.11.0 --filter @qianliu/control-api run test:integration
corepack pnpm@11.11.0 --filter @qianliu/gateway run test:integration
corepack pnpm@11.11.0 --filter @qianliu/worker run test
corepack pnpm@11.11.0 --filter @qianliu/web run test
corepack pnpm@11.11.0 --filter @qianliu/web run test:e2e
OPENSPEC_TELEMETRY=0 openspec validate simplify-api-cost-and-official-balance --strict --no-interactive
```

- 单包测试脚本有的会同时发现集成用例，不能一概当成无数据库单测；先查当前配置并选择相关文件。Database 集成测试已有容器化 PostgreSQL 夹具；Web Playwright globalSetup 会迁移、清库、播种，必须配置专用 `_e2e` 数据库，禁止指向共享或生产库。
- 根 Vitest 配置含 `passWithNoTests: true`；若运行结果是 0 tests，不可算通过。Control API/Worker 的 `test:e2e`、Web 的 `test:integration` 研究时仍是占位脚本，不作为任何验收证据。
- 不运行 Gateway 的真实 Codex E2E 脚本来“顺便验证”；本期集成用模拟上游。真实厂商余额联通若未来需要，应由接手方在允许的环境单独记录，只做余额查询。
- 相关既有用例入口：domain `billing-rule.test.ts`；adapters `provider-operating-facts.test.ts`；worker `provider-operating-sync/runner.test.ts`；gateway `billing-evidence.test.ts`、`w11-resource-pool.test.ts`、`employee-monthly-quota.test.ts`；database `pool010-provider-operating.test.ts`、`provider-finance-recorded-cost-disposition.integration.test.ts`、`pool043-operating-bill-accounts.integration.test.ts`。旧断言应按新/历史口径区分，不直接删除套件以求全绿。
- 运行改动包的 typecheck/lint/build 及仓库对本改动适用的 CI/质量门禁。复用现有覆盖率/变异测试要求，不擅自降阈值；原有失败先留基线，新增失败修复，影响本功能的既有失败不能仅标“历史问题”就放行。

## 7. 评审、切换和交付要求

建议提交批次：契约/夹具 → 费用读取 → API 退出/迁移 → 余额同步 → 页面/导出 → 集成及运维证据。每批包含本包测试和文档；有依赖的迁移与服务代码应在同一候选版本中验证，不单独上线 UI 掩盖后台旧行为。

发布候选必须列出每项迁移和各服务版本，明确切换窗口内如何停止旧 API 资金写、处理在途结算和旧 Worker，验证套餐任务不被总开关误停。切换时只使用既有必要运维手段，不额外建设发布平台。

回退不得简单运行所有 down 迁移或恢复要求 API 有期初的旧服务：切换后可能已有无资金账户的新消费。回退演练必须证明这些消费仍可读、可结算、可受原额度约束；不通过回退删除新用量或补造资金。

最终交付包含：源码/提交与候选版本、迁移说明、接口与配置文档、验收结果及证据、已知限制、发布/回退清单。状态分别报告“实现完成／测试通过／发布完成／业务验收”，不能互相代替；`tasks.md` 仅在相应实际交付和验证完成后勾选。
