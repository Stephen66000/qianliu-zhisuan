## Goals / Non-Goals

**Goals**：实现三个独立读取合同：API 消费用量及费用估算、官方账户余额快照、Coding Plan 套餐与费用。新 API 无需资金建账即可使用；其他控制和历史证据完整保留。

**Non-Goals**：不新增模型、自动换厂商策略、自动充值、厂商价格爬取平台、汇率转换、财务总账、自动账户识别或新的通用同步基础设施；不清理其他任务代码，不重写旧迁移或已关账账单。

## Decisions

### D1 费用来源为消费事实，资金数据不再提供费用完整性前提

- 复用 Attempt 用量、`api_cost`、币种、规则版本/快照、结算时间及已有处置投影；内部字段名可兼容保留，不为了中文改名重写不可变记录。
- 为所有消费视图提供同一费用聚合入口，返回按币种已知金额、完整性及原因；不得从资源资金账户键集合决定是否存在可计价消费。
- 价格规则维护保留现有入口；补充或展示官方来源、模型与有效期的可追溯依据。已有自定义/倍率规则不能直接宣称为官方价；先盘点受影响规则并标记待核，本次不自动批量改价格。
- 当前计价器无法覆盖的适用收费项显示依据不完整，不猜测为零；不承诺把所有厂商的所有计费形式一次实现。
- 历史费用处置仍为费用质量规则，和退出的钱包余额管理分开。无需专门新增一张估算流水再复制现有账本。
- 替代方案：仅改标签无法解决开关、账户与余额缺失影响计价的问题，因此不采用。

### D2 余额使用官方快照独立投影

- 优先复用经营快照的来源、币种、总额/赠送/充值组成、可用标记和采集时间，以及已有同步错误记录；读取时明确筛选 `PROVIDER_SYNC` 与 `PROVIDER_API`，不采用“最近任意来源”作为官方余额。
- 官方返回的账户总额不按模型或 Key 相加；本期不提供跨资源账户余额总合计，避免为了去重引入新的账户体系。若已有可靠账户标识可明确关联，否则仅显示资源查询结果并说明账户范围。
- UI 文案为“官方账户余额”，展示最近成功采集时间；同步尝试时间另列，页面刷新或缓存读取不改写成功时间。
- 后台按可配置周期运行，并提供服务端刷新入口；正常余额查询不创建 API 充值或余额调整事件，不触发模型推理。
- **工程默认建议（本次提案值，非用户已确认参数）**：同步周期 15 分钟、过期阈值 30 分钟、手动刷新冷却 30 秒。用配置支持调整；尊重官方限流，复用已有超时和任务机制，不增加自制调度框架。
- 现有 `(企业,资源,同步日)` 唯一记录不能表达日内多次同步；实施时调整尝试记录约束/标识或复用适合的任务记录，并保留旧尝试。手动与周期刷新共享同一查询逻辑和最小在途/冷却约束。
- 同步与原资金总开关解耦；套餐资金停写继续作用于套餐。既有运维静默租约的用途须保留并核实，不能为了解耦余额同步顺带删除。
- 替代方案：每次模型调用前查余额会增加延迟和上游请求，且不能使账户数据绝对实时，不采用；维持每天一次不满足本次更新余额的目标。

### D3 API 资金写操作停用，套餐写操作保留

- API 期初、期初更正、充值、对账、余额调整及相关资金冲销不再接受新写入；共享路由必须按资源模式区分。完成原认证/权限检查后，对旧 API 专属写操作建议返回 `410 api_funding_management_retired`，明确迁移至官方余额和费用估算；不做成功空操作。
- 审查普通路由、旧购买入口、经营数据手填、候选/初始化/激活、旧候选应用、自动任务和数据库触发器，保证没有旁路继续建账。历史费用质量修复不是钱包操作，不按上述规则误禁。
- 资金初始化仅保留套餐所需事实。包含 API 资金事实的过时混合候选必须重新生成，不能静默剔除一半再沿用旧确认结果。
- 不把企业 `strict_writes_enabled` 统一关闭，不将套餐的严格写、订单证据、幂等、冲销、周期与续订合同一并删除。
- 旧 API 资金历史只读查询保留；历史金额、币种及审计不变，不计算新的当前内部余额，也不要求每月继续维护。
- 替代方案：关闭整个 finance 模块会同时停止余额同步或套餐管理，不采用。

### D4 API 调用仅解除资金前置条件

- 新口径下 `finance_state=PENDING` 不再是 API 的阻断理由；旧状态可留档，不用伪造期初或批量把所有资源设为 ACTIVE。
- 逐项核实候选构建、资源创建触发器、结算触发器和兼容读取中的 API 资金依赖。数据库合同只针对已退役的 API 资金前提调整，保留原始消费、幂等与事务约束。
- 余额为参考。同步失败/过期不新增调用阻断；上游明确余额不足后的既有隔离、更新官方可用证据后的恢复及真实调用确认继续工作。
- 员工月额度、Key 与项目限制、套餐窗口、授权、凭证和人工停用原样执行。`reconcile-employee-quota-and-reporting` 的月度额度实现不被本次改为“无限”。

### D5 展示和历史版本按口径区分

| 页面/产物 | 新口径行为 |
|---|---|
| 厂商资源列表/详情 | Token 用量、API费用估算、官方余额、同步状态；不展示内部充值和结余 |
| 用量总览/请求明细 | 同源费用及完整性，不把货币余额放进 Token/套餐剩余额度 |
| 套餐与订阅 | 只管理 Coding Plan；API 旧记录有明确的只读历史入口 |
| 首页/经营账单/年度统计/CSV | 删除现行 API 期初、充值、内部结余和待补账提示；统一估算及合计口径 |
| 部门/项目/费用分摊 | 输入费用改用同源估算，保留原分摊合同，不改变真实 Token 或主体范围 |
| 企业微信等含 API 金额的通知 | 金额名称及完整性随新口径；不修改纯 Token 模板、接收人、发送时间或重发历史 |
| 健康、告警与供给预测 | 官方来源和时效有效才作为余额参考；预测明确局限，不新增自动切换/硬拒绝 |
| 已关账旧版本 | 保留原快照、金额及历史口径，不套用当前价格或当前余额 |

- 未关账/现行动态视图切换为新口径；历史范围若有可信请求计价事实可据原快照汇总，否则显示缺口，不回填余额桥接金额。
- 固定版本和历史导出保留旧口径；新口径产物附口径说明/版本，避免同名“费用”掩盖不同算法。实现不要求再新增通用版本平台。
- 套餐当前各视图可能区分采购实付、周期费用及分摊费用，本次不统一重算套餐；合计须说明其套餐分量口径。

### D6 与其他在途方案的关系

| 在途方案 | 本次替代/保留关系 |
|---|---|
| `provider-finance-initialization` | 新口径替代其 API 期初、充值、资金 readiness 及混合初始化的对应要求；保留 Coding Plan、原审计和历史查询要求。旧方案不改写，实施必须以本次 API 合同解除冲突 |
| `reconcile-employee-quota-and-reporting` | 保留员工月度额度、超额、月份及报表事实合同；API 金额展示由本次费用估算合同补充，不改其额度单位 |
| `coding-plan-quota-window-recovery` | 保留套餐耗尽、窗口恢复和硬阻断，不能因删除 API 余额逻辑误删 |
| `wecom-token-report-and-query` | 仅在实际包含 API 金额时对齐用词和事实，投递可靠性及纯 Token 报表不扩范围 |

## Risks / Trade-offs

- [删 UI 后后台仍写资金或调用仍被 PENDING 阻断] → 同批检查入口、触发器和候选路径，用新 API 无期初场景做集成验收。
- [资金模块与套餐、历史费用处置共享] → 按资源模式及行为切分，不按 finance 目录整批删除或关总开关。
- [同账户多 Key 重复余额] → 本期不做跨资源官方余额合计，无需自动账户识别。
- [周期采集存在延迟及厂商限流] → 时间和失败状态始终可见，支持手动刷新及配置，不宣称严格实时。
- [切换后旧余额算法和新 Token 算法金额不同] → 记录口径、保留关账快照，不以“必须相等”作为新验收条件。
- [本地存在其他任务未提交代码] → 实施前记录文件基线并最小化修改，不回退其他任务；发布版本需要另行核实。

以上均为已观察到的既有依赖或正常数据约束；本方案不引入额外通用锁、分布式一致性框架或理论安全边界扩展。

## Migration Plan

以下为未来实施步骤，不是本轮执行记录。

1. 记录当前服务版本、资金/套餐开关、受影响 API 状态和价格规则，生成本地/只读影响清单；不得用真实模型付费调用验证配置。
2. 新增兼容的费用读取和官方余额状态合同，保留旧数据；以真实消费事实比较新旧聚合并解释口径差异。
3. 通过新迁移解除 API 专属资金写前提、同步日约束及初始化依赖；核实实施时迁移序号，不改旧迁移。
4. Control API、Worker、Gateway 与 Web 协调切换：停用旧 API 资金写；启用新估算读取、独立余额同步与 UI；套餐正常运行。
5. 以隔离环境覆盖三份规格场景，出具同源金额核对、无期初 API 调用、余额刷新、真实耗尽恢复和套餐回归证据。
6. 发布前形成具体发布/回退清单与备份方案。若切换后已有无期初的新 API 消费，不能直接回退到强制资金 readiness 的旧代码；回退包须仍兼容这些消费，停用刷新不等于恢复旧建账要求。
7. 已关账版本保持冻结，不自动重开、重算或补发；生产部署和业务验收在未来授权工作中单独记录。

## Configuration and Implementation Details Deferred

- 同步周期、过期阈值和刷新冷却为 D2 的提案默认值，可按实际厂商限制调整，不改变需求边界。
- 新迁移编号、兼容响应字段的精确命名及现有运维开关落点，实施时依据届时基线确定并更新接口文档。
- 无需要先新增账户管理、付费查询或新厂商接入才能完成本期需求的前置任务。
