## 1. 收口目标

把仟流智算 1.0 的开发前基线、开发过程、产品结果、代码、质量、安全、发布、运维和真实业务验证全部闭环，形成一套：

- 可审阅：每项结论都有来源和证据；
- 可交付：客户、管理者或新成员可以找到完整资料；
- 可接手：代码、架构、部署和故障处理能够被其他人理解；
- 可追溯：需求、代码、测试、发布和运行结果可以关联；
- 可演进：遗留问题和 2.0 输入有明确去向。

1.0 收口不是“代码写完”，而是完成一次阶段性工程、产品和业务闭环。

## 2. 适用范围

### 2.1 必须纳入 Review 的对象

- 开发前 PRD、TRD、开发规划、详细计划、原型、走查、PoC 和 ADR；
- 开发时间线、Planning Change、审核记录、Handoff、发布记录和事故记录；
- `apps/`、`packages/` 中全部产品代码；
- 数据库迁移、部署文件、发布／回滚脚本、Worker、测试、CI、配置和项目工具脚本；
- Gateway、协议适配、路由、经营调度、Token、额度、账本、Key、权限、运行保障和通知模块；
- 生产发布、备份恢复、监控告警、真实客户端和真实业务周期证据；
- 当前工作区中未归档的新增文件、热修复和候选变更。

### 2.2 必须登记但不做产品代码逐行审核的对象

- `node_modules/`、构建产物、缓存和可再生成文件；
- `_quarantine/`、`参考/` 等隔离的历史或只读参考内容；
- 第三方依赖源码。

上述对象必须在范围清单中标记排除原因，并完成依赖、许可证、来源和“不参与产品构建”的确认。

## 3. Review 总体门禁

```text
冻结 Review 候选
→ 清点全部资产和权威来源
→ 产品、架构、进度和过程 Review
→ V1.4 全量代码审核
→ 代码语义标注检查与补齐
→ 新候选重新审核、测试和质量门禁
→ 发布、运维、灾备和真实业务 Review
→ 遗留问题与 2.0 输入确认
→ Owner Final Review
→ Git Tag、Hash、最终档案和阶段性 Ending
```

### 3.1 两个收口状态

由于工程交付与完整自然月业务验证不是同一事件，必须区分：

1. **1.0 工程封板**：V1.4 代码审核、语义标注、测试、安全、发布和运维证据通过。
2. **1.0 业务收口**：真实业务周期、经营结果、用户反馈和遗留问题 Review 完成。

未完成的业务验证必须明确标记为 `DOING` 或 `EVIDENCE_INSUFFICIENT`，不得写成已完成。

### 3.2 最终通过条件

- V1.4 全量代码审核针对最终候选通过；
- 代码语义标注检查完成，缺失项已补齐并复审；
- PRD／TRD 需求—交付—证据追踪矩阵没有未说明项；
- 阻断性 P0/P1 问题为零，或按 V1.4 允许的方式形成 Owner 签字豁免；
- 质量、安全、依赖、许可证、隐私、发布和恢复证据完整；
- 最终代码、数据库迁移、构建制品和生产部署版本可对应；
- 遗留问题、技术债和 2.0 输入均有 Owner、优先级和去向；
- Owner 完成 Final Review 决定并生成最终档案。

## 5. V1.4 代码审核与语义标注标准

### 5.1 代码审核范围

必须覆盖生产代码、数据库迁移、部署和回滚脚本、测试、CI、配置和项目工具。审核排除项必须登记，不得默默跳过。

### 5.2 代码语义标注最低要求

#### 文件或模块级

至少说明：

- 模块名称和业务职责；
- 处理范围与明确不处理的内容；
- 输入、输出和主要副作用；
- 关键安全、隐私、账本、并发和幂等约束；
- 对应 PRD／TRD／FR／WT；
- 相关测试或 Evidence。

#### 核心函数或类级

至少说明：

- 输入和输出；
- 状态变化；
- 失败、重试、回退和取消边界；
- 是否访问数据库、Redis、上游或外部系统；
- 是否必须幂等；
- 调用者不能破坏的业务不变量。

#### 复杂业务逻辑级

重点说明“为什么这样做”，尤其是：

- Gateway 请求链路；
- Provider Adapter 和协议转换；
- 路由、Affinity、经营调度和故障切换；
- Token、额度、费用、Attempt 和账本；
- Key、权限、Secret 和正文零留存；
- Worker、运行保障、通知和数据库迁移；
- 发布、回滚、备份和恢复。

注释不应重复代码本身已经表达清楚的内容。代码说明“怎么做”，注释说明“为什么、边界和不能破坏什么”。

### 5.3 语义标注变更规则

语义标注即使不改变运行逻辑，只要改变源码，也会生成新的代码候选。最终 V1.4 审核、质量门禁、Hash、Tag 和归档必须针对补齐标注后的最终候选，不得沿用旧候选的最终结论。

## 6. 代码、版本与证据标注

最终代码必须具备以下身份信息：

- Git Annotated Tag：建议 `v1.0.0-final`；
- 最终 Commit 和代码树 Hash；

- `pnpm-lock.yaml` Hash；

## 9. 后续执行规则

本文件作为 1.0 Review 的唯一检查基线。后续每完成一个工作包，必须更新：

1. 工作包状态；
2. 交付物路径；
3. Evidence 路径；
4. 候选 Commit 或版本；
5. 遗留问题和风险；
6. 复核结论。

任何新增代码、迁移、配置、发布脚本或关键文档变更，都必须重新判断是否影响既有 Review、V1.4 审核、质量门禁、Hash 和最终封板状态。

Final Review 前不得把“文件存在”当成“交付完成”；必须同时具备内容、证据、Owner 结论和可追溯版本。

## 10. 2.0 交接规则

1.0 Review 结束时，必须单独输出 `2.0 输入清单`，至少包含：

- 未完成产品需求；
- 未启用协议和 Provider；
- 技术债和架构债务；
- 运营、客户和员工反馈；
- 安全与合规遗留；
- 高可用、多租户、RBAC、身份源和 Agent 的演进输入；
- 不能进入 2.0 的事项及原因。

2.0 不直接修改 1.0 Final 档案。任何 1.0 归档后的修复都必须通过勘误、补丁版本或新候选记录处理。
