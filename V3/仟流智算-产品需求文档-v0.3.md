> **产品最高原则**
>
> 仟流智算的基础是企业级 Token 管理。无论企业购买的是 API、Coding Plan 还是其他账号套餐，员工和项目最终消耗的最小计量事实都是输入、输出、缓存等 Token。对外可以把产品定义为“AI 算力与使用权益管理”，但资源、额度、调度和账本都必须落回可验证的 Token 事实。
>
> Token 是统一基础，不等于所有 Token 的价值、扣减倍率和成本天然相同。系统必须保留模型、资源、Token 类型和规则版本，再计算厂商实际扣减与真实费用。所有业务功能、技术方案和验收标准必须服务于以下四个核心性质：
>
> 1. **持续生产**：算力需要持续供给，系统必须知道资源是否可用、还能支撑多久、何时恢复。
> 2. **按量消耗**：每次使用都会消耗额度、容量或资金，必须识别谁用了、用了多少、归属哪里。
> 3. **存在峰谷差异**：不同时段的价格、扣减倍数、速率和机会成本不同，必须在请求发生前参与判断。
> 4. **必须计量和调度**：企业必须对请求执行放行、切换、限流、拒绝或经授权超额，并证明决策和结果。
>
> 每项核心业务能力必须至少映射到一条原则，并形成“数据输入 → 确定性判断 → 执行动作 → 结果落账 → 可解释查询 → 对账修正”闭环。安全、隐私、部署等横向能力作为四条原则共同的可信边界。

### 面向客户的核心表达

| 底层性质 | 客户真正的问题 | 1.0 如何回答 |
| --- | --- | --- |
| 持续生产 | 现在还能不能用？还能用多久？ | 资源健康、剩余额度、消耗速度、预计耗尽、恢复时间 |
| 按量消耗 | 谁用了？用了多少？用在哪里？ | 员工账、项目账、请求数、Token、额度和费用 |
| 峰谷差异 | 什么时候使用更划算？ | 分时价格、扣减倍率、资源周期、机会成本和节省依据 |
| 计量和调度 | 为什么这次放行、切换或拒绝？ | 请求前门禁、候选资源、调度动作、Attempt 和账本证据 |

客户价值闭环：**持续供给 → 使用归属 → 成本差异 → 调度执行 → 结果计量 → 价值确认**。

其中，使用主体、用量、成本和调度结果由系统记录；业务价值由企业负责人基于事实和证据确认，系统负责关联、留痕、汇总和结账。

## 1. 一句话定位

仟流智算是以企业 AI Gateway 为核心执行引擎的企业级 AI Token 管理与算力权益平台：统一接入 API、Coding Plan 和账号池资源，以 Token 为基础计量事实，完成协议适配、资源路由、账号池调度、额度与费用记账、安全管控和运行审计。

企业 AI Gateway 不是外围组件，而是仟流智算把资源配置变成真实执行结果的核心模块；资源管理、额度规则和账本是围绕 Gateway 构成的管理闭环。

Gateway 负责执行“计量和调度”，资源与账本负责证明“持续生产、按量消耗和峰谷差异”。只有转发没有请求前控制，不算完成调度；只有最终账单没有逐次真实消耗，不算完成计量。

产品最终服务对象是购买和使用多种 AI 资源的企业客户及其团队。一期只服务仟流科技，是内部先行验证和产品打磨阶段，不是最终客户边界。

## 2. 首期要解决的问题

企业同时购买 DeepSeek、智谱、Kimi 等资源后，通常存在以下问题：

1. 厂商账号、充值余额、套餐费用和有效期分散在不同后台。
2. 多名员工共享企业资源，但无法准确知道每个人用了多少。
3. Coding Plan 可以被多人在不同时间或同时使用，但厂商只给出一份总额度。
4. API 与套餐的采购和结算方式不同，但员工和项目的底层消耗都表现为 Token；系统仍需分别计算厂商扣减和真实费用。
5. 员工使用 WorkBuddy、Claude Code、ZCode 等不同工具，企业难以统一分配和统计。
6. 管理员最关心资源是否可用、额度是否即将耗尽，以及谁的用量突然异常。
7. OpenAI、Anthropic 等客户端协议和厂商协议不同，字段、流式事件和错误语义容易在转换中丢失。
8. 直连厂商时，上游凭证容易散落在员工电脑，无法统一限制模型、来源 IP、有效期和并发。
9. 多账号路由、限流切换和流式失败缺少统一边界，容易重复请求、拼接两段输出或重复记账。
10. 一次调用为何选择某个账号、失败后切到哪里、是否已产生费用，缺少逐次路由证据。

## 3. 首期目标

1. 管理员可以登记 DeepSeek API、智谱 Coding Plan、Kimi Coding Plan。
2. 管理员可以创建员工或项目，给每个使用主体分配独立 Key、模型和额度。
3. WorkBuddy、Claude Code、ZCode、仟流 IDE 可以通过仟流 Gateway 使用已分配资源。
4. 每次调用都能归属到员工或项目，并记录输入／输出／缓存 Token、实际扣减和费用。
5. 管理员可以在桌面 Web 中查看本月资源、费用、人数、额度和异常。
6. 员工额度耗尽时默认停止；管理员可以单独允许超额使用。
7. 使用内容默认不保存，只保存完成计量所需的元数据。
8. Gateway 对外提供稳定的 OpenAI／Anthropic 兼容协议，对内通过能力注册和 Provider Adapter 适配不同上游。
9. Gateway 按优先级、权重、健康状态和会话亲和选择资源，并在明确边界内完成故障切换。
10. 每次上游尝试都生成可审计、不可覆盖的真实消耗明细，同时保证一次业务调用只有一个幂等结算汇总。
11. 管理员可以看到资源的消耗速度、预计耗尽时间、下一恢复时间和供给覆盖天数。
12. 峰谷价格、扣减倍数、剩余周期和额度稀缺程度在请求前参与调度，并能解释本次动作及节省。

## 4. 阶段边界

### 4.1 一期范围

- 企业内部先行验证：只服务仟流科技，用真实团队完成首个企业样板。
- 管理入口：桌面 Web。
- 管理角色：管理员，所有管理员权限相同。
- 使用主体：员工、项目。
- 员工工具：仟流 IDE、WorkBuddy、Claude Code、ZCode。
- 首批资源：DeepSeek API、智谱 Coding Plan、Kimi Coding Plan（首用模型为 Kimi K3）。
- 资源管理、Key、额度、Gateway、计量、费用、异常、操作日志。
- 运行保障：运行态势、可管理且可版本回滚的熔断规则、熔断事件、异常中心、人员与通知配置；普通 5xx／超时／网络错误只预警，不自动硬熔断。
- 运行保障通知：仅通过企业微信自建应用，按内部成员 `userid` 向对应人员本人发送熔断触发／恢复固定消息；不使用通知群、群机器人或 Webhook。
- 10 人完成一个完整自然月的内部真实使用。

#### 4.1.1 Gateway 一期核心能力

- 对外端点：`GET /v1/models`、`POST /v1/chat/completions`、`POST /v1/messages`。
- 协议适配：OpenAI Chat 与 Anthropic Messages 请求、流式事件、用量和错误的双向规范化。
- 能力注册：明确每个 Provider、资源和模型支持的协议、流式、工具调用及扩展能力；不支持的能力必须显式拒绝，不得静默丢字段。
- 路由与账号池：统一管理 API Key、OAuth 和套餐账号，处理凭证刷新、额度重置、冷却和恢复；按模型授权、资源模式、优先级、权重、健康、实时负载、错误率、首包时延、额度余量、重置时间、边际成本、并发和会话亲和选择上游。
- 有界故障切换：首个有效响应输出前允许切换；输出后不得把第二个上游的内容拼接给客户端。
- Session Affinity：同一会话优先命中同一健康资源以提高上下文缓存命中率，资源异常时允许脱离绑定。
- Key 安全：下游 Key 一次展示、摘要保存，并可限制模型、来源 IP、有效期、额度和并发。
- 路由证据：业务请求、候选资源、每次上游尝试（Attempt）、切换原因、最终资源、用量和记账结果可关联查询。
- 持续供给：计算消耗速度、预计耗尽时间、下一恢复时间、覆盖天数和预测可信度。
- 经营调度：在健康路由基础上叠加时段、价格／倍率、剩余额度和周期，执行放行、预授权等价资源切换、限流、拒绝或允许超额。

目标协议与传输能力必须覆盖 OpenAI Chat／Responses／Embeddings、Anthropic Messages／count_tokens、流式 SSE 和需要长会话的 WebSocket。它们都进入统一能力模型、Adapter 契约和测试矩阵；一期最低交付仍为 Models、Chat Completions、Messages，其他端点和 WebSocket 的一期启用顺序由 Stage 01 真实客户端与上游 PoC 冻结。分期只决定开发顺序，不代表从目标架构删除。

#### 4.1.2 后发吸收基线

v0.3 将 TokenHub 和 Sub2API 已验证的优势纳入仟流目标架构：

- TokenHub：企业／团队／项目治理、Provider／Resource／Route 分层、能力注册、Key 安全、路由证据、企业身份接入和多实例部署；
- Sub2API：API Key／OAuth／套餐账号池、凭证生命周期、复杂账号评分、粘性会话、配额和并发控制、SSE／WebSocket、多协议 Adapter 及故障注入测试；
- 仟流自有：以 Token 为基础事实的额度与账本、企业采购资源管理、逐 Attempt 真实消耗、持续供给预测、峰谷经营调度和可解释节省。

“纳入目标架构”意味着必须进入领域模型、接口边界、测试计划和开发路线；不要求一期同时开放全部 UI 和协议，但不得以“一期不做”为理由形成不可扩展的封闭实现。

### 4.2 二期范围

- 仟流智算 Agent，供管理员查询、解释和执行常用管理操作。
- 仟流智算 Agent 的入口在一期原型中预留于页面右上角；一期制品不开放该功能。
- 除一期运行保障成员定向消息外的企业微信消息、邮件、短信等外部通知渠道。
- 员工把单次任务指定到某个项目。
- 面向企业客户的企业开通、团队／项目／成本中心、分级 RBAC、企业身份源和多企业隔离。
- 按 PoC 排序开放目标协议矩阵中的更多端点、WebSocket 和更多 Provider。
- 跨区域部署、多活容灾和企业级高可用。

### 4.3 一期不做

- 手机端。
- 员工 Web 管理后台。
- 语音入口。
- OA、短信、邮件及非运行保障场景的企业微信集成。
- 部门预算、产品预算和多层预算体系。
- 自动抓取厂商价格与套餐规则。
- 自动采购和充值。
- 保存员工提示词、代码、文件内容和模型回答正文。当前默认零留存；未来只有出现明确企业需求时，才作为独立受控能力立项。
- 终端流量监听、浏览器扩展、VPN、根证书或 TLS 解密。

## 5. 用户和使用主体

### 5.1 管理员

- 使用桌面 Web。
- 是系统最高权限。
- 可以创建其他管理员账号。
- 老板不单独建立角色，老板账号就是管理员账号，显示名称可以修改。
- 可以管理资源、员工、项目、Key、额度、规则、账本和异常。
- 提交管理操作后直接执行，并记录操作人、时间、对象、结果和失败原因。

### 5.2 使用主体

系统统一使用“使用主体”表示消耗企业 AI 资源的对象：

| 类型 | 说明 |
| --- | --- |
| 员工 | 真实员工，可以使用账号登录仟流 IDE，也可以在第三方工具中使用个人 Key |
| 项目 | 非人的调用主体，拥有独立 Key、模型和额度，使用方式与员工相同 |

员工和项目复用同一套 Key、分配、额度、计量、停用和异常能力。部门仅作为员工的可选信息，不形成独立额度层。

## 6. 核心业务流程

### 6.1 员工开通

顺序固定：

1. 管理员创建员工账号。
2. 系统为员工生成一把独立仟流 Key。
3. 管理员为员工分配 DeepSeek、智谱、Kimi 的使用权限和额度。
4. 系统生成员工接入信息。
5. 员工在自己的工具中完成配置并开始使用。

不得把模型分配放在账号和 Key 之前。

### 6.2 项目开通

1. 管理员创建项目。
2. 系统为项目生成独立仟流 Key。
3. 管理员为项目分配模型和额度。
4. 项目服务通过 Gateway 调用。

### 6.3 员工接入信息

接入信息包含：

- Gateway 地址；
- 员工专属 Key；
- 已开通模型名称；
- WorkBuddy、Claude Code、ZCode 的配置说明；
- 一键复制内容。

Key 明文只在创建或重置时显示一次，之后只显示掩码。重置后旧 Key 立即失效。

仟流 IDE 使用员工账号登录，自动取得 Gateway 地址、可用模型和受控凭证，不要求员工手动复制 Key。

### 6.4 停用

- 停用员工或项目后，其 Key 立即失效，全部模型权限停止。
- 历史用量、费用和异常记录保留。
- 重新启用员工后必须生成新 Key。
- 修改名称不改变历史记录的归属。

## 7. 厂商资源

Gateway 使用四个不同层次表达“厂商、账号、模型和路由”，不得把它们压成一张账号表：

| 对象 | 产品含义 |
| --- | --- |
| Provider | 一类上游厂商或协议适配器，例如 DeepSeek、智谱、Kimi |
| Provider Resource | 一个可调用、可计量、可独立健康检查的 API 账号或套餐账号 |
| Unified Model | 员工看到的稳定模型名，不暴露具体上游账号 |
| Model Route | 从统一模型到一个或多个资源的候选关系，包含优先级、权重、启停和兜底策略 |

### 7.1 两种资源模式

| 模式 | 示例 | 主要记录 |
| --- | --- | --- |
| API | DeepSeek API | 充值金额、余额、本月用量、本月费用、价格规则 |
| Coding Plan／套餐 | 智谱、Kimi K3 | 套餐名称、套餐费用、总额度、已用额度、有效期、扣减规则 |

两种模式的采购形态和上游结算方式不同，但仟流的底层使用事实统一为 Token。输入、输出、缓存命中／未命中等 Token 分项必须保留；厂商额度扣减和费用是基于这些事实及规则版本计算出的派生结果。

### 7.2 资源账号

同一厂商可以登记多个账号或套餐。每个资源账号至少记录：

- 厂商；
- 资源模式；
- 账号名称；
- 可用模型；
- 充值金额或套餐费用；
- 总额度和剩余额度；
- 生效、失效和重置时间；
- 状态；
- 上游凭证；
- 价格或额度扣减规则。
- 支持的协议、模型和能力；
- 路由优先级和权重；
- 健康状态、最近探测时间、冷却截止时间；
- 并发上限和当前占用。
- 凭证类型：API Key、OAuth 或套餐会话；
- 凭证过期、刷新状态和刷新失败原因；
- 额度余量、下一重置时间和冷却原因；
- 当前并发、容量余量、错误率、首包时延和最近成功时间。

### 7.3 资源池

- 员工或项目只分配厂商、模型和个人额度，不绑定具体上游账号。
- Gateway 自动选择资源池中的可用账号。
- 单个账号限流、失效或耗尽时，可以切换到同一资源池的其他账号。
- 只有使用主体额度耗尽，或资源池全部不可用时才停止。
- 系统记录每次调用实际使用的上游账号。
- 不人为串行化多人请求；上游并发、限流和总额度才是实际边界。
- 同一优先级内按权重分配；低优先级只在高优先级没有可用资源时参与。
- 资源在探测失败、连续错误、限流或凭证失效时进入不可用或冷却状态，恢复后重新参与路由。
- 同一会话优先复用原资源；原资源不可用时，路由器必须优先保证请求成功，不为亲和性阻塞故障切换。
- 同一优先级候选不能只按静态权重盲选。系统应使用版本化评分策略综合健康、容量余量、当前负载、错误率、首包时延、额度余量、重置时间、边际成本和会话亲和；所有评分因子和最终选择理由必须进入路由证据。
- OAuth／套餐凭证刷新失败时先隔离对应资源，不得拖累整个账号池；恢复或重新授权后通过受控探测重新入池。

### 7.4 套餐与 API 路由

- 同一模型同时存在套餐和 API 时，默认优先套餐。
- 套餐不可用后默认不自动转 API，避免产生非预期费用。
- 管理员可开启“允许 API 兜底”并设置资源优先级。
- API 兜底产生的费用单独统计。
- 只有明确标记为可重试的网络错误、限流和上游临时故障，才允许在预算内切换资源；鉴权失败、请求不合法和能力不支持不得盲目重试。
- 非流式请求在确认上游未形成可计费成功结果时才切换。
- 流式请求在首个有效内容或工具调用事件发给客户端前允许切换；一旦提交输出，只能按当前协议返回错误或结束连接，禁止连接第二个上游继续拼接。
- API 兜底和每次故障切换均记录原因、候选资源、上游错误和最终结果。

### 7.5 持续供给与经营调度

系统对每个资源账号和统一模型至少计算：

- 最近 1 小时、24 小时和 7 天的消耗速度；
- 按当前速度预计耗尽时间；
- 厂商下一次额度恢复／重置时间；
- 当前剩余额度可覆盖的预计时长；
- 预测使用的数据窗口、更新时间和可信度；
- 预测为空的原因，例如数据不足、规则不明确或上游余额未知。

Gateway 每次请求在健康和协议能力判定后，再按以下经营因素调度：

1. 当前时段及其价格／额度扣减倍数；
2. 资源剩余额度、距离周期结束的时间和预计耗尽风险；
3. 套餐与 API 的真实边际成本；
4. 管理员预先发布的等价资源、优先级和允许动作；
5. 主体额度、是否允许超额和并发状态。

一期同步请求支持的调度动作：

- `ALLOW`：按当前资源放行；
- `SWITCH`：切换到管理员预先确认的等价模型／资源；
- `RATE_LIMIT`：按照规则限制并发或速率；
- `REJECT`：额度、成本或安全规则触发时拒绝；
- `ALLOW_OVERAGE`：管理员预先允许后超额放行并单列。

一期不对同步 IDE／Chat 请求做服务端排队，也不未经管理员授权自动更换非等价模型。可延迟任务的谷时排队进入二期，但一期必须保留调度动作和决策记录的扩展位。

每次调度保存输入快照、命中规则、候选动作、最终动作和理由。只有存在明确价格／扣减基线和实际执行证据时，才计算“调度节省”；只有提示但没有发生行为变化时不得计入节省。

## 8. 额度

### 8.1 分配方式

- 管理员可以直接填写某个使用主体的额度数值。
- 管理员可以创建额度规则模板并批量套用。
- 套用后允许单独修改。
- 优先级：主体单独设置 > 额度规则 > 系统默认值。
- 使用主体额度以 Token 为基础单位；可按模型、Token 类型、周期和资源组设置。
- 金额和厂商原生额度作为资源采购、结算与对账维度保存，不替代主体 Token 用量事实。

### 8.2 有效期

- 使用主体额度的生效、失效和重置周期跟随对应厂商资源。
- 厂商进入新周期后，已使用额度自动清零，分配规则继续沿用。
- 上一周期未使用额度默认不结转。
- 厂商资源到期、耗尽或失效后，关联使用主体停止使用。

### 8.3 用完和超额

- 额度用完默认停止该主体继续使用该资源。
- 管理员可以为主体开启“允许超额使用”。
- 超额部分单独统计和预警。
- 超额列表按超出比例排序。

## 9. 用量、扣减和费用

系统不得把三个概念混成一个数字：

| 概念 | 含义 |
| --- | --- |
| Token 用量事实 | 上游返回或 Gateway 计算的输入、输出、缓存等原始 Token |
| 实际扣减额度 | Token 用量事实经过套餐规则折算后的额度 |
| 实际费用 | API 调用按照调用当时价格计算的真实费用 |

计量遵守“渠道无关，凡消耗必记账”：

- 一个下游业务请求形成一个结算汇总，避免客户端重试造成重复结算；
- 每个实际访问上游的 Attempt 都有独立、不可覆盖的用量和费用／扣减明细；
- 失败、超时或被切换的 Attempt 只要产生了可证明用量，也必须进入结算汇总；
- 同一上游计量事实重复到达时幂等，不得重复扣减；
- 不能用“最终成功资源”覆盖前序 Attempt 的真实消耗；
- 上游未提供逐请求数据时必须标记计量质量，不得把估算或账号汇总冒充精确值。

### 9.1 API

- 原始 Token 不因价格变化而改变。
- 费用按照调用发生时命中的价格版本计算。
- 使用主体额度按 Token 扣减；金额用于企业成本、预算和对账，不覆盖 Token 用量事实。

### 9.2 Coding Plan

- Token 用量事实按照厂商套餐规则折算为实际扣减额度。
- 员工或项目费用显示“套餐内”，不显示为 0 元。
- 套餐固定费用记录在厂商资源账号，不伪造员工真实单次费用。
- 异常判断主要依据额度消耗速度和超出比例。

### 9.3 规则配置

厂商资源配置支持两类可版本化规则：

1. API 分时价格规则；
2. 套餐额度扣减规则。

规则至少包含：

- 厂商、资源、模型；
- 生效和失效日期；
- 星期、时间段和时区；
- 输入、输出、缓存等价格项，或额度扣减倍数；
- 优先级和启用状态。

一期由管理员选择系统模板并手工维护。规则修改只影响新调用，历史调用继续引用原规则版本。

初始业务口径：

- DeepSeek：API 模式，支持版本化分时价格规则，但系统不预置固定时段和单价；管理员根据实际采购渠道、合同或厂商当期规则配置。
- 智谱：Coding Plan 模式，支持北京时间 14:00–18:00 的高峰扣减规则。
- Kimi：Coding Plan 模式，首用 Kimi K3，支持按模型档位和厂商规则配置扣减倍数。

- API／套餐；

- 谁；
- 类型；
- 分配多少；
- 使用多少；
- 超出多少；
- 超出比例。

支持按以下条件筛选：

- 员工／项目；
- 工具；
- 厂商和模型；
- 时间；
- 成功、失败和拒绝；
- 是否超额。

每条记录至少显示：

- 仟流请求 ID；
- 发起主体；
- 客户端；
- 模型；
- 上游账号；
- 输入／输出／缓存 Token 用量事实；
- 实际扣减额度；

### 10.4 空状态

空状态必须说明“为什么为空、下一步做什么”，不能用空白表格冒充正常页面：

| 场景 | 空状态文案要点 | 允许动作 |
| --- | --- | --- |
| 新企业没有厂商资源 | 尚未登记可用 AI 资源，无法产生模型和路由候选 | 去“厂商资源”登记 DeepSeek API、智谱或 Kimi 资源 |
| 没有员工或项目 | 尚未创建使用主体，也未生成主体 Key | 创建员工或项目并完成四步开通 |
| 资源存在但没有统一模型／Route | 资源尚未绑定对外模型，员工不能调用 | 创建统一模型并配置 Model Route |
| 当前自然月没有调用 | 本账期尚无真实请求、Token、费用或异常 | 查看接入信息；不得展示模拟趋势或伪造节省 |
| 用量账本为空 | 当前筛选条件没有账本记录 | 清除筛选或发起真实调用；不得把测试数据混入正式周期 |
| 异常告警为空 | 当前没有未处理告警 | 显示“运行正常”，保留查看历史事件入口 |
| 预测不可计算 | 数据不足、余额未知或周期规则未冻结 | 展示具体原因和最近更新时间，不输出伪精确耗尽日期 |
| 调度节省不可计算 | 没有已发布反事实基线，或动作未真实执行 | 展示 `NOT_CALCULABLE` 原因，不计入首页节省 |

## 11. 异常告警

一期保留四个告警域：

1. 厂商或模型不可用、错误率突然升高，或预计在周期结束前提前耗尽；
2. 某个人或项目用量／费用突然异常增长；
3. 频繁限流、调用拒绝或额度扣减异常；
4. 账号、凭证失效或出现非预期使用。

重点突出：

- 资源是否还能使用；
- 谁的额度或费用异常。

一期告警只在管理后台展示，可以标记已处理，不发送到外部渠道。

资源连续失败、进入熔断／冷却、路由无可用候选和流式提交后中断，均归入“厂商或模型不可用”类告警，并可从告警追踪到具体请求和上游尝试。

## 13. 安全和隐私

- Web 和 Gateway 通过公网 HTTPS 提供服务。
- Web 与 Gateway 使用不同子域名。
- 上游真实凭证只保存在服务器，不交给员工。
- 上游真实凭证加密保存，解密密钥与数据库分离。
- 员工 Key 使用不可逆摘要和服务端 Pepper 保存，明文仅展示一次。
- 员工 Key 可限制模型、来源 IP、有效期、额度和并发；重置、停用或吊销后必须立即阻断新请求。
- 管理员密码和员工密码使用安全密码哈希保存。
- 默认不保存提示词、代码、文件内容和模型回答正文。
- 计量元数据包括主体、客户端、资源、模型、用量、扣减、费用、时间、耗时和错误。
- Session Affinity 只保存客户端显式会话 ID 的 HMAC 伪名或系统生成的随机标识，不保存正文，也不得用提示词或代码的普通哈希充当会话标识。
- 数据库、应用日志、链路追踪、错误对象和告警中均不得出现请求与响应正文。
- 零正文留存是当前默认策略，不是永久产品边界。未来如企业明确需要内容审计或质检，必须独立启用、默认关闭，并具备企业授权、数据分类、字段级加密、最小权限、访问审计、留存期限和可验证删除；不得通过普通日志开关偷偷开启。
- 所有管理操作记录操作人、时间、对象、前后变化摘要和结果。
- 停用主体或重置 Key 必须立即生效。

## 15. 真实业务周期

内部验证使用 10 名员工，连续运行一个完整自然月。厂商额度仍按各自有效期和重置周期执行，不因验证周期改变。

核心指标：

1. 10 名员工全部使用独立账号和 Key。
2. 纳入试点的调用主体归因率不低于 90%。
3. 重复记账率为 0，已确认调用事件丢失率低于 0.1%。
4. 价格、额度倍数、有效期和周期重置计算与配置规则一致。
5. 仟流 IDE、WorkBuddy、Claude Code、ZCode 均完成真实接入。
6. 管理员无需询问员工即可看到资源、人员、额度、费用和异常。
7. 默认正文落库数量为 0。
8. 所有 Gateway 请求均可通过请求 ID 追踪候选资源、上游尝试、账本明细和最终结算，路由证据完整率为 100%。
9. 流式故障测试中跨上游输出拼接次数为 0，重复结算次数为 0；所有产生可证明用量的 Attempt 明细完整率为 100%。
10. 数据库中下游 Key 明文数量为 0，上游凭证明文数量为 0。
11. 每日保存资源预计耗尽和下一恢复快照；自然月结束时可以对比预测与实际结果并解释偏差。
12. 所有峰谷经营调度均保存请求前输入、命中规则、动作和结果；没有反事实证据的提示不得计入调度节省。
13. 所有进入账号池选路的请求均保存路由策略版本、评分因子、总分和 reason code；历史回放结果可复现。
14. API Key／OAuth／套餐凭证异常只隔离对应资源，未导致健康账号被连带停止。
15. PoC 冻结后启用的 Responses／Embeddings／count_tokens／WebSocket 契约测试通过率为 100%，未启用能力均返回明确错误。

四种工具各至少覆盖 2 名真实员工；同一员工可以使用多种工具。

测试、演示和开发数据必须与真实周期数据隔离。

## 16. 原型真实任务走查

K3 原型增量走查必须以本文和 [TRD v0.3](./仟流智算-技术需求文档-v0.3.md) 为输入，至少覆盖以下任务：

1. `WT-01`：管理员登记 DeepSeek API、智谱套餐和 Kimi 套餐。
2. `WT-02`：管理员创建员工、取得 Key、分配模型和额度。
3. `WT-03`：员工根据接入信息在第三方工具中完成首次调用。
4. `WT-04`：管理员创建项目并按同样方式分配资源。
5. `WT-05`：管理员查看某员工输入／输出／缓存 Token、实际扣减和 API 费用。
6. `WT-06`：员工额度耗尽后停止；开启允许超额后恢复并产生超额记录。
7. `WT-07`：套餐账号失效后切换同资源池账号；套餐转 API 只在开关开启时发生。
8. `WT-08`：管理员从首页发现资源不可用或使用主体异常，并进入明细。
9. `WT-09`：管理员停用员工或重置 Key，旧 Key 立即不可用。
10. `WT-10`：管理员查看统一模型的路由候选、优先级、权重、健康和冷却状态。
11. `WT-11`：一次调用经历两个上游 Attempt 后成功，管理员看到一个结算汇总；若两个 Attempt 都产生可证明用量，则看到两条不可覆盖的账本明细。
12. `WT-12`：流式响应提交后上游中断，系统不拼接第二个上游，并留下可诊断的中断记录。
13. `WT-13`：同一会话优先命中原资源；原资源不可用时切换到健康资源，且系统不保存会话正文。
14. `WT-14`：调用未支持的协议能力时收到明确错误，管理员可以定位到 Provider 能力配置。
15. `WT-15`：管理员查看某资源的消耗速度、预计耗尽、下一恢复和覆盖时长，并能看到预测依据和可信度。
16. `WT-16`：高峰时段请求命中已发布规则，在预授权等价资源间切换或执行限流／拒绝，路由明细可以解释输入、动作和结果。
17. `WT-17`：系统只对实际发生且具备价格／倍率基线的调度计算节省；仅提示或没有反事实证据时节省为“不可计算”。
18. `WT-18`：管理员查看一次账号池选路的全部评分因子，能解释静态优先级、负载、错误率、时延、额度、重置时间、成本和 Affinity 如何影响结果。
19. `WT-19`：OAuth／套餐凭证到期或刷新失败时仅隔离对应资源，其他健康账号继续服务；重新授权后资源受控恢复。
20. `WT-20`：对目标协议矩阵执行能力检查；已启用的 Responses／Embeddings／count_tokens／WebSocket 正常工作，未启用能力返回明确错误，不静默降级。

走查必须记录发现的问题、修改结论和原型版本。
