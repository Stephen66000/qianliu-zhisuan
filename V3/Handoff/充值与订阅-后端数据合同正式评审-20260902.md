## 3. P0 Findings

### FIN-P0-01：缺少“API 使用费用不完整”余额状态

**证据**：合同 7.1 允许 API 行 `api_cost` 为空；8.3 的余额状态只有正常、缺期初、负余额和历史封存。

当前 Gateway 在没有可用计价规则时会生成真实使用事实，但 `api_cost = null`。如果余额投影只汇总已知 `api_cost`，未知费用会被忽略，余额仍可能返回 `NORMAL`。

**必须修订**：新增余额状态：

```text
INCOMPLETE_USAGE_COST
```

规则：切换边界后、asOf 之前存在已结算 API 行且费用未知时：

- `balance = null`；
- 返回缺口行数、请求 ID、资源、结算时间和原因；
- 不创建负余额案件；
- 资源利用、供给预测和经营成本失败关闭；
- 不得把已知费用部分当完整余额。

### FIN-P0-02：精确零审计行与费用币种约束冲突

**证据**：合同 7.1 规定“API 且 api_cost 非空时币种必须非空”。现有 `attempt-usage-settlement.ts` 对确认未访问上游的 API Attempt 写入：

```text
api_cost = 0.00000000
billing_rule_id = null
billing_rule_snapshot = null
```

这类行是精确零审计，不应要求费用币种，也不影响余额。

**必须修订**：增加费用事实分类或等价判定：

```text
PRICED_USAGE
CONFIRMED_ZERO_NO_UPSTREAM
UNKNOWN_COST
```

约束应改为：

- `PRICED_USAGE`：费用和币种必须同时存在；
- `CONFIRMED_ZERO_NO_UPSTREAM`：费用固定为 0，币种允许 NULL，不参与余额扣减且不形成缺口；
- `UNKNOWN_COST`：费用、币种为空，触发 `INCOMPLETE_USAGE_COST`。

不能用 `api_cost IS NULL/NOT NULL` 单独判断完整性。

### FIN-P0-03：对账案件状态机无法满足终态约束

**证据**：合同 3.3 要求对账事件引用状态为 `CONFIRMED` 的案件；5.2 又要求确认、写调整和变成 `RESOLVED` 在同一事务中完成。

事务提交时案件已是 `RESOLVED`，事件却要求关联 `CONFIRMED`。跨表状态也无法用普通外键/CHECK直接保证。

**必须二选一并写死**：

推荐方案：删除持久化 `CONFIRMED` 状态，状态机改为：

```text
OPEN -> REJECTED
OPEN -> RESOLVED
```

`RESOLVED`必须同时具备：

- `decision = CONFIRMED`；
- `adjustment_event_id` 非空；
- 调整事件反向引用案件；
- 调整金额等于案件差额；
- 同一事务提交。

由仓储事务和数据库约束触发器共同保证，不要求事件引用一个提交后不存在的瞬时状态。

### FIN-P0-04：余额读取缺少跨表一致性隔离

余额同时读取：

- `provider_finance_event`；
- `ledger_line`；
- OPEN 对账案件。

合同未规定读取必须使用同一个数据库快照。若查询过程中恰好写入充值或使用结算，组件金额与水位可能来自不同时点。

**必须修订**：`getCurrentBalance`必须满足以下之一：

1. 一个 SQL 语句完成全部聚合和水位；或
2. `REPEATABLE READ` 只读事务，并在事务开始锁定 `asOf` 和数据库快照。

响应水位必须来自同一快照。不得先查资金事件、再用普通 READ COMMITTED 查使用账本。

### FIN-P0-05：冲销和更正的业务时间未定义

合同只规定冲销接口由服务端派生金额，没有规定派生 `occurred_at`。

如果冲销使用“现在”，原月现金支出不会被纠正；如果期初更正使用“现在”，9月1日至更正时间之间的历史 asOf 仍错误。

**必须修订**：

- `API_OPENING_BALANCE_CORRECTION.occurred_at` 固定等于切换边界；`created_at`记录实际更正时间；
- OPEN账期内的充值/订阅 `REVERSAL.occurred_at` 固定等于原事件 `occurred_at`；
- 已结账账期必须先重开；
- 对账调整 `occurred_at` 等于案件 `balance_as_of` 或明确的厂商确认业务时点，二者需选定一个；
- 所有月度指标按业务时间归属，审计按创建时间追溯。

### FIN-P0-06：Coding Plan 周期暗写时序不成立

切换手册要求暗部署阶段 Gateway 开始写 `subscription_period_id`，但周期表的 carryover 和新周期到正式切换窗口才迁入。暗部署到切换之间的新 Coding Plan 使用没有可命中的周期。

**必须修订切换顺序**，二选一：

推荐方案：

1. 加法迁移后先暗创建/迁入订阅周期；
2. 只生成周期事实，不生成新现金支出；
3. 校验周期后启用 Gateway 暗写周期 ID；
4. 正式窗口只迁资金事件并完成增量周期/使用回填。

若周期不能提前创建，则暗部署只能先写 `api_cost_currency`，`subscription_period_id`继续为空并在正式窗口暂停相关新结算或完成增量回填后再切 Gateway。合同和手册必须选择一种，不能同时要求“提前完整暗写”和“正式窗口才有周期”。

## 4. P1 Findings

### FIN-P1-01：历史使用回填缺少不可变例外

合同要求回填现有 `ledger_line.api_cost_currency` 和 `subscription_period_id`，但上位规则把使用账本定义为不可覆盖历史事实。

应明确：

- 迁移只允许补充空的归属/币种列；
- 不修改 Token、费用金额、资源、请求、规则快照和结算时间；
- 回填前后逐行哈希非目标字段；
- 回填迁移只执行一次并留 Evidence；
- 或改用追加式 side table，完全不 UPDATE `ledger_line`。

### FIN-P1-02：可冲销事件矩阵不完整

“可冲销事件”没有枚举。建议第一版只允许：

```text
API_RECHARGE
CODING_PLAN_PURCHASE
CODING_PLAN_RENEWAL
```

禁止冲销：

```text
API_OPENING_BALANCE
API_OPENING_BALANCE_CORRECTION
API_BALANCE_RECONCILIATION
REVERSAL
```

期初用更正，对账差异用新案件/新调整继续修正。

### FIN-P1-03：二次确认令牌没有合同

无外部凭证的重复候选要求“新的确认令牌”，但没有定义：

- 令牌由谁签发；
- 绑定哪些请求字段；
- 有效期；
- 是否一次性；
- 存储表；
- 重放和并发行为。

应新增重复候选确认对象，或取消令牌，改为服务端返回候选 ID，确认接口携带候选 ID、原 request_hash 和新的幂等键。

### FIN-P1-04：外部凭证唯一范围过窄

当前唯一索引包含 `event_type`。同一付款可被分别登记为 `CODING_PLAN_PURCHASE` 和 `CODING_PLAN_RENEWAL`，造成重复现金支出。

建议现金事件唯一范围改为：

```text
enterprise_id + provider_resource_id + external_reference
```

事件类型不参与唯一性；冲销事件不复用原外部凭证。

### FIN-P1-05：必须写明复合租户外键

所有以下关系都应同时携带并校验 `enterprise_id`：

- 资金事件 -> 资源；
- 事件 -> 原事件/期初/案件；
- 周期 -> 资源/资金事件/冲销事件；
- 案件 -> 资源/调整事件；
- `ledger_line.subscription_period_id` -> 周期。

不能只使用单列 UUID 外键后依赖应用层判断企业一致。

### FIN-P1-06：金额精度和舍入未定义

合同使用 `numeric(24,8)`，但未明确：

- 人民币实付是否最多两位小数；
- API 微额费用何时舍入；
- 聚合中间值是否舍入；
- CNY/USD 展示精度；
- 冲销如何保证逐字节相反。

建议：账户金额和 API 费用最多 8 位小数；人民币实付最多 2 位；聚合过程中不舍入，入账时按计价合同冻结，显示层单独格式化；冲销直接复制原存储值取反。

### FIN-P1-07：业务时间边界未定义

应明确：

- 管理员普通充值/订阅不得登记未来业务时间；
- 允许补录的最早时间为切换边界且账期必须开放；
- Coding Plan 前端提交自然日，服务端转换为 Asia/Shanghai 00:00；
- `period_end_exclusive`按上海自然日计算；
- `asOf`晚于当前时间时是否拒绝，建议拒绝普通查询或钳制并显式返回实际 asOf。

### FIN-P1-08：结算时间没有独立字段

合同规定余额扣减使用结算完成时间，但现有 `ledger_line`只有 `created_at`。当前实现通常在结算时写入，但该语义没有被字段名和数据库合同锁死。

建议新增或明确：

```text
ledger_line.settled_at
```

新写入显式赋值；历史行以现有 `created_at`回填并记录迁移依据。余额、月度成本和周期归属统一读取 `settled_at`。

## 5. 已验证成立的合同部分

以下方向通过本轮评审：

- 现有 `ledger_line`继续作为唯一API扣费事实，不复制第二份使用账本；
- `billing_rule_snapshot`当前已冻结 `currency`，具备主要币种回填来源；
- 期初、充值、订阅、对账、更正和冲销使用追加式事件；
- 期初余额允许已确认零值并与缺期初区分；
- CNY/USD余额分开，人民币实付独立统计现金支出；
- Coding Plan费用与使用量分离；
- 5小时/7天窗口继续保留；
- 已结账月份必须显式重开；
- 加法迁移可提前，同一窗口切读写和废止旧写入口；
- 新写入恢复后不得直接回旧链；
- 负余额不能导致已发生使用事实丢失；是否阻断未来请求仍保持非目标。
