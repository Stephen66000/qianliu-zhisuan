## 1. 启动条件

以下条件全部满足才允许排期：

- [ ] 资金规则、后端提案、数据合同和旧链影响清单已评审；
- [ ] 实时 `origin/main`、候选 Commit/Tree、迁移头和生产部署拓扑已锁定；
- [ ] 独立工作树干净，无共享脏工作区内容；
- [ ] 新迁移为加法迁移，未删除旧表和旧字段；
- [ ] 新 Gateway 已能暗写 `api_cost_currency`、`api_cost_status` 和 `settled_at`，旧读取仍不受影响；
- [ ] Coding Plan暗周期已创建并校验后，Gateway才开始暗写 `subscription_period_id`；
- [ ] 每个 API 资源的 9 月 1 日期初余额候选已经需求方确认；
- [ ] 9 月 1 日后充值、订阅、API扣费和 Coding Plan 周期缺口报告为 0，或每个缺口有明确处置；
- [ ] 迁移脚本已在生产等价副本完整演练一次；
- [ ] 守恒报告模板、备份、回滚点和健康检查已验证；
- [ ] 切换窗口内执行人、Owner、数据库、主机和通知范围已锁定。

任一条件不满足，状态为 `NO-GO`。

## 2. 切换对象锁

切换记录必须固定：

| 对象 | 要求 |
| --- | --- |
| Git Commit / Tree | 精确 SHA，不使用浮动分支名代替 |
| 数据库迁移头 | 切换前实时读取 |
| 数据库实例 | 精确主机/库名，不使用模糊环境变量输出敏感信息 |
| 部署候选 | 已完成定向测试和静态检查的同一对象 |
| 切换边界 | 2026-09-01 00:00:00 Asia/Shanghai |
| 切换水位 T0 | 旧资金写入口冻结后的时间和最后事件 ID |
| 使用水位 T1 | 读切换前最后一条已结算 `ledger_line` ID/时间 |
| Owner | 期初余额和资金守恒最终确认人 |

候选字节、迁移或配置发生变化，原有验证结论失效，必须重新冻结候选。

## 3. 切换前暗部署

暗部署不改变用户可见读取和资金写入口，只提前准备新能力：

1. 部署加法数据库迁移；
2. 创建新资金表、订阅周期、对账案件和幂等表；
3. 增加 `ledger_line.api_cost_currency`、`api_cost_status`、`settled_at` 与 `subscription_period_id` 可空列；
4. 部署 Gateway 新结算代码，使新 API 使用行开始填写费用币种、费用状态和独立结算时间；
5. 按已审核旧事实暗创建 `MIGRATED_CARRYOVER` 和 `MIGRATED_PURCHASE` 周期，不生成资金事件和月度成本；
6. 周期校验通过后，启用 Gateway 暗写 `subscription_period_id`；
7. 部署包含新旧两套读写代码但默认仍使用旧链的应用版本；
8. 运行暗读比对，新投影不得影响生产响应；
9. 生成迁移候选和缺口报告。

暗部署阶段不得开放新充值/订阅写入口，不得关闭旧端点。

## 4. 切换前数据准备

### 4.1 期初余额候选

逐资源列出：

- 企业；
- 厂商；
- 资源账号；
- 账户币种；
- 2026-09-01 00:00:00 期初金额；
- 证据；
- 确认人；
- 确认状态。

旧快照只能作为候选证据，不能自动确认。未确认资源保持 `MISSING_OPENING_BALANCE`。

### 4.2 充值与订阅候选

生成 9 月 1 日后：

- API_RECHARGE 数量、原币金额、人民币实付、外部凭证；
- Coding Plan 购买/续费数量、订单金额、人民币实付和周期；
- 9 月 1 日前已购买但切换日仍有效的 carryover 周期。

缺人民币实付、币种、周期或凭证冲突的记录不得自动迁入。

### 4.3 使用事实候选

API：

- 不复制使用流水；
- 列出切换边界后已结算 `ledger_line`；
- 按冻结计价快照/版本回填费用币种；
- 分类回填 `PRICED_USAGE`、`CONFIRMED_ZERO_NO_UPSTREAM`、`UNKNOWN_COST`；
- 以原创建时间回填独立 `settled_at`；
- 缺币种、规则冲突、费用未知和未结算行分别统计。

Coding Plan：

- 按结算时间匹配开始日最新的覆盖周期；
- 生成 `subscription_period_id` 回填候选；
- 无覆盖周期和多义冲突分别统计。

历史使用回填只允许补空的币种、费用状态、结算时间和周期ID；迁移前后必须逐行证明Token、费用金额、资源、请求和规则快照未改变。

## 5. 正式切换窗口

### 5.1 进入维护状态

1. 宣布切换开始；
2. 暂停旧资金写入口：充值、订阅、期初余额、旧购买和旧经营快照资金字段；
3. API 使用可以继续，但必须确认暗部署后的新结算行持续写入费用币种、费用状态和结算时间；Coding Plan周期ID暗写必须已通过周期准备门禁；
4. 记录旧资金最后写入水位 T0；
5. 创建生产备份并验证可读取；
6. 再次读取迁移头、Commit/Tree和服务健康。

若 Gateway 暗写字段不完整，应暂停相关新请求或停止切换；不能让费用未知或周期归属缺失的增量无限增长。

### 5.2 数据写入

按以下顺序执行，任一步失败立即停止：

1. 插入已确认期初余额；
2. 迁入 9 月 1 日后 API 充值；
3. 迁入 9 月 1 日后 Coding Plan 购买/续费，并把资金事件绑定到已暗创建周期；
4. 回填 9 月 1 日后 API 费用币种、费用状态和独立结算时间；
5. 回填尚未暗写的 Coding Plan 使用周期 ID；
6. 记录使用水位 T1；
7. 再次补齐 T0/T1 后产生的增量结算行。

若切换前旧 `UNKNOWN_COST` 行不能逐笔恢复，但厂商API余额证明存在真实动态费用，只允许通过0060历史成本封口：覆盖窗口固定从9月1日开始，以厂商同步余额快照结束；未知行保留原状并关联封口，聚合缺失成本同时进入余额和经营成本。Coding Plan固定月费不得进入该流程。8月测试数据保持封存。

资金事件导入必须幂等；重跑同一批次只能返回原结果，不能重复入账。

### 5.3 守恒检查

全部通过才允许切换读取：

#### 数量守恒

- 期初事件数 = 已确认 API 资源币种数；
- 新充值事件数 = 合格旧充值记录数；
- 新订阅事件/周期数 = 合格购买/续费数；
- carryover 周期数 = 审核通过的历史有效周期数；
- 9 月 1 日后 API 结算行数切换前后相等；
- API结算行 = 已计价 + 确认未上游零事实 + 费用未知，不允许丢失；
- Coding Plan 结算行 = 已归属周期 + 明确缺口，不允许丢失。

#### 金额守恒

- 按资源和币种核对充值原币金额；
- 核对人民币实付；
- 按资源和币种核对 API 使用扣费；
- 核对 Coding Plan 订单金额与人民币固定成本；
- 不允许 CNY/USD 混加。

#### 余额守恒

逐 API 资源执行：

```text
期初 + 充值 + 更正 + 对账 - 已结算使用 + 冲销 = 当前余额
```

缺期初和费用未知必须返回不可计算；确认未上游零事实不形成费用缺口；负余额必须返回异常待对账，不能静默归零。

#### 周期守恒

- 扣费日 = 周期开始日；
- 默认周期从扣费日到下个月同日，随月份为28/29/30/31天；
- 重叠周期按开始日最新归属；
- 已冲销周期不接收新使用；
- 真实 Token = 输入 + 输出。

### 5.4 同窗切换读写

守恒通过后，在同一个发布动作中：

1. 启用新资金写接口；
2. 启用统一余额和月度资金读取；
3. 厂商资源、资源利用、用量总览、供给预测、经营账单、首页和告警同时切换；
4. 旧资金写端点关闭并返回明确废止响应；
5. 旧经营快照资金字段拒绝写入；
6. 禁止双写新旧账本。

任何消费者仍读旧余额，状态为 `NO-GO`，不能恢复资金写入。

### 5.5 真实验收

恢复写入前，在真实用户路径验证：

- 充值入口只剩一处；
- API/Coding Plan 字段正确；
- 同一资源在所有页面余额、币种、截止时间一致；
- 同一余额响应的事件、使用和案件水位来自同一数据库快照；
- 首页没有充值卡片和待充值明细；
- 经营账单现金支出与经营成本分开；
- CNY/USD 不混算；
- 5小时/7天窗口仍可用；
- 历史资金事件可查；
- 旧端点不能新增资金事实。

验收通过并由 Owner 明确确认后，才恢复正常资金写入。

## 6. 第一次失败立即停止

出现以下任一情况，立即停止，不自动格式化、重跑、拼接或继续后续阶段：

- 实时迁移头与候选不一致；
- 数据库迁移冲突或失败；
- 期初余额未确认；
- 充值、订阅或使用缺口超出已批准清单；
- API费用币种无法回填；
- API费用事实无法分类或仍存在未批准 `UNKNOWN_COST`；
- Coding Plan暗周期未准备完成却已启用周期ID写入；
- 数量、金额、余额或周期不守恒；
- 新旧消费者返回不同余额；
- 旧写入口仍可写入；
- 候选代码或配置在验证后发生变化；
- 备份不可读取；
- 任一核心服务健康失败。

失败现场必须保留：候选 SHA/Tree、迁移日志、数据水位、缺口报告、守恒报告、服务健康和数据库备份标识。

## 7. 回滚边界

### 7.1 恢复资金写入前

若尚未开放新资金写入：

- 保持旧资金写入口暂停；
- 关闭新读取开关；
- 恢复旧读取；
- 新增表中的迁移候选可保留为隔离证据；
- 不删除旧数据，不强行回滚破坏性迁移。

### 7.2 恢复新资金写入后

一旦新账本已经接收真实写入，不允许直接切回旧写链，否则会丢失新事实。

此时必须：

1. 再次暂停资金写入；
2. 保留所有新事件；
3. 评估前滚修复或生成受控反向投影；
4. 禁止把新事件人工复制到旧快照；
5. 由 Owner 决定新的恢复方案。

因此，真实用户验收必须尽量在开放新写入前完成。

## 8. 切换后观察

切换后至少持续检查：

- 新旧端点调用量；
- 资金事件写入失败和幂等冲突；
- 余额状态分布；
- `MISSING_OPENING_BALANCE` 与负余额案件；
- API费用币种缺失；
- Coding Plan 周期缺失；
- 页面间余额水位差异；
- 月度现金支出与经营成本缺口；
- 旧快照资金字段是否仍有新写入。

观察通过只说明新链稳定，不自动授权删除旧表或历史数据。
