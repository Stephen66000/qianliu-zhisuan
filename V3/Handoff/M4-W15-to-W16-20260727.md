## 2. 关键决策（接手者必须知道，否则会走偏）

1. **所有规则/状态机都是 domain 纯函数，副作用在仓储**。路由（routing-policy)、计价（billing-rule)、额度（quota-gate)、预测（supply-forecast)、状态机（resource-lifecycle）全部时钟注入、无随机、可回放。W16 的 dispatch-policy 也必须遵循这个模式。
2. **额度按 deducted_quota 扣减**（W13 倍率后），不是 raw。
3. **并发不穿透用 PG 行锁**；Redis 短期计数是 W25 的性能优化层，正确性以 PG 为准。
4. **quotaRepo 已就绪但还没插进 real-pipeline 热路径**——W16 做经营调度时，在「评分选中后、Attempt 前」一并插入额度门禁 + dispatch 判定（这是 W14 预留的插入点）。
5. **历史不重算**：billing_rule/ledger_line 冻结 rule_version;dispatch_decision 同理（W16 落 decision 后配置变化不改写本次理由）。
6. **不伪精确**：预测/节省在数据不足或基线不可比时必须给 NOT_CALCULABLE + 原因，不能编造数值。

## 3. W16 要做什么（明确范围）

**详细计划行 292**：峰谷／成本／额度／周期策略、等价资源、限流／拒绝、反事实与节省。验收：WT-16/17；无基线为 `NOT_CALCULABLE`。

### 建议拆解（照 W12~W15 模式）

1. **迁移 0014**：
   - `dispatch_policy`：状态（DRAFT/VALIDATED/PUBLISHED/RETIRED）+ 匹配条件（统一模型/资源模式/时间/价格倍率/剩余额度比例/预计耗尽风险/主体范围）+ 允许动作（ALLOW/SWITCH/RATE_LIMIT/REJECT/ALLOW_OVERAGE）+ 等价资源组引用 + 版本。只有 PUBLISHED 进热路径。
   - `dispatch_decision`：请求前经营输入快照 + 命中策略 + 候选动作 + 最终动作 + 理由 + 反事实基线 + 可证明节省（不可覆盖，§5.7 行 342）。
2. **domain `dispatch-policy.ts`**（纯函数）：
   - 策略匹配（按请求时间/模型/资源/剩余额度比例/耗尽风险）→ 动作判定；
   - `computeDispatchSaving` = 反事实基线成本 − 实际成本；基线不可比/未执行/无价格证据 → `NOT_CALCULABLE`（TRD §9.1 行 631）。
3. **real-pipeline**：评分选中后、Attempt 前查 PUBLISHED 策略 → 判定动作 → 落 dispatch_decision；SWITCH 只在等价资源组内；此处一并插入 W14 额度门禁。
4. **测试**：WT-16（高峰命中规则在等价资源间切换/限流/拒绝，路由明细可解释输入/动作/结果）+ WT-17（节省只对实际执行+有基线计算，仅提示或基线不可比 → NOT_CALCULABLE）。
