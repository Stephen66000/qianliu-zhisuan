> 一句话目标：**管理员为单个员工开通时，在同一条流程内完成“生成 Key → 选择具体型号 → 分配额度 → 保存 → 复制接入信息”；批量页只是多员工操作入口，两个入口必须共用同一份权限与额度数据。**

---

## 1. 问题与已确认结论

### 1.1 当前问题

`/principals` 的“接入配置”现在同时存在：

1. `Key 模型权限`：直接写 `principal_key.allowed_model_ids`；
2. `分配模型与额度`：直接创建 `principal_grant`；
3. `/employee-model-rules`：又通过版本化规则管理 Key 权限和 Grant。

这会导致两个问题：

- 管理员以为同一员工要配置两遍；
- 手工权限与规则权限同时存在时，停用规则后员工仍可能通过手工基线继续调用，撤权语义不直观。

### 1.2 产品结论（不再讨论）

- **单人开通的主入口**：“使用主体 → 接入配置”。
- **批量操作的辅助入口**：原“员工使用规则”建议改名为“批量模型授权”。
- 单人与批量入口必须调用同一套规则、Grant 和 Key 派生逻辑，**不允许再形成两套权限来源**。
- 授权不能只停在“厂商”层级，必须选择厂商下的**具体型号**，例如 `deepseek-v4-flash` 或 `deepseek-v4-pro`。
- 每个具体型号可独立设置 Token 额度、是否允许超额和有效期。
- 型号选项必须来自已同步、已确认、`ACTIVE` 且路由／计价就绪的模型目录，禁止手工输入模型名。

## 2. 目标操作流程

### 2.1 新员工

```text
新建主体
  → 生成 Key（完整明文仅展示一次）
  → 按厂商展开具体型号
  → 勾选型号
  → 为每个型号填写额度
  → 保存并生效
  → 复制 Base URL、Key、已授权模型
```

- Key 已生成但尚未保存模型时，应显示“待授权”，Key 安全地保持不可调用任何模型。
- “保存并生效”必须在后端原子完成规则发布、Grant、额度计数器和 Key 白名单更新。

### 2.2 现有员工

```text
使用主体 → 接入配置
  → 读取当前有效型号、额度和权限来源
  → 增加／移除型号或调整额度
  → 保存新版本
```

- 保存前显示“新增／保留／撤销”预览。
- 移除型号后，该型号必须同时从 `/v1/models` 和调用热路径失效，不得只改页面。

### 2.3 批量模型授权

仅在多名员工执行同一操作时使用，例如：

- 为 10 名员工同时增加 `deepseek-v4-pro`；
- 为一个部门同时追加 5,000,000 Token；
- 统一撤销某个型号；
- 设置一个临时项目组的生效和失效时间。

批量调额必须显式选择语义，禁止使用含糊的“调整”：

- **设置总额度**：将每人该型号总额度设为指定值；
- **追加额度**：在每人现有总额度上增加指定值，计算必须在后端锁内完成。

## 3. 页面要求

### 3.1 “接入配置”页

1. 页面顺序固定为：`Key → 具体型号与额度 → 接入信息`。
2. 型号按“厂商／厂商资源”分组。
3. 每行显示：
   - 勾选框；
   - 展示名；
   - 真实上游型号；
   - 资源模式（API／Coding Plan）；
   - 就绪状态；
   - Token 额度（千分位）；
   - 是否超额；
   - 有效期（可选）。
4. 未就绪型号可展示但禁止勾选，必须显示具体原因（路由、计价、资源状态等）。
5. 仅勾选厂商名不构成授权；“全选本厂商”只代表勾选当前全部就绪型号。
6. 底部实时汇总已选型号数和额度；“保存并继续”是唯一主操作。
7. 已授权项需显示来源：“单人配置”、“批量规则 + 版本”或“历史手工授权待接管”。
8. 完整 Key 仍只能展示一次；已关闭明文弹窗后不得从任何 API、日志或前端状态恢复。

### 3.2 “批量模型授权”页

- 保留 `POOL-029` 已有的草稿、校验、发布、停用、新版本和历史能力。
- 页面名称和说明改成批量语义，不把它描述为新员工的必经步骤。
- 型号同样按厂商分组，显示具体上游型号，不只显示统一模型别名。
- 单人页创建的授权版本必须能在批量页的历史中查到，反之亦然。

## 4. 后端与数据约束

### 4.1 唯一事实源

正常页面不得再分别调用以下旧写入形成新的手工授权：

- `PATCH /principals/:id/key` 直接更新 `allowed_model_ids`；
- `POST /principals/:id/grants` 直接创建 Grant。

这些 API 可为旧客户端暂时保留，但新 UI 必须通过统一授权服务写入。

建议增加一个面向单主体的编排端点（路径可按项目风格调整）：

```http
GET /principals/:id/access-configuration
PUT /principals/:id/access-configuration
```

`PUT` 输入核心形状：

```json
{
  "expected_version": 3,
  "idempotency_key": "uuid",
  "models": [
    {
      "unified_model_id": "uuid",
      "provider_resource_id": "uuid",
      "quota_value": "30000000",
      "allow_overage": false,
      "valid_until": null
    }
  ]
}
```

服务端必须在同一事务内：

1. 验证企业、员工、ACTIVE Key、型号、资源、路由和计价就绪性；
2. 锁定 ACTIVE Key；
3. 创建或更新该主体的授权规则版本；
4. 创建／调整／停用 Grant 与额度计数器；
5. 按所有当前有效规则重算 Key `allowed_model_ids`；
6. 记录管理员、版本、来源、变更预览和结果，不记录 Key 明文；
7. 任一步失败全部回滚。

### 4.2 每个型号独立额度

当前 `employee_model_rule_version` 只有一个 `quota_value` 和 `allow_overage`，会对规则中所有型号使用同一额度，**不满足本次产品结论**。

最小兼容方案：

- 扩展 `model_targets` 元素，增加 `quota_value`、`allow_overage` 和可选 `valid_until`；
- 旧版本不含这些字段时，回退使用版本级 `quota_value`、`allow_overage`、`valid_until`；
- 新版本优先使用型号级字段；
- 暂不删除旧列，避免破坏 `POOL-029` 历史回放和生产数据。

如开发者选择正规化新表，必须保持上述兼容语义，不得原地改写已发布版本。

### 4.3 历史手工授权接管

生产已有 `principal_model_manual_authorization` 数据，不能直接删除。首次用新页保存时必须原子“接管”：

1. 发布等价的受管规则版本；
2. 将匹配的历史 ACTIVE Grant 绑定到新规则或无损迁移，保留已用额度和账本链；
3. 再移除对应手工基线；
4. 重算 Key 白名单；
5. 全过程不得出现权限空窗、额度归零、重复 Grant 或账本丢失。

在接管完成前，页面应标记“历史手工授权待接管”，不得伪装成已由规则管理。

### 4.4 并发、幂等和热路径

- 单人保存与批量发布可能同时命中同一员工，必须共用稳定锁顺序，不丢权限、不死锁。
- 重试相同 `idempotency_key` 只能返回同一结果，不重复创建规则、Grant 或额度计数器。
- `/v1/models`、Chat Completions、Responses 和 Messages 继续在上游前执行同一硬门禁。
- Key 重置必须继承当前有效受管授权，不恢复已撤销型号。
- 跨企业员工、型号、资源、规则和 Grant 不可查询或复用。

## 6. 验收标准

### 6.1 业务验收

1. 新建员工生成 Key 后，可在同一接入配置中选择 `DeepSeek V4 Flash` 与 `DeepSeek V4 Pro`，分别设置不同额度并一次保存。
2. 保存后 Key 白名单、有效 Grant、额度计数器和接入信息一致；不需再去批量页操作。
3. 员工只能看到并调用已勾选的具体型号，未授权型号在访问任何上游前被拒绝。
4. 现有员工增加或移除一个型号后，其他型号权限和额度不受影响。
5. 批量页可对多名员工执行型号授权／撤权、设置总额度或追加额度；单人页立即反映结果和来源。
6. 停用受管规则后，不得因为旧手工基线而继续获得同一型号权限。
7. 复制接入信息只包含当前真正有效的型号；Key 明文只展示一次。

### 6.2 失败与并发验收

1. 模拟任一数据库步骤失败，规则、Grant、额度和 Key 全部回滚。
2. 单人保存与批量发布并发命中同一员工，最终权限等于所有有效规则的确定合并，不丢更新、不死锁。
3. 重复提交相同幂等键不生成重复数据。
4. 已用 Token 超过新总额度时，后端按既定额度语义返回可操作错误或进入超额状态，不得静默清空已用量。
5. 跨企业、已停用员工、无 ACTIVE Key、未就绪型号均必须明确拒绝。

### 6.3 自动化与质量门禁

至少补齐：

- Web 组件／API 测试：厂商分组、型号选择、独立额度、千分位、未就绪原因、预览和保存。
- Control API 集成：新员工全流程、现有员工增删型号、两型号不同额度、历史手工权限接管、失败回滚、并发、幂等和企业隔离。
- Gateway：`/v1/models` 和各调用协议使用同一有效授权结果。
- Chromium E2E：新建员工→生成 Key→选型号→填额度→保存→复制接入信息，以及现有员工变更与批量调额。
- 对新的权限合并／配置差异纯函数增加覆盖率和变异测试，并纳入 ratchet。
