## 0. 需求方确认的授权模型（2026-08-05，优先级高于 handoff 文字）

管理员开通员工时的心智流程：

1. **选厂商**：给这员工开哪几个厂商（智谱 / Kimi / DeepSeek / 以后新增）；
2. **按厂商给额度**：Kimi 给 5000 万，DeepSeek 给 3 亿——额度是"这个厂商一共能用多少"，**不是每个型号多少**；
3. **型号默认全开**：厂商下所有就绪型号默认勾选，特殊情况才单独掐掉（"不想让他用 Pro 就把 Pro 关掉"）；
4. **总额度自动汇总**：主体总额度 = 各厂商池之和，系统算，不是单独填的字段。

语义推论（需求方确认）：

- **池挂"主体 × 厂商"**。员工在智谱的 5.2 / 5.3 / 5.5 之间随便用，烧的都是智谱那一个池；池空即拒；
- 掐掉某型号**不影响池**——DeepSeek 3 亿的池掐掉 Pro，Flash 可以烧满 3 亿。型号只是准入开关，不是额度单位；
- **型号级独立额度整个不做**（不作为进阶可选项保留）。handoff §1.2"每个具体型号可独立设置 Token 额度"及验收 6.1.1 相应修订；
- "是否允许超额"与**有效期**保留在**厂商池**粒度（沿用 handoff 对额度属性的要求，粒度从型号上移到池）；
- handoff §9"不改变账本口径"的边界不变：用量账本本就逐请求记录（含型号），厂商池只改**封顶判定**的归集维度，不动账。**例外**：原"不改变 GLM 高峰调度策略 / 供给预测 / Coding Plan 同步"等仍有效。

## 1. 数据模型（迁移 0039 `0039_principal_provider_pool.js`）

### 1.1 额度归集：`principal_grant` 升级为厂商池

核心思路：**不新建池表**，把现有 `principal_grant` + `quota_counter` 的语义从"每型号一份"升级为"每厂商一份"，最大限度复用热路径与账本结构。

0039 变更：

1. `principal_grant` 新增列 `pool_model_alias varchar(64)`——**池标识**，池 Grant 上固定为 `*`（通配该厂商全部型号）；旧数据为 NULL（= 型号级旧语义，仅用于识别，见 §5 迁移）；
2. 部分唯一索引：
   - `principal_grant_pool_uq (enterprise_id, principal_id, provider) WHERE pool_model_alias = '*' AND status = 'ACTIVE'`——**每主体每厂商至多一个 ACTIVE 池**；
   - 保留旧 `(principal_id, provider, model_alias)` 普通索引，兼容旧查询；
3. 新约束：`pool_model_alias = '*'` 的行 `model_alias` 列同步写 `*`（冗余但让所有按 model_alias 过滤的旧代码自然排除/包含池行，见 §1.3 查询语义）。

**池 Grant 字段语义**：`quota_value` = 池总额；`allow_overage`、`valid_from`、`valid_until` 池级生效；`authorization_rule_version_id` 仍标记受管来源；`quota_counter` 照旧 1:1 挂 grant_id——**热路径结算逻辑零改动**，因为它只按 grant_id 操作计数器。

### 1.2 型号开关：规则只管准入

- `employee_model_rule_version` 的 `quota_value` / `allow_overage` 停用：0039 放宽 `quota_value` 的 NOT NULL 约束为**允许 NULL**（非空时仍须 `>= 0`），新版本写入 NULL 表示"额度不在规则上"；旧版本数值原样保留仅用于回放。类型层标记 deprecated；
- `model_targets` 元素**不扩展额度字段**（v1 方案废弃），保持 `{unified_model_id, provider_resource_id}` 纯准入语义；
- `employee_model_rule_assignment` 结构不变（principal × model × resource ↔ grant_id），**但 grant_id 改为指向该厂商的池 Grant**（同一厂商下多个型号的 assignment 共享同一 grant_id）。

### 1.3 热路径改造（`quota-gate-repository.ts`）

现状键 `(principal, provider, model_alias)` 精确匹配型号。改为**两级回退**：

```text
查 ACTIVE grant WHERE principal=? AND provider=?
  AND (model_alias = :modelAlias OR pool_model_alias = '*')
ORDER BY (model_alias = :modelAlias) DESC   -- 精确型号行优先（兼容旧数据/接管过渡期）
       , pool_model_alias IS NOT NULL DESC
LIMIT 1
```

- `hasActiveGrant` / `reserveQuota` 用同一查询；命中池行即按池计数器预占/结算；
- **旧型号级 Grant（`pool_model_alias IS NULL`）在新流程下不再产生**，存量由 §5 迁移/接管收敛；回退逻辑仅为过渡兼容与防御，长期只剩池行；
- `evaluateQuotaGate` 纯函数不变（输入还是一份 quota/used/estimate，只是这份数现在来自池）。

**多资源同厂商**：provider_resource 可有多条（如 DeepSeek 的 API 资源与备用资源），池挂 `provider.code` 而非 resource——同厂商所有资源烧同一个池，符合"别管用哪个，都是这家"的语义。

## 2. 编排端点契约（单人页唯一写入通道）

### 2.1 `GET /principals/:id/access-configuration`

```jsonc
{
  "principal": { "id", "name", "status", "department_label" },
  "key": { "key_prefix", "status", "created_at",
           "authorization_status": "PENDING" },   // 无 ACTIVE Key 时整体为 null；PENDING=无任何有效授权
  "providers": [                                  // 按厂商分块，含未开通的厂商（供"点开即配"）
    {
      "provider_code": "deepseek", "provider_name": "DeepSeek",
      "resources": [ { "provider_resource_id", "resource_name", "mode": "API" } ],
      "pool": {                                   // 该厂商的池；未开通为 null
        "grant_id": "…", "quota_value": "300000000", "quota_used": "1234567",
        "allow_overage": false, "valid_until": null,
        "source": "MANAGED_SINGLE"                // MANAGED_SINGLE | MANAGED_BATCH | MANAGED_MIXED | MANUAL_PENDING
      },
      "models": [                                 // 该厂商全部型号（就绪与否都列）
        { "unified_model_id", "display_name", "alias", "upstream_model",
          "ready": true, "unavailable_reasons": [],
          "enabled": true,                        // 准入开关：勾选状态
          "source": "MANAGED_SINGLE" }            // 该型号开关的来源
      ]
    }
  ],
  "summary": { "total_quota": "350000000", "provider_count": 2, "model_count": 5 },
  "manual_pending_takeover": ["unified_model_id", …],
  "config_version": 3,
  "access_info": { "base_url": "…", "models": ["deepseek-v4-flash", "k3"] }   // 仅当前有效型号
}
```

- 未开通厂商的块也返回（`pool: null`，型号 `enabled: false`），前端"点开块→填额度→默认全勾"即可；
- 未就绪型号照常列出、禁选、带原因（已确认口径）；
- `source` 判定同 v1（单人规则 / 批量规则 / 混合 / 待接管）。

### 2.2 `PUT /principals/:id/access-configuration`

```jsonc
{
  "expected_version": 3,
  "idempotency_key": "uuid",
  "providers": [
    {
      "provider_code": "deepseek",
      "quota_value": "300000000",
      "allow_overage": false,
      "valid_until": null,
      "enabled_model_ids": ["uuid-flash"],          // 该厂商下勾选的型号（默认前端传全部就绪型号）
      "disabled_model_ids": ["uuid-pro"]            // 显式掐掉的（可选，用于审计/预览）
    },
    { "provider_code": "kimi", "quota_value": "50000000", "enabled_model_ids": ["…","…"] }
  ]
}
```

- `providers` 里**没出现的厂商 = 本员工不开通该厂商**；若该厂商原有池/开关，保存即关闭（走"新增/保留/撤销"预览）；
- `enabled_model_ids: []` + 给了额度 → 报错（给了额度却不给型号是矛盾输入）；`quota_value` 缺省或 0 → 该厂商视为不开通；
- 响应含 `changes`（池层面 + 型号开关层面两组 added/retained/removed）、`takeover`、`config_version`、`summary`。

## 3. PUT 服务端事务

锁序与 v1 一致（advisory → 主体 Key 行锁 → 写入），与批量发布兼容。事务步骤：

1. 预校验：主体 ACTIVE 未归档、有 ACTIVE Key；厂商 code 合法且属本企业；`quota_value` 字符串→bigint 校验；`enabled_model_ids` 全部属该厂商且就绪；
2. 幂等短路（同 v1，新表 `principal_access_idempotency`）；
3. 取锁 + 比对 `expected_version`（config_version 新表，同 v1 §5.2-B）；
4. 型号就绪校验（复用 029 校验逻辑，按厂商分组返回 issues）；
5. **池 Upsert**：逐厂商——存在 ACTIVE 池 Grant 则 `UPDATE quota_value/allow_overage/valid_until`（version+1，counter 不动→**已用量保留**）；不存在则建池 Grant + counter；`providers` 中消失的原开通厂商 → 池 Grant 置 DISABLED（行保留、账本不断）；
6. **型号开关**：以本主体单人规则承载（`owner_principal_id` 列方案同 v1，决策点①已确认做法一）——创建/新版本化单人规则，`model_targets` = 所有厂商的 enabled 型号并集；走 029 发布主流程建/停 assignment（**assignment 的 grant_id 指向池 Grant**，029 发布函数需相应改造为"按 target 找池、无池则报错"——这是 029 引擎唯一的实质改动）；
7. **手工接管**（见 §5）；
8. 重算白名单（refreshKeyModels，语义不变）；
9. 审计 + 幂等存档。

新增型号的默认行为（**已定 8.4**）：企业新接入并就绪的型号，**自动并入已开通该厂商的员工**——即型号准入开关集合在保存时快照，但厂商池存续期间，该厂商新增就绪型号对该员工默认可用（实现上：准入判定以"该厂商是否开通 + 型号是否被显式掐掉"为准，显式掐掉集合持久化，未提及的新就绪型号默认放行）；**型号接入/确认页面必须提示"该型号就绪后，已开通 XX 厂商的 N 名员工将自动可用"**。

## 4. 并发、幂等、热路径门禁

- 单人 PUT × 批量发布：锁序同 v1，最终权限 = 各有效规则开关并集 + 池独立存在。**注意新语义**：批量规则现在也只能动型号开关，不能动池——批量页"统一加 500 万额度"操作的是池（见 §6），两条路径都改池时按 Key 行锁串行、后写覆盖 quota_value（或按批量语义"追加"在锁内 read-modify-write）；
- 追加额度（批量场景）必须在池 Grant 行锁内 `quota_value = quota_value + :delta`，禁止读改写到应用层；
- 热路径：撤型号=assignment 失效→`hasActiveGrant` 回退不到池（型号精确行已停）→ 拒；池 DISABLED→全厂商拒；池空→`reserveQuota` 拒。三级各自独立生效；
- Key 重置继承现状（白名单=手工∪受管），不恢复已撤销型号——语义不变。

## 5. 存量手工数据迁移与接管（0039 数据迁移 + 运行时接管）

**0039 迁移时做一次性升格**（比 v1 的纯运行时接管更彻底，因为池模型下"每型号一份手工 Grant"必须收敛成池）：

1. 对每个 `(enterprise, principal, provider)` 分组的 ACTIVE 手工 Grant（`authorization_rule_version_id IS NULL`）：
   - 若同组存在受管池 → 不处理（运行时按池优先）；
   - 否则：取该组手工 Grant 升格为池（`pool_model_alias='*'`）。**现状（029 上线次日）每组仅一条，逐条一对一平移：额度、已用量、账本原样保留，无合并口径问题**。防御性检查：若个别分组确有多条 ACTIVE 手工 Grant，迁移**报错并列出清单**，人工确认后处理，不自动猜测合并；
   - `used_value` / `overage_value` 随原 Grant 平移（一对一，无求和）；被 DISABLED 的 Grant 行与其 counter 原样保留（账本链完整可查）；
2. 手工基线表 `principal_model_manual_authorization` 的处置同 v1：保留到单人页首次保存时清空（"待接管"标记照旧）；0039 只升格 Grant，不动基线行——**权限集合在迁移瞬间不缩**（基线行还在，白名单不变），只是封顶结构变了。

**运行时接管**（单人页首次保存）：手工基线∩最终有效集的型号转入单人规则 assignment（指向池）；基线行清空；手工池（迁移升格的）若在 PUT 的 providers 中出现 → UPDATE 换绑到单人规则版本（`authorization_rule_version_id` 回填），否则保留为手工来源直至覆盖。

**已用量 > 新池额度**：PUT 不自动拒绝——按"进入超额状态"语义：counter.used 不动，quota_value 调小后下一请求自然 REJECT（`evaluateQuotaGate` 现成语义）；GET 响应里标 `over_limit: true` 让页面提示。与 handoff 验收 6.2.4"不得静默清空已用量"一致。

## 6. 批量页（"批量模型授权"）适配

029 的草稿/校验/发布/停用/版本/历史全部保留，但发布载荷分两类（对应 handoff §2.3）：

- **型号开关类**：原有能力，语义变为只控准入（不再携带额度）；
- **池额度类**（新）：`SET`（设为指定值）/ `ADD`（锁内追加）两种显式语义，作用于目标员工的指定厂商池——没有池的员工报错列出（"先开通厂商"），不隐式建池。

批量发布事务与单人 PUT 共用 config_version 自增与 Key 行锁，互可见、可并发。

## 7. 前端页面结构（单人"接入配置"页）

按需求方流程重排（替代原型 v1 的"逐型号填额度"）：

1. **Key 区**（不变）；
2. **厂商区块**（每厂商一块，默认收起=未开通）：
   - 块头：厂商名 + 资源列表 + 池额度输入（千分位）+ 超额开关 + 有效期 + "开通/关闭"状态；
   - 块内型号表：勾选框（默认全选就绪型号）+ 展示名 + 上游型号 + 就绪状态/原因；未就绪禁选；
   - 未开通厂商的块：型号全部灰显不可勾，填了额度即激活；
3. **底部汇总**：总额度（各池之和，自动计算）+ 已开通厂商数/型号数 + "保存并生效"；
4. 保存前预览：池变更（新开/调额/关闭）+ 开关变更（新增/保留/撤销）两组；
5. 来源标记与"待接管"同 v1。

原型 `员工模型接入配置原型.html` 需要相应改版（型号行内不再填额度，额度上移到厂商块头）。

## 8. 决策点（已全部确认，2026-08-05）

1. **单人规则标识**（v1 决策点①）：`owner_principal_id` 列 + 部分唯一索引——**做法一，已定**；
2. **029 规则表旧额度字段**：0039 放宽 `quota_value` NOT NULL 约束为**允许 NULL**（非空仍须 ≥ 0），新版本写 NULL——**已定**；
3. **存量手工 Grant 合并口径**：**撤销该决策点**——029 上线次日，现状每组仅一条手工 Grant，一对一平移，无合并场景；防御性检查遇多条 ACTIVE 则迁移报错列清单人工处理，不自动合并——**已定**；
4. **企业新接型号默认**：**自动并入已开通厂商**（准入以"厂商开通 + 未被显式掐掉"为准），型号接入页提示"将影响 N 名员工"——**已定**；
5. **迁移命名**：`0039_principal_provider_pool.js`——**已定**。
