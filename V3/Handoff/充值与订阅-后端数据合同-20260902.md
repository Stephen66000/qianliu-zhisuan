## 3. 表：`provider_finance_event`

资金事件只追加，是期初、充值、订阅、余额调整与冲销的唯一事实表。

### 3.1 字段

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `id` | uuid | 是 | 主键 |
| `enterprise_id` | uuid | 是 | 企业 |
| `provider_resource_id` | uuid | 是 | 厂商资源账号 |
| `event_type` | varchar | 是 | 资金事件类型 |
| `account_amount` | numeric(24,8) | 是 | 带符号的账户原币金额 |
| `account_currency` | varchar(3) | 是 | CNY/USD |
| `cash_paid_cny` | numeric(24,8) | 否 | 带符号的人民币实付；仅充值、订阅和其冲销使用 |
| `occurred_at` | timestamptz | 是 | 业务发生时间 |
| `external_reference` | varchar(255) | 否 | 厂商订单号、支付流水或凭证编号 |
| `reversal_of_event_id` | uuid | 否 | `REVERSAL` 引用原事件 |
| `correction_of_event_id` | uuid | 否 | 期初更正引用原期初事件 |
| `reconciliation_case_id` | uuid | 否 | 对账调整关联案件 |
| `description` | varchar(1000) | 否 | 说明 |
| `evidence_ref` | text | 否 | 证据引用；不得包含凭证明文 |
| `source` | varchar | 是 | 事件来源 |
| `idempotency_key` | varchar(128) | 是 | 技术幂等键 |
| `created_by_admin_user_id` | uuid | 否 | 人工事件必填；迁移事件可空 |
| `created_at` | timestamptz | 是 | 数据库创建时间 |

### 3.2 金额方向

| 事件 | `account_amount` | `cash_paid_cny` |
| --- | --- | --- |
| `API_OPENING_BALANCE` | >= 0；零表示已确认零余额 | NULL |
| `API_OPENING_BALANCE_CORRECTION` | != 0，可正可负 | NULL |
| `API_RECHARGE` | > 0 | > 0 |
| `API_BALANCE_RECONCILIATION` | != 0，可正可负 | NULL |
| `CODING_PLAN_PURCHASE` | > 0 | > 0 |
| `CODING_PLAN_RENEWAL` | > 0 | > 0 |
| `REVERSAL` | 原事件 `account_amount × -1` | 原事件 `cash_paid_cny × -1` 或 NULL |

### 3.3 模式约束

- API 资源只接受 `API_*` 和引用 API 原事件的 `REVERSAL`；
- Coding Plan 资源只接受 `CODING_PLAN_*` 和引用 Coding Plan 原事件的 `REVERSAL`；
- `API_OPENING_BALANCE_CORRECTION.correction_of_event_id` 必须引用同企业、同资源、同币种的 `API_OPENING_BALANCE`；
- `API_BALANCE_RECONCILIATION.reconciliation_case_id` 必须引用同企业、同资源、同币种的案件，并与案件 `RESOLVED + decision=CONFIRMED` 及 `adjustment_event_id` 形成同一事务闭环；
- `REVERSAL.reversal_of_event_id` 必须引用同企业、同资源的可冲销事件，不能引用另一笔 `REVERSAL`；
- 第一版只允许冲销 `API_RECHARGE`、`CODING_PLAN_PURCHASE`、`CODING_PLAN_RENEWAL`；
- `API_OPENING_BALANCE`、`API_OPENING_BALANCE_CORRECTION`、`API_BALANCE_RECONCILIATION`、`REVERSAL` 禁止冲销；期初使用更正事件，对账差异使用新案件和新调整继续修正。

### 3.4 唯一索引

1. `(enterprise_id, provider_resource_id, account_currency)` 对 `API_OPENING_BALANCE` 部分唯一；
2. `(enterprise_id, provider_resource_id, external_reference)` 对充值、购买和续费事件在外部凭证非空时唯一；事件类型不参与，避免同一付款以购买/续费两种类型重复入账；
3. `reversal_of_event_id` 在非空时唯一；
4. `(enterprise_id, provider_resource_id, idempotency_key)` 唯一；
5. `correction_of_event_id` 不唯一，允许多次追加更正，但每次更正事件本身不可修改。

### 3.5 不可变

数据库必须通过触发器拒绝对 `provider_finance_event` 的 UPDATE 和 DELETE。纠错只追加更正或冲销事件。

### 3.6 业务生效时间

- `API_OPENING_BALANCE.occurred_at` 固定为切换边界；
- `API_OPENING_BALANCE_CORRECTION.occurred_at` 固定为切换边界，`created_at`记录实际更正时间；
- OPEN 账期内 `REVERSAL.occurred_at` 固定等于原事件业务时间；已结账账期必须先重开；
- `API_BALANCE_RECONCILIATION.occurred_at` 固定等于案件 `balance_as_of`；
- 普通充值和订阅不得登记未来业务时间；允许补录的最早业务时间为切换边界且账期必须开放；
- 月度指标按 `occurred_at` 归属，审计按 `created_at` 追溯。

### 3.7 精度

- `account_amount` 与 API 费用最多 8 位小数；
- `cash_paid_cny` 最多 2 位小数；
- 聚合过程使用十进制定点数且不做中间舍入；
- 冲销直接复制原数据库十进制值取反；
- 展示精度由前端格式化，不回写账本。

## 4. 表：`provider_subscription_period`

### 4.1 字段

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `id` | uuid | 是 | 主键 |
| `enterprise_id` | uuid | 是 | 企业 |
| `provider_resource_id` | uuid | 是 | Coding Plan 资源 |
| `finance_event_id` | uuid | 否 | 新购/续费资金事件；历史延续周期可空 |
| `product_name` | varchar(255) | 是 | 产品/套餐名称 |
| `period_start` | timestamptz | 是 | 周期开始，Asia/Shanghai 自然日边界 |
| `period_end_exclusive` | timestamptz | 是 | 周期失效时点 |
| `source` | varchar | 是 | PURCHASE/RENEWAL/MIGRATED_CARRYOVER/MIGRATED_PURCHASE |
| `migration_source_record_id` | uuid | 否 | 迁移周期关联旧购买记录，暗创建和切换绑定使用 |
| `reversed_by_event_id` | uuid | 否 | 冲销事件 |
| `created_by_admin_user_id` | uuid | 否 | 操作人 |
| `created_at` | timestamptz | 是 | 创建时间 |

### 4.2 约束

- 资源必须是 `CODING_PLAN`；
- `period_end_exclusive > period_start`；
- 新购/续费的资金事件发生日期必须等于 `period_start` 的上海自然日；
- `finance_event_id` 非空时唯一；
- `reversed_by_event_id` 非空时唯一，且必须引用冲销 `finance_event_id` 的 `REVERSAL`；
- 历史延续周期使用 `MIGRATED_CARRYOVER`，不得生成现金支出或经营成本；
- 9月1日后旧购买记录可在暗部署阶段先创建 `MIGRATED_PURCHASE` 周期，并用 `migration_source_record_id` 唯一绑定；正式切换写入资金事件后再填充 `finance_event_id`，该受控迁移更新必须留 Evidence。

### 4.3 当前状态投影

```text
REVERSED：reversed_by_event_id 非空
ACTIVE：未冲销且 period_start <= now < period_end_exclusive
EXPIRED：未冲销且 now >= period_end_exclusive
```

### 4.4 周期归属

结算时间同时落入多个未冲销周期时，选择 `period_start` 最新的周期。结算时把周期 ID 冻结到使用明细，后续不因周期冲销而物理改写历史使用。

前端提交自然日；服务端将开始日转换为 `Asia/Shanghai 00:00:00`，默认失效时点为下个月同日 `00:00:00`，实际周期随月份为28、29、30或31天。开始日在下个月不存在时取下个月最后一个自然日。不得使用服务器本地时区、固定30天或固定24小时毫秒数替代自然月计算。

## 5. 表：`provider_finance_reconciliation_case`

### 5.1 字段

| 字段 | 类型 | 必填 | 语义 |
| --- | --- | --- | --- |
| `id` | uuid | 是 | 主键 |
| `enterprise_id` | uuid | 是 | 企业 |
| `provider_resource_id` | uuid | 是 | API 资源 |
| `account_currency` | varchar(3) | 是 | CNY/USD |
| `local_balance` | numeric(24,8) | 是 | 本地算法余额 |
| `provider_confirmed_balance` | numeric(24,8) | 是 | 厂商确认余额 |
| `difference_amount` | numeric(24,8) | 是 | 厂商确认 - 本地算法，可正可负，不得为 0 |
| `balance_as_of` | timestamptz | 是 | 本地余额计算截止时间 |
| `fact_watermark` | jsonb | 是 | 参与计算的事件/结算水位 |
| `status` | varchar | 是 | OPEN/REJECTED/RESOLVED |
| `decision` | varchar | 否 | CONFIRMED/REJECTED；OPEN 时为空 |
| `evidence_ref` | text | 是 | 厂商余额证据 |
| `opened_by_admin_user_id` | uuid | 否 | 人工发起人 |
| `decided_by_admin_user_id` | uuid | 否 | 确认/驳回人 |
| `adjustment_event_id` | uuid | 否 | 对账调整事件 |
| `decision_note` | varchar(2000) | 否 | 决策说明 |
| `version` | integer | 是 | 乐观锁 |
| `created_at/updated_at/decided_at/resolved_at` | timestamptz | 按状态 | 时间链 |

### 5.2 状态机

```text
OPEN -> REJECTED
OPEN -> RESOLVED（decision=CONFIRMED）
```

- 确认操作在同一事务中写入调整事件，并把案件直接改为 `RESOLVED + decision=CONFIRMED`；
- `RESOLVED + CONFIRMED` 必须有 `adjustment_event_id`，调整事件必须反向引用案件，金额必须等于案件差额；
- 驳回操作写入 `REJECTED + decision=REJECTED`，不得有调整事件；
- `REJECTED` 和 `RESOLVED` 都不能再次决策；
- 同一资源、币种只允许一个 OPEN 案件，避免并行对账覆盖。

跨表闭环由专用仓储事务和 `DEFERRABLE INITIALLY DEFERRED` 数据库约束触发器在提交时保证；普通外键只保证对象存在，不尝试用无法跨表查询的 CHECK 约束瞬时状态。

案件只允许基于完整可计算余额创建；`MISSING_OPENING_BALANCE`和`INCOMPLETE_USAGE_COST`不得创建对账案件。`local_balance`允许为负，`provider_confirmed_balance`必须非负，`difference_amount`由两者在数据库中校验等式生成或约束。

## 7. 现有使用账本扩展

### 7.1 `ledger_line.api_cost_currency`

- 类型 `varchar(3)`；
- `PRICED_USAGE` 时费用与币种必须同时存在；费用允许为精确0；
- `CONFIRMED_ZERO_NO_UPSTREAM` 时费用固定为0，币种允许为空，不参与余额扣减且不形成缺口；
- `UNKNOWN_COST` 时费用和币种为空，并触发余额 `INCOMPLETE_USAGE_COST`；
- Coding Plan 行保持空；
- 新结算从命中的冻结计价规则写入；
- 9 月 1 日后的历史行按冻结快照回填，缺失或冲突时失败关闭。

### 7.1.1 `ledger_line.api_cost_status`

- API 行必须为 `PRICED_USAGE`、`CONFIRMED_ZERO_NO_UPSTREAM` 或 `UNKNOWN_COST`；
- Coding Plan 行固定为 `NOT_APPLICABLE`；
- 已访问上游且缺计价事实的 API 行为 `UNKNOWN_COST`；
- 确认未访问上游的零事实行为 `CONFIRMED_ZERO_NO_UPSTREAM`；
- 命中冻结计价规则的行为 `PRICED_USAGE`。

### 7.2 `ledger_line.subscription_period_id`

- 类型 uuid，可空；
- 指向同企业、同资源的 `provider_subscription_period`；
- 切换后 Coding Plan 已结算行必须非空；
- API 行必须为空；
- 9 月 1 日后的 Coding Plan 历史行按结算时间和“开始日最新覆盖周期”回填；
- 无可用周期时进入缺口清单，不伪造周期。

### 7.3 时间归属

新增 `ledger_line.settled_at timestamptz`。API 余额扣减和 Coding Plan 周期归属都使用 `settled_at`，不是请求开始时间、Attempt 开始时间或通用数据库创建时间。新结算显式写入；历史行以原 `ledger_line.created_at` 回填并记录迁移依据。

### 7.4 不复制使用流水

新资金模块直接读取现有 `ledger_line`。不得为 API 使用再建立第二张扣费事件表；`ledger_transaction.total_api_cost` 不承担跨币种余额计算，余额按资源和 `ledger_line.api_cost_currency` 聚合。

### 7.5 历史账本受控回填例外

9月1日后历史 `ledger_line` 只允许一次性补充以下空字段：

```text
api_cost_currency
api_cost_status
subscription_period_id
settled_at
```

回填不得修改 Token、费用金额、资源、请求、规则快照或原创建时间。迁移前后对所有非目标字段计算逐行哈希并保存 Evidence；回填迁移必须幂等。若无法接受 UPDATE 历史行，则改用追加式归属 side table，不能半更新、半旁路。

### 7.6 Coding Plan 暗写顺序

加法迁移后先依据已审核旧订阅事实暗创建 `MIGRATED_CARRYOVER` 和 `MIGRATED_PURCHASE` 周期，再启用 Gateway 写 `subscription_period_id`。暗创建周期不生成资金事件和月度成本；正式切换写入资金事件后，受控绑定 `finance_event_id`。如果周期尚未准备完成，Gateway不得被要求提前完整写周期ID，相关行继续进入切换增量回填清单。

## 8. 余额只读合同

### 8.1 请求

```text
getCurrentBalance(
  enterpriseId,
  providerResourceId,
  accountCurrency,
  asOf
)
```

### 8.2 响应

```jsonc
{
  "providerResourceId": "uuid",
  "currency": "CNY",
  "asOf": "2026-09-02T12:00:00.000Z",
  "state": "NORMAL",
  "balance": "144.00000000",
  "components": {
    "openingBalance": "50.00000000",
    "openingCorrections": "0.00000000",
    "recharges": "100.00000000",
    "usageDebits": "6.00000000",
    "balanceReconciliations": "0.00000000",
    "reversals": "0.00000000"
  },
  "factWatermark": {
    "latestFinanceEventId": "uuid-or-null",
    "latestFinanceOccurredAt": "iso-or-null",
    "latestLedgerLineId": "uuid-or-null",
    "latestSettledAt": "iso-or-null"
  },
  "reconciliationCaseId": null,
  "gaps": []
}
```

### 8.3 状态语义

- `LEGACY_ARCHIVED`：`asOf` 早于切换边界，`balance = null`；
- `MISSING_OPENING_BALANCE`：缺期初，`balance = null`；
- `INCOMPLETE_USAGE_COST`：切换边界后、asOf前存在 `UNKNOWN_COST` API使用，`balance = null`，返回请求、资源、结算时间和原因缺口；不得只汇总已知费用；
- `NORMAL`：余额 >= 0；
- `NEGATIVE_RECONCILIATION_REQUIRED`：余额 < 0，返回真实负数和 OPEN 案件（若检测任务尚未创建，案件 ID 可短暂为空但必须告警重试）。

只有余额完整可计算后才能判断 NORMAL 或负余额；`INCOMPLETE_USAGE_COST` 不创建负余额案件。

状态优先级固定为：`LEGACY_ARCHIVED` > `MISSING_OPENING_BALANCE` > `INCOMPLETE_USAGE_COST` > `NEGATIVE_RECONCILIATION_REQUIRED` > `NORMAL`。同一查询不得返回多个互斥主状态，详细问题进入 `gaps`。

### 8.4 稳定折叠

资金事件按 `(occurred_at, created_at, id)` 稳定排序。余额加减具备交换性，但响应水位和历史重放必须稳定。使用扣费按结算时间、创建时间、ID稳定归集。

### 8.5 一致性隔离

`getCurrentBalance` 必须在一个 PostgreSQL `REPEATABLE READ READ ONLY`事务中完成资金事件、使用账本和对账案件读取，并在事务开始固定 `asOf`。也可使用一个SQL语句完成全部聚合；无论采用哪种方式，响应组件与事实水位必须来自同一个数据库快照。禁止在普通 READ COMMITTED 下分多次读取后拼接余额。

普通查询不接受未来 `asOf`；省略时由服务端在事务开始生成当前时间。充值币种必须已有同资源、同币种的期初余额，否则写入拒绝并提示先完成期初初始化。

## 9. 月度资金合同

### 9.1 请求

```text
getMonthlyFinanceSummary(enterpriseId, month, timezone=Asia/Shanghai)
```

### 9.2 响应

下例假设：CNY 充值 100 元、USD 充值 20 美元且人民币实付 140 元、Coding Plan 人民币实付 199 元；CNY API 消耗 6 元、USD API 消耗 3 美元。

```jsonc
{
  "month": "2026-09",
  "timezone": "Asia/Shanghai",
  "cashOutflowCny": "439.00000000",
  "apiRecharges": [
    { "currency": "CNY", "amount": "100.00000000" },
    { "currency": "USD", "amount": "20.00000000" }
  ],
  "apiOperatingCosts": [
    { "currency": "CNY", "amount": "6.00000000" },
    { "currency": "USD", "amount": "3.00000000" }
  ],
  "codingPlanOrders": [
    { "currency": "CNY", "amount": "199.00000000" }
  ],
  "codingPlanFixedCostCny": "199.00000000",
  "operatingCostCny": "205.00000000",
  "operatingCostByCurrency": [
    { "currency": "USD", "amount": "3.00000000" }
  ],
  "complete": true,
  "gaps": []
}
```

`operatingCostCny`只包含具备人民币事实的成本；USD API 成本保留在 `operatingCostByCurrency`，不能临时换算并塞入人民币总额。存在币种、期初或周期缺口时返回具体 `gaps`，不伪造完整。

标准缺口码至少包括：

```text
OPENING_BALANCE_MISSING
API_USAGE_COST_UNKNOWN
API_COST_CURRENCY_MISSING
API_COST_CURRENCY_CONFLICT
SUBSCRIPTION_PERIOD_MISSING
CASH_PAID_CNY_MISSING
EXTERNAL_REFERENCE_CONFLICT
```

`complete=true`仅表示合同要求的事实完整；多币种本身不是缺口，只要分别保留且没有伪合计即可。

## 10. 命令接口

### 10.1 期初余额

```text
POST /provider-resources/:id/finance/opening-balances
```

请求：账户币种、期初金额、`occurred_at=切换边界`、证据、幂等键。

### 10.2 期初余额更正

```text
POST /provider-resources/:id/finance/opening-balance-corrections
```

请求：原期初事件 ID、带符号差额、原因、证据、幂等键。

### 10.3 API 充值

```text
POST /provider-resources/:id/finance/recharges
```

请求：账户金额、账户币种、人民币实付、实际充值时间、外部付款凭证、说明、证据、幂等键。

### 10.4 Coding Plan 购买/续费

```text
POST /provider-resources/:id/finance/subscriptions
```

请求：PURCHASE/RENEWAL、产品名、订单金额、订单币种、人民币实付、扣费日期、周期开始/结束、外部付款凭证、说明、证据、幂等键。

### 10.5 冲销

```text
POST /provider-finance-events/:id/reversal
```

请求只提供原因、证据和幂等键；服务端从原事件派生反向金额。已结账月份未重开时返回冲突。

第一版只允许冲销 API充值、Coding Plan购买和续费。服务端将冲销业务时间固定为原事件业务时间，不能由客户端传入。

### 10.6 对账案件

```text
POST /provider-resources/:id/finance/reconciliation-cases
POST /provider-finance-reconciliation-cases/:id/confirm
POST /provider-finance-reconciliation-cases/:id/reject
```

确认接口在同一事务中写对账事件并把案件置为 RESOLVED。

对账调整业务时间固定为案件 `balance_as_of`。确认后案件终态为 `RESOLVED + decision=CONFIRMED`；驳回终态为 `REJECTED + decision=REJECTED`。

### 10.7 重复候选确认

```text
POST /provider-finance-duplicate-candidates/:id/confirm
```

请求：一次性确认令牌、原请求哈希、新幂等键。确认成功后候选变为 CONSUMED 并关联唯一资金事件。

## 12. 事务合同

### 12.1 通用写入

1. 认证管理员；
2. 锁定企业、资源与账期；
3. 校验资源模式、币种、金额、业务时间；
4. 检查结账写屏障；
5. 检查幂等回执和外部凭证唯一性；
6. 写资金事件；
7. 订阅场景同时写周期；冲销场景同时翻转周期；
8. 写操作审计；
9. 写幂等回执；
10. 提交后使统一查询缓存失效。

普通管理员请求的业务时间不得晚于服务端当前时间；补录不得早于切换边界。Coding Plan自然日由服务端按Asia/Shanghai转换，不接受客户端自带时区覆盖。

### 12.2 使用结算

真实使用结算不得因余额计算为负而回滚或改写金额。结算先完整写入使用账本，再由余额投影即时反映负数；对账案件检测失败不能造成使用事实丢失，必须通过可重试任务补建案件。

### 12.3 已结账月份

业务时间落入 CLOSED 账期时，资金写入、冲销和更正默认返回冲突。只有显式重开后才能操作；禁止在当前月静默抵消历史错误。

### 12.4 对账确认事务

1. 锁定 OPEN 案件及资源；
2. 重新计算同一 `balance_as_of` 和水位，水位变化或差额变化则返回冲突并要求重开案件；
3. 写 `API_BALANCE_RECONCILIATION`，金额等于案件差额，业务时间等于 `balance_as_of`；
4. 案件写 `RESOLVED + decision=CONFIRMED + adjustment_event_id`；
5. 写审计和幂等回执；
6. 同一事务提交。

### 12.5 复合租户外键

所有跨表关系必须以 `(enterprise_id, id)` 复合外键或等价数据库约束保证企业一致，包括：事件到资源/原事件/期初/案件，周期到资源/资金事件/冲销事件，案件到资源/调整事件，以及使用行到订阅周期。不能只依赖单列UUID和应用层校验。

## 13. 业务重复检测

技术幂等与业务去重分开：

- 技术幂等：资源 + 客户端请求号；
- 业务唯一：企业 + 资源/订阅 + 外部付款凭证；购买/续费事件类型不参与唯一性，避免同一付款换类型重复入账；
- 无外部凭证：同资源、同事件类型、同账户金额、同币种、同人民币实付、同业务时间命中重复候选，返回需二次确认的冲突响应；
- 二次确认使用 `provider_finance_duplicate_candidate` 的一次性令牌，不允许前端直接忽略警告；
- 一个原事件最多有一个冲销事件。

---

## 14. 安全与审计

- 资金证据不得包含 API Key、OAuth Token、Cookie 或订阅会话明文；
- 金额、币种、业务时间、资源、事件类型、外部凭证和关联事件必须进入审计摘要；
- 对账确认与资金登记使用管理员权限；
- 所有人工更正、冲销和重开记录操作者与原因；
- 查询按企业隔离；跨企业资源 ID 返回 404，不泄露存在性。

## 15. 非目标

当前合同不包含：

- 自动处理赠送余额、现金退款或扣费纠正；
- 汇率服务和历史汇率重算；
- 根据负余额自动阻断 Gateway 新请求；
- 删除旧快照或旧账本；
- 将历史 Coding Plan 使用物理迁移到新周期；
- 生产部署、数据初始化或真实验收。
