## 1. 现状摘要（代码核实结果）

三条写入路径确实存在，与 handoff §1.1 一致：

1. `PATCH /principals/:id/key` → `KeyRepository.updateAllowedModels()`：全量重写手工基线 + 合并受管集合后写回 `allowed_model_ids`；
2. `POST /principals/:id/grants` → `GrantRepository.create()`：创建 `authorization_rule_version_id = NULL` 的手工 Grant；
3. `POST /employee-model-rules/*` → `EmployeeModelRuleRepository.publish()`：版本化规则 → Grant + assignment + 白名单重算。

029 已有的可复用资产（确认不要重造）：

- 发布/停用的完整事务（校验 → 撤旧版 → 逐主体建 Grant+counter+assignment → 重算白名单 → 审计）；
- 就绪校验与变更预览（`validateEmployeeModelRule` + `classifyPermissionKeys`，预览口径是"发布前后最终权限"，正是单人页要的语义）；
- 锁秩序：`pg_advisory_xact_lock(hashtext(enterprise:rule_id))` + 主体 ID 排序 + `refreshKeyModels` 内 Key 行锁；
- 手工基线表与捕获机制（`captureManualBaseline`）；
- `publish_idempotency_key` 唯一索引。

关键现状事实（决定下面设计取舍）：

- 规则粒度是 `(principal, unified_model, provider_resource)`，assignment 亦然——**型号级额度放进 target 后粒度天然兼容**；
- `principal_grant` 无 `unified_model_id` 列，靠 `(provider, model_alias)` 解析，靠 `authorization_rule_version_id IS NULL` 区分手工/受管——**接管匹配只能按 alias，这是接管方案最大的风险点**（见 §6）；
- `captureManualBaseline` 是"空则快照"，**首次捕获后不同步**——PATCH key 和 create-with-models 会重建手工行，但规则发布不再感知（见 §6 差异清单）；
- `quota_counter.used_value` 挂在 grant_id 上，接管要保已用量就必须**原 grant 换绑**，不能新建。

## 2. 迁移 0039：`model_targets` 型号级额度（选 handoff 最小兼容方案）

不改表结构，只扩展 `employee_model_rule_version.model_targets` jsonb 元素：

```jsonc
{
  "unified_model_id": "uuid",
  "provider_resource_id": "uuid",
  "quota_value": "30000000",      // 新增，字符串承载 bigint
  "allow_overage": false,          // 新增
  "valid_until": null              // 新增，可选
}
```

兼容语义（纯函数 `resolveTargetQuotas(version)`，进变异测试 ratchet）：

- 元素缺新字段 → 回退版本级 `quota_value` / `allow_overage` / `valid_until`；
- 新字段存在 → 优先使用；`quota_value` 非法（非非负整数字符串）→ 校验期报错，不静默回退；
- 已发布版本**绝不原地改写**：0039 不做数据订正，旧版本靠回退语义继续回放；POO-029 历史发布记录原样可审计。

版本级三列保留：`model_scope = ALL` 时充当全部型号的默认额度，同时是旧数据的回退源。校验规则：`SELECTED` 模式下允许版本级 `quota_value` 缺省（要求所有 target 自带额度）或继续必填但作为默认——**倾向后者（保持必填=默认值），改动最小且 DB CHECK 约束不用动**，草案按后者写。

发布时 Grant 字段逐 target 取值：`quota_value/allow_overage/valid_until` 来自解析后的 target；`valid_from` 仍取版本级（型号的"生效时间"即保存时间，handoff 只要求型号级**失效**时间）。

## 3. 编排端点契约

路径挂在 principals 域下（与现有 `/principals/:id/key|grants` 同族）：

### 3.1 `GET /principals/:id/access-configuration`

返回单人页所需的全部读模型（前端不再拼多个接口）：

```jsonc
{
  "principal": { "id", "name", "status", "department_label" },
  "key": {                                  // 无 ACTIVE Key 时为 null
    "key_prefix": "sk-qianliu-W…",
    "status": "ACTIVE",
    "created_at": "…",
    "authorization_status": "PENDING"        // PENDING = allowed 全集为空；AUTHORIZED = 非空
  },
  "catalog": [                               // 复用 EmployeeModelRuleRepository.catalog() 的 models 部分
    {
      "provider_code": "deepseek", "provider_name": "DeepSeek",
      "provider_resource_id": "…", "resource_name": "deepseek-仟流智算", "resource_mode": "API",
      "models": [
        {
          "unified_model_id": "…", "display_name": "DeepSeek V4 Flash",
          "alias": "deepseek-v4-flash", "upstream_model": "deepseek-v4-flash",
          "ready": true, "unavailable_reasons": [],
          "current": {                        // 该型号当前授权；未授权为 null
            "source": "MANAGED_SINGLE",       // MANAGED_SINGLE | MANAGED_BATCH | MANAGED_MIXED | MANUAL_PENDING
            "rule_versions": [{ "rule_id", "version", "name" }],
            "quota_total": "30000000",        // 字符串
            "quota_used": "1234567",
            "allow_overage": false,
            "valid_until": null
          }
        }
      ]
    }
  ],
  "manual_pending_takeover": ["unified_model_id", …],   // 非空则页面顶部标"历史手工授权待接管"
  "config_version": 3,                       // 见 §5.2 乐观锁
  "access_info": { "base_url": "…", "models": ["deepseek-v4-flash"] }  // 仅当前真正有效型号
}
```

要点：

- **catalog 全量返回、不就绪的行带 `unavailable_reasons`**——即昨天确认的"禁选+原因"口径，reasons 与保存时后端拒绝理由同源（同一校验函数）；
- `current.source` 四态：本主体专属规则=`MANAGED_SINGLE`；批量规则（SELECTED 含本主体或 ALL）=`MANAGED_BATCH`；两者都有=`MANAGED_MIXED`（取效规则列表照实返回）；仅手工基线=`MANUAL_PENDING`；
- 型号多规则命中时 `quota_total` 为各 ACTIVE Grant 合计（与热路径扣减口径一致：逐 Grant 扣，总额即总和）。

### 3.2 `PUT /principals/:id/access-configuration`

请求：

```jsonc
{
  "expected_version": 3,
  "idempotency_key": "uuid",
  "models": [
    {
      "unified_model_id": "uuid",
      "provider_resource_id": "uuid",
      "quota_value": "30000000",
      "allow_overage": false,
      "valid_until": null
    }
  ]
}
```

`models: []` 合法，语义=撤销本主体单人配置下的全部型号（其他来源不受影响）。

响应（200）：`{ "version": <发布后的规则版本概要>, "config_version": 4, "changes": {added, retained, removed}, "takeover": {performed: true, adopted_grants: 2, cleared_manual: 3}, "access_info": … }`。

错误映射：`400` 请求非法/额度格式错；`404` 主体不存在；`409` 版本冲突（expected_version 不符）/ 主体停用 / 无 ACTIVE Key / 就绪校验不过（带 issues）/ 已用量超新额度且未带确认标记；`422` 幂等键冲突（同键不同体）。

## 4. PUT 服务端事务（单事务，全部回滚）

命名：新仓储 `PrincipalAccessConfigRepository`（database 包），路由 `apps/control-api/src/principals/access-configuration.ts`。复用而非分叉 029 引擎的方式见 §7。

主体确定规则（**先定义，全文档一致**）：

> **每主体至多一条"单人规则"**：`rule_id = principal_access_rule_id(principal_id)` 由服务端派生并记录在规则版本上（建议 `name` 固定为 `接入配置-{principal_id}`，另在 `employee_model_rule_version` 上加 nullable 列 `owner_principal_id` + 部分唯一索引 `(enterprise_id, owner_principal_id) WHERE owner_principal_id IS NOT NULL`——比靠 name 约定可靠）。批量规则 `owner_principal_id = NULL`。单人规则 `employee_scope=SELECTED, principal_ids=[self], model_scope=SELECTED`。

事务步骤（对应 handoff §4.1 七步）：

1. **解析与预校验**：主体存在、ACTIVE 未归档、属本企业；存在 ACTIVE Key（无则 409，`KEY_UNAVAILABLE`）；型号去重、`quota_value` 字符串→bigint 格式校验。
2. **幂等短路**：查 `access_config_idempotency`（见 §5.1），命中同体→直接返回存档响应；命中异体→422。
3. **取锁**（顺序固定，与批量发布兼容）：
   a. `pg_advisory_xact_lock(hashtext(enterprise:owner_principal_id))`——单人规则串行化；
   b. **主体 Key 行锁**（`FOR UPDATE`）——与批量发布 `refreshKeyModels`、PATCH key 共用同一把锁，排在 advisory 之后、任何 Grant 写入之前；
   c. 读 `config_version`（见 §5.2）比对 `expected_version`，不符→409。
4. **就绪校验**：对请求 models 逐条跑与 `validateEmployeeModelRule` 相同的型号就绪判定（模型 ACTIVE、route enabled、资源 ACTIVE/DEGRADED、厂商 ACTIVE、计价生效）；任一不就绪→409 + issues。**校验范围只含本主体+请求型号，不引入批量规则的全员校验**。
5. **计算目标态**：
   - `final_targets` = 请求 models（单人规则的完整新目标）；
   - `effective_after` = `final_targets` ∪（本主体其他 PUBLISHED 批量规则的 ACTIVE 目标）；手工基线**不并入**（本次保存即接管清除）；
   - 预览 `changes` 用 029 同款 `classifyPermissionKeys`：before=当前有效全集（含手工），after=`effective_after` ∪ 手工（接管在下一步才清，预览语义=权限不丢）。
6. **历史接管**（存在手工基线时；详见 §6）：
   a. 手工∩最终有效 的型号：将匹配的手工 ACTIVE Grant **UPDATE 换绑**到新规则版本（`authorization_rule_version_id = 新版本 id`，按需调整额度字段），并补 assignment 行——`grant_id` 不变，counter 和账本链原样保留；
   b. 手工不在最终有效集的型号：保留其 Grant 不动（它没有 assignment、不在任何白名单合并源里清完后即失效——见 c）；
   c. 删除本主体 `principal_model_manual_authorization` 全部行。
7. **落规则版本**：
   - 无单人规则 → 直接创建 version 1（状态走 DRAFT→VALIDATED→PUBLISHED 的内部直通，对外表现为一次保存）；
   - 已有单人规则 → `createNextVersion` 语义创建 N+1 版，内容=`final_targets` + 型号级额度；随后复用 029 `publish` 主流程（撤旧版→建/换绑 Grant+counter+assignment→审计）。**撤销的 Grant 走 029 既有 `disableVersionLocked`（置 DISABLED，不删行），已用额度与账本随 Grant 行保留可查**。
8. **重算白名单**：`refreshKeyModels` 语义（手工已清空，结果=全部受管型号），同事务内生效，`/v1/models` 与热路径门禁无需任何改动。
9. **审计与幂等存档**：`operation_log` 记管理员、版本、来源（SINGLE）、changes、takeover 明细；写幂等表（键+请求体 hash+响应快照）。不记 Key 明文（Key 根本不在本端点出现）。

任一步异常→整体回滚，手工基线也回滚，无权限空窗。

**新员工主流程的组装**（前端两步，后端各自原子）：
`POST /principals/:id/key {allowed_model_ids: []}`（生成 Key，空权限=安全"待授权"）→ `PUT access-configuration`（选型+额度一次保存）。两步之间 Key 不可调用任何模型，满足 handoff §2.1。不做一个"建 Key+授权"超级大事务——Key 明文只在创建响应出现一次，与授权解耦后失败面更小。

## 5. 并发与幂等

### 5.1 幂等

0039 新表：

```sql
CREATE TABLE principal_access_idempotency (
  enterprise_id uuid NOT NULL,
  principal_id uuid NOT NULL,
  idempotency_key varchar(128) NOT NULL,
  request_hash varchar(64) NOT NULL,     -- 规范化请求体的 sha256
  response_snapshot jsonb NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (enterprise_id, principal_id, idempotency_key)
);
```

同键同体→返回 `response_snapshot`（含当时的 config_version、changes、takeover 结果），不重复建规则/Grant/counter；同键异体→422。与批量发布的 `publish_idempotency_key` 机制并列、互不干扰。

### 5.2 config_version（乐观锁）

两个候选：

- **A. 派生计数**：本主体单人规则最新 version 数 + 作用于本主体的批量发布事件数。零新表，但定义绕、事件计数难做准；
- **B. 新表 `principal_access_config_state(enterprise_id, principal_id, config_version)`**：单人 PUT 与批量发布都在持 Key 行锁后 `config_version + 1`。**选 B**，锁内自增，批量页"单人页立即反映结果和来源"的读取也顺带有了版本锚点。029 发布流程要加一行 upsert——这是 029 引擎唯一需要改动的点。

### 5.3 单人 × 批量并发

统一锁序：**advisory（各自 rule 域）→ 主体 ID 排序的 Key 行锁 → Grant/assignment 写入**。批量发布已是这个顺序（advisory 在先、refreshKeyModels 持 Key 锁）；单人 PUT 照此加入后，两个方向都只会在 Key 行锁上串行等待，不存在反向持锁，不死锁。合并语义天然满足"最终权限=所有有效规则的确定合并"：白名单永远从（手工 ∪ 受管）全集重算，任何一方提交后另一方在其锁后读到的是最新全集。

## 6. 历史手工授权接管（本方案风险最高处，先锁定）

### 6.1 现状代码与 handoff 叙述的三处差异（评审时须知）

| # | handoff 的假设 | 代码实际 | 对方案的影响 |
| --- | --- | --- | --- |
| 1 | 手工 Grant 可能"绑定到新规则" | 029 从未做过换绑，只有"发布新规则=新建受管 Grant + 捕获手工基线行" | 换绑是**新机制**，需要按 `(provider, model_alias)` 反解 `unified_model_id` 做匹配 |
| 2 | 手工基线在发布规则后"继续生效" | `captureManualBaseline` 只在表空时捕获；但 PATCH key / create-with-models 会重建手工行 → 效果等价于继续生效 | 接管清除后，**PATCH key 的旧直写语义必须同步收敛**（§7.3），否则手工行会被旧客户端再建出来 |
| 3 | 停用规则后"不再因手工基线放行" | 029 的 disable 只动受管侧，手工行确实原样保留→问题真实存在 | 接管是关闭该漏洞的唯一时机 |

### 6.2 接管匹配规则（保守、可审计）

匹配键：手工 Grant 的 `(provider, model_alias)` → 解析为企业内 ACTIVE unified_model（取 `provider.code` + `unified_model.alias`，均来自现有列）。逐手工 Grant 判定：

- **可换绑**：解析出的 model 在本次最终有效集内、且存在同资源就绪路由 → UPDATE 换绑到新单人规则版本，额度字段按请求值覆盖（管理员在页面上看到的就是新额度，语义=保存即生效），`version+1`，补 assignment；
- **不可换绑**（alias 解析不到、手工 Grant 已 DISABLED/EXPIRED、无匹配资源路由）：不强行迁移，该 Grant 保持原状并随白名单重算失去权限入口；在审计与响应中逐条列出（`takeover.unmigrated`），页面提示管理员可事后单独清理；
- **手工基线行 vs 手工 Grant 不一致**（有行无 Grant / 有 Grant 无行）：以白名单实际生效源（手工基线行）为准做权限清除，Grant 侧按上两条独立判定，全部进审计明细。

红线兜底：任何一步解析歧义（一个 alias 对应多个 ACTIVE model——理论上 alias 唯一，但防御性检查）→ 整个 PUT 失败回滚，不做猜测式迁移。**宁肯保存失败，不可错绑账本。**

### 6.3 接管前展示

`GET` 返回 `manual_pending_takeover` 非空即触发页面"历史手工授权待接管"标记；这些型号在列表中照常显示额度（读手工 Grant），来源标 `MANUAL_PENDING`。不要求管理员做任何额外动作——**首次保存自动完成接管**，这是把"两遍配置"消化掉的最后一公里。

## 7. 与 029 引擎的整合方式 + 旧 API 收敛

### 7.1 不分叉 publish

029 的 `publish()` 目前内部自含"校验→撤旧→建 Grant→重算→审计"。为让单人 PUT 复用同一套核心，计划做**纯内部重构**：

- 抽出 `publishValidatedVersionLocked(trx, version, validation, ctx)`：撤旧版 + 逐主体 Grant/counter/assignment + refreshKeyModels + 审计；
- 029 路由的 publish = 锁 + 校验 + 调用抽出函数（行为不变，029 集成测试应原样全绿）;
- 单人 PUT = 锁 + 校验 + 组装版本 + 接管 + 调用同一函数。

差异点仅两个，都以参数注入：Grant 额度来源（版本级 vs target 级——`resolveTargetQuotas` 统一解析后 029 路径行为不变）和审计 action 名。

### 7.2 `EmployeeModelTarget` 类型扩展

`EmployeeModelTarget` 增加可选字段；029 全链路（create/updateDraft/createNextVersion/publish/validation）透传不解析；只有 `resolveTargetQuotas` 和发布落 Grant 处消费。`model_scope=ALL` 时 target 为空数组，全部走版本级默认。

### 7.3 旧写入路径收敛（handoff §4.1 "新 UI 必须走统一服务，旧 API 仅为旧客户端保留"）

| API | 处置 |
| --- | --- |
| `PATCH /principals/:id/key` | 保留但语义改为**仅维护手工基线暂存区**（现状已是）；新 UI 不再调用。响应和审计中加入 `deprecated_for: "access-configuration"` 提示。行为本身不动，避免破坏旧客户端和 w03 测试 |
| `POST /principals/:id/grants` | 同上保留；新 UI 不调用。加 `X-Deprecated` 头与审计标记 `source: "legacy_manual"` |
| 前端 `Principals.tsx` | 删除"Key 模型权限"和"分配模型与额度"两个直写入口，替换为接入配置统一页 |

**不在本次做**：物理下线旧 API（有旧客户端与集成测试依赖）；给旧 API 加管理开关（如评审认为需要"企业级开关强制关闭直写"，可作为 P2 追加）。

## 8. 测试与 Evidence 计划（对应 handoff §6）

集成测试新文件 `pool-access-config.test.ts`（沿用 029 测试基建）：

1. 新员工全流程：建主体→生成 Key（空权限）→PUT 两个型号不同额度→断言白名单/Grant/counter/assignment/审计五处一致；
