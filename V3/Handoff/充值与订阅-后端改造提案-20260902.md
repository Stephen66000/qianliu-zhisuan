> **结论**：厂商资源后端从“资源经营快照 + 多处自行计算”调整为“资源目录 + 唯一资金事件账本 + 现有真实使用账本 + 统一资金投影 + 受控写入口”。新产品余额不再读取或覆盖 `current_balance` 快照。

---

## 1. 调整目标

后端必须统一回答三类问题：

1. 企业实际支付了多少钱；
2. API/Coding Plan 实际形成多少经营成本；
3. 每个 API 资源账号当前还剩多少钱。

所有页面只读同一服务，不再各自查询余额、充值或套餐成本。

## 2. 保留与替换

### 2.1 保留

- 厂商、厂商资源、统一模型与模型路由；
- `provider_resource.mode = API | CODING_PLAN`；
- API 计价规则及其历史版本；
- `usage_event`、`ledger_line`、`ledger_transaction` 真实使用结算链；
- Coding Plan 的 5 小时、7 天额度窗口；
- 经营账单自然月、结账与显式重开机制。

### 2.2 新增

- 唯一资金事件账本；
- Coding Plan 服务周期；
- 待对账问题对象；
- API 费用币种冻结字段；
- Coding Plan 使用命中的服务周期 ID；
- 统一余额、现金支出、经营成本和订阅周期使用查询。

### 2.3 停止作为新产品事实来源

- `provider_resource_operating_snapshot.current_balance`；
- 经营快照中的 `recharge_amount`；
- 旧资源表单的手工充值和当前余额；
- 充值后厂商同步直接覆盖产品余额；
- Dashboard、资源利用、用量总览等模块各自选择“最新余额”的 SQL。

旧数据先封存只读，真实验收前不删除。

## 3. 唯一资金事件

第一版事件类型固定为：

```text
API_OPENING_BALANCE
API_OPENING_BALANCE_CORRECTION
API_RECHARGE
API_BALANCE_RECONCILIATION
CODING_PLAN_PURCHASE
CODING_PLAN_RENEWAL
REVERSAL
```

约束：

- 已确认期初余额允许等于 0，用于区分“已确认零余额”和“缺少期初”；充值、订阅金额必须大于 0；
- 余额对账和期初更正允许正负，不允许 0；
- `REVERSAL` 的金额、币种和人民币实付由原事件反向派生，调用方不能自行填写；
- 每个 API 资源、每种币种只有一笔期初余额；
- 期初余额错误只走 `API_OPENING_BALANCE_CORRECTION`；
- 一个原事件最多冲销一次；第一版只允许冲销 API充值、Coding Plan购买和续费，期初、期初更正、余额对账和冲销事件本身禁止冲销；
- 所有资金事件只追加，不允许更新或删除。

期初更正业务时间固定为切换边界；OPEN账期内冲销业务时间固定为原事件业务时间；余额对账调整业务时间固定为案件 `balance_as_of`。月度指标按业务时间归属，审计按创建时间追溯。

暂不支持：厂商赠送余额、原路现金退款、使用扣费纠正。真实发生前必须先扩展规则和数据合同，禁止借用余额对账事件。

现金事件外部付款凭证在企业+资源范围内唯一，不按购买/续费类型拆开；无凭证重复候选必须通过一次性确认对象处理。所有跨表关系使用复合租户外键。账户金额/API费用最多8位小数，人民币实付最多2位，聚合过程不做中间舍入。

## 4. API 余额投影

```text
当前余额（同一资源、同一账户币种、截至 asOf）
= 期初余额
+ 期初余额更正
+ API 充值
+/- 余额对账调整
- 已结算 API 使用扣费
+ 冲销的反向影响
```

API 使用扣费继续使用现有 `ledger_line`，不得复制到第二张使用流水表。

必须增加：

```text
ledger_line.api_cost_currency
ledger_line.api_cost_status
ledger_line.settled_at
```

余额投影只接受与资源账户币种一致的扣费。币种回填顺序：

1. 冻结的 `billing_rule_snapshot.currency`；
2. 冻结规则版本的币种；
3. 两者都缺失则失败关闭，不根据当前规则或当前资源币种猜测。

余额状态至少包括：

```text
NORMAL
MISSING_OPENING_BALANCE
INCOMPLETE_USAGE_COST
NEGATIVE_RECONCILIATION_REQUIRED
LEGACY_ARCHIVED
```

- `asOf < 2026-09-01 00:00:00 Asia/Shanghai` 返回 `LEGACY_ARCHIVED`；
- 缺期初余额返回 `MISSING_OPENING_BALANCE`，金额不可计算，不能显示 0；
- 存在已结算但费用未知的 API 使用时返回 `INCOMPLETE_USAGE_COST`，金额不可计算；确认未访问上游的精确零审计行不形成缺口；
- 负余额返回 `NEGATIVE_RECONCILIATION_REQUIRED`；已发生使用仍必须完整结算，余额依赖型页面和预测不得输出正常可用结论；
- 是否阻断未来 Gateway 新请求不属于本资金提案，需单独产品确认。

余额读取必须使用一个SQL语句或同一 `REPEATABLE READ READ ONLY`数据库快照，资金事件、使用账本、案件和事实水位不得在普通 READ COMMITTED 下分次拼接。

## 5. Coding Plan 周期与使用

购买/续费在同一事务中：

1. 写入资金事件；
2. 写入服务周期；
3. 默认开始日为扣费日；
4. 默认从扣费日持续到下个月同日，实际为28/29/30/31个自然日；
5. 写审计和幂等回执。

库级约束：

- 扣费日期 = 周期开始日；
- 周期结束时点必须晚于开始时点；
- 周期重叠时，使用归属开始日最新的覆盖周期。

新增：

```text
ledger_line.subscription_period_id
```

Coding Plan 使用结算时冻结命中的周期 ID。周期冲销后：

- 周期状态同步改为 `REVERSED`；
- 已结算使用不物理改写、不追溯迁移；
- 历史使用仍可在原周期下审计，并标记周期已冲销；
- 如将来需要重新归属，新增独立“使用归属更正事件”，不得 UPDATE 历史使用。

真实 Token 固定为输入 + 输出；缓存和推理是子集，只单独展示，不重复累计。

## 6. 待对账问题

新增持久化对象：

```text
provider_finance_reconciliation_case
```

状态：

```text
OPEN -> REJECTED
OPEN -> RESOLVED（decision=CONFIRMED）
```

记录资源、币种、本地算法余额、厂商确认余额、差额、计算水位、关联事件、证据和处理人。

确认操作在同一事务中写 `API_BALANCE_RECONCILIATION`，并将案件直接改为 `RESOLVED + decision=CONFIRMED`；驳回写 `REJECTED + decision=REJECTED`。

## 7. 统一服务

后端统一提供：

```text
getCurrentBalance(resourceId, currency, asOf)
getMonthlyCashOutflow(month)
getMonthlyOperatingCost(month)
getFinanceEventHistory(filters)
```

所有结果必须携带资源账号、币种、人民币实付、时间范围、计算截止时间、事实水位和状态。

首页、资源利用、用量总览、供给与健康、经营账单、告警和调度不得再直接读取旧余额字段。

## 8. 切换原则

加法迁移可以提前暗部署。Coding Plan周期必须在启用Gateway暗写周期ID前，依据已审核旧事实先行暗创建；周期暗创建不生成现金支出。以下正式动作必须在同一受控切换窗口完成：

1. 暂停旧资金写入口；
2. 锁定切换水位；
3. 确认各 API 资源期初余额；
4. 迁入 9 月 1 日后充值和 Coding Plan 订阅；
5. 将 9 月 1 日后已结算 API 使用纳入新投影并回填费用币种；
6. 回填 Coding Plan 周期归属；
7. 运行余额、现金支出、经营成本与数量守恒；
8. 同时切换新写入口和所有读取消费者；
9. 同窗关闭旧写端点；
10. 真实验收通过后恢复写入。

不得出现“充值写新账本、页面仍读旧快照”的分脑窗口。

## 9. 验收补充

除规则文档既有验收外，必须增加：

- 对账下调；
- 期初余额更正；
- 9 月 1 日前 `asOf` 封存；
- 9 月 1 日至切换时点 API 扣费完整纳入；
- API 费用币种缺失失败关闭；
- 负余额进入异常待对账，查询和预测停止输出正常可用结论；
- 已发生使用在负余额下仍完整结算；
- 订阅全额冲销同步翻转周期状态，历史使用不改写；
- 写入和读取同窗切换，不存在双写或双读漂移。
