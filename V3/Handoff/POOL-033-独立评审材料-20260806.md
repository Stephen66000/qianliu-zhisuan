## 1. 验收标准逐条对照（蓄水池 10 条）

### #1 单页开通多厂商、型号默认全选可掐、一次保存生效、总额自动汇总

**自查结论：闭合。**

- 编排端点：`access-configuration.ts` 的 GET/PUT。PUT Schema：`providers[]`，每厂商 `{provider_code, quota_value, allow_overage, valid_until, enabled_model_ids[]}`。
- 单事务：`principal-access-config-repository.ts` `put()`（行 236 起），步骤 1-9 全在 `this.db.transaction().execute(...)` 内：预校验 → 幂等短路 → config_version 乐观锁 → 就绪校验 → 池 upsert → 型号开关版本化 → 清手工基线 → 白名单重算 → 审计+幂等存档。
- 总额汇总：GET 响应 `summary.total_quota`（各池 `quota_value` 之和，行 ~200）。
- 默认全选/可掐：前端面板 `PrincipalAccessConfigPanel.tsx`（311 行）厂商块内型号勾选；未开通厂商填额度即激活。
- **核验点**：PUT 内是否有任何一步在事务外执行？幂等存档与审计是否同事务？

### #2 同厂商跨型号统一池扣减；池空该厂商全拒、他商不受影响

**自查结论：闭合。**

- `quota-gate-repository.ts` `findAdmissibleGrant`（行 56-107）：先查精确型号行（过渡期兼容），未命中查池行（`pool_model_alias='*'` AND `status='ACTIVE'` AND 有效期）；池命中后查 `principal_provider_disabled_model`，被掐型号返回 null（拒）。
- `reserveQuota`（行 112 起）：事务内同语义查询 + counter 行锁预占；REJECT 不改 counter。
- 池粒度 = `(enterprise, principal, provider)`，他商池独立。
- **核验点**：预占是否确实锁在池 counter 行上（不是型号行）？池空 REJECT 路径是否影响其他厂商的查询（应为否）？

### #3 保存后 Key/池/计数器一致，不需再去批量页

**自查结论：闭合。**

- PUT 步骤 5-8：池 upsert（含新建池时插 `quota_counter` 行）→ 开关版本化 → 清基线 → `refreshKeyModels` 重算白名单。
- 白名单语义（POOL-033）：`手工 ∪ 受管开关 ∪ 池内未禁用型号`（`refreshKeyModels`，`employee-model-rule-repository.ts` 行 380 起；纯函数 `computeAllowedModelIds` 在 `principal-access-config-repository.ts` 末尾，单测 5/5）。
- **核验点**：池 upsert 更新存量池时是否误动 counter？（应只改 `quota_value/allow_overage/valid_until`）

### #4 调小已用不清零、调大立即可用

**自查结论：闭合。**

- 池 upsert UPDATE 分支（`principal-access-config-repository.ts` 行 ~326）：只 `set({quota_value, allow_overage, valid_until, ...})`，不触 `quota_counter`。
- 已用 > 新额度：按草案 §5，不拒绝、进入超额态，下一请求自然 REJECT；GET 应标 `over_limit`（**请核验 GET 读模型是否实现了 `over_limit` 标记**——自查时未逐行确认此字段）。
- **核验点**：找一笔"调小低于已用"的测试或手动推演 counter 行为。

### #5 批量页"设置总额度/追加额度"显式选择

**自查结论：闭合（本次缺口修复新增，提交 7208b9f）。**

- 后端：`employee-model-rules/routes.ts` `PublishSchema` 新增 `quota_mode: z.enum(["SET","ADD"]).default("SET")`；repository `publish()` 在池行已持 `forUpdate` 锁内执行 `quota_value = quota_value + :delta`（ADD 分支，行 ~296-305）；规则 `quota_value` 为 NULL 时 ADD 报错。审计 `change_summary` 含 `quota_mode`。
- 前端：`EmployeeModelRules.tsx` 发布按钮旁下拉"设置总额度/追加额度"（`quotaMode` state）；`api/employee-model-rules.ts` hook 透传。
- 测试：集成测试"POOL-033 §6：批量发布 ADD 模式在池行锁内追加额度"——SET 建池 500000 → ADD 追加至 1000000 → 非法 mode 400。
- **核验点**：追加是否在锁内（SQL 自增而非应用层读改写）？草案 §4 明确禁止读改写到应用层。
- **已知设计偏差（需评审裁定）**：草案 §6 原文说批量规则"只能动型号开关，不能动池"，池额度类是独立发布载荷、且"没有池的员工报错列出，不隐式建池"。实现选择了**更简口径**：publish 始终确保池存在（SET 建池/覆盖，ADD 追加），没有池的员工隐式建池。偏差理由：029 原有"发布即开通"语义延续；但与草案文字不完全一致，**请裁定接受或要求对齐草案**。

### #6 停用规则不得因旧手工基线继续获得权限；接管前标记

**自查结论：闭合。**

- PUT 步骤 7：`deleteFrom("principal_model_manual_authorization")` 清空该主体基线（权限已由池+开关承载），响应 `takeover.cleared_manual` 计数。
- GET 读模型返回 `manual_pending_takeover`（待接管型号列表）。
- 停用路径：`disableVersionLocked`（`employee-model-rule-repository.ts` 行 424 起）——assignment 置 DISABLED → 无其他 ACTIVE assignment 维护的型号写入显式禁用清单 → 白名单重算。不删基线（基线属手工权限）。
- **核验点**：停用一个曾接管过手工基线的规则，该型号是否被正确拒绝（走禁用清单而非复活基线）？集成测试"校验后原子发布 Key＋Grant…"末尾断言了 `principal_provider_disabled_model` 含被停型号。

### #7 任一步失败全回滚；并发不丢更新不死锁；幂等键不重复

**自查结论：闭合（测试覆盖）。**

- 回滚：集成测试"发布中途写入失败时 Key、Grant 和任务全部回滚"（PG trigger 注入异常）。
- 并发： advisory lock（`hashtext(enterprise:rule_id)`）串行化同规则 publish/disable；Key 行锁串行化同主体；测试"不同规则并发发布到同一员工不丢权限""手工授权与规则发布并发按 Key 行锁串行化"。
- 幂等：publish 幂等键冲突 409、同键重放返回原结果；编排端点 `principal_access_idempotency` 表存 request_hash，异请求同键 409（`IDEMPOTENCY_CONFLICT`）。
- config_version 乐观锁：`principal_access_config_state` 行锁内比对+自增（`lockAndCheckConfigVersion`）。
- **核验点**：编排端点与批量 publish 并发改同一主体池时，锁序是否一致（Key 行锁 → 池行锁）？有无反向等待路径？
