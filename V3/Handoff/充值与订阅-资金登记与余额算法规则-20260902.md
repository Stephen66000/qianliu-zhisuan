# 充值与订阅：资金登记与余额算法规则

| 项目 | 内容 |
| --- | --- |
| 日期 | 2026-09-02 |
| 适用时区 | Asia/Shanghai |
| 新账本切换日 | 2026-09-01 |
| 产品状态 | 口径已确认；本文只固化规则，不代表已完成代码、迁移、部署或真实数据验收 |
| 适用范围 | 厂商资源 → 充值与订阅；首页、资源利用、用量总览、经营账单及未来所有资金/余额消费者 |

> **最高原则**：`充值与订阅`是仟流智算唯一的厂商资金事实入口。任何页面涉及“付了多少钱、消耗了多少钱、还剩多少钱”，只能读取本模块提供的统一结果，不得自行维护余额或重复计算。

---

## 1. 产品只保留两种资金模式

近一至两年内，厂商资源统一归入以下两种模式：

1. **API**：先有期初余额，后续充值，调用时按实际结算金额持续扣减；
2. **Coding Plan**：预付固定订阅费，从订阅当天开始获得一个自然月的服务周期，下个月同日续期；周期实际天数随月份为28、29、30或31天，周期内记录真实 Token 与厂商额度窗口事实。

模式必须是资源级明确字段，不允许同一资源同时按两套算法结算。未来新增厂商或产品时，必须先选择 `API` 或 `CODING_PLAN`；不得私自新增第三种资金算法。

### 1.1 当前厂商映射

| 厂商 / 产品 | 当前主要模式 | 资金规则 |
| --- | --- | --- |
| DeepSeek API | API | 期初余额 + 充值 - 已结算 API 消耗 ± 对账调整 |
| Kimi Coding Plan | Coding Plan | 实际订阅/续费金额一次入账；默认下个月同日续期 |
| 智谱 Coding Plan | Coding Plan | 实际订阅/续费金额一次入账；默认下个月同日续期 |
| Copilot 及未来订阅产品 | Coding Plan | 在已登记厂商下新增订阅产品，沿用相同订阅与周期规则 |
| 未来新增 API 厂商 | API | 沿用相同期初余额、充值、使用扣费与对账规则 |

> 算法由资源模式决定，不由厂商名称写死。若同一厂商同时登记 API 资源和 Coding Plan 资源，两条资源分别执行各自模式。

## 2. 核心对象与唯一归属

### 2.1 余额属于厂商资源账号，不属于模型

余额唯一键为：

```text
企业 + 厂商资源账号 + 币种
```

- 同一 DeepSeek API 账号下挂载的所有模型，引用同一个余额；
- 不得为 `deepseek-chat`、`deepseek-reasoner` 等模型分别复制余额；
- 若企业登记两个 DeepSeek API 账号，两个账号分别有独立余额；
- “DeepSeek 总余额”只能是所有 DeepSeek API 账号余额的汇总，不能冒充某个账号的余额。

### 2.2 资金事实与使用事实分离

| 事实类型 | 回答的问题 | 写入来源 |
| --- | --- | --- |
| 期初余额 | 新账本从多少钱开始 | 管理员在切换时确认一次 |
| API 充值 | 实际向 API 账号充了多少钱 | 充值与订阅唯一入口 |
| API 使用扣费 | 调用实际消耗了多少钱 | 请求结算自动生成 |
| Coding Plan 购买/续费 | 实际支付了多少订阅费 | 充值与订阅唯一入口 |
| Coding Plan 使用 | 周期内实际使用多少 Token | 请求账本自动生成 |
| 对账调整 | 厂商事实与本地计算差异是多少 | 有依据的人工/厂商对账 |

### 2.3 账本币种

资源账户币种支持人民币（CNY）和美元（USD）。一笔充值或订阅同时保留两个不同事实：

1. **账户入账/订阅金额**：金额 + CNY/USD，用于资源余额或订阅订单；
2. **人民币实付**：支付渠道实际扣减的人民币金额，用于企业现金支出。

规则如下：

- CNY 账户：账户金额与人民币实付通常相同，但两个字段仍按各自事实落账；
- USD 账户：必须同时登记厂商实际入账的 USD 金额和支付渠道实际扣减的人民币金额；
- 当前余额始终按资源账户币种计算，CNY 与 USD 不得混算；
- 本月现金支出统一汇总人民币实付；
- 系统当前不维护汇率，也不得用人民币实付反推 USD 余额或用临时汇率重算历史；
- API 使用扣费按资源账户币种落账；没有经过冻结汇率或人民币结算事实时，USD 经营成本不得伪装成人民币成本。

## 3. API 模式规则

### 3.1 唯一余额公式

```text
当前余额
= 期初余额
+ 所有成功充值
- 所有已结算 API 使用扣费
± 余额对账调整
```

公式内全部金额必须与资源账户币种一致。任何页面不得使用另一套公式，不得读取管理员手工维护的 `current_balance` 作为独立事实。

### 3.2 期初余额

1. 每个 API 资源账号、每个币种只能登记一笔新账本期初余额；
2. 新账本切换日固定为 `2026-09-01`，时区固定为 `Asia/Shanghai`；期初余额为 `2026-09-01 00:00:00` 时点值，该时点之后的充值、扣费与订阅事件全部进入新账本；
3. 期初余额是一次性账本事件，不是每日快照；
4. 期初余额确认后不可覆盖、不可删除，只能通过有审计依据的调整事件纠正；
5. 9 月 1 日以前的旧余额数据封存只读，不参与新余额算法。

### 3.3 API 充值

1. 所有充值必须从 `厂商资源 → 充值与订阅 → 充值 → API 充值`进入；
2. 只能选择已经登记的 API 厂商资源账号；
3. 必填字段：
   - 厂商资源账号；
   - 资源账户币种（CNY/USD）；
   - 厂商实际入账金额；
   - 人民币实付；
   - 实际充值时间；
4. 厂商订单号、支付流水号或付款凭证编号在能够取得时必须登记；说明可选，但修改/补录/对账场景必须填写原因或证据；
5. 点击“入账确认”后形成不可覆盖的充值事件；
6. 幂等键由前端在提交时生成（客户端请求号），服务端按 `厂商资源账号 + 客户端请求号` 去重；重复点击、网络重试只能产生一笔充值；
7. 其他页面和旧资源经营表单不得再提供充值写入口。

### 3.4 API 使用扣费

1. 只有已成功结算的真实调用可以形成使用扣费；
2. 扣费必须绑定：企业、资源账号、请求、模型、结算时间、币种及计价规则版本；
3. 失败、取消、未结算请求不得伪造成已扣费；
4. 前端不得根据 Token 临时估算后直接改余额；
5. 若使用 Token 计价，必须使用请求发生时已冻结的计价规则，后续改价不得重算历史。

### 3.5 对账调整

当前版本只支持“余额对账调整”。当本地账本余额与厂商确认余额存在差异时，不覆盖原余额，不补写快照，新增一笔对账调整事件：

```text
调整金额 = 厂商确认余额 - 本地算法余额
```

调整事件必须记录：

- 调整前本地余额；
- 厂商确认余额；
- 差额；
- 正负方向；
- 对账时间；
- 操作人；
- 原因与证据；
- 关联的厂商资源账号。

余额对账调整事件只影响余额结果，不计入本月现金支出、本月经营成本等任何月度指标。

当前版本暂不支持以下业务事件：

- 厂商赠送余额；
- 原路现金退款；
- 使用扣费纠正。

在真实业务发生前，不预建复杂分类；一旦出现，必须先补充并确认独立事件类型和月度指标影响，禁止借用“余额对账调整”代替。

#### 3.5.1 9月1日至暗部署前的DeepSeek历史费用封口

生产预检发现切换后旧账本存在零Token但费用为空的API记录，厂商余额下降又证明不能把它们全部伪造为零费用。Owner确认9月后的DeepSeek厂商余额为资金确认事实，因此增加一次性迁移事件 `API_LEGACY_COST_ADJUSTMENT`：

```text
历史缺失API成本
= 截止厂商快照时的本地可计算余额
- 同时点厂商确认余额
```

规则：

1. 只允许API资源，当前实际对象仅DeepSeek；Kimi和智谱Coding Plan继续按固定月费处理；
2. 窗口固定从2026-09-01 00:00开始，到一条真实 `PROVIDER_SYNC + PROVIDER_API` 余额快照结束；
3. 旧未知行不伪造逐笔费用，只关联到唯一历史封口记录；
4. 缺失成本计入封口发生月的API经营成本，并以负向资金事件同步扣减余额；
5. 本规则只用于一次性迁移，暗部署后的新API调用必须继续逐笔精确计价，不得恢复余额差额倒推；
6. 8月1日至8月31日为测试期，封存用于Token完整性校验，不进入9月正式资金账本。

### 3.6 API 月度指标

| 指标 | 计算规则 |
| --- | --- |
| 本月 API 充值 | 本自然月内成功充值事件按资源账户币种分别汇总 |
| 本月 API 实际消耗 | 本自然月内已结算 API 使用扣费按资源账户币种分别汇总 |
| 当前余额 | 从期初余额开始，按资源账户币种累计充值、扣费与余额对账调整 |
| 本月 API 现金支出 | 本自然月内成功充值事件的人民币实付之和 |
| 本月 API 经营成本 | 本自然月内已结算 API 使用扣费按原币种分别汇总；无人民币结算事实时不得跨币种合计 |

「本月 API 充值」回答厂商账户实际入账多少，「本月 API 现金支出」回答企业实际支付多少人民币，两者在 USD 账户下不是同一指标；「本月 API 经营成本」与「本月 API 实际消耗」是同一原币种使用事实的两种业务叫法，不得重复计算。本自然月按 `Asia/Shanghai` 切分。API 充值不得再次计入 API 经营成本，避免重复计算。

## 4. Coding Plan 模式规则

### 4.1 预付费原则

Coding Plan 是预付费产品。购买或续费发生时：

1. 实际支付金额一次性确认为订阅支出；
2. 订阅日期同时作为服务周期开始日；
3. 不按天摊销；
4. 不将套餐内 Token 再折算成 API 费用；
5. 每次续费都形成一笔新的订阅事件和新的服务周期。

### 4.2 登记字段

从 `厂商资源 → 充值与订阅 → 充值 → Coding Plan`进入，必填：

- 已登记厂商；
- 产品/套餐名称；
- 订阅订单币种（CNY/USD）；
- 厂商订阅金额；
- 人民币实付；
- 实际扣费日期；
- 服务周期开始日；
- 服务周期结束日。

厂商订单号、支付流水号或付款凭证编号在能够取得时必须登记。说明可选；补录、调整或特殊套餐必须填写原因。

### 4.3 自然月服务周期

默认规则：订阅日为周期开始日，下个月同日为下一周期开始日和本周期失效时点。周期不是固定30天，实际包含28、29、30或31个自然日。

例如：

```text
订阅日期：2026-09-19
服务开始：2026-09-19 00:00:00
服务失效：2026-10-19 00:00:00
下次续费：2026-10-19
时区：Asia/Shanghai
```

例如从8月19日到9月19日实际跨31天，从9月19日到10月19日跨30天；二月则随平年/闰年跨28或29天。订阅日在下个月不存在时，续期日取下个月最后一个自然日。若厂商实际订单明确提供不同结束日，以订单事实为准并填写调整原因。

当前Owner确认的订阅事实：

| Coding Plan | 续费日 | 当前月费 | 切换日有效carryover |
| --- | --- | ---: | --- |
| Kimi | 每月19日 | CNY 199 | 2026-08-19 00:00 至 2026-09-19 00:00 |
| 智谱 Max | 每月26日 | CNY 422.10 | 2026-08-26 00:00 至 2026-09-26 00:00 |

月费是当前登记事实，不作为永久价格硬编码；后续每次续费仍以实际扣费金额入账。上述两个carryover均在切换日前开始，只迁周期，不补记9月支出。

补充口径：

1. 实际扣费日期与服务周期开始日必须为同一天，费用一次性确认在周期第 1 天；
2. 服务周期失效时点默认由系统按“下个月同日”自动计算，仅当订单事实不同时人工改写并填写原因；
3. 若提前续费导致服务周期重叠，使用量归属包含该时间戳、且开始日最新的服务周期；重叠不影响费用确认。

### 4.4 Coding Plan 费用

| 指标 | 计算规则 |
| --- | --- |
| 本月套餐扣费 | 实际扣费日期落在本自然月的订阅事件按订单币种分别汇总 |
| 本月 Coding Plan 现金支出 | 本自然月订阅事件的人民币实付之和 |
| 单周期套餐成本 | 使用该次购买/续费的人民币实付确认固定经营成本；订单原币金额单独保留 |
| 跨月使用 | 使用量按服务周期统计；费用不跨月摊销 |
| 续费 | 新建订阅事件，不覆盖上一周期 |

例如 Kimi 在 9 月 19 日支付 199 元：

- 9 月套餐扣费增加 199 元；
- 服务周期为 9 月 19 日至 10 月 18 日；
- 10 月不重复确认该 199 元；
- 下一次续费重新形成一笔订阅事件。

### 4.5 Coding Plan 使用量

Coding Plan 额度是厂商黑盒，系统只记录真实观测事实，不伪造官方总额度：

- 周期内真实 Token；真实 Token = 输入 Token + 输出 Token，缓存是输入子集、推理是输出子集，只单独展示，不重复相加；
- 请求次数；
- 5 小时窗口使用量、剩余/比例、恢复时间；
- 7 天窗口使用量、剩余/比例、恢复时间；
- 触发限额的时间和使用水平；
- 周期累计使用量；
- 历史周期最高观测量。

“历史最高观测量”只表示已经实际达到的水平，不得命名为“官方总额度”，也不得自动写入员工授权、计费或调度额度。

## 5. 现金支出、经营成本与余额必须分开

示例：本月 DeepSeek 充值 100 元，API 实际消耗 6 元，Kimi 订阅 199 元。

| 指标 | 结果 | 解释 |
| --- | ---: | --- |
| 本月现金支出 | 299 元 | API 充值 100 + Coding Plan 扣费 199 |
| 本月经营成本 | 205 元 | API 实际消耗 6 + Coding Plan 扣费 199 |
| API 余额变化 | +94 元 | API 充值 100 - API 消耗 6 |

任何页面显示“本月花费”时，必须明确是“现金支出”还是“经营成本”，不得只写含义不明的“总支出”。

## 6. 唯一写入口规则

### 6.1 允许写入

| 业务动作 | 唯一入口 |
| --- | --- |
| API 期初余额 | 充值与订阅模块的切换/初始化流程 |
| API 充值 | 充值与订阅模块 |
| Coding Plan 购买/续费 | 充值与订阅模块 |
| API 使用扣费 | 请求结算系统自动写入 |
| Coding Plan Token 使用 | 请求账本自动写入 |
| 对账调整 | 充值与订阅模块的受控对账入口 |

### 6.2 禁止写入

- 首页不得写入或重算资金数据；
- 资源利用不得修改充值、余额或订阅金额；
- 用量总览不得修改资金数据；
- 经营账单不得补写充值或覆盖余额；
- 厂商资源旧表单不得继续填写 `充值金额` 或独立 `当前余额`；
- 导入、脚本和后台任务不得绕过统一账本直写余额；
- 前端不得通过“旧余额 + 新充值”自行维护第二份余额。

### 6.3 冲销与更正规则

1. 已入账的充值、订阅和资金事件不得直接修改或删除；
2. 充值或订阅金额、资源、币种、人民币实付、业务日期等登记错误时，必须追加一笔引用原事件 ID 的 `REVERSAL` 冲销事件；
3. 冲销事件按原事件金额和指标影响反向入账；冲销成功后，再登记一笔正确事件；
4. 期初余额登记错误时，不得创建第二笔期初余额，使用引用原期初事件的“期初余额更正”事件修正；
5. 账期尚未结账时，冲销和正确事件归入原业务账期；
6. 账期已经结账时，默认拒绝补录、冲销和回填；确需修正，必须先走显式重开账期流程，禁止在当前月份静默抵消历史错误；
7. 所有冲销、更正与重开必须记录操作人、原因和证据。

### 6.4 业务重复入账防护

1. 客户端请求号只负责防止重复点击和网络重试，不等同于业务凭证；
2. 厂商订单号、支付流水号或付款凭证编号一旦登记，在同一企业、资源/订阅和事件类型下必须唯一；
3. 缺少外部凭证时，服务端应对同一资源/订阅、同一事件类型、相同金额、相同业务时间的重复登记给出明确警告并要求二次确认；
4. 冲销事件必须引用唯一原事件，不得重复冲销同一事件。

## 7. 统一查询与下游调用规则

资金模块至少统一提供以下四类结果：

1. `当前余额`：某个 API 资源账号按账户币种计算的当前可用金额；
2. `本月现金支出`：API 充值与 Coding Plan 实际扣费的人民币实付之和；
3. `本月经营成本`：API 已结算消耗按原币种分别汇总，Coding Plan 使用人民币实付确认固定成本；无人民币结算事实时不得跨币种伪合计；
4. `订阅周期使用`：Coding Plan 周期 Token、5 小时和 7 天窗口事实。

下游要求：

| 消费页面 | 只允许读取的结果 |
| --- | --- |
| 首页 | 只读取本月经营成本及必要摘要，不计算；当前确认版本不展示充值入口、本月充值卡片或待充值明细 |
| 厂商资源 → 资源利用 | 当前余额、月度 API 消耗、订阅周期使用 |
| 厂商资源 → 用量总览 | 与资源账号绑定的统一余额、Token 与费用 |
| 厂商资源 → 供给与健康 | 基于统一余额/窗口事实预测；不得读取另一套余额 |
| 经营账单 | 月度现金支出、经营成本与明细台账 |
| 充值与订阅 | 唯一写入口、历史资金事件和余额结果 |

所有结果必须携带可追溯信息：资源账号、币种、截止时间、计算范围和事实来源。前端只格式化，不重新加减。

6. 9 月 1 日后的新购和续费全部进入新订阅账本；
7. 旧数据不得与新数据拼接后冒充一条完整的新账本历史。

## 9. 数据完整性规则

1. 所有资金事件追加写入，不覆盖、不删除；
2. 每笔事件必须具备企业、资源/订阅、类型、金额、币种、业务发生时间、创建时间和来源；
3. 人工事件必须记录操作人；
4. 补录和对账事件必须记录原因与证据；
5. 重试必须幂等；
6. 不同资源账户币种不得直接相加；本月现金支出只汇总事件明确记录的人民币实付；
7. 未结算使用不得扣减余额；
8. 使用扣费事件不得因余额不足被拒绝或改写金额；当算法余额出现负数时，余额进入「异常待对账」状态：必须生成对账问题，展示层与下游页面不得将其当作正常余额消费，待对账调整事件修正后恢复，不能静默归零；
9. 缺少期初余额时，当前余额必须显示“不可计算”，不得伪造为 0；
10. 同一资源账号下所有模型必须返回相同余额结果；
11. 余额按（业务发生时间、事件创建时间、事件 ID）稳定排序折叠全部事件计算，同时点多笔事件顺序确定，历史重放结果一致。
12. 充值、订阅、冲销和更正事件必须保留原币金额、原币币种和人民币实付；任何字段缺失都不得通过临时汇率补算。

## 10. 验收规则

### 10.1 API

- [ ] 每个 API 资源只能登记一笔 2026-09-01 期初余额；
- [ ] 充值只能从充值与订阅入口提交；
- [ ] 重复点击和网络重试只生成一笔充值；
- [ ] 相同厂商订单号、支付流水号或付款凭证编号不能重复入账；
- [ ] 充值后所有页面读取同一个余额结果；
- [ ] 已结算 API 消耗实时减少余额；
- [ ] 未结算、失败或取消请求不减少余额；
- [ ] 对账差异通过调整事件处理，不覆盖历史；
- [ ] 多模型共享同一资源余额；多资源账号分别计算；
- [ ] 旧资源页面不再出现充值金额和手工当前余额写入口；
- [ ] 错误充值只能通过冲销原事件并重新登记修正；已结账月份未重开时拒绝回填。

### 10.2 Coding Plan

- [ ] 购买/续费只能从充值与订阅入口提交；
- [ ] 扣费日期一次性确认套餐支出；
- [ ] 默认生成从扣费日到下个月同日的自然月服务周期，并正确覆盖28/29/30/31天；
- [ ] 续费生成新事件和新周期，不覆盖历史；
- [ ] 套餐费用不摊销、不重复折算 API 费用；
- [ ] 周期 Token、5 小时窗口、7 天窗口分别可查；
- [ ] 真实 Token 只计算输入 + 输出，缓存与推理不重复累计；
- [ ] 历史最高值标记为“观测量”，不冒充官方额度。

### 10.3 全局一致性

- [ ] 首页、资源利用、用量总览、供给预测、经营账单读取同一资金服务；
- [ ] 同一查询时点、同一资源账号、同一币种在所有页面返回相同余额；
- [ ] “现金支出”和“经营成本”名称、公式和金额不混用；
- [ ] CNY 与 USD 余额分别计算；人民币现金支出只取人民币实付；
- [ ] 任一资金数字都能下钻到不可变事件明细；
- [ ] 删除缓存后可仅凭期初余额和事件账本完整重算余额及月度指标。
