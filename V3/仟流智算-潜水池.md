## POOL-013：为所有可创建业务对象补齐后续管理闭环

| 核心判断 | 添加只是建档；所有可创建业务对象都必须具备后续管理入口，但不等于所有数据都允许原地覆盖 |
| 建议优先级 | P1（横向管理能力，具体排期另行确认） |

### 产品规则

1. 配置类允许直接编辑，并保留操作日志、乐观锁和影响提示：
   - 厂商资源名称、上游模型、并发上限；
   - Model Route 的上游模型、资源、优先级、权重和启停状态；
   - 主体名称、部门和额度配置。
2. 规则类在界面提供“编辑”，底层生成新版本，不覆盖已经生效的历史：
   - 高峰计价规则；
   - 额度规则；
   - 调度策略；
   - 高峰禁用时段。
3. 事实类禁止修改，只能追加更正或冲正记录：
   - 用量账本；
   - 上游 Attempt；
   - 结算记录；
   - 操作日志。
4. 特殊字段使用专用生命周期：
   - 主体 Key、厂商凭证只能轮换或撤销；
   - 已被客户端使用的统一模型别名不原地改名，采用新别名和迁移；
   - 厂商和资源模式创建后不原地变更。

### 通用交互能力

- 详情；
- 编辑；
- 启用／停用；
- 复制为新版本；
- 历史版本；
- 操作日志；
- 影响范围预览；
- 回滚到上一版本；
- 并发修改冲突提示。

### 首个落地点

1. Model Route 增加编辑功能，至少覆盖 `upstream_model`、资源、优先级、权重和启停状态。
2. 高峰计价规则增加“编辑并创建新版本”，自动承接旧规则并设置新旧版本生效边界。
3. 增加跨层一致性校验：资源声明模型、Model Route 上游模型、计价规则匹配模型不一致时禁止发布或明确告警。
4. 消除恢复死锁：错误路由导致资源降级时，管理员仍可受控修正路由并恢复资源，不得出现“因降级不能修路由、因路由错误无法恢复”的闭环阻塞。

### 验收口径

- 后台所有“新增”入口均完成对象分类，并提供相应的编辑、版本化或不可修改说明；
- 修改生产生效配置前展示影响范围，保存后生成完整操作日志；
- 已生效计价规则的历史账单和结算结果不因新版本发布而变化；
- 能在不直连数据库的情况下完成错误 Model Route 修正、资源恢复和真实调用回归；
- UI、API、数据库和自动化测试覆盖直接编辑、版本切换、并发冲突和回滚路径。

### 边界说明

当前智谱生产故障的应急修复不进入潜水等待：`model_route.upstream_model` 的 `5.2` → `glm-5.2` 以及对应计价规则版本修正，仍应作为当前故障立即处理。POOL-013 负责解决同类问题以后不再依赖直连数据库。

## POOL-014（历史需求，已转入测试池）：Gateway 真实流式、Anthropic 工具协议与 Kimi 稳定性保护闭环

| 项目 | 内容 |
| --- | --- |
| 状态 | 待排期 |
| 提出／确认 | 佳哥，2026-08-01 |
| 触发事件 | Claude Desktop 经 CC Switch 调用 `Kimi` 时，多次在约 60 秒后收到上游 404 HTML；Web Search 后又出现 `invalid_request_error → 502 → 503`；同日还出现 Kimi 429 后唯一资源被熔断、Gateway 返回 503 |
| 核心判断 | Gateway 同时存在真实流式、Anthropic 工具历史转换、错误语义和单资源保护缺口；必须把协议、错误分类、资源调度和真实客户端回归作为一条链治理，不能只消除最终的 503 文案 |
| 建议优先级 | P0（客户端可用性；进入正式计划时优先排期） |

### 目标范围

1. Claude → K3 优先使用 Kimi 官方 Anthropic 协议，由 Gateway 做透明代理、鉴权、计量和调度；只有上游不支持 Anthropic 时才进入 OpenAI Chat Completions 转换链。
2. 完整实现 Anthropic Messages 工具协议转换：覆盖 `tool_use`、`tool_result`、`tool_choice`、`tool_calls`、`tool_call_id`、并行工具、工具顺序、流式工具事件、`server_tool_use`、图片、thinking 和上下文压缩后的工具历史。
3. 修复错误语义：上游 HTTP 400 保持客户端请求错误且 `retryable=false`，不得包装为 502，不得累计资源失败或污染健康状态；401、403、429、5xx、超时和取消分别归类。
4. `/v1/messages` 实现真实 Anthropic SSE：上游事件到达后立即转发，不等待完整响应。
5. `/v1/chat/completions` 实现真实 OpenAI SSE，覆盖未来经 CC Switch 接入的 Codex 和其他 OpenAI 兼容客户端。
6. 明确 Codex 接入策略：继续由 CC Switch 将 Responses 转为 Chat Completions，或单独建设 `/v1/responses`；在决策前不得宣称 Responses 原生兼容。
7. 建立分层超时：首字节、流式空闲和请求总时长分别配置；超时统一返回结构化 504 `upstream_timeout`，禁止透传 HTML 错误页。
8. 细分 Kimi 429：至少区分引擎临时过载、并发限制、短周期窗口耗尽和周期额度耗尽；仅临时过载／并发限制按 `Retry-After` 短退避，额度耗尽直接切换资源或明确返回不可重试原因。
9. 为 K3 配置第二个健康资源或明确降级路由；第二资源优先使用独立账号／独立额度池，避免两个 Key 共享同一套餐而同时失效。
10. 增加单资源半开保护：冷却到期只允许一个真实业务请求探测；同一波并发失败不重复累计冷却时长；资源池不得自动剔除 100% 候选。
11. 保留全链路诊断证据：记录客户端协议、是否请求流式、首字节耗时、失败所在层、原始上游状态码、稳定错误码和请求 ID，不保存消息正文。

### 验收口径

- `stream:true` 时响应为对应协议的 `text/event-stream`，事件顺序、结束事件、usage 和工具调用均符合客户端协议；
- K3 连续生成超过 60 秒时仍持续收到事件，不再因完整响应缓冲而失败；
- Gateway 收到上游首个事件后 1 秒内向客户端转发，不做整段缓存；
- 上游超时、网络错误和非 JSON 错误均转换为稳定 JSON/SSE 错误，不再让客户端显示无关的“模型不存在”；
- Web Search 完成后，`tool_use → tool_result → 模型继续回答` 全链路成功，不再出现协议转换导致的 `invalid_request_error`；
- MCP 连续调用 20 轮不丢失工具历史；并行工具、流式工具调用、上下文压缩、图片和 thinking 场景保持协议正确；
- HTTP 400／401／403 不触发资源熔断；普通技术错误不自动硬隔离资源；每类错误的 HTTP 状态、`retryable` 和健康状态影响符合冻结矩阵；
- Kimi 返回 429 后，Gateway 保留 429 语义和 `Retry-After`；临时过载冷却到期能够自动半开恢复，周期额度耗尽切换到独立资源或明确降级路由；
- 并发 429 不会把同一故障波次重复计数，也不会把唯一 Kimi 资源永久踢出候选；
- 主 K3 资源故障时第二资源能够在提交前接管；两个资源同时不可用时返回真实原因和事件编号，不再只显示笼统 503；
- Claude Desktop、Claude Code、经 CC Switch 转换的 Codex、WorkBuddy 各完成一轮真实客户端回归；
- 自动化测试覆盖非流式、流式、Web Search、MCP 多轮、并行工具、客户端取消、首字节超时、流式空闲超时、400／401／403／四类 429／5xx、资源切换、半开恢复和并发失败去重。

### 边界说明

- 已确认 Gateway 当前存在“声明支持流式、实际返回一次性 JSON”的差异；它是本次 60 秒故障的重要诱因和放大器。
- 已用最小载荷确认当前转换器会把 Anthropic `tool_use`／`tool_result` 和 `tool_choice` 原样送入 OpenAI Chat Completions；这是 Web Search 后 `invalid_request_error` 的直接协议缺口。
- 404 HTML 最终由哪一层产生，仍需在实施前结合生产 Gateway、反向代理和 Kimi 上游日志定位，不能把所有失败简单归因于流式。
- 增加第二个 Kimi 独立资源属于容量与高可用配置项，可与本任务并行，但不能替代协议正确性、真实流式和正确熔断。
- 完成本条目不承诺外部模型零故障；验收目标是消灭已知协议放大链，让剩余 503 只代表可证明的真实不可用，并能按 request ID 直接定位。
