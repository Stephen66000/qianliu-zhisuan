## 1. 为什么先写计划

涉及项目整理、问题修复、目录移动和文件清理时，不能把一句想法直接当成执行指令。

先形成计划文档有两个目的：

1. **充分讨论，达成共识**  
   先明确目标、范围、顺序、风险和处理边界，把双方共识记录下来，避免边讨论边执行导致跑偏。
2. **过程有循可依，结果可以对照**  
   执行过程中以本文档为依据；完成后逐项核对和打勾，判断是否真正实现了目标。

本计划既是执行清单，也是双方对本次工作的范围约定和验收依据。

## 2. 本次工作的目标

当前 M6 大部分工作已经完成，各阶段也经历了双审。项目目录在持续开发、审核、测试和交付过程中积累了历史文件、临时文件、重复文件和可再生成的产物。

本次工作的目标是：

- 让项目目录结构清晰，能够快速识别程序、文档、部署、测试和历史资料；
- 把确认过期但仍有历史价值的文件封禁保存，不直接删除；
- 清理确认无价值且可安全删除的垃圾文件；
- 审计并解决仍然存在的 P2、P3、P4、P5 遗留问题；
- 整理后保持程序可构建、可测试、可运行，关键链路不被破坏。

衡量标准不是单纯“文件数量变少”，而是任何人打开项目后，都能较快判断：

1. 程序在哪里；
2. 如何构建、测试和运行；
3. 哪些文件当前有效；
4. 哪些文件已经废弃；
5. 遗留问题是否已经闭环。

## 3. 已确认的工作范围

### 3.1 过期文件封禁

- 识别被替代、已废弃或只具有历史留档价值的文件；
- 移入统一封禁目录；
- 不删除封禁文件；
- 记录原始路径、封禁原因、替代文件、引用检查结果和恢复方法。

### 3.2 程序类文件整理

- 识别程序源码、测试、部署、数据库、工具脚本和配置模板；
- 将明显散落、混放的程序类内容整理到合理位置；
- 优先沿用已有 `apps/`、`packages/`、`deploy/` 等工程结构；
- 只做必要移动，不借整理之名进行无关重构。

### 3.3 P2—P5 遗留问题收口

- 汇总双审报告、阶段 Evidence、任务书、整改记录、代码标记和测试记录中的 P2—P5；
- 去重并确认问题是否仍然存在；
- 区分“已经解决但没有销项”和“确实尚未解决”；
- 对仍然存在的问题逐项修复、验证并记录结果。

### 3.4 垃圾文件清理

- 清理确认无价值且可重新生成的缓存、日志、临时文件、重复产物、系统文件和测试残留；
- 对无法确认的文件不直接删除，转入待确认清单或封禁区；
- 按实际情况补充忽略规则，避免同类垃圾再次进入项目。

## 4. 明确不在本次范围内的事项

- 不制作 Windows 最小交付包；
- 不新增 Windows 打包或交付脚本；
- 不因为“看起来没用”就删除文件；
- 不擅自删除历史代码、历史文档或审核 Evidence；
- 不进行与目录整理、遗留问题修复无关的架构重构；
- 不擅自改变产品范围、业务规则、部署方式或技术基线；
- 不提交、推送、发布或操作外部环境，除非 Owner 另行明确授权。

Windows 测试只是暴露“项目目录中可能存在大量无用文件”的场景证据，不代表本次需要建设 Windows 专项交付机制。

## 5. 核心处理原则

1. **先盘点，后处理。**
2. **先修问题，后移动文件。**
3. **先验证，后封禁和清理。**
4. **过期文件以封禁为主，确认是垃圾后才删除。**
5. **无法确认用途的文件默认不动。**
6. **程序目录整理坚持最小移动，避免无关重构。**
7. **每次移动后检查引用，每轮修改后执行针对性验证。**
8. **发现范围、依赖或风险变化时暂停执行，先更新计划并重新确认。**

## 6. 文件分类标准

| 分类 | 判断标准 | 处理方式 |
| --- | --- | --- |
| 当前有效 | 被当前程序、构建、测试、部署或有效文档使用 | 保留；必要时整理位置 |
| 过期但有历史价值 | 已被替代、停止使用，但需要保留历史依据 | 移入封禁区并登记 |
| 可确认垃圾 | 无有效引用、无审计价值、可重新生成或明显属于临时残留 | 列入清理清单，经确认后删除 |
| 暂时无法判断 | 用途、来源或依赖关系不明确 | 不动，列入待确认清单 |

判断文件是否有效时，至少检查：

- 当前代码是否引用；
- 构建、测试、部署、数据库迁移是否依赖；
- M6 当前基线及后续阶段是否需要；
- 是否属于必须保留的审核 Evidence；
- 是否已有明确替代文件；
- 是否只是缓存、日志、临时包、重复副本或可再生成产物。

## 8. 验收标准

本计划完成需要同时满足：

- [ ] P2—P5 已完成全面汇总，每项都有明确状态；
- [ ] 仍然存在且属于本次范围的问题已修复并有验证证据；
- [ ] 过期文件已封禁且可追溯、可恢复；
- [ ] 垃圾文件只在确认安全后删除，并留下实际删除清单；
- [ ] 程序、测试、部署、数据库和当前有效文档边界清晰；
- [ ] 有效代码、脚本和文档不依赖封禁区；
- [ ] 整理后的项目通过约定范围内的验证；
- [ ] 没有夹带无关重构或新增需求；
- [ ] 最终结果可以逐项与本计划对照。

## 9. 计划变更规则

执行中如果出现以下情况，安东尼必须暂停受影响工作，不得自行扩大范围：

- 发现文件用途无法判断；
- 发现移动会影响未纳入计划的重要链路；
- P2—P5 中包含产品取舍或需要改变业务规则的问题；
- 需要删除具有历史、审核或恢复价值的文件；
- 需要新增 Windows 专项机制或其他新功能；
- 需要进行大范围目录重构；
- 当前有效基线无法通过验证。

处理方式：

1. 记录发现的事实和影响；
2. 提出可选方案及风险；
3. 更新本计划或处理清单；
4. 经 Owner 确认后继续。
