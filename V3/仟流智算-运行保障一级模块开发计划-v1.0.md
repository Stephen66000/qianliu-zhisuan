## 1. 执行合同

### 1.1 背景

生产接入 Kimi、智谱 Coding Plan 的过程中，先后暴露出以下问题：

1. 上游 429、模型代码错误、额度耗尽、凭证异常等信号被混入同一资源不可用状态；
2. 当前资源状态迁移只有一条正式写入路径，但错误分类存在分裂：各 Provider Adapter 已有厂商分类逻辑，生产 Pipeline 却使用内联 `mapToClassification`，厂商特有业务码没有进入正式路径；
3. 当前真实 HTTP Caller 只完整实现 DeepSeek；主本地项目目录中的智谱／Kimi 仍走 DeepSeek Caller 兜底，非 2xx 正文只被输出后丢弃，无法结构化识别业务码和恢复字段；
4. 连续失败可能由既有状态机自行触发资源不可用，唯一资源被完全剔除；多个在途失败还可能放大一次故障波峰；
5. 已发布配置缺少编辑入口，模型路由、计价规则修正依赖新增或直连数据库；
6. 现有 `apps/worker` 只是单次 reconciliation CLI，没有持续调度、Outbox 消费和到期恢复扫描；现有异常评估仍依赖管理员请求页面；
7. 使用主体与自然人、项目负责人、企业微信身份尚未建立正式关系。

本计划将“运行保障”建设为管理后台一级模块，闭合“规则制定 → 运行判断 → 熔断执行 → 中文反馈 → 负责人通知 → 自动／人工恢复 → 历史审计”。

### 1.2 已确认的 Owner 决策

1. 管理后台新增一级菜单“运行保障”。
2. 模块内容不能因追求简化而删减运行态势、规则管理、熔断事件、异常中心和通知配置。
3. 所有可创建规则必须可编辑、可管理；已发布规则编辑时生成新版本，不覆盖历史。
4. 硬熔断只允许由“上游明确原始信号”或“管理员明确计划熔断规则”触发。
5. 5xx、超时、网络错误、连续失败和失败率只触发预警／降级，不得自行触发硬熔断。
6. WorkBuddy、Claude Code、ZCode 等客户端只要求能够看到清晰中文错误，不强制第三方客户端实现弹窗。
7. 先建立“人员”对象，再建立人员与企业微信 `userid` 的映射；不得把 `wecom_userid` 直接塞进使用主体。
8. 人主体关联一个人员；项目主体必须绑定一个项目负责人。
9. 第一版企业微信通知采用成员应用消息，按人员 `userid` 直接发送给本人；人主体通知本人，项目主体通知项目负责人。不得使用通知群或群机器人 Webhook 代替个人通知。
10. 当前是单公司、约 10 人内部使用的试验产品；所有规则、资源、人员和通知配置均属于同一个工作空间，不建设多租户能力。

### 1.3 版本目标

管理员可以在“运行保障”中添加、编辑、发布和回滚可用性规则；Gateway 对明确上游信号和计划时段做确定性熔断，对普通技术故障只告警；受影响请求得到中文说明；对应人员或项目负责人在自己的企业微信中收到成员应用消息；熔断和恢复全过程可追溯、可回放、可审计。

### 1.4 非目标

本版本不实现：

- 企业微信群机器人、通知群、个人微信私聊；
- 邮件、短信、飞书、钉钉和通用通知编排平台；
- 值班表、轮班、逐级升级和个人免打扰；
- LLM 判断故障或生成运行时处置；
- 主动制造模型请求探活；
- 自动采购和自动续费；
- 多租户、企业开户、企业切换、企业级权限隔离、企业独立配置和跨企业运营；
- 任意脚本／正则表达式规则；
- 用失败次数、失败率或延迟阈值直接触发硬熔断。

### 1.5 退出条件

全部满足才可标记模块完成：

1. 一级导航与五个功能区完整可用；
2. 规则新建、编辑新版本、启停、回滚、历史和冲突校验闭合；
3. Kimi、智谱至少各完成一条真实上游信号映射验证；
4. OpenAI／Anthropic 兼容错误均能显示中文原因和恢复信息；
5. 人主体和项目主体两条企微成员定向通知链路均通过；
6. 同事件同人员只通知一次，恢复只通知一次；
7. 企业微信消息 API 失败不阻塞 Gateway，不泄露应用 Secret 和 access token；
8. 普通 5xx／超时只生成预警，不会把资源硬熔断；
9. 迁移、升级、回滚、全量测试、Evidence 和生产只读验收完成。

## 2. 产品信息架构

### 2.1 一级导航

将当前一级入口“异常告警”升级为“运行保障”，前端路由为 `/runtime-assurance`。一级入口总数保持不变；SPA 显式增加 `/alerts` → `/runtime-assurance?tab=alerts` 的兼容跳转。这里仅调整前端页面路由，现有后端 `/alerts`、`/alerts/disposition` API 保持不变。

### 2.2 五个功能区

| 功能区 | 目标 | 核心内容 |
| --- | --- | --- |
| 运行态势 | 回答“现在还能不能用” | 正常／预警／熔断资源数、正在熔断、无备用资源、影响主体、预计恢复时间 |
| 熔断规则 | 回答“为什么会停、如何恢复” | 上游信号规则、计划熔断规则、故障预警规则；新增、编辑、发布、启停、回滚、历史 |
| 熔断事件 | 回答“哪次规则真正执行了” | 当前事件、历史、触发信号、规则版本、影响范围、恢复条件和恢复记录 |
| 异常中心 | 回答“哪些问题需要关注” | 复用 `alert_event`，承载 5xx、超时、凭证、额度、账本、路由和安全预警 |
| 通知配置 | 回答“通知发到哪里、是否送达” | 企业微信应用配置、成员可见范围提示、指定人员测试发送、启停、脱敏展示、最近发送记录 |

### 2.3 业务页面联动

- 厂商资源：展示 `正常／预警／已熔断`，链接到对应事件；
- 使用主体：人主体关联人员；项目主体设置项目负责人；
- Gateway 错误：返回中文原因、恢复时间、可否重试和事件编号；
- 首页：只展示“正在熔断”和“无可用资源”等需要行动的摘要，不复制整个运行保障页面；
- 系统设置：保留操作日志；企业微信应用 Secret 的配置和轮换操作同时进入操作日志。

## 3. 规则体系

### 3.1 三类规则

| 规则类型 | 触发来源 | 动作 |
| --- | --- | --- |
| `UPSTREAM_SIGNAL` | Adapter 识别到上游明确业务信号 | 硬熔断；按上游时间或人工恢复 |
| `SCHEDULE_BLOCK` | 管理员配置模型／资源禁用时段 | 计划熔断；到时自动恢复 |
| `OBSERVATION_ALERT` | 5xx、超时、网络错误、连续失败、错误率 | 只预警／降级；继续允许请求 |

### 3.2 第一版统一信号

目标链路由 Adapter 负责把厂商原始 HTTP 状态、业务码和响应字段规范化，规则引擎只匹配稳定信号，不直接执行任意正文正则。当前生产 Pipeline 尚未使用 Adapter 的厂商分类方法，W04 必须先完成以下前置整改：

1. 为智谱、Kimi 建立真实厂商 Caller，或从正式集成基线合并已有实现，禁止继续使用 DeepSeek Caller 兜底；
2. 非 2xx 响应只在内存中按厂商安全解析允许字段，提取 HTTP 状态、业务码、`Retry-After`／重置时间和脱敏摘要；原始正文不得落库、回传或输出到普通日志；
3. 将 Adapter 规范化结果接入生产 Pipeline，移除内联分类作为厂商业务信号的权威来源；
4. 资源状态迁移仍保留一个权威写入点，规则引擎不得形成第二套并行状态机。

| 统一信号 | 典型原始信号 | 默认动作 | 恢复 |
| --- | --- | --- | --- |
| `RATE_LIMIT_RETRY_AFTER` | 429 + `Retry-After` | 临时熔断 | 到 `Retry-After` |
| `QUOTA_EXHAUSTED` | 额度耗尽 + `resetTime/next_flush_time` | 额度熔断 | 到上游重置时间 |
| `PLAN_EXPIRED` | Coding Plan 过期 | 硬熔断 | 人工续费后恢复 |
| `MODEL_UNAUTHORIZED` | 套餐不含模型／模型权限不足 | 硬熔断 | 修改模型或权限后恢复 |
| `UPSTREAM_MAINTENANCE` | 上游明确维护／下线／不可用 | 硬熔断 | 按上游时间或人工恢复 |
| `CONFIGURATION_ERROR` | 模型代码不存在、参数错误 | 预警 | 修正配置；不熔断资源 |
| `TECHNICAL_FAILURE` | 5xx、超时、连接失败 | 预警／降级 | 成功后自动清除预警 |

智谱第一版至少覆盖：`1211` 配置错误；`1302/1305` 临时限流／负载；`1308/1310` 额度；`1309` 套餐过期；`1311` 模型无权限。Kimi 以实际官方响应字段和已验证错误为准，不凭推测写死业务码。

### 3.3 规则作用域和优先级

作用域从具体到一般：

1. 指定厂商资源 + 上游模型；
2. 指定厂商资源；
3. 指定厂商 + 上游模型；
4. 指定厂商；
5. 系统默认。

同作用域冲突时：

- 硬熔断优先于允许；
- 计划熔断和上游信号熔断分别保留来源，不互相覆盖历史；
- 优先级数值只解决同类型、同作用域规则冲突；
- 发布前必须给出确定性命中结果，禁止运行时随机选择。

### 3.4 规则生命周期

| 状态 | 可做操作 | 说明 |
| --- | --- | --- |
| `DRAFT` | 直接编辑、删除、预览、发布 | 尚未进入热路径 |
| `PUBLISHED` | 编辑为新版本、停用、复制、查看影响 | 历史内容不可原地覆盖 |
| `SUPERSEDED` | 查看、复制、回滚为新版本 | 已被新版本承接 |
| `DISABLED` | 查看、重新启用为新版本 | 不进入匹配 |

编辑语义：管理员始终看到“编辑”；若对象为 `PUBLISHED`，后台复制当前值生成新版本，并自动设置新旧版本的生效边界。回滚同样生成新版本，不把旧记录重新改成当前记录。

### 3.5 规则管理必备能力

- 添加、编辑、复制、启用、停用；
- 立即生效和预约生效；
- 历史版本、版本差异、回滚；
- 作用范围和影响主体预览；
- 模型、资源、时区、时间窗合法性校验；
- 跨午夜时间窗和夏令时确定性处理；
- 并发编辑使用单调 `version` 乐观锁；
- 发布前冲突检查；
- 完整操作日志；
- 已发生事件冻结 `rule_id/rule_version`，历史不重算。

### 3.6 第一版规则字段

| 字段组 | 字段 |
| --- | --- |
| 基本信息 | 规则名称、规则类型、说明、优先级、启用状态 |
| 作用范围 | 厂商、厂商资源、统一模型、上游模型；允许逐级留空形成上级默认 |
| 信号条件 | 统一信号；原始业务码只在 Adapter 映射和详情页展示，不允许管理员自由写正文正则 |
| 执行动作 | `WARN_ONLY`、`BLOCK` |
| 恢复方式 | `RETRY_AFTER`、`UPSTREAM_RESET_TIME`、`FIXED_DURATION`、`SCHEDULE_END`、`MANUAL` |
| 时段配置 | 时区、星期、开始时间、结束时间；仅计划熔断使用 |
| 版本配置 | 生效时间、失效时间、规则版本、乐观锁版本 |

硬熔断规则必须明确恢复方式。若配置为读取上游 `Retry-After/resetTime`，但实际响应没有该字段：

- 规则同时配置了固定兜底时长时，按兜底时长恢复；
- 没有兜底时长时，不得编造恢复时间，降为预警并把“缺少恢复字段”写入异常中心。

这样既坚持“熔断由上游信号触发”，也避免一个缺少恢复时间的 429 把资源永久封死。

## 4. 人员、主体和企业微信身份

### 4.1 对象关系

“人员”是自然人主数据；“使用主体”是额度、Key、计量和项目归因对象；两者不得混为一个表。

```text
人员 person
├── 人主体 principal(type=EMPLOYEE) ── person_id
├── 项目主体 principal(type=PROJECT) ── owner_person_id
└── 外部身份 person_external_identity(provider=WECOM) ── userid
```

### 4.2 第一版约束

1. 每个人主体必须关联一个有效人员；
2. 每个启用的项目主体必须有一个有效项目负责人；
3. 一个人可以负责多个项目；
4. 一个企微 `userid` 在当前系统内只能绑定一个有效人员；
5. 人员停用前必须检查其负责的启用项目并完成负责人移交；
6. 没有企微身份不阻止主体使用 Gateway，但页面必须明确显示“无法企微提醒”；
7. 人员必须具有有效企微 `userid` 且位于应用可见范围；否则不阻止模型调用，但必须记录“个人企微消息未送达”和具体错误码。

### 4.3 最小人员字段

- `name`；
- `department_label`；
- `status`；
- `version`；
- `created_at/updated_at`。

企微身份最小字段：

- `person_id`；
- `provider=WECOM`；
- `provider_user_id`（第一版存企业微信内部成员 `userid`，不是外部联系人 `external_userid`）；
- `status`；
- `verified_at`；
- `version`。

## 5. 熔断事件和运行状态

### 5.1 健康与可用性分离

避免继续用一个 `UNAVAILABLE` 混合所有语义：

- 健康状态：`ACTIVE / DEGRADED`；
- 可用性决定：`ALLOW / BLOCKED_UPSTREAM / BLOCKED_SCHEDULE`；
- 凭证／额度事实仍保留 `CREDENTIAL_INVALID / EXPIRED / EXHAUSTED`，但必须映射为明确的可用性原因。

普通技术故障只改变健康状态和异常中心，不直接写入硬熔断状态。

现有 `provider_resource.status` 六态在第一版继续保留，运行态势通过“资源事实 + 活跃可用性事件”派生，不直接新增第二个可写状态列：

| 现有资源状态 | 健康展示 | 可用性展示 | 第一版处理口径 |
| --- | --- | --- | --- |
| `ACTIVE` | 正常 | `ALLOW` | 无活跃熔断事件时允许请求 |
| `DEGRADED` | 预警 | `ALLOW` | 技术故障只预警／降级，不因连续失败硬熔断 |
| `EXHAUSTED` | 正常或预警 | `BLOCKED_UPSTREAM` | 仅在 Adapter 确认额度信号并产生活跃事件后阻断 |
| `EXPIRED` | 正常或预警 | `BLOCKED_UPSTREAM` | 仅在确认套餐／资源过期后阻断，人工续费后恢复 |
| `CREDENTIAL_INVALID` | 预警 | `BLOCKED_UPSTREAM` | 凭证明确无效时阻断，修复凭证后恢复 |
| `UNAVAILABLE` | 需迁移判定 | 不直接映射 | 这是既有混合态；按最近失败分类、状态原因和活跃事件拆分。技术性 5xx／超时回填为 `DEGRADED + ALLOW`，明确上游或计划信号才形成 `BLOCKED_*` |

W01/W05B 必须提供既有 `UNAVAILABLE` 数据的只读盘点、迁移规则和 Shadow 对比；禁止把历史 `UNAVAILABLE` 批量等同于新硬熔断。

### 5.2 事件生命周期

`OPEN → RECOVERED`；人工关闭使用 `MANUALLY_RECOVERED`，取消错误规则产生的事件使用 `CANCELLED` 并保留原因。

每个事件至少保存：

- 厂商、资源、统一模型、上游模型；
- 统一信号和脱敏原始码；
- 命中的规则 ID／版本；
- 触发请求和主体；
- 开始、预计恢复、实际恢复时间；
- 恢复方式；
- 影响请求数、影响人员数；
- 当前状态；
- 通知结果摘要。

### 5.3 去重

同一资源、模型、信号、规则版本和恢复窗口只生成一个活跃事件。在途请求只追加影响计数，不重复延长恢复时间，除非收到上游新的明确恢复时间。

同一熔断事件对同一人员：触发通知一次，恢复通知一次。

## 6. 客户端中文反馈

### 6.1 Gateway 新增错误合同

`recover_at`、`event_id` 为本模块新增合同字段，并非现有错误体的展示调整。W04 必须同步修改 `packages/contracts/src/northbound.ts`、Gateway `error-envelope` 及 OpenAI／Anthropic 两条协议转换；OpenAI 和 Anthropic 兼容错误保持各自外层协议，同时统一内部字段：

```json
{
  "error": {
    "code": "upstream_quota_exhausted",
    "message": "智谱 glm-5.2 的上游额度已耗尽，预计 8 月 3 日 11:00 恢复。",
    "retryable": true,
    "recover_at": "2026-08-03T11:00:00+08:00",
    "event_id": "BRK-20260731-001"
  }
}
```

有明确秒数时同时返回标准 `Retry-After`。没有可靠恢复时间时不得编造时间，应显示“等待管理员处理”或“等待上游恢复”。

中文 `message` 只能由规范化信号、允许字段和本地模板生成。上游原始正文、请求头、凭证、企业微信应用 Secret 和 access token 不得写入客户端错误、数据库普通字段、Evidence、Trace 或普通日志。

### 6.2 展示边界

- WorkBuddy、Claude Code、ZCode：以显示中文 `message` 为验收底线；
- 仟流自有 Agent／IDE：后续可将同一错误合同渲染为弹窗，不在本版本强制；
- 流式响应提交前可返回标准错误；提交后不得切换上游，只能按现有流式中断合同结束并记录事件。

## 7. 企业微信成员定向通知

### 7.1 第一版范围

整个试验系统配置一个企业微信自建应用，使用成员应用消息 API 按 `userid` 直接发送到对应人员自己的企业微信。发送两类固定模板：

1. 熔断触发；
2. 熔断恢复。

通知接收关系：

- 人主体：关联人员；
- 项目主体：项目负责人；
- 从人员的企微身份读取 `userid`，向本人发送应用消息；
- 同一事件涉及多个主体时，人员去重后每人只发送一次。

### 7.2 固定消息内容

触发消息包含：资源／模型、中文原因、影响主体、开始时间、恢复时间、是否有备用资源、事件编号和后台详情链接。

恢复消息包含：资源／模型、实际恢复时间、持续时长、影响请求数和事件编号。

### 7.3 安全和可靠性

当前 `apps/worker` 是单次 reconciliation CLI，不是持续调度服务。为避免调度骨架与业务任务混为一个交付物，拆成两个子工作包：W05A 建立可部署的持续执行基础（启动／停止、租约、并发互斥、Outbox 领取、幂等、健康检查）；W05B 实现到期事件恢复、状态聚合和恢复 Outbox 业务任务。W06 只在该基础上接入企微发送。具体可采用常驻 Worker 或平台周期任务，但生产必须有唯一明确的调度责任方。

- `CorpID`、`AgentID` 可配置；应用 Secret 加密保存，只展示掩码和指纹；
- 使用应用 Secret 获取并缓存 `access_token`，按官方有效期刷新；Secret 和 token 不得出现在日志、Trace、数据库普通字段、操作日志和错误响应中；
- 仅允许企业微信官方 API Host，防止 SSRF；
- Gateway 事务只写 Outbox，不同步等待企微；
- Worker 异步发送，指数退避并设次数上限；
- 企业微信 API 超时、限频、无效 `userid` 或不在应用可见范围时只记录和告警，不回滚熔断事件、不阻塞模型请求；
- 提供“选择一名人员测试发送”，结果写操作日志；
- 第一版不做消息内容自由模板，避免敏感字段误配和格式失控。

## 8. 数据设计候选

当前主本地项目目录的迁移文件最大为 `0019`；权威 `仟流智算-stage-state-v0.3.yaml` 同时记录 Mac Mini 已部署数据库升至 `0029`。因此开发前必须先把 `0020～0029` 的迁移文件和对应代码完整同步回主本地项目目录，再从本地完整迁移链领取下一个可用编号（预期不小于 `0030`）；本计划不自行猜测或硬编码迁移号。

### 8.1 Local First 开发基线

运行保障坚持 Local First：`/Users/mac/Projects/仟流智算` 主本地项目目录是开发唯一事实源，本机完成编码、迁移、测试和 Evidence；Mac Mini 是部署与验收目标，其他本地副本和已部署文件只能作为比对／同步来源，不能反过来决定开发流程。

冻结规则如下：

1. 先对主本地项目目录做时间点快照和文件清单，保留并标明已有修改，不覆盖、不丢弃；
2. 将已经部署但主本地目录缺少的 `0020～0029` 迁移及对应源码同步回主本地目录，并逐文件核对；
3. 用本地数据库执行从空库到最新版本的完整升级、回滚、重升，确认本地 Schema 与 Mac Mini 当前 Schema 一致；
4. W01 Evidence 保存本地源码清单、迁移清单、Schema 指纹、测试结果和差异处置记录；
5. 后续所有运行保障开发只在主本地项目目录推进，完成本地门禁后再部署到 Mac Mini；若 Mac Mini 临时发生变更，必须先同步回本地并验证，禁止直接以远端状态继续开发。

### 8.2 新增表

W01 已通过 `ADR-RUNTIME-ASSURANCE-FOUNDATION` 决定采用“稳定规则身份 + 不可变版本”双表。既有 `billing_rule`、`dispatch_policy` 的单表版本模式适合按版本直接消费；运行保障规则还需要稳定的管理身份、草稿／发布状态、预约生效、回滚派生和事件冻结查询。双表可以让 `availability_rule` 承载稳定身份和启停状态，让 `availability_rule_version` 承载不可变规则快照，避免在单表中混合管理态与运行态。该决定只适用于运行保障规则，不追溯改造既有计费或调度表。

试验版所有新增表均属于同一个本地工作空间，不新增 `tenant_id`、`enterprise_id`、企业配置表、企业选择器或租户隔离中间件；`notification_endpoint` 只允许一条有效系统配置。未来若产品转向多公司服务，必须另立 Planning Change，不能在本模块中预埋半套多租户结构。

| 表 | 用途 |
| --- | --- |
| `person` | 自然人主数据 |
| `person_external_identity` | 人员与企微 userid 映射 |
| `availability_rule` | 可用性规则稳定身份 |
| `availability_rule_version` | 草稿／发布／历史版本和有效期 |
| `availability_event` | 熔断触发、影响和恢复事实 |
| `notification_endpoint` | 企业微信应用 CorpID／AgentID、Secret 密文／指纹和状态 |
| `notification_delivery` | 触发／恢复通知的幂等发送、重试和结果 |

### 8.3 现有表变更

- `principal`：人主体增加 `person_id`；项目主体增加 `owner_person_id`；
- `provider_resource`：不继续增加模糊状态含义，逐步改由事件／可用性查询组合判断；
- `alert_event`：保留异常中心事实表，增加与可用性事件的可选关联，不复制熔断事实；
- `operation_log`：记录规则发布、回滚、人员绑定、负责人变更、企微应用配置／测试和人工恢复。

### 8.4 不可变边界

- 已发布规则版本不可覆盖；
- 熔断事件不可删除，只能追加恢复／取消；
- 通知发送记录不可编辑；
- 企业微信应用 Secret 和 access token 不可回显；
- 上游响应正文不落库，只保存稳定业务码、必要恢复字段和脱敏摘要。

## 13. 发布、迁移和回滚

### 13.1 发布顺序

1. 从当前生产发布候选拉取并确认下一迁移编号；
2. 生产备份与恢复演练；
3. 上线加法迁移和后端读路径，运行模式默认为 `OBSERVE`；
4. 导入人员、主体关系和项目负责人，不启用外部通知；
5. 配置企业微信应用凭证和可见范围，选择试点人员执行脱敏测试发送；
6. 启用运行保障页面和异常中心新入口；
7. 规则先以只记录模式观察至少一个业务窗口；
8. 逐厂商启用硬熔断执行；
9. 开启触发／恢复通知；
10. 生产只读核验和业务签字。

### 13.2 运行模式与通知开关

第一版不把“规则评估”做成独立开关，而是采用一个三级运行模式：

| 模式 | 系统行为 | 使用场景 |
| --- | --- | --- |
| `OFF` | 不执行规则判断，不产生 Shadow 命中或新熔断事件 | 功能整体停用或紧急回退 |
| `OBSERVE` | 执行规则判断，只记录 Shadow 命中和预警；不阻断请求、不创建正式熔断事件、不发送熔断通知 | 新规则上线观察、验证误判率 |
| `ENFORCE` | 执行规则判断，命中后按规则熔断、记录事件并进入通知链路 | 正式运行 |

另设一个企微通知总开关：

- `RUNTIME_ASSURANCE_MODE=OFF|OBSERVE|ENFORCE`；
- `RUNTIME_ASSURANCE_WECOM_NOTIFY=true|false`。

两项均由本地部署配置提供，服务启动时严格校验；修改后滚动重启。企微开关只控制正式熔断／恢复消息，测试发送仍由管理员明确操作。

当前只有一家公司、约 10 名内部用户。管理员在同一后台添加、编辑、启停厂商／模型／资源规则，例如只停用 Kimi 规则而继续使用智谱。运行模式用于全系统上线观察和严重故障回退，不作为日常厂商管理工具。规则停用不会自动撤销已经打开的熔断事件，仍需受控恢复／取消。

### 13.3 回滚

- 应用回滚：恢复上一发布包；
- 功能回滚：关闭执行／通知开关，Gateway 回到既有路由；
- 规则回滚：发布历史规则的新版本；
- 数据库：迁移前执行备份和回滚演练；产生正式人员、事件和通知记录后优先保留加法 Schema，不做破坏性降级；
- 企微通知：立即停用 endpoint；若凭证疑似泄露则轮换应用 Secret；
- 熔断误判：取消对应事件，记录规则版本和恢复原因，不删除历史。

## 16. 最终判断

本模块不是单一“熔断开关”，而是仟流智算对资源可用性的正式管理入口。第一版保持通知渠道简单，只做客户端中文提示和按 userid 发送的企微成员应用消息，不建设通知群或群机器人；但规则管理、人员关系、事件事实、恢复、审计和测试闭环不能省略。开发按“先规则和事实、再执行、再通知、最后页面与生产灰度”的顺序进行。
