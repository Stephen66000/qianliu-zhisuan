## POOL-001 峰谷计价/扣减规则缺少完整配置闭环

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是**功能缺陷，不是使用问题**，按 **P0** 修复。5 个缺口及独立复核发现的问题均已修复，代码验收通过，问题关闭。

### 现象

额度规则页面只能填写固定 Token 单价，无法配置时区、每日时间窗、星期和额度倍率，导致 DeepSeek V4 分时 API 价格与智谱 Coding Plan 高峰扣减倍率无法正确设置。

### 影响

- 管理员无法仅通过 Web 完成峰谷计价与套餐额度扣减规则配置。
- DeepSeek 分时 API 成本可能按错误价格结算，影响成本、账单和利润数据。
- 智谱 Coding Plan 高峰使用量可能未按 3 倍扣减，影响套餐额度准确性。
- API 费用规则与套餐 Token 扣减倍率可能被错误混用，造成计费语义污染。
- 缺少命中规则版本与时段解释，账本结果难以审计和复核。

### 业务规则

1. **DeepSeek**：北京时间每日 `09:00–12:00`、`14:00–18:00`，缓存命中、缓存未命中输入、输出价格均为低谷价格 2 倍。该规则影响 API 费用，不应写成套餐 Token 扣减倍率。
2. **智谱**：北京时间每日 `14:00–18:00`，使用量按 3 倍扣减；非高峰倍率按当期套餐/活动版本配置。

### 根因证据

- `apps/web/src/pages/QuotaRules.tsx` 的 `BillingRuleSchema` 和表单没有 `timezone`、`days_of_week`、`start_time`、`end_time`、`multiplier`。
- `apps/control-api/src/read-models/routes.ts` 的 `CreateBillingRuleSchema` 和 `POST /billing-rules` 没有接收、下传时间窗字段。
- `packages/domain/src/billing-rule.ts` 的 `matchPriceRule` 只按资源、模型和生效日期匹配 `API_PRICE`，没有判断时间窗，因此 DeepSeek 分时价格即使写入数据库也不会命中。
- 数据库 `billing_rule` 表已经具备 `timezone`、`days_of_week`、`start_time`、`end_time`、`multiplier`，问题属于上层配置与执行闭环漏项。

### 建议修复范围

1. **API 价格分时规则**：补齐前端配置、创建/编辑 API，以及 `API_PRICE` 的时区、星期、时间窗和分时单价匹配。
2. **套餐用量分时倍率**：独立配置套餐额度扣减倍率，补齐前端、接口与结算执行链路，不与 API 价格规则混用。
3. **多时间窗口**：同一规则支持多个时间窗口，例如 DeepSeek 每日 `09:00–12:00`、`14:00–18:00` 两个高峰段。
4. **基础规则与高峰规则优先级**：明确基础规则、高峰规则及重叠时间窗的命中优先级，保证结果唯一且可解释。
5. **生效日期和规则版本**：支持生效区间、规则来源、版本留存与历史追溯；新版本不得重算历史账本。
6. **账本命中信息展示**：在账本或结算详情展示命中的规则版本、时段、单价或倍率版本。

配套验证：补齐单元测试、接口测试和真实 Web E2E。

### 验收标准

1. **API 价格分时规则**：管理员可仅通过 Web 配置 DeepSeek 分时 API 价格；峰内、峰外及 `12:00`、`14:00`、`18:00` 边界结算正确。
2. **套餐用量分时倍率**：管理员可仅通过 Web 配置智谱每日 `14:00–18:00` 的 3 倍扣减及当期非高峰倍率；峰内、峰外及 `14:00`、`18:00` 边界扣减正确。
3. **多时间窗口**：同一规则可保存并正确执行 DeepSeek 每日 `09:00–12:00`、`14:00–18:00` 两个高峰窗口。
4. **规则优先级**：基础规则、高峰规则或时间窗重叠时，系统按明确优先级唯一命中；API 价格与套餐扣减语义隔离，不互相误用。
5. **生效日期和规则版本**：规则只在配置的生效区间内命中；版本可追溯，新版本不影响历史账本、不触发历史重算。
6. **账本命中信息展示**：页面或账本详情可明确展示实际命中的时段、单价或倍率版本，以及对应规则版本。

配套验收：单元测试、接口测试和真实 Web E2E 覆盖上述场景并通过。

## POOL-002 官方 Codex 接入协议与模型权限门禁缺失

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：待业务验收（代码缺陷已关闭）

### 结论

官方 Codex 客户端接入协议和主体 Key 模型权限门禁均未形成闭环，属于影响可用性、权限隔离与费用安全的 **P0 功能缺陷**。代码缺陷已修复并通过代码验收；正式业务验收仍需真实厂商凭证与独立 IDE/App E2E，当前不能直接发给同事使用。

### 现象

员工使用官方 Codex 并配置管理员分配的仟流主体 Key 后，仍无法使用仟流统一模型；同时系统不能保证该 Key 只能使用管理员分配的模型。

### 影响

- 官方 Codex CLI、IDE、App 无法通过仟流 Gateway 正常使用统一模型。
- 主体 Key 的模型授权配置无法约束模型列表和实际调用，存在越权调用风险。
- 未授权请求可能进入上游调用链，产生非预期费用并破坏企业模型权限边界。
- Responses API 的 Usage 若未完整映射，账本可能丢失输入、输出、缓存或推理 Token。
- Key 停用、重置和模型撤权若不能即时生效，会留下持续访问窗口。

1. 官方 Codex 自定义 Provider 当前使用 Responses API；仟流智算当前只支持 `/v1/chat/completions`、`/v1/messages`，`/v1/responses` 明确标记为 `UNSUPPORTED` 并返回 `422`。

3. 相关代码位置：
   - `packages/contracts/src/northbound.ts`

   - `apps/gateway/src/routes/models.ts`

3. **主体 Key 模型权限硬门禁**：让 `allowed_model_ids` 同时约束 `GET /v1/models` 查询结果和所有请求热路径；未授权模型必须在访问任何上游前拒绝，并覆盖撤权、Key 停用与重置即时生效。
4. **真实客户端 E2E**：使用官方 Codex CLI 和实际使用端验证非流式、流式、工具调用、模型过滤、越权拒绝、撤权及账本归因，并保存完整证据。

## POOL-003 调度策略管理闭环缺失

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：已关闭

### 结论

Gateway 热路径已经支持按时段执行 `REJECT`，但管理后台缺少调度策略的新建、校验、发布、停用页面及写接口，导致管理员无法通过 Web 配置“智谱高峰期禁止使用”。这是管理与执行链路未闭环的 **P0 功能缺陷**。管理、发布、热路径与审计闭环已补齐，代码验收通过，问题关闭。

### 现象

管理员需要设置智谱北京时间每日 `14:00–18:00` 不可使用，但现有页面只能配置计价或套餐用量倍率。调度策略只有查询能力，没有新建和发布入口，无法把硬拒绝规则投入 Gateway 热路径。

### 影响

- 管理员无法通过 Web 实施高峰期资源禁用策略。
- 将倍率设为 `0` 或较大数值都不能形成调用硬门禁。
- 高峰期请求仍可能消耗智谱套餐额度或产生非预期费用。
- 策略发布、版本、命中结果和操作过程无法形成完整审计闭环。

### 建议修复范围

1. 增加调度策略新建、校验、发布、停用接口。
2. 增加管理后台调度策略配置页面。
3. 支持按厂商资源、统一模型、资源模式、主体范围、时区、星期和时间窗口匹配。
4. 支持 `REJECT / SWITCH / RATE_LIMIT` 等动作，并明确无替代资源时的行为。
5. 支持策略版本、优先级、状态、来源及操作日志。
6. 在请求下钻和调度决策账本中展示命中策略、版本、时段、动作及原因。

### 验收标准

1. 管理员可仅通过 Web 创建并发布智谱 `14:00–18:00`、`Asia/Shanghai`、每日生效的 `REJECT` 策略。
2. `13:59` 请求允许；`14:00–17:59` 返回 `403 dispatch_rejected`；`18:00` 恢复允许。
3. 被拒请求不访问上游、不扣套餐额度、不产生上游费用。
4. 调度决策记录包含策略 ID、版本、匹配时段、最终动作和拒绝原因。
5. 策略停用后立即不再命中，历史决策记录保持不变。
6. 单元测试、接口测试和真实 Web/Gateway E2E 覆盖上述边界并通过。

### 特别约束

- “绝对禁用”必须使用 `REJECT`。
- 当前 `SWITCH` 在没有可用替代资源时会退回允许原资源，不能代替硬拒绝；如业务需要“优先切换、无目标则拒绝”，应提供明确的 `SWITCH_OR_REJECT` 语义并独立验收。

### 修复与验收记录

- 已增加调度策略草稿创建、引用校验、确认发布、停用、全状态查询与企业隔离写接口，状态机固定为 `DRAFT → VALIDATED → PUBLISHED → RETIRED`。

- Gateway 使用请求开始时刻做确定性匹配，决策快照冻结实际命中的时区、星期和起止时段。
- Gateway 边界集成测试验证 `13:59:59` 放行、`14:00` 和 `17:59:59` 拒绝、`18:00` 恢复；峰内不访问上游、不扣额度。
- Control API 接口测试和 Chromium 真实 Web E2E 已覆盖创建、校验、发布与停用闭环。

## POOL-007 WorkBuddy 工具回合复用请求 ID 触发主键冲突

- **严重级别**：P0
- **发现时间**：2026-07-31（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是 Gateway 请求 ID 与幂等语义没有闭环导致的 **P0 功能缺陷**，不是
WorkBuddy 使用问题。迁移 `0024` 与 Gateway 已发布生产，生产 API、真实
WorkBuddy、数据库和账本验收均证明原 `23505/ai_request_pkey` 缺陷消失；
但真实工具任务最终仍因唯一 Kimi 上游进入冷却而返回 503，完整业务验收未通过，
状态退回“待业务验收”，由独立的 POOL-008 跟踪新根因。

### 现象

- WorkBuddy `5.2.5` macOS 使用生产 Gateway 和 `Kimi` 时，普通文本流式回复正常。
- 发送“调用终端创建文件并读取”的真实工具任务后，客户端展示 `500 Unknown error`，错误码为 `23505`。
- 对应客户端请求 ID 为 `db4f2a81-dde0-6871-3d9a-1c76e1528e02`；该 ID 的首条请求已经成功结算，工具后续回合再次使用同一 ID 时失败。

### 影响

- WorkBuddy 通过仟流 Gateway 的真实工具调用无法稳定完成。
- 任何复用 `x-request-id` 做重试、续接或多回合工具调用的客户端都可能触发相同故障。
- Gateway 向客户端泄漏数据库错误码并返回不可解释的 500，客户端无法安全判断重试或恢复方式。
- 首次成功请求已经产生上游调用和账本；后续重放若处理不当，存在重复调用、重复费用或重复结算风险。

### 根因证据

1. `apps/gateway/src/plugins/request-id.ts` 对格式合法的客户端 `x-request-id` 无条件采用，并注释为“幂等重试”。
2. `apps/gateway/src/pipeline/real-pipeline.ts` 在进入上游前直接以 `request.requestId` 创建请求意图。
3. `packages/database/src/repositories/gateway-ledger-repository.ts` 的 `createRequest` 对 `ai_request` 执行普通 `INSERT`，没有 `ON CONFLICT`、重放状态识别或已完成响应返回。
4. 生产 PostgreSQL 日志于 `2026-07-31 02:29:18.269 UTC` 明确记录：
   - `duplicate key value violates unique constraint "ai_request_pkey"`；
   - `Key (id)=(db4f2a81-dde0-6871-3d9a-1c76e1528e02) already exists`。
5. 数据库中该请求原记录状态为 `SUCCEEDED`、账本状态为 `SETTLED`，`idempotency_key` 为空，证明冲突对象是 `ai_request.id`，不是 `idempotency_key`。

## POOL-008 单套餐多主体共享调度缺失导致 WorkBuddy 返回无可用资源

- **严重级别**：P0
- **发现时间**：2026-07-31（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是套餐共享调度和资源降级策略缺陷，不是 WorkBuddy 使用问题，也不能要求用户
再购买一份套餐规避。产品的核心业务规则是：一个 Coding Plan 厂商资源可以授权
给多个主体使用，Gateway 必须允许多个主体在厂商套餐并发范围内同时调用，并在
超过管理员配置上限时等待、限流和准确分账。不能把共享实现成“一人用完、下一人
再用”的串行队列。下游保留每位员工独立 Key、权限、额度和账本，上游统一复用同
一个 `provider_resource` 套餐凭证；厂商看到的是同一套餐身份下的多条并发请求，
不是把多条请求伪造成一条。原实现没有完成这个闭环；一次上游限流会立即把唯一套餐资源置为
`UNAVAILABLE`，冷却期间后续工具回合直接返回
`503 no_healthy_candidate`。

### 现象

- WorkBuddy `5.2.5` macOS 已成功完成文本流式回复和终端文件创建、读取。
- 同一工具任务的最终回合显示：
  `503 无可用上游资源 (71b69fd73f2bceec755a0c77ed53534e/928b4ebc-0bfa-4dd1-93f0-049cd8fb1754)`。
- 客户端错误码为 `custom-model-503`，Request ID
  `27819137ffbd4cb6a914f90ed0ae0f20`，Trace ID
  `4379dcb1bbc2d2b4143881d986928852`。
- 资源冷却后自动恢复为 `DEGRADED`，但已发起的 WorkBuddy 工具任务不会自动恢复，
  用户仍然得到失败结果。

### 影响

- WorkBuddy 可在普通回复后于工具回合中途失败，不能作为稳定业务入口交付。
- 一个已购买的 Coding Plan 无法稳定分给两个人使用，直接违背产品核心目标。
- 单一资源的任意瞬时限流都会扩大成该模型对全体主体的短时不可用。
- 并发请求中可能一条成功、另一条直接 503，用户看到的结果不稳定且难以解释。
- 只有自动冷却恢复，没有当前请求的公平排队和受控重试，恢复后仍需用户手工重试。

### 根因证据

1. 业务配置本身合法：生产数据库只有一个已购买的 `Kimi` Coding Plan 资源，
   但它需要由两个及以上主体共享；当前只有一条启用路由：
   - `provider_resource.id=e75fe982-c83b-46a7-9fcb-c7876754e5a9`；
   - `resource_pool_id=NULL`；
   - `api_fallback_enabled=false`；
   - 没有针对单套餐多主体共享的队列和公平调度策略。
2. `packages/domain/src/resource-lifecycle.ts` 对首次
   `UPSTREAM_RATE_LIMITED` 直接迁移为 `UNAVAILABLE`，冷却基数 30 秒。
3. `packages/database/src/repositories/resource-pool-repository.ts` 在冷却期硬过滤
   `UNAVAILABLE` 资源。
4. `apps/gateway/src/pipeline/real-pipeline.ts` 在过滤后候选为空时直接返回
   `503 no_healthy_candidate`，没有排队、短重试或单资源降级策略。
5. 生产状态事件记录 `ACTIVE → UNAVAILABLE`、原因 `RATE_LIMITED`、
   错误分类 `UPSTREAM_RATE_LIMITED`；随后半开探测成功恢复为 `DEGRADED`。
6. 同一 WorkBuddy 客户端追踪 ID 下，`c0930bc2-c39e-4bc8-ba28-3cb2f22b38e0`
   成功，紧随其后的 `4d98c91b-b0ef-4d95-9056-878dad95eade` 以
   `no_healthy_candidate` 失败，证明是资源准入问题而非 POOL-007 主键冲突。

### 建议修复范围

1. 把 `provider_resource.concurrency_limit` 作为真实上游并发上限执行，不得使用
   默认 100 放大请求；管理员可按套餐能力配置。
2. 每个套餐资源支持管理员配置正整数并发上限（可按 2、4、5 等实际员工规模和
   厂商套餐能力调整）；上限以内必须真正并行，不得串行互斥。
3. 为每个套餐资源建立跨 Gateway 实例共享的有界信号量；只有超过配置上限的请求
   才短暂等待，禁止某一主体或工具任务长期独占。
4. 资源槽位暂满属于容量调度，不等于资源故障；请求应等待或返回明确的
   `resource_busy + retry_after_ms`，不得直接把资源标记为不可用。
5. 区分厂商 429 的引擎拥塞、并发限制、5 小时窗口耗尽和月度额度耗尽；首次瞬时
   429 不得立即全局隔离唯一套餐资源，优先遵循上游 `Retry-After`，在请求
   总时限内执行受控退避重试，持续失败达到阈值后才进入熔断。
6. 工具多回合的每次真实上游调用独立获取和释放槽位，同时保留主体、会话和账本
   归因；客户端等待、取消或断流必须释放队列位置和并发租约。
7. 半开探测增加原子探测权和并发保护；第二套餐、同池账号或 API 兜底只能作为
   可选扩容能力，不能作为两人共享一份套餐的必要条件。
8. 503 仅用于资源真实不可恢复；并发等待超时返回 429、稳定错误码和
   `retry_after_ms`；增加模型拥塞、等待长度、限流和恢复告警。
9. 补充单套餐 2～5 个主体并发、429、等待、取消、超时、冷却、半开、工具多回合、
   多 Gateway 实例和账本不重复测试。

### 验收标准

1. 只配置一份 Kimi Coding Plan，管理员可把并发上限设为 2、4 或 5；对应数量
   的不同主体可同时发起普通回复和工具任务，最终均成功，不需等待前一个主体结束。
2. 实际访问上游的并发数始终不超过资源配置上限；超出的请求公平排队，不出现
   `custom-model-503`，也不会饿死其中一个主体。

   正确获取、释放上游槽位，客户端取消后无租约泄漏。

6. 排队超时或资源确实不可服务时返回稳定错误码和 `retry_after_ms`，不伪装成
   “模型未配置”或无解释 503。
7. 两个主体的额度、Usage 和费用分别归因；每个内部请求的 Attempt、Usage、
   Ledger Line 和 Ledger Transaction 唯一，
   失败与重试不伪成功、不漏账、不重复结算。
8. Gateway 单元/集成测试、生产 Kimi 单套餐双主体冒烟及 WorkBuddy `5.2.5` macOS、
   `5.3.5` Windows E2E 全部通过并保存证据。

## POOL-010 厂商资源额度与金额没有独立数据闭环

- **严重级别**：P0
- **发现时间**：2026-07-31（Asia/Shanghai）
- **状态**：已关闭（生产业务验收通过）

### 结论

这是资源经营数据模型缺失和首页统计口径错误导致的 **P0 功能缺陷**。厂商资源页
没有记录或展示厂商账号的总额度、已用、剩余、金额和周期；首页却把分配给使用
主体的额度合计标成“总额度”，混淆了“企业从厂商购买多少”和“企业给员工分配
多少”两个完全不同的事实。附件二与附件五属于同一根因，合并处理。

### 现象

- 厂商资源列表只能看到名称、厂商/模型、模式、凭证指纹、状态和创建时间，看不到
  套餐总额度、已用、剩余、有效期和重置时间，也看不到 API 充值、余额或套餐费用。
- 首页 Kimi “总额度”为 `220,000`、“已用额度”为 `451,239`，已用大于总额；
  该“总额度”实际是主体 Grant 的分配额度，不是 Kimi 厂商套餐总额度。
- DeepSeek API 的额度列为 `—`，页面也没有对应的充值金额、账户余额和累计费用
  口径，管理员无法判断厂商侧还剩多少钱。

### 影响

- 管理员无法从系统判断厂商资源还能用多久、是否需要充值或续费。
- 主体分配额度被误展示为厂商总额度，会造成错误的资源采购和超额判断。
- 预测耗尽和调度策略缺少可靠的厂商余额/剩余额度输入，可能在厂商资源耗尽后才
  被动发现。
- 厂商账单、内部账本和主体分配三套口径无法对账。

### 根因证据

1. `provider_resource` 表和 `ProviderResourceTable` 只有凭证、模型、并发、状态及
   健康字段，没有套餐费用、总额度、原生单位、已用/剩余、充值金额、余额、生效/
   失效/重置时间。
2. `apps/control-api/src/providers/routes.ts` 的创建、编辑和列表 DTO 没有接收或
   返回上述资源经营字段；`apps/web/src/pages/Resources.tsx` 因而无法配置和展示。
3. `DashboardRepository.sumProviderQuota` 从 `principal_grant.quota_value` 和
   `quota_counter.used_value` 聚合，并将结果映射为 `totalQuota/usedQuota`；这统计
   的是主体分配与扣减，不是厂商资源的购买额度与真实消耗。
4. 首页 `ResourceBreakdown` 没有“剩余额度”，也没有区分“厂商资源额度”和
   “主体已分配额度”；PRD §7.2、§10.2 已明确要求分别记录厂商资源的金额、总额、
   已用、剩余及周期。

### 建议修复范围

1. 为厂商资源建立版本化经营字段：
   - API：币种、充值金额、当前余额、累计费用、余额更新时间；
   - 套餐：套餐名称、套餐费用、厂商总额度、原生单位、已用、剩余、生效/失效、
     重置周期和下一重置时间。
2. 明确数据来源为“管理员录入 / 厂商接口同步 / 厂商账单对账”，每个快照保留来源、
   采集时间和版本；未知值显示未知，禁止用主体 Grant 推导厂商额度。
3. 补齐数据库迁移、创建/编辑 API、厂商资源 Web 表单与详情展示。
4. 首页资源摘要拆分展示“厂商总额度、厂商已用、厂商剩余”和“已分配给主体额度”；
   API 模式展示充值/余额，套餐模式展示 Token 或厂商原生额度，单位不能混算。
5. 供给预测、耗尽告警和调度策略改用实际厂商资源快照；主体额度仍独立按 Grant/
   Counter 计算。
6. 补迁移兼容、聚合口径、周期重置、数据来源、首页和真实 Web E2E 测试。

### 验收标准

1. 管理员可仅通过 Web 给 Kimi/智谱套餐录入或同步总额度、已用、剩余、费用、
   有效期和下一重置时间；三者满足一致口径并显示原生单位与更新时间。
2. DeepSeek API 可展示充值金额、当前余额和本月实际费用；未知值明确显示“未录入/
   未同步”，不显示伪造的 `0` 或主体分配额度。

   分配之和超过厂商额度，也不会把两者混为一列。
4. 厂商资源页与首页对同一资源的总额、已用、剩余、币种/单位和快照时间一致。
5. 历史资源快照和历史账本不因管理员修改当前额度而重算；周期重置产生新快照，
   可追溯旧周期。

### 处置记录

2. 前置对象为空时页面明确提示缺什么、去哪里创建，不能提交无效配置。

## POOL-014 Gateway 真实流式与 Kimi 稳定性保护闭环

- **严重级别**：P0
- **发现时间**：2026-08-01（Asia/Shanghai）
- **状态**：已关闭（完整验收、合并、生产发布和最小生产冒烟均完成）

### 现象

- Claude Desktop 经 CC Switch 调用 Kimi 时，多次在约 60 秒后收到上游 404 HTML，
  客户端误报 `claude-fable-5` 不存在。
- 同日 Kimi 返回 429 后，唯一资源进入熔断，Gateway 后续返回 503。
- Gateway 的 `stream:true` 代码路径会先聚合完整上游 SSE，再一次性生成北向响应，
  客户端无法在长生成期间持续收到事件。

### 影响

- Claude Desktop、Claude Code、CC Switch、Codex 和 WorkBuddy 等长流客户端可能在
  上游仍生成时被中间层或客户端误判超时。
- HTML/网络故障可能被第三方客户端重写成无关的模型错误，增加误诊。
- 唯一 Kimi 套餐资源遇到短时 429 后可能被长期排除，限流被放大成全员 503。
- 首字节、空闲、总时长和失败层缺少独立证据，无法判断 404 由 Gateway、反代还是
  厂商产生。

### 根因证据

1. `packages/provider-adapters/src/openai-compatible-caller.ts` 原实现完整消费 SSE、
   聚合文本与工具参数后才返回 `Outcome`。
2. `apps/gateway/src/pipeline/real-pipeline.ts` 原实现拿到完整 `Outcome` 后才写 Chat SSE；
   Messages 不处理 `stream:true`，Responses 也是缓冲式转换。
3. 资源状态机原先把连续 429 推入通用 `UNAVAILABLE`，没有独立 `RATE_LIMITED`；
   半开准入只有布尔标记，没有跨请求原子租约。
4. `upstream_attempt.first_byte_at` 字段虽已存在，但真实 Caller 没有写入；没有失败层字段。

## POOL-017 额度类数字输入缺少千分位防错展示

- **严重级别**：P1
- **发现时间**：2026-08-02（Asia/Shanghai）
- **状态**：已关闭（代码验收通过）

### 结论

这是大额 Token／用量配置的输入防错能力缺失。额度字段直接显示连续数字，例如
`30000000`，管理员难以快速判断数量级，容易多输或少输一个零；所有同类大整数额度
输入应统一采用千分位展示。

### 现象

- “Token 额度”等输入框直接展示无分隔的大整数。
- 页面缺少统一的额度数字输入组件，不同模块可能各自解析和校验。

- 额度可能被误配为预期值的 10 倍或十分之一，直接影响员工可用量和超额控制。
- 管理员需要反复数零，配置效率低，发布前也不易复核。
- 若各页面自行增加格式化，可能把逗号误传 API、造成游标跳动或精度错误。

1. 建立统一的非负整数额度输入组件，覆盖主体模型 Token 额度、套餐总额度、周期额度、
   用量校准值及其他同语义的大整数数量字段。
2. 输入和回显使用千分位，例如 `30,000,000`；支持粘贴 `30000000` 和
   `30,000,000`，保存前统一转换为无分隔整数。
3. 使用字符串完成编辑态解析和边界校验，避免 JavaScript 浮点数精度丢失；提交 API

4. 正确处理输入法、删除、选区粘贴和光标位置，不得在每次格式化后把光标强制跳到
   末尾。
5. 空值、`0`、最大值、负数、小数、字母、连续分隔符和超安全整数范围都要给出明确
   校验提示。
6. 本项只处理整数“额度／用量”字段；Token 单价等高精度小数字段不得套用整数千分位
   组件，应继续使用独立的十进制定点输入与展示规则。

1. 在任一额度输入框键入或粘贴 `30000000`，页面明确显示 `30,000,000`，保存后的
   实际值仍为 `30000000`。

6. Web 单元测试和 Chromium E2E 覆盖键入、粘贴、编辑、校验与提交，TypeScript、
   ESLint、生产构建和 `git diff --check` 全部通过。

## POOL-018 厂商套餐重置周期缺少每季和每年

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：已关闭（代码验收通过，尚未部署）

### 结论

这是厂商套餐额度周期建模的**功能缺口，不是使用问题**。当前“重置周期”
只支持不重置、每日、每周和每月，无法准确表达按季度或按年重置的厂商
套餐，按 **P1** 补齐前端、接口和周期计算闭环。

### 现象

- 厂商资源的“重置周期”下拉框只有“不重置／每日／每周／每月”。
- 管理员无法选择“每季”或“每年”，也无法保存对应的重置锚点。
- 若用“每月”或“不重置”代替，系统计算的当前额度周期与厂商真实账期不一致。

### 影响

- 按季度或年度购买的 Coding Plan／额度包无法按真实周期归集用量。
- 已用额度、剩余额度、下一重置时间及耗尽预测可能失真，进而影响告警和调度判断。
- 管理员只能手工换算或周期性修改配置，容易遗忘、错配或破坏历史可解释性。

### 根因证据

1. `apps/web/src/pages/Resources.tsx` 的 `reset_cycle` Schema 仅枚举
   `NONE / DAILY / WEEKLY / MONTHLY`，创建和编辑下拉框也只展示这四项。

## POOL-019 金额类输入与展示未统一保留两位小数

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：已关闭（代码验收通过，尚未部署）

### 结论

这是金额输入与展示规范未统一造成的**功能缺陷，不是使用问题**。金额字段直接
暴露数据库的八位小数文本，既影响可读性，也增加管理员录入和核对错误的风险，
按 **P1** 补齐全站金额格式化与输入校验闭环。此次只规范金额的交互边界，底层
计费、账本和数据库仍保留原有高精度。

### 现象

- 厂商资源运营数据中，充值金额显示为 `109.41000000`、当前余额显示为
  `68.00000000`、本期实际费用显示为 `47.41000000`。
- 历史配置快照继续原样展示八位小数，当前表单、历史记录和其他页面的金额格式
  不一致。
- 管理员无法从界面确认金额字段统一采用两位小数，也缺少对超出两位小数输入的
  明确约束和错误提示。

### 影响

- 金额信息噪声过多，充值、余额、费用及历史快照难以快速核对。
- 同一笔金额在不同页面可能显示为整数、两位或八位小数，降低账务可解释性。
- 若录入时无精度门禁，管理员可能误把高精度值当作有效金额保存，导致后续对账
  和人工复核产生歧义。

### 根因证据

1. `apps/web/src/pages/Resources.tsx` 将 `recharge_amount`、`current_balance`、
   `current_period_cost` 和 `cumulative_cost` 的接口字符串直接写入表单和页面，
   未经过统一金额格式化。
2. 同文件的历史快照文案直接插入 `snapshot.recharge_amount`、
   `snapshot.current_balance` 和 `snapshot.current_period_cost`，因此数据库返回的
   `numeric(24, 8)` 文本会原样显示为八位小数。
3. `apps/web/src/lib/format.ts` 已提供统一的 `formatMoney`，并固定保留两位小数；
   Dashboard、Usage 和 RequestDrilldown 已使用该方法，但厂商资源页面绕过了它。
4. `packages/database/migrations/0026_provider_resource_operating_snapshot.js` 将相关
   金额保存为 `numeric(24, 8)`；高精度存储本身合理，缺口位于前端输入和展示层，
   不应通过降低数据库精度解决。

### 建议修复范围

1. 盘点 Web 中所有“总金额”字段，包括充值金额、余额、本期／累计费用、API 总
   费用、套餐付款和节省金额等，统一复用金额格式化组件或函数，固定展示两位小数。
2. 创建、编辑表单的金额输入最多允许两位小数；允许输入 `109`、`109.4`、
   `109.41`，失焦或保存回显时分别规范为 `109.00`、`109.40`、`109.41`；超过
   两位时明确拒绝并提示，不得静默截断。
3. 列表、详情、确认信息、历史快照及导出（如有）采用同一规则；适合阅读的只读
   金额增加千分位，输入框不得因千分位破坏编辑、粘贴或光标位置。
4. 格式化只发生在输入和展示边界；接口、数据库、结算计算与账本继续保留原始
   精度，不重算历史数据，也不把二进制浮点误差写回金额字段。
5. Token 单价、缓存单价、输入／输出单价、汇率及其他需要高精度的小数**不属于
   本问题的两位小数范围**，不得格式化为 `0.00`。
6. 补 Web 单元测试和真实 Chromium E2E；若接口契约需要调整，同步补 Control API
   测试，并执行 TypeScript、ESLint、生产构建和 `git diff --check`。

### 验收标准

1. 全站所有总金额输入、列表、详情、确认信息和历史快照均固定显示两位小数；
   截图中的三个值分别显示为 `109.41`、`68.00`、`47.41`。
2. 金额输入接受零、一或两位小数并在失焦／保存后规范为两位；三位及以上小数、

3. 旧记录即使接口仍返回八位小数，也只在 UI 显示两位；数据库原值、计费结果、

5. 对历史账本只读聚合，不修改既有 `ledger_line`、`ledger_transaction` 和厂商快照。

## POOL-021 本月调度节省反事实成本恒等导致指标失真

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）

### 结论

这是调度节省计算未完成造成的**功能缺陷**。当前实际执行 `SWITCH` 时把反事实成本

### 现象

- 首页“本月调度节省（元）”长期显示 `0.00`。
- 即使调度把请求从原候选切换到另一资源，只要进入可计算分支，落库结果仍为 0。
- 页面无法展示原候选、实际候选、双方规则版本和节省计算依据。

### 影响

- 无法量化统一调度带来的真实费用收益，也无法判断切换是否反而更贵。
- 经营决策、资源采购和调度策略优化缺少可信数据。

### 根因证据

1. `apps/gateway/src/pipeline/real-pipeline.ts` 在 `SWITCH` 分支将
   `counterfactualCost` 直接赋值为 `actualCost`，随后计算二者差值，结果恒为 0。
2. `packages/domain/src/dispatch-policy.ts` 的差值公式已存在，但上游没有提供真实的
   原评分 winner 成本。
3. `packages/database/src/repositories/dashboard-repository.ts` 只负责汇总
   `saving_calculable=true` 且 `dispatch_saving` 非空的数据，无法修正错误输入。

### 建议修复范围

1. 在调度决策冻结原始 winner、最终资源、动作是否真实执行、请求时间和各自命中的
   价格／倍率规则版本。
2. 使用同一次请求的实际输入、输出、缓存和推理 Token，分别按原始 winner 与最终
   资源在当时有效的规则重放成本；`节省 = 原始候选成本 - 实际成本`。
3. API 资源按实际单价计算；套餐资源只有在存在可比较的货币机会成本或明确倍率
   证据时才计算，否则稳定标记 `NOT_CALCULABLE`，不得伪造金额。
4. 保存反事实资源、规则版本、反事实成本、实际成本、节省值和不可计算原因；既有
   历史决策不补算、不覆盖。
5. 首页汇总只纳入动作已执行、证据完整且 `saving_calculable=true` 的决策；允许
   负值表示实际方案更贵。
6. 补 Domain、Gateway、Database、Control API、Web 和真实 E2E，覆盖节省为正、
   为零、为负、不可计算、重试和多 Attempt 场景。

### 验收标准

1. 构造原候选成本 10 元、实际成本 6 元的真实切换后，决策冻结 4 元节省，首页

2. 实际成本高于原候选时保存负节省；没有执行切换或缺少可比证据时不计金额，并
   展示明确不可计算原因。
3. 同一请求重试、幂等重放或页面刷新不会重复累计节省。
4. 管理员可下钻看到原／实际资源、双方规则版本、Token 依据及完整算式。
5. 规则后续修改不改变历史节省；自然月边界按 Asia/Shanghai 计算正确。
6. 全量测试、生产构建和 `git diff --check` 通过，保存非零节省真实 E2E 证据。

### 修复与验收记录（2026-08-03）

- Gateway 已冻结原候选与实际候选的计价证据，按同一 Token 事实计算反事实成本；证据
  不完整时明确不可计算，不伪造节省，允许正、零、负值。

## POOL-025 缺少企业 AI 算力月度经营账单闭环

- **严重级别**：P0
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：已关闭（代码验收通过，尚未部署）

### 结论

这是“企业 AI 资产总账升级”的**核心新增需求**。现有系统已经分别记录厂商资源、
使用主体和请求级用量，但缺少一个按月结算、可冻结复核的经营账单，老板仍然无法
在同一处回答“买了什么、谁在用、产生了什么价值”。按 **P0** 建立月度费用归集、
员工／项目汇总、套餐利用、人工价值确认和结账版本闭环。

### 现象

- 首页只展示当前自然月实时指标，不是可以结账和历史复核的月度账单。
- 用量账本是请求级明细，管理员需要逐条筛选，无法直接获得员工／项目汇总账。
- 套餐支付、API 消耗、充值金额和期末余额分散展示，容易把充值误当费用或重复统计。
- 系统不能直接识别用满、未用满、提前耗尽、无人使用和闲置权益。
- Token 和费用只有投入事实，缺少业务负责人填写、确认价值事项及依据的入口。
- 历史月份没有冻结版本；价格、规则或归属变化可能导致复核口径不一致。

### 影响

- 预算审批和续费时，无法统一说明本月各厂商花了多少、费用最终归集到谁和什么项目。
- 无法识别重复采购、闲置套餐、额度提前耗尽和资源错配，采购决策继续依赖个人偏好。
- AI 投入与项目成果脱节，高使用量不能解释为高价值，低使用量也无法说明真实贡献。
- 财务、技术负责人和业务负责人使用不同数据口径，历史账单难以审计和复核。

### 功能范围

经营账单作为独立一级入口，内部包含五个页签：

1. **月度总览**：总投入、API 消耗、套餐费用、期末余额、套餐利用率、活跃主体和
   人工确认价值。
2. **员工／项目账**：按员工或项目汇总使用厂商、Token、额度扣减、归集成本和活跃情况，
   可下钻到请求级用量账本。
3. **套餐利用分析**：识别用满、未用满、提前耗尽、无人使用和闲置权益，并保留
   判断依据。
4. **价值确认**：业务负责人填写价值事项、金额或非金额指标、关联项目、依据、
   提交人、确认人和确认时间。
5. **结账管理**：支持待结账、已结账、重开、历史版本和操作记录；结账后冻结当期口径。

### 核心业务口径

1. 月度经营成本 = 当月 API 实际消耗 + 当月应计固定套餐费用；**充值金额不等于费用**，
   当前余额作为期末可用资产单独展示，不重复计入总投入。
2. API 成本按厂商账单或已冻结价格规则归集；固定套餐的厂商成本保持固定，可按使用占比
   生成员工／项目内部管理分摊，但分摊合计不得改变或重复累计厂商成本。
3. 厂商支持余额接口时可自动同步余额和采集时间；没有公开账单明细接口时，允许账单导入
   或人工登记，并明确记录来源、账期和确认人。
4. 套餐利用率按厂商原生额度、有效期和重置周期计算，不把不同单位直接相加；闲置权益
   金额必须展示折算规则，不能伪装成厂商退款金额。
5. 系统只记录可验证的投入和使用事实；业务价值由人确认，系统不得根据 Token 用量自动
   推断收入、节省或生产率。
6. 结账生成不可覆盖的月度快照和版本；重开必须填写原因并生成新版本，原版本和操作记录
   永久保留。后续价格、规则或归属变化不得静默改写历史账单。
7. 自然月边界统一使用 Asia/Shanghai；厂商套餐周期可跨月，月度账单与厂商重置周期分别
   保存，不互相替代。

### 当前原型

- Web 已有本地可点击原型入口：`/operating-bill`。
- 原型已覆盖五个页签、员工／项目切换、价值事项新增与确认、结账／重开和版本留痕交互。
- 当前全部为演示数据，尚未建立数据库、后端聚合、真实厂商账单同步和生产结账能力，
  **不能视为功能已完成**。

### 建议实现范围

1. 新增月度账单、账单厂商明细、主体／项目归集、价值事项、结账版本和操作审计数据模型。
2. 建立确定性的月度聚合任务：消费请求级账本、厂商经营快照和套餐规则，生成可对账草稿；
   结账时冻结所有事实来源 ID、版本、价格和计算结果。
3. 补齐项目归属入口和请求／主体到项目的归因关系；未归属成本必须单列，不能自动摊入其他项目。
4. 对接厂商可公开获取的余额或账单能力；不支持 API 的厂商提供 CSV／账单导入和人工确认降级路径。
5. 五个页签接入真实读写接口，并支持从汇总账下钻到厂商资源、主体、项目和请求事实。
6. 结账和重开采用管理员权限、二次确认、幂等控制和完整审计；并发操作不得产生两个当前版本。
7. 补 Domain、Database、Worker、Control API、Web 和 Chromium E2E，覆盖跨月、跨套餐周期、
   账单缺失、规则变更、未归属成本、重开和并发结账。

### 验收标准

1. 选择任一历史月份，可在一个入口看到总成本、API 消耗、套餐费用、期末余额、利用率、
   活跃主体和人工确认价值，口径说明完整且相互不重复。
2. 示例账期中 DeepSeek API 费用 1,000 元、智谱套餐 500 元、Kimi 套餐 300 元时，

3. 员工／项目汇总成本之和与企业月度总成本一致；未归属部分独立展示，并可下钻核对
   厂商、模型、Token、额度和请求明细。
4. 套餐利用分析能准确识别用满、未用满、提前耗尽、无人使用和闲置权益；跨月、重置日、
   峰值倍率和不同原生单位不会造成错误判断。
5. 业务负责人可创建金额或非金额价值事项，保存依据并完成确认；系统展示“人工确认”，
   未确认事项不得计入已确认价值。
6. 结账后修改价格、额度规则、主体或项目归属不改变已冻结版本；重开后生成新版本，
   可完整对比版本并追溯操作人、时间和原因。
7. 厂商同步失败、账单缺失或数据不完整时禁止静默结账，页面明确提示缺口；经授权带缺口

## POOL-026 生产版本升级缺少结构化日志与后台查询入口

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：已关闭（代码验收通过，尚未部署）

### 结论

这是生产运维追溯能力缺失。当前每次 Mac Mini 发布的版本、数据库迁移、备份、健康
检查和验收结果主要散落在本地 Evidence、Release 目录和阶段状态文件中，管理后台
无法查询。升级记录不应混入现有 `operation_log`：操作日志回答“管理员做了什么”，
升级日志应独立回答“生产系统何时从哪个版本升级到哪个版本、改了什么、结果怎样”。

### 产品口径

- 按“实际升级事件”记录，不要求没有发布的日期生成空日志。
- “系统日志”增加两个子页面／页签：`操作日志`、`升级日志`。
- 升级日志由发布流程自动生成，管理员可以查看，不依赖人工补录关键事实。
- 已完成记录不可原地改写；补充说明使用追加方式，失败、回滚同样保留完整记录。

### 现象

- 管理后台当前“系统设置 · 操作日志”只展示 `operation_log`，没有升级日志入口。
- Release 路径、候选包哈希、数据库迁移版本、备份、容器状态和生产冒烟结果只能从
  服务器文件或 Evidence 文档查询。
- 管理员无法直接确认当前生产版本、上次升级时间、升级内容和回滚基线。

### 影响

- 出现故障时，无法快速判断是否与刚完成的发布、迁移或配置变化有关。
- 版本交接和日常复盘依赖聊天记录、终端输出和个人记忆，容易丢失关键事实。
- 生产已经运行的候选包可能没有对应 Git 提交，后台也无法提示这种可追溯性风险。
- 发布失败或回滚如果没有结构化记录，后续容易重复踩坑。

### 建议修复范围

1. 新增只追加的生产升级日志数据模型和查询 API，至少记录：
   - 升级 ID、开始／结束时间、状态（进行中、成功、失败、已回滚）；
   - 升级前版本、升级后版本、Git commit（若有）、候选包 SHA-256；
   - 数据库迁移起止版本、Release 标识、操作人／发布主体；
   - 本次功能、修复项和关联 `POOL-*` 编号；
   - 发布前备份引用、回滚目标、健康检查和生产冒烟摘要；
   - 脱敏 Evidence 引用及失败原因分类。
2. 发布脚本／CLI 自动写入：发布开始创建记录，成功后补齐结果；失败或回滚时更新为
   对应终态。使用稳定 `deployment_id` 保证重试幂等，不产生重复发布记录。
3. 当 Control API 正在重启或不可用时，发布流程先保存本地脱敏 Release Manifest，
   服务恢复后自动或显式导入，不能因为“日志 API 不可用”阻断紧急回滚。
4. 在“系统日志”中增加“升级日志”子页面，列表展示时间、版本、摘要、状态和操作人；
   详情展示迁移、关联问题、校验、备份和回滚信息。
5. 支持按时间、版本、状态和关联问题编号搜索／筛选；分页、URL 条件和企业边界与现有
   管理页面保持一致。
6. 禁止记录数据库密码、API Key、Cookie、会话令牌、`.env` 内容、用户请求正文和
   未脱敏终端日志；文件引用只允许展示批准公开的路径摘要或 Evidence 标识。
7. 升级记录完成后不可删除或覆盖；补充说明、失败修复和回滚必须形成追加事件并写入
   操作审计。

### 验收标准

1. 完成一次 Mac Mini 正常发布后，后台“系统日志 → 升级日志”自动出现唯一记录，
   升级前后版本、候选包哈希、迁移版本、关联问题、健康检查和冒烟结果与生产事实一致。
2. 发布脚本重复执行或日志导入重试不会产生重复记录；同一 `deployment_id` 只能对应
   一条升级主记录和有序追加事件。
3. 模拟发布失败和回滚后，页面分别显示失败阶段、脱敏原因、回滚目标和最终状态，成功
   历史不会被覆盖。
4. Control API 暂时不可用时可完成安全回滚；恢复后能导入此前 Manifest，且时间线
   顺序正确。
5. 管理员可按日期、版本、成功／失败状态和 `POOL-*` 编号查询，详情可从当前版本追溯
   到上一个版本和对应 Evidence。
6. 页面、API、数据库和普通日志中不出现 Secret、密码、Token、`.env` 明文或用户
   请求正文；越权和跨企业查询被拒绝。
7. Database、Control API、Web、发布脚本测试和 Chromium E2E 覆盖成功、失败、回滚、
   幂等、离线 Manifest 导入和敏感信息扫描；TypeScript、ESLint、生产构建与
   `git diff --check` 全部通过。

## POOL-027 厂商资源创建缺少可用模型自动发现与一键接入闭环

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是厂商资源接入和多版本模型供给的产品闭环缺失。底层已经支持一个企业创建多个统一
模型、把不同上游模型映射到一个或多个厂商资源，并按员工 Key 独立授权；但当前后台
把这一能力拆成“手工填写资源上游模型 → 手工创建统一模型 → 手工填写 Model Route”
三段技术配置。管理员容易写错模型 ID、大小写或套餐范围，也无法及时发现厂商为当前
凭证开放的新模型。

正式产品应在“新建厂商资源”中自动检测当前资源实际可调用的模型，管理员通过搜索、
多选或全选确认后，系统自动创建／复用统一模型并建立路由。普通管理员不再手工输入
上游模型 ID。

### 已确认产品口径

1. 模型入口放在“厂商资源”新建流程，而不是要求管理员先理解统一模型和 Model Route。
2. 展示范围是“当前资源、凭证、地区和套餐实际可调用的模型”，不是厂商宣传页的全部
   模型。
3. “全选”只选择 Gateway 当前协议和能力可以安全承载的模型；不兼容模型展示原因但
   不允许误选。
4. 确认加入后自动创建／复用统一模型和 Model Route，但不自动扩大任何员工 Key 权限，
   也不自动创建员工额度 Grant。
5. 同一模型由第二个资源提供时复用已有统一模型，只增加路由候选，不创建重复模型。
6. 厂商后续开放新模型时，资源详情通过“同步模型”发现并提示，由管理员确认加入，
   不自动上线。

### 现象与根因证据

- `apps/web/src/pages/Resources.tsx` 的“上游模型”是自由文本框，多个模型依赖英文逗号
  分隔。
- `apps/web/src/pages/QuotaRules.tsx` 要求管理员再次手工创建统一模型，并在创建
  Model Route 时手工输入上游模型。
- 当前 Provider Adapter 没有统一的模型发现契约，也没有资源级模型快照、同步时间、
  来源和可用性状态。
- 新模型虽然可以人工配置，但不能由资源凭证自动发现；模型下架、套餐变更和账户权限
  变化也无法在后台识别。

### 官方能力依据

- DeepSeek 官方提供 `GET /models`，返回当前可用及可用于请求的模型 ID。
- Kimi 开放平台提供 List Models API；Kimi Code Coding Plan 是独立的订阅系统，Key 与
  Base URL 不可和开放平台混用。Coding Plan 官方公开模型 ID，但未公开订阅 Key 的
  List Models 契约。
- 智谱通用 API 文档公开模型集合，但 Coding Plan 使用独立端点且只允许套餐模型子集；
  不能把官网全部模型直接当作当前 Plan 可用模型。
- 调研与来源见
  `_knowledge_base/厂商API模型自动发现与后台选择-2026年8月.md`。

### 建议修复范围

1. 将“新建厂商资源”改为四步向导：
   - 填写厂商、资源模式、名称和凭证；
   - 服务端测试凭证并同步当前可用模型；
   - 管理员搜索、单选、多选或全选兼容模型；
   - 确认摘要并一次完成资源、模型和路由接入。
2. 建立 Provider Model Discovery 适配器契约：DeepSeek、Kimi API 资源调用官方 List
   Models；Kimi Coding Plan 与其他缺少账号级动态列表的资源使用仟流维护的版本化官方
   模型目录，再按 API／Coding Plan、地区、套餐和凭证探测结果过滤。
3. 所有发现请求由 Control API／受控 Worker 在服务端执行，使用现有加密凭证；浏览器、
   响应、普通日志和 Evidence 不得接触凭证明文或厂商原始敏感响应。
4. 保存资源级脱敏模型快照：上游模型 ID、显示名称、模型类型、已知能力、来源、首次／
   最近发现时间、最近验证时间和状态；同步历史只追加，不删除已经进入 Route、Usage
   或账本的旧模型事实。
5. 根据模型类型和 Gateway 能力注册过滤可选项；Chat、Responses、Messages、工具调用、
   推理、图像输入、上下文和输出上限等能力未知时不得宣称支持。
6. 管理员确认后在单一事务中：创建或复用统一模型、生成稳定仟流别名、创建当前资源的
   Model Route、写操作日志并返回逐项结果；重试使用幂等键，不能生成重复模型或路由。
7. 模型缺少必需计价／套餐额度规则时标记“待配置”，禁止授权或进入 Gateway 热路径；
   页面明确引导完成计价、额度和调度规则后再启用。
8. 现有资源增加“同步模型”：显示上次同步时间、新增、仍可用、权限收回和厂商下架；
   新模型需确认加入，已下架模型停止新授权但保留历史追溯，并提供受控停用路径。
9. 普通管理员页面移除上游模型自由文本输入。若厂商尚未同步新模型，只允许平台维护层
   通过受审计、版本化目录更新补充，不能由普通管理员绕过。
10. 员工授权继续执行现有最小权限：新加入模型默认不进入任何现有 Key 的
    `allowed_model_ids`，管理员必须显式保存 Key 模型权限并创建对应 Grant。

### 验收标准

1. 使用有效 DeepSeek API 资源创建向导，点击检测后能看到该凭证实际返回的兼容模型；

   全选，并明确展示不可选原因。

   带来源和日期版本的官方套餐目录，不冒充凭证实时授权结果。

6. 已有模型快照同步失败时保留上次成功结果并标记过期，不宣称最新；恢复后可安全重试。

## POOL-028 Agent 客户端缺少标准化识别与员工使用画像

- **严重级别**：P1
- **发现时间**：2026-08-03（Asia/Shanghai）
- **状态**：待业务验收（代码验收通过，待三个真实 Agent 回归）

### 结论

这是客户端观测与使用分析闭环缺失。员工可以使用同一个主体 Key 从 WorkBuddy、Codex、
Z Code 等不同 Agent 调用 Gateway，管理员需要知道“谁在使用什么 Agent、哪个版本、
何时使用以及消耗多少”，用于兼容性分析、故障排查和工具采购判断。

现有 Gateway 已读取 `x-client-id`，缺少时读取 `User-Agent`，并把结果写入
`ai_request.client_id`；用量账本也能展示和筛选该字段。但当前只是截断后的原始字符串，
没有 Agent 家族、版本、识别来源、可信度和员工级汇总，不能稳定回答管理员的问题。

### 已确认产品口径

1. 不要求 Agent 连接后额外回调；每次 API 请求自动携带或被 Gateway 识别客户端信息。
2. 同一员工可以使用多个 Agent，后台全部保留，不把员工永久绑定到单一工具。
3. 同时展示“预期 Agent”和“实际观察 Agent”：前者来自接入信息交付选择，后者来自
   真实请求；不一致时只提示，不阻断调用。
4. Agent 识别用于统计、兼容性和诊断，不能代替主体 Key 鉴权，不能改变模型权限、额度、
   计费或调度结果。
5. 第三方请求头可以伪造，页面必须展示识别来源和可信度，无法可靠识别时显示
   `UNKNOWN`，不得硬猜。

### 现象与根因证据

- `apps/gateway/src/pipeline/real-pipeline.ts` 的 `clientIdentity` 只在
  `x-client-id` 与 `User-Agent` 之间二选一，清理控制字符后截取 64 字符。
- `ai_request` 只有单一 `client_id` 字段，没有标准 Agent 名称、版本、识别方式和置信度。
- Codex 的 `/v1/models?client_version=...` 已有协议特征，但没有进入统一客户端识别器。
- 用量账本直接展示原始 `clientId`，管理员可能看到不同大小写、版本串、SDK 名称或
  `UNKNOWN`，无法准确汇总 WorkBuddy、Codex 和 Z Code。

### 建议修复范围

1. 建立版本化 Client Identity Registry，把允许的显式标识、已验证 `User-Agent`、
   请求路径、协议和查询特征归一为稳定 Agent 家族，例如 `WORKBUDDY`、`CODEX`、
   `ZCODE`、`CLAUDE_CODE`、`QIANLIU_IDE`、`OTHER`、`UNKNOWN`。
2. 统一识别优先级：
   - 仟流受控客户端的签名／受信标识；
   - 第三方客户端显式声明的标准请求头；
   - 已通过真实客户端样本验证的 `User-Agent` 与协议特征；
   - `UNKNOWN`。
3. 保持现有 `x-client-id` 兼容，并定义可选标准头，例如 Agent 家族和版本；仅当客户端
   支持自定义 Header 时配置。不得要求不支持自定义头的第三方客户端才能使用。
4. 为请求事实增加或派生：标准 Agent 家族、Agent 版本、识别来源、可信度／验证级别和
   规则版本；原始标识仅做长度限制、控制字符清理和敏感信息检查后保存，或保存不可逆
   指纹，不采集设备名称、项目路径和用户正文。
5. 在主体接入信息中允许管理员选择“预期 Agent”，生成对应配置说明；这是交付元数据，
   不冒充真实观察结果。同一主体可保存多个有效接入配置档案。
6. 用量账本显示友好 Agent 名称、版本和识别来源，并支持按标准 Agent 家族筛选；历史
   原始 `client_id` 继续可追溯，不因规则升级静默改写。
7. 员工／项目主体详情增加“Agent 使用情况”：首次／最近使用时间、请求数、Token、费用、
   使用模型和最近版本；同一主体使用多个 Agent 时分别汇总。
8. 真实客户端识别规则必须来自脱敏请求头和协议样本，并经过回归测试；规则更新使用
   版本号，避免新规则把历史客户端误分类。
9. 对“预期 Agent 与实际 Agent 不一致”“客户端版本过旧”“UNKNOWN 占比过高”提供提示
   和筛选，但一期不自动封禁或报警。
10. 所有展示和日志严格执行企业边界；客户端标识不得包含 Key、Cookie、Authorization、
    请求正文、文件路径或其他个人敏感信息。

### 验收标准

1. 按员工真实使用关系验收：于滔只使用 WorkBuddy，需使用自己的主体 Key 从真实
   WorkBuddy 发起请求；Codex 和 Z Code 使用实际使用这两个客户端的员工或受控验收主体
   完成真实回归。后台主体详情和用量账本应显示正确 Agent 家族；可取得版本时正确显示
   版本，不能取得时明确显示“版本未知”。不要求同一员工使用并不属于其工作范围的全部
   Agent。
2. Codex 的 `client_version`、Responses 路径和真实 `User-Agent` 能进入统一识别结果；
   WorkBuddy、Z Code 使用各自真实客户端样本验证，不用测试伪造字符串冒充验收。
3. 同一员工同时使用多个 Agent 时，请求、Token、费用和最近使用时间按 Agent 分组，
   分组合计与该员工请求级账本一致。
4. 管理员交付配置时选择的“预期 Agent”与实际识别结果分开保存；不一致时页面提示，
   但请求鉴权、模型权限、额度扣减和计费结果不受影响。
5. 无客户端头、未知 SDK、伪造标识、大小写差异、超长值和控制字符分别归一或安全落为
   `OTHER/UNKNOWN`，不会污染日志、破坏页面或形成注入。
6. 第三方仅自报 `x-client-id: Codex` 时不能标记为“受信”；页面展示声明来源和有限
   可信度，管理员不会把它误认为强认证事实。
7. 可按 WorkBuddy、Codex、Z Code、其他和未知筛选用量；分页、总数、员工汇总和请求
   下钻始终一致且不跨企业。
8. 识别规则更新后，新请求使用新规则版本，历史记录仍保留当时识别事实；必要重分类
   必须是显式、可审计的离线操作。
9. Database、Gateway、Control API、Web 和真实 Chromium E2E 覆盖显式标识、协议特征、
   UNKNOWN、多 Agent 汇总、筛选、伪造与企业隔离；至少完成 WorkBuddy、Codex、Z Code
   三个真实客户端回归。
10. TypeScript、ESLint、生产构建、敏感信息扫描和 `git diff --check` 全部通过，生产
    发布后完成三个真实 Agent 的最小请求与账本展示确认。

### 修复与验收记录（2026-08-03）

## POOL-029 已同步模型缺少员工使用规则与授权发布闭环

- **严重级别**：P1
- **发现时间**：2026-08-04（Asia/Shanghai）
- **状态**：待验收（最终候选独立代码复核通过，待集成与生产验收）

### 结论

这是员工模型授权流程的产品闭环缺失，不是厂商模型同步失败，也不是管理员填写错误。
`POOL-027` 已完成企业模型池同步；此前缺少后续“哪些员工可以使用哪些模型”的集中规则
入口，Key `allowed_model_ids` 与主体额度 Grant 也需要管理员跨页面分别维护，容易形成
“模型可见但无额度”或“有额度但不可见”的半配置状态。

### 现象与影响

- 同步确认后的模型可能仍处于待配置状态，管理员无法按“选择员工 → 选择模型 → 设置额度
  → 校验 → 发布”的自然顺序完成授权。
- 员工客户端模型列表不能稳定反映当前有效授权，规则撤权、停用和有效期缺少统一闭环。
- 批量员工／模型授权缺少版本、幂等发布、变更预览、操作日志和历史追溯。

### 根因证据

- 厂商模型、统一模型、Model Route、Key 模型权限与主体 Grant 分散在不同页面和写接口。
- 原有 Key 权限与 Grant 分别写入，没有同一事务内的就绪检查、原子发布和失败回滚。
- 使用主体页只展示 `ACTIVE` 模型，未形成面向管理员的模型就绪原因和授权发布入口。

### 建议修复范围

1. 新增“员工使用规则”入口，支持员工搜索、单选／多选／全部员工；模型按厂商和资源分组，
   支持搜索、单选／多选／全部就绪模型。
2. 规则包含 Token 额度、是否允许超额、生效／失效时间，并支持草稿、校验、显式发布、
   停用、新版本和历史查看。
3. 校验统一检查员工主体与 Key、统一模型、Model Route、厂商／资源可服务状态及生效时点
   的计价／扣减规则；未就绪项显示具体原因并阻止发布。
4. 发布事务内原子写入规则分配、受管 Grant、额度计数器和 Key `allowed_model_ids`；任一步
   失败整体回滚，并发发布串行化，重复请求按幂等键返回同一结果。
5. 兼容既有手工 Key 权限：迁移时冻结为手工基线；规则发布、换版和停用只能合并或撤销
   自己管理的权限，不得静默破坏手工授权。
6. 发布前展示新增／保留／撤销的员工、模型和资源；发布、停用记录管理员、规则版本、
   数量和结果，禁止记录 Key、厂商凭证或请求正文。
7. Gateway 模型列表和调用热路径同时校验 Key、主体、模型、当前有效 Grant；未授权、已
   撤权或已过期模型在访问任何上游前拒绝。
