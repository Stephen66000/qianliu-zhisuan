## POOL-001 峰谷计价/扣减规则缺少完整配置闭环

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是**功能缺陷，不是使用问题**，按 **P0** 修复。5 个缺口及独立复核发现的问题均已修复，代码验收通过，问题关闭。

### 现象

额度规则页面只能填写固定 Token 单价，无法配置时区、每日时间窗、星期和额度倍率，导致 DeepSeek V4 分时 API 价格与智谱 Coding Plan 高峰扣减倍率无法正确设置。

### 影响

- 管理员无法仅通过 Web 完成峰谷计价与套餐额度扣减规则配置。
- DeepSeek 分时 API 成本可能按错误价格结算，影响成本、账单和利润数据。
- 智谱 Coding Plan 高峰使用量可能未按 3 倍扣减，影响套餐额度准确性。
- API 费用规则与套餐 Token 扣减倍率可能被错误混用，造成计费语义污染。
- 缺少命中规则版本与时段解释，账本结果难以审计和复核。

### 业务规则

1. **DeepSeek**：北京时间每日 `09:00–12:00`、`14:00–18:00`，缓存命中、缓存未命中输入、输出价格均为低谷价格 2 倍。该规则影响 API 费用，不应写成套餐 Token 扣减倍率。
2. **智谱**：北京时间每日 `14:00–18:00`，使用量按 3 倍扣减；非高峰倍率按当期套餐/活动版本配置。

### 根因证据

- `apps/web/src/pages/QuotaRules.tsx` 的 `BillingRuleSchema` 和表单没有 `timezone`、`days_of_week`、`start_time`、`end_time`、`multiplier`。
- `apps/control-api/src/read-models/routes.ts` 的 `CreateBillingRuleSchema` 和 `POST /billing-rules` 没有接收、下传时间窗字段。
- `packages/domain/src/billing-rule.ts` 的 `matchPriceRule` 只按资源、模型和生效日期匹配 `API_PRICE`，没有判断时间窗，因此 DeepSeek 分时价格即使写入数据库也不会命中。
- 数据库 `billing_rule` 表已经具备 `timezone`、`days_of_week`、`start_time`、`end_time`、`multiplier`，问题属于上层配置与执行闭环漏项。

### 建议修复范围

1. **API 价格分时规则**：补齐前端配置、创建/编辑 API，以及 `API_PRICE` 的时区、星期、时间窗和分时单价匹配。
2. **套餐用量分时倍率**：独立配置套餐额度扣减倍率，补齐前端、接口与结算执行链路，不与 API 价格规则混用。
3. **多时间窗口**：同一规则支持多个时间窗口，例如 DeepSeek 每日 `09:00–12:00`、`14:00–18:00` 两个高峰段。
4. **基础规则与高峰规则优先级**：明确基础规则、高峰规则及重叠时间窗的命中优先级，保证结果唯一且可解释。
5. **生效日期和规则版本**：支持生效区间、规则来源、版本留存与历史追溯；新版本不得重算历史账本。
6. **账本命中信息展示**：在账本或结算详情展示命中的规则版本、时段、单价或倍率版本。

配套验证：补齐单元测试、接口测试和真实 Web E2E。

### 验收标准

1. **API 价格分时规则**：管理员可仅通过 Web 配置 DeepSeek 分时 API 价格；峰内、峰外及 `12:00`、`14:00`、`18:00` 边界结算正确。
2. **套餐用量分时倍率**：管理员可仅通过 Web 配置智谱每日 `14:00–18:00` 的 3 倍扣减及当期非高峰倍率；峰内、峰外及 `14:00`、`18:00` 边界扣减正确。
3. **多时间窗口**：同一规则可保存并正确执行 DeepSeek 每日 `09:00–12:00`、`14:00–18:00` 两个高峰窗口。
4. **规则优先级**：基础规则、高峰规则或时间窗重叠时，系统按明确优先级唯一命中；API 价格与套餐扣减语义隔离，不互相误用。
5. **生效日期和规则版本**：规则只在配置的生效区间内命中；版本可追溯，新版本不影响历史账本、不触发历史重算。
6. **账本命中信息展示**：页面或账本详情可明确展示实际命中的时段、单价或倍率版本，以及对应规则版本。

配套验收：单元测试、接口测试和真实 Web E2E 覆盖上述场景并通过。

## POOL-002 官方 Codex 接入协议与模型权限门禁缺失

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：待业务验收（代码缺陷已关闭）

### 结论

官方 Codex 客户端接入协议和主体 Key 模型权限门禁均未形成闭环，属于影响可用性、权限隔离与费用安全的 **P0 功能缺陷**。代码缺陷已修复并通过代码验收；正式业务验收仍需真实厂商凭证与独立 IDE/App E2E，当前不能直接发给同事使用。

### 现象

员工使用官方 Codex 并配置管理员分配的仟流主体 Key 后，仍无法使用仟流统一模型；同时系统不能保证该 Key 只能使用管理员分配的模型。

### 影响

- 官方 Codex CLI、IDE、App 无法通过仟流 Gateway 正常使用统一模型。
- 主体 Key 的模型授权配置无法约束模型列表和实际调用，存在越权调用风险。
- 未授权请求可能进入上游调用链，产生非预期费用并破坏企业模型权限边界。
- Responses API 的 Usage 若未完整映射，账本可能丢失输入、输出、缓存或推理 Token。
- Key 停用、重置和模型撤权若不能即时生效，会留下持续访问窗口。

### 根因证据

1. 官方 Codex 自定义 Provider 当前使用 Responses API；仟流智算当前只支持 `/v1/chat/completions`、`/v1/messages`，`/v1/responses` 明确标记为 `UNSUPPORTED` 并返回 `422`。
2. `principal_key.allowed_model_ids` 虽能写入数据库，但 Gateway 鉴权、`GET /v1/models` 和请求热路径均未执行该限制；API 模式也不会经过 Coding Plan 的 `principal_grant` 门禁。
3. 相关代码位置：
   - `packages/contracts/src/northbound.ts`
   - `apps/gateway/src/auth/principal-auth.ts`
   - `apps/gateway/src/routes/models.ts`

1. **Responses API 协议**：实现 `/v1/responses` 非流式与流式接口，完整兼容官方 Codex 使用的请求、响应和流式事件协议。

3. **主体 Key 模型权限硬门禁**：让 `allowed_model_ids` 同时约束 `GET /v1/models` 查询结果和所有请求热路径；未授权模型必须在访问任何上游前拒绝，并覆盖撤权、Key 停用与重置即时生效。
4. **真实客户端 E2E**：使用官方 Codex CLI 和实际使用端验证非流式、流式、工具调用、模型过滤、越权拒绝、撤权及账本归因，并保存完整证据。

## POOL-003 调度策略管理闭环缺失

- **严重级别**：P0
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：已关闭

### 结论

Gateway 热路径已经支持按时段执行 `REJECT`，但管理后台缺少调度策略的新建、校验、发布、停用页面及写接口，导致管理员无法通过 Web 配置“智谱高峰期禁止使用”。这是管理与执行链路未闭环的 **P0 功能缺陷**。管理、发布、热路径与审计闭环已补齐，代码验收通过，问题关闭。

### 现象

管理员需要设置智谱北京时间每日 `14:00–18:00` 不可使用，但现有页面只能配置计价或套餐用量倍率。调度策略只有查询能力，没有新建和发布入口，无法把硬拒绝规则投入 Gateway 热路径。

### 影响

- 管理员无法通过 Web 实施高峰期资源禁用策略。
- 将倍率设为 `0` 或较大数值都不能形成调用硬门禁。
- 高峰期请求仍可能消耗智谱套餐额度或产生非预期费用。
- 策略发布、版本、命中结果和操作过程无法形成完整审计闭环。

### 建议修复范围

1. 增加调度策略新建、校验、发布、停用接口。
2. 增加管理后台调度策略配置页面。
3. 支持按厂商资源、统一模型、资源模式、主体范围、时区、星期和时间窗口匹配。
4. 支持 `REJECT / SWITCH / RATE_LIMIT` 等动作，并明确无替代资源时的行为。
5. 支持策略版本、优先级、状态、来源及操作日志。
6. 在请求下钻和调度决策账本中展示命中策略、版本、时段、动作及原因。

### 验收标准

1. 管理员可仅通过 Web 创建并发布智谱 `14:00–18:00`、`Asia/Shanghai`、每日生效的 `REJECT` 策略。
2. `13:59` 请求允许；`14:00–17:59` 返回 `403 dispatch_rejected`；`18:00` 恢复允许。
3. 被拒请求不访问上游、不扣套餐额度、不产生上游费用。
4. 调度决策记录包含策略 ID、版本、匹配时段、最终动作和拒绝原因。
5. 策略停用后立即不再命中，历史决策记录保持不变。
6. 单元测试、接口测试和真实 Web/Gateway E2E 覆盖上述边界并通过。

### 特别约束

- “绝对禁用”必须使用 `REJECT`。
- 当前 `SWITCH` 在没有可用替代资源时会退回允许原资源，不能代替硬拒绝；如业务需要“优先切换、无目标则拒绝”，应提供明确的 `SWITCH_OR_REJECT` 语义并独立验收。

### 修复与验收记录

- 已增加调度策略草稿创建、引用校验、确认发布、停用、全状态查询与企业隔离写接口，状态机固定为 `DRAFT → VALIDATED → PUBLISHED → RETIRED`。
- Web 已支持模型、资源、模式、主体、时区、星期、时间窗、优先级及 `REJECT / SWITCH / RATE_LIMIT` 等配置，发布和停用均需确认。
- Gateway 使用请求开始时刻做确定性匹配，决策快照冻结实际命中的时区、星期和起止时段。
- Gateway 边界集成测试验证 `13:59:59` 放行、`14:00` 和 `17:59:59` 拒绝、`18:00` 恢复；峰内不访问上游、不扣额度。
- Control API 接口测试和 Chromium 真实 Web E2E 已覆盖创建、校验、发布与停用闭环。

## POOL-004 接入信息展示错误且缺少一键复制

- **严重级别**：P1
- **发现时间**：2026-07-30（Asia/Shanghai）
- **状态**：已关闭

### 结论

生产管理后台曾展示本机开发地址 `http://127.0.0.1:8787/v1`，员工在其他设备上按页面接入必然失败；页面同时缺少完整接入信息的一键复制能力。该问题影响员工交付和真实客户端接入，按 **P1** 修复。代码修复已发布，真实业务验收通过，问题关闭。

### 现象

- 主体“接入信息”中的 Base URL 显示为 `http://127.0.0.1:8787/v1`，没有显示已经上线的 Gateway 地址 `https://gw.qianliuai.com/v1`。
- 管理员需要手工选择并拼接 Base URL、API Key 和模型别名，页面没有“复制接入信息”按钮。
- Key 完整明文仅生成或重置时展示一次，后续页面只有掩码，容易把不可用的掩码 Key 误发给员工。

### 影响

- 员工电脑会把 `127.0.0.1` 解释为自己的设备，无法连接 Mac Mini Gateway。
- 手工复制容易漏字段、复制掩码 Key、写错模型别名或大小写。
- 管理员无法快速完成 Codex、ZCode、WorkBuddy 等真实客户端的接入交付。

### 建议修复范围

1. Web 生产构建显式注入 `VITE_GATEWAY_BASE_URL=https://gw.qianliuai.com/v1`，禁止生产环境回退到 localhost。
2. “接入信息”展示真实 Gateway Base URL，并区分 OpenAI 兼容 `/v1` 地址和其他协议需要的地址。
3. 增加“复制接入信息”按钮，复制 Base URL、当前一次性完整 Key、已授权且额度有效的模型别名和协议提示。
4. 完整 Key 不在页面重新回显；生成或重置后允许一次性复制，离开后仅显示掩码，并明确提示丢失后必须重置。
5. 复制成功或失败提供明确反馈，禁止把掩码 Key 当作可用接入信息复制。

## POOL-007 WorkBuddy 工具回合复用请求 ID 触发主键冲突

- **严重级别**：P0
- **发现时间**：2026-07-31（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是 Gateway 请求 ID 与幂等语义没有闭环导致的 **P0 功能缺陷**，不是
WorkBuddy 使用问题。迁移 `0024` 与 Gateway 已发布生产，生产 API、真实
WorkBuddy、数据库和账本验收均证明原 `23505/ai_request_pkey` 缺陷消失；
但真实工具任务最终仍因唯一 Kimi 上游进入冷却而返回 503，完整业务验收未通过，
状态退回“待业务验收”，由独立的 POOL-008 跟踪新根因。

### 现象

- WorkBuddy `5.2.5` macOS 使用生产 Gateway 和 `Kimi` 时，普通文本流式回复正常。
- 发送“调用终端创建文件并读取”的真实工具任务后，客户端展示 `500 Unknown error`，错误码为 `23505`。
- 对应客户端请求 ID 为 `db4f2a81-dde0-6871-3d9a-1c76e1528e02`；该 ID 的首条请求已经成功结算，工具后续回合再次使用同一 ID 时失败。

### 影响

- WorkBuddy 通过仟流 Gateway 的真实工具调用无法稳定完成。
- 任何复用 `x-request-id` 做重试、续接或多回合工具调用的客户端都可能触发相同故障。
- Gateway 向客户端泄漏数据库错误码并返回不可解释的 500，客户端无法安全判断重试或恢复方式。
- 首次成功请求已经产生上游调用和账本；后续重放若处理不当，存在重复调用、重复费用或重复结算风险。

### 根因证据

1. `apps/gateway/src/plugins/request-id.ts` 对格式合法的客户端 `x-request-id` 无条件采用，并注释为“幂等重试”。
2. `apps/gateway/src/pipeline/real-pipeline.ts` 在进入上游前直接以 `request.requestId` 创建请求意图。
3. `packages/database/src/repositories/gateway-ledger-repository.ts` 的 `createRequest` 对 `ai_request` 执行普通 `INSERT`，没有 `ON CONFLICT`、重放状态识别或已完成响应返回。
4. 生产 PostgreSQL 日志于 `2026-07-31 02:29:18.269 UTC` 明确记录：
   - `duplicate key value violates unique constraint "ai_request_pkey"`；
   - `Key (id)=(db4f2a81-dde0-6871-3d9a-1c76e1528e02) already exists`。
5. 数据库中该请求原记录状态为 `SUCCEEDED`、账本状态为 `SETTLED`，`idempotency_key` 为空，证明冲突对象是 `ai_request.id`，不是 `idempotency_key`。

### 建议修复范围

1. 拆分“内部请求主键”“客户端追踪 ID”和“业务幂等键”语义；客户端 `x-request-id` 不得未经冲突处理直接充当数据库主键。
2. 定义同一主体、Key、路由、请求体下的幂等重放规则，以及同 ID 不同请求体的稳定拒绝规则。
3. 对 `IN_PROGRESS / SUCCEEDED / FAILED` 三类既有请求分别定义并发重放、结果重放和可重试行为，禁止再次访问上游或重复结算。

## POOL-008 单套餐多主体共享调度缺失导致 WorkBuddy 返回无可用资源

- **严重级别**：P0
- **发现时间**：2026-07-31（Asia/Shanghai）
- **状态**：已关闭

### 结论

这是套餐共享调度和资源降级策略缺陷，不是 WorkBuddy 使用问题，也不能要求用户
再购买一份套餐规避。产品的核心业务规则是：一个 Coding Plan 厂商资源可以授权
给多个主体使用，Gateway 必须允许多个主体在厂商套餐并发范围内同时调用，并在
超过管理员配置上限时等待、限流和准确分账。不能把共享实现成“一人用完、下一人
再用”的串行队列。下游保留每位员工独立 Key、权限、额度和账本，上游统一复用同
一个 `provider_resource` 套餐凭证；厂商看到的是同一套餐身份下的多条并发请求，
不是把多条请求伪造成一条。原实现没有完成这个闭环；一次上游限流会立即把唯一套餐资源置为
`UNAVAILABLE`，冷却期间后续工具回合直接返回
`503 no_healthy_candidate`。

### 现象

- WorkBuddy `5.2.5` macOS 已成功完成文本流式回复和终端文件创建、读取。
- 同一工具任务的最终回合显示：
  `503 无可用上游资源 (71b69fd73f2bceec755a0c77ed53534e/928b4ebc-0bfa-4dd1-93f0-049cd8fb1754)`。
- 客户端错误码为 `custom-model-503`，Request ID
  `27819137ffbd4cb6a914f90ed0ae0f20`，Trace ID
  `4379dcb1bbc2d2b4143881d986928852`。
- 资源冷却后自动恢复为 `DEGRADED`，但已发起的 WorkBuddy 工具任务不会自动恢复，
  用户仍然得到失败结果。

### 影响

- WorkBuddy 可在普通回复后于工具回合中途失败，不能作为稳定业务入口交付。
- 一个已购买的 Coding Plan 无法稳定分给两个人使用，直接违背产品核心目标。
- 单一资源的任意瞬时限流都会扩大成该模型对全体主体的短时不可用。
- 并发请求中可能一条成功、另一条直接 503，用户看到的结果不稳定且难以解释。
- 只有自动冷却恢复，没有当前请求的公平排队和受控重试，恢复后仍需用户手工重试。

### 根因证据

1. 业务配置本身合法：生产数据库只有一个已购买的 `Kimi` Coding Plan 资源，
   但它需要由两个及以上主体共享；当前只有一条启用路由：
   - `provider_resource.id=e75fe982-c83b-46a7-9fcb-c7876754e5a9`；
   - `resource_pool_id=NULL`；
   - `api_fallback_enabled=false`；
   - 没有针对单套餐多主体共享的队列和公平调度策略。
2. `packages/domain/src/resource-lifecycle.ts` 对首次
   `UPSTREAM_RATE_LIMITED` 直接迁移为 `UNAVAILABLE`，冷却基数 30 秒。
3. `packages/database/src/repositories/resource-pool-repository.ts` 在冷却期硬过滤
   `UNAVAILABLE` 资源。
4. `apps/gateway/src/pipeline/real-pipeline.ts` 在过滤后候选为空时直接返回
   `503 no_healthy_candidate`，没有排队、短重试或单资源降级策略。
5. 生产状态事件记录 `ACTIVE → UNAVAILABLE`、原因 `RATE_LIMITED`、
   错误分类 `UPSTREAM_RATE_LIMITED`；随后半开探测成功恢复为 `DEGRADED`。
6. 同一 WorkBuddy 客户端追踪 ID 下，`c0930bc2-c39e-4bc8-ba28-3cb2f22b38e0`
   成功，紧随其后的 `4d98c91b-b0ef-4d95-9056-878dad95eade` 以
   `no_healthy_candidate` 失败，证明是资源准入问题而非 POOL-007 主键冲突。

### 建议修复范围

1. 把 `provider_resource.concurrency_limit` 作为真实上游并发上限执行，不得使用
   默认 100 放大请求；管理员可按套餐能力配置。
2. 每个套餐资源支持管理员配置正整数并发上限（可按 2、4、5 等实际员工规模和
   厂商套餐能力调整）；上限以内必须真正并行，不得串行互斥。
3. 为每个套餐资源建立跨 Gateway 实例共享的有界信号量；只有超过配置上限的请求
   才短暂等待，禁止某一主体或工具任务长期独占。
4. 资源槽位暂满属于容量调度，不等于资源故障；请求应等待或返回明确的
   `resource_busy + retry_after_ms`，不得直接把资源标记为不可用。
5. 区分厂商 429 的引擎拥塞、并发限制、5 小时窗口耗尽和月度额度耗尽；首次瞬时
   429 不得立即全局隔离唯一套餐资源，优先遵循上游 `Retry-After`，在请求
   总时限内执行受控退避重试，持续失败达到阈值后才进入熔断。
6. 工具多回合的每次真实上游调用独立获取和释放槽位，同时保留主体、会话和账本
   归因；客户端等待、取消或断流必须释放队列位置和并发租约。
7. 半开探测增加原子探测权和并发保护；第二套餐、同池账号或 API 兜底只能作为
   可选扩容能力，不能作为两人共享一份套餐的必要条件。
8. 503 仅用于资源真实不可恢复；并发等待超时返回 429、稳定错误码和
   `retry_after_ms`；增加模型拥塞、等待长度、限流和恢复告警。
9. 补充单套餐 2～5 个主体并发、429、等待、取消、超时、冷却、半开、工具多回合、
   多 Gateway 实例和账本不重复测试。

### 验收标准

1. 只配置一份 Kimi Coding Plan，管理员可把并发上限设为 2、4 或 5；对应数量
   的不同主体可同时发起普通回复和工具任务，最终均成功，不需等待前一个主体结束。
2. 实际访问上游的并发数始终不超过资源配置上限；超出的请求公平排队，不出现
   `custom-model-503`，也不会饿死其中一个主体。
3. 单一资源首次 429 不会立即造成该模型全局不可用；Gateway 按
   `Retry-After` 或冻结退避策略恢复，重试总次数和等待时限有上限。
4. 工具任务完成“模型调用工具 → 执行工具 → 回传结果 → 最终回复”闭环；每轮
   正确获取、释放上游槽位，客户端取消后无租约泄漏。
5. 冷却期和半开期只允许规定数量的探测请求；持续失败才熔断，成功后自动恢复。
6. 排队超时或资源确实不可服务时返回稳定错误码和 `retry_after_ms`，不伪装成
   “模型未配置”或无解释 503。
7. 两个主体的额度、Usage 和费用分别归因；每个内部请求的 Attempt、Usage、
   Ledger Line 和 Ledger Transaction 唯一，
   失败与重试不伪成功、不漏账、不重复结算。
8. Gateway 单元/集成测试、生产 Kimi 单套餐双主体冒烟及 WorkBuddy `5.2.5` macOS、
   `5.3.5` Windows E2E 全部通过并保存证据。

### 处置记录

- 冻结业务规则：一份套餐允许分配给多个主体；第二套餐或 API 兜底不是基本验收前提。

## POOL-014 Gateway 真实流式与 Kimi 稳定性保护闭环

- **严重级别**：P0
- **发现时间**：2026-08-01（Asia/Shanghai）
- **状态**：已关闭（完整验收、合并、生产发布和最小生产冒烟均完成）

### 现象

- Claude Desktop 经 CC Switch 调用 Kimi 时，多次在约 60 秒后收到上游 404 HTML，
  客户端误报 `claude-fable-5` 不存在。
- 同日 Kimi 返回 429 后，唯一资源进入熔断，Gateway 后续返回 503。
- Gateway 的 `stream:true` 代码路径会先聚合完整上游 SSE，再一次性生成北向响应，
  客户端无法在长生成期间持续收到事件。

### 影响

- Claude Desktop、Claude Code、CC Switch、Codex 和 WorkBuddy 等长流客户端可能在
  上游仍生成时被中间层或客户端误判超时。
- HTML/网络故障可能被第三方客户端重写成无关的模型错误，增加误诊。
- 唯一 Kimi 套餐资源遇到短时 429 后可能被长期排除，限流被放大成全员 503。
- 首字节、空闲、总时长和失败层缺少独立证据，无法判断 404 由 Gateway、反代还是
  厂商产生。

### 根因证据

1. `packages/provider-adapters/src/openai-compatible-caller.ts` 原实现完整消费 SSE、
   聚合文本与工具参数后才返回 `Outcome`。
2. `apps/gateway/src/pipeline/real-pipeline.ts` 原实现拿到完整 `Outcome` 后才写 Chat SSE；
   Messages 不处理 `stream:true`，Responses 也是缓冲式转换。
3. 资源状态机原先把连续 429 推入通用 `UNAVAILABLE`，没有独立 `RATE_LIMITED`；
   半开准入只有布尔标记，没有跨请求原子租约。
4. `upstream_attempt.first_byte_at` 字段虽已存在，但真实 Caller 没有写入；没有失败层字段。
5. 生产约 60 秒 404 HTML 的最终产生层尚无对应生产 request ID/代理日志证据，
   因此本条只确认“缓冲是诱因和放大器”，不把全部 404 先验归因于流式。

### 修复范围

1. `/v1/chat/completions` 逐个转发 OpenAI Chat SSE chunk，保留 finish reason、
   usage、工具调用和 `[DONE]`。
2. `/v1/messages` 实时转换并输出 Anthropic `message_start`、内容块、工具参数、
   `message_delta`、`message_stop` 及流中 error 事件。
3. `/v1/responses` 明确降级为 `TRANSFORMED`：当前只支持 Responses 子集到 Chat
   Completions 的缓冲式转换，不宣称原生兼容；Codex 暂优先经 CC Switch 走 Chat。
4. 增加首字节、流式空闲、请求总时长三层超时；HTML、协议、网络和超时统一为
   稳定 JSON/SSE 错误，不读取、保存或回传 HTML 正文。
5. 429 保留 `Retry-After`，资源进入短时 `RATE_LIMITED`；冷却期间唯一资源返回
   429 而非 503，冷却到期自动半开。
6. 使用数据库条件更新获取单资源半开租约；同波并发 429 事务内去重，冷却和失败
   次数不重复放大。
7. 账本补失败层，并启用既有首字节字段；记录协议、stream、客户端标识、上游状态
   和 request ID，不增加正文存储。
8. Caddy Gateway 反向代理显式配置 `flush_interval -1`。

### 验收标准

- `stream:true` 返回对应协议的 `text/event-stream`；事件顺序、结束事件、usage 与
  工具调用符合协议。
- K3 连续生成超过 60 秒仍持续收到事件；Gateway 收到首事件后 1 秒内转发。
- 首字节、流式空闲和总时长分别触发稳定 504；流已提交后的错误使用 SSE，不透传 HTML。
- Kimi 429 保留状态和 `Retry-After`；冷却到期自动半开，并发探测只有一个真实请求。
- 同一波并发 429 只累计一次；唯一资源不会永久退出，也不会在冷却中改报 503。
- 非流式、流式、工具调用、客户端取消、三层超时、429 冷却、半开恢复与并发失败
