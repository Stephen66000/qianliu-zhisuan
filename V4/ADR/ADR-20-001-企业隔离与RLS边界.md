# ADR-20-001：企业隔离与 RLS 边界

> **历史方案（2026-08-12）**：本 ADR 属于 PC-20260812-03 之前的平台／多企业方案，不是当前仟流智算 2.0 实现合同；仅保留研究结论。当前边界以 PRD／TRD 为准。

## 背景

1.0 明确按单工作空间实现。2.0 即使首发采用一企业一部署，也不能让产品代码、迁移和运维工具依赖“库里恰好只有一家企业”才能安全。需要决定 PostgreSQL RLS 是否进入标准合同，以及如何与应用授权、Schema 约束和连接池共同工作。

## 决策

采用“应用授权＋企业化 Schema＋复合约束＋RLS 第二道防线”的纵深隔离：

1. 所有租户业务事实直接携带非空 `enterprise_id`；同企业引用用 `(enterprise_id, id)` 复合唯一与复合 FK 固化。
2. Control API、Gateway 和 Worker 使用非表 Owner、`NOSUPERUSER`、`NOBYPASSRLS` 的独立运行角色；迁移／表 Owner 使用另一角色和连接配置。
3. 对企业、身份、资源、授权、请求、账本、预算、账期、导出、运行保障等高风险租户表启用并强制 RLS。低风险或平台级表是否启用由表归属矩阵逐表决定，禁止笼统全开或全关。
4. 企业上下文只能在同一数据库连接的短事务内通过参数化 `set_config(..., true)` 设置；Repository 必须接收该事务对象。禁止 session-level `SET`，禁止跨外部 HTTP／SSE 持有事务。
5. 标准版一企业一部署从受信的部署配置取得 `DEPLOYMENT_ENTERPRISE_ID` 完成认证 bootstrap，再验证 Session／Key 的企业归属。请求 Header、Query 或 Body 不能决定当前企业。
6. Worker Job 和可重建缓存 Key 必须显式包含企业 ID；平台调度仅负责枚举企业，业务处理逐企业进入上下文。
7. RLS 不替代认证、RBAC、应用层过滤、审计、复合约束或跨企业负向测试。

## 备选方案

| 方案 | 结论 | 原因 |
| --- | --- | --- |
| 只依赖一企业一部署 | 拒绝 | 运维脚本、错误 Join、未来部署变化仍可能越界；无法形成代码级安全合同 |
| 只依赖 Repository 过滤 | 拒绝 | 当前事实链已有大量单列 FK 和全局查询，漏一个过滤即可串租户 |
| RLS 作为唯一隔离手段 | 拒绝 | 超级用户／Owner 可绕过；连接上下文、认证 bootstrap、跨表一致性仍需其他防线 |
| 所有角色统一使用超级用户 | 拒绝 | 直接使 RLS 失去第二道防线价值 |

## 后果

- 正面：错误 SQL、遗漏过滤和连接复用获得数据库级拦截；跨表归属可由约束证明；未来共享 SaaS 有明确演进基础。
- 成本：需要拆分数据库角色、改造 Repository 事务入口、补齐企业列／复合 FK、逐表 Policy、Worker 企业化及较完整的负向回归。
- 风险：RLS 查询计划和连接事务成本尚未在目标规模验证；由 POC20-004 冻结容量阈值。如其证明标准包络不可接受，必须提交 Planning Change，不得静默关闭 RLS。

## 验证要求

- POC20-002：真实 `0044` 结构的归属审计、回填、复合约束、回滚和重升。
- 开发验收：每个高风险入口同时证明应用授权拒绝与数据库 fail-closed；连接 commit／rollback／异常／并发复用无上下文残留。
- POC20-004：在冻结数据量与并发下验证 RLS 索引、计划、延迟和运维成本。
- 共享 SaaS：另立认证 bootstrap、平台跨租户操作和支持访问 ADR；不得沿用一企业一部署假设直接上线。
