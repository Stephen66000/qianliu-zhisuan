# ADR-20-002：0044 迁移与回滚边界

> **历史方案（2026-08-12）**：本 ADR 属于 PC-20260812-03 之前的迁移方案，不是当前 2.0 迁移编号或实现合同；真实迁移头由 W20-01 重新核验，当前边界以 TRD §13 为准。

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-08-11（Asia/Shanghai） |
| 适用版本 | 仟流智算 2.0 标准版 |
| 依据 | [POC20-002 Evidence](../Evidence/Stage01/POC20-002/README.md) |
| 复查触发 | 正式 Schema 改为非加性；标准部署不再一企业一部署；生产副本出现归属歧义；回滚 RTO 合同改变 |

## 决策

1. 2.0 从真实 `0044_operating_bill_model_identity` 迁移；正式迁移文件在 Stage 02 产生，Stage 01 的代表性 SQL 不进入产品迁移目录。
2. 每次迁移必须绑定显式目标企业部署清单。先审计所有企业引用和 10 张单工作空间表的归属候选；缺清单、目标不存在、多企业标准部署或引用冲突均在 DDL 前 fail-closed，禁止任选企业回填。
3. 10 张表采用“nullable 无默认列 → 可证明回填 → 缺失为 0 → 复合约束验证 → NOT NULL”的顺序。孤立 `person`、`availability_rule`、`notification_endpoint` 只能以部署清单作为有记录的归属来源。
4. 历史 Request、Attempt、Usage、Ledger、Statement 不重写。迁移验收使用显式 0044 老字段 SHA-256、全 Token／金额／Attempt 守恒和 Statement Hash，不使用 `SELECT *`。
5. 迁移、2.0 Runtime、1.0 兼容角色分离。2.0 Schema 上的 1.0 兼容角色只读，且必须是非 Owner、非超级用户、`NOBYPASSRLS`。
6. 回滚分两段：
   - `R1 / Writer 切流前`：确认无 2.0-only 写入后，允许 Schema down；完成 Hash 对账前旧版保持只读。
   - `R2 / Writer 或身份 Writer 切流后`：禁止 Schema down；只允许回退到兼容当前 `schema_epoch / identity_epoch / app_min_version` 的前一 2.0 候选＋前向修复，或隔离恢复升级前备份／PITR 并单独处置切流后写入。1.0 二进制不再是可服务流量的回退目标。
7. 数据库持久化 epoch／最小应用版本；应用启动、认证／Session 签发和 Gateway 入口都必须校验。身份切流后旧密码、旧角色、旧 Session 和 1.0 二进制稳定拒绝；1.0 兼容角色只用于离线 `SELECT` 对账，不能启动服务、签 Session、接 Gateway 或 Worker。
8. 物理列序号不属于兼容合同。正式查询、导出和脚本必须显式列名；语义 Schema、约束和数据 Hash 才是 up／down／re-up 的验收对象。

## 后果

- 正面：未知归属和跨企业历史脏数据不会被迁移静默“修好”；回滚不会在 2.0 已产生新事实后破坏性删列；旧应用不能误写不兼容 Schema。
- 成本：发布包必须增加部署清单、归属审计报告、三角色连接配置、Writer 切流屏障、Hash 对账和恢复演练。
- 限制：POC20-002 没有证明生产数据、Schema drift、大表锁时、新旧应用候选或组织／RBAC／预算最终 DDL；这些仍是正式迁移和 Gate 2 Evidence。

## 被拒绝方案

| 方案 | 原因 |
| --- | --- |
| 按库中任意企业回填 | 多企业或脏数据时会不可逆串租户 |
| 给新增企业列设置默认企业 | 新旧 Writer 并存时会把遗漏上下文伪装成合法数据 |
| Writer 切流后继续允许 down，或让1.0二进制服务流量 | 会删除2.0-only事实，或用陈旧密码／角色重新授权已撤权身份 |
| 用当前超级用户账号验证只读兼容 | 超级用户可绕过权限／RLS，证明无效 |
| 用 `SELECT *` Hash 或列序号做兼容合同 | 新增列与 PostgreSQL drop／re-add 会产生假差异 |
