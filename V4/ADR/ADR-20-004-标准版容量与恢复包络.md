# ADR-20-004：标准版容量与恢复包络

> **历史容量方案（2026-08-12）**：本 ADR 的 1,000 Principal／1,000 万 Ledger 与旧工作包编号不再是当前首发承诺。当前标准容量以立项基线 §5／TRD §15 为准；更高档位只能由新候选 Evidence 提升。

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-08-11（Asia/Shanghai） |
| 适用版本 | 仟流智算 2.0 标准版 |
| 依据 | [POC20-004A Evidence](../Evidence/Stage01/POC20-004/README.md) |
| 复查触发 | 默认部署 BOM 改变；共享 SaaS；正式查询或账期算法改变；W20-19 证明更高档位；目标环境架构差异 |

## 决策

1. 标准版默认容量冻结为：100 成员、1,000 Principal、50 个并发 Gateway 请求、其中最多 20 个并发流式请求、每月 1,000 万条已结算 ledger line。
2. 默认性能门槛为：常用管理查询 P95≤500ms、Gateway 相对同机直连 Stub 的自增 TTFT P95≤150ms、正式账期检查＋分摊＋Statement ≤30 分钟。
3. 500 Gateway＋200 流式并发是 Stretch Goal，不是默认承诺。POC20-004A 在 `v1.0.0-final` 上虽然功能成功率为 100%，但自增 TTFT P95 为 788.328ms；100／50 为 193.859ms，只有 50／20 的 79.408ms 达到 150ms 门槛。只有 W20-19 在完整 2.0 同一候选上满足全部门槛，才能通过新 Evidence 提升默认值。
4. 月账本“1,000 万条”统一指一个月内完成 Settlement 的 ledger line 数量，不解释为 `usage_event` 和 `ledger_line` 各 1,000 万，也不按人均请求量反推。
5. 标准版默认 BOM 为 8 vCPU、16GB RAM、250GB SSD 的一企业一部署。PostgreSQL、Redis 可按目标环境外置，但容量合同不因外置自动提高；容器资源上限、磁盘水位和扩容点在 W20-18／W20-19 固化。
6. 恢复目标保持 RPO≤24h、RTO≤4h。每日加密备份、校验、保留和每月隔离 Restore 是实现合同；一次本地 Restore 只证明恢复路径与观测 RTO，不证明持续 RPO。
7. Stage 01 使用 POC20-004A 冻结开发目标。完整 2.0 容量资格验证属于 W20-18／W20-19：必须绑定同一 Commit、Tree、迁移、配置、BOM、数据集和 Evidence，失败时不允许发布。
8. W20-19 的正式负载模型必须补齐请求体分布、流式时长、稳态／峰值 RPS、读写比、上游失败率、Attempt 分布、冷热缓存和固定查询集；本 ADR 的并发数不能替代这些输入。

## 后果

- 正面：开发有明确、可达且已校准的默认值；不会把“500 并发都返回成功”误写成低延迟容量通过；10 人生产样本也不会冒充 2.0 容量证据。
- 成本：标准版默认档低于原 500／200 候选；若业务需要更高并发，必须先优化连接池、Quota 热点和结算写路径，并在完整候选复测。
- 限制：POC20-004A 不是完整 2.0 压测，BOM 也未在完整 Compose 和目标网络／磁盘上验证。

## 被拒绝方案

| 方案 | 原因 |
| --- | --- |
| 继续把 500／200 写为标准默认 | Final Tag 自增 TTFT P95 788.328ms，违反既定 150ms 门槛 |
| 只看成功率，不看延迟和账本守恒 | 会把排队和性能退化误判为容量通过 |
| 用 1.0 的 10 人生产数据外推 2.0 | 样本和自动化 Principal 负载不等价 |
| Stage 01 等待完整 2.0 候选后再退出 | 与 W20-18／W20-19 形成循环依赖，无法进入开发 |
| 把一次 Restore 写成 RPO 已通过 | RPO 依赖持续备份调度、加密、保留和监控，不是单次耗时 |
