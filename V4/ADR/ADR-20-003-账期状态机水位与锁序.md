# ADR-20-003：账期状态机、水位与锁序

> **历史方案（2026-08-12）**：本 ADR 属于旧账期扩张方案。当前 2.0 只继承 1.0 月账状态与锁序，具体以 PRD FR2-005／TRD §9 为准；下文不得据此新增第五状态或平台结账链。

| 项目 | 内容 |
| --- | --- |
| 状态 | `accepted` |
| 日期 | 2026-08-11（Asia/Shanghai） |
| 适用版本 | 仟流智算 2.0 标准版 |
| 依据 | [POC20-003 Evidence](../Evidence/Stage01/POC20-003/README.md) |
| 复查触发 | Settlement 可跨多个账期；账期状态合同变化；共享 SaaS；数据库不再是 PostgreSQL；结账引入外部调用 |

## 决策

1. `operating_period.status` 只允许 `DRAFT / CHECKING / CLOSED / REOPENED`。`period_check.result` 单独使用 `RUNNING / PASSED / FAILED`；`CHECKING_FAILED` 不是账期状态。任何检查失败都保存结构化结果并回到 `DRAFT`，旧 Statement 和当前版本指针不被删除。
2. Close 分为两个短事务阶段：
   - Fence：取得企业账期锁与 period 行锁，校验状态／`expected_version`，创建 RUNNING Check、设置 Lease，并提交 `CHECKING`；
   - Finalize：再次按相同顺序取锁，复核 Check、在途事实和水位，在同一事务内完成 Check、不可变 Statement、当前版本、`CLOSED` 和审计事件。
3. 正式结账水位为 `{settlement_seq, last_settled_at, last_settlement_id, transaction_snapshot}`。`settlement_seq` 在账期锁内随 Settlement 事务递增，是事实包含边界；时间和事务快照用于审计与复核，不能单独替代顺序。
4. 冻结锁序：
   - Settlement：请求行锁 → 按企业／账期排序的 advisory xact lock → period 行锁 → quota／lease 等稳定 ID 行锁；
   - Check／Close／Reopen／恢复：按企业／账期排序的 advisory xact lock → period 行锁 → check／statement／event；
   - Close 不得在取得账期锁后再反向锁 Request；完整性扫描只读 Request。
5. `CHECKING` 和 `CLOSED` 对目标账期的新 Settlement fail-closed。相同 Settlement ID 的终态重放仅在 request hash 一致时返回原结果，不再新增事实。
6. Close／Reopen 接口必须携带 `operation_id + expected_version + request_hash`：同键同参返回原结果；同键异参拒绝；旧 expected version 拒绝，防止 `close v1 → reopen → close v2 → 延迟 reopen v1` 的 ABA。
7. Statement 采用 append-only 版本。数据库运行角色不能 UPDATE／DELETE 历史 Statement；账期只指向本账期当前版本。正式实现保存：
   - `source_fact_hash`：水位内事实、归属和规则版本的稳定清单；
   - `statement_hash`：Canonical Statement envelope；
   - `hash_algorithm=SHA-256` 和 `canonicalization_version=statement-json-v1`。
8. Canonical JSON v1 固定对象键、领域数组稳定排序、Token 十进制整数字符串、金额固定精度十进制字符串、UTC ISO 毫秒、显式 `null`；拒绝 `undefined`、`NaN` 和 JavaScript 浮点结算。
9. CHECKING 使用可续租 Lease。恢复器取得相同账期锁和行锁，确认 Lease 过期且 Check ID 未变化后，把 Check 标为 `FAILED/CHECK_LEASE_EXPIRED` 并将账期回 `DRAFT`；不得跨外部服务持有数据库事务。
10. 账期归属按业务事实发生时间和企业 IANA timezone 的 `[period_start, period_end)` 计算，不按 Settlement 完成时间计算。

## 后果

- 正面：结账与迟到 Settlement 的先后关系可解释；水位可复算；重复 Close／Reopen 不会生成多版本；旧 Statement 不会被覆盖；崩溃不会永久卡在 CHECKING。
- 成本：正式 Schema 需增加 Check、Operation、Lease、水位、双 Hash 和不可变约束；Gateway 终态发布、Worker 恢复器与账期服务必须统一锁序；测试需覆盖并发、故障和跨时区。
- 限制：POC20-003 使用代表性 Overlay，没有证明正式迁移、真实进程／数据库故障、分摊守恒、跨语言 Canonical JSON 或目标规模性能。

## 被拒绝方案

| 方案 | 原因 |
| --- | --- |
| 增加 `CHECKING_FAILED` 第五态 | 把检查结果混入账期生命周期，Schema、前端和测试合同漂移 |
| 只用 `settled_at` 作为水位 | 并发提交可能同时间戳，无法表达权威包含顺序 |
| Close 持有一个长事务执行所有检查 | 会放大锁等待，并可能跨 HTTP／模型调用持锁 |
| Reopen 只判断当前状态 | 延迟请求可能重开新版本，产生 ABA |
| 重开时覆盖旧 Statement | 历史审计、Hash 和规则版本失真 |
| 只靠应用层约定不可变 | 运行脚本或错误 Repository 仍可更新历史版本 |
