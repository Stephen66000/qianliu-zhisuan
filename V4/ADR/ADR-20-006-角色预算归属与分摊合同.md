# ADR-20-006：角色、预算、归属与分摊合同

> **部分历史方案（2026-08-12）**：旧平台角色、团队／成本中心和复杂分摊审批已退出当前 2.0；部门预算与唯一归属只以 PRD FR2-004／TRD §8 为当前合同，下文旧工作包和角色条款不得直接执行。

## 决策

### 1. 角色与组织

1. 2.0 固定 1 类平台角色＋7 类企业角色：平台运营管理员；企业 Owner、AI 管理员、团队负责人、成本中心负责人、财务／审计、普通员工、项目负责人。
2. 团队、成本中心和项目是三个独立作用域；团队使用独立 `team + team_membership` 事实并以复合企业外键约束，不从组织类型或名称猜测。同一人可多角色叠加，但跨企业、Secret 不可回显、支持访问审批和职责分离边界不可被叠加绕过。
3. 财务／审计默认只读；企业 Owner 是结账／重开的最终执行者。AI 管理员不能授予 Owner／财务／平台角色。
4. 角色权限集是只读系统定义，2.0 只允许分配角色与 scope，不允许自定义角色。合法组合固定为 `ENTERPRISE_OWNER→ENTERPRISE`、`AI_ADMIN→ENTERPRISE|ORG_UNIT`、`TEAM_MANAGER→TEAM`、`COST_CENTER_MANAGER→COST_CENTER`、`FINANCE_AUDITOR→ENTERPRISE|COST_CENTER`、`EMPLOYEE→SELF`、`PROJECT_MANAGER→PROJECT`；`ENTERPRISE.scope_id=enterprise_id`、`SELF.scope_id=person_id`，其余必须引用同企业同类型对象，禁止空值／通配符／借位。AI 管理员只可分配 `EMPLOYEE@SELF / TEAM_MANAGER@TEAM / PROJECT_MANAGER@PROJECT`，其中组织级 AI 管理员仅可为其组织树成员分配 `EMPLOYEE@SELF`。完整 oracle 以角色权限矩阵为准。分摊独立使用 `allocation:read|manage|approve`，不得借用 budget 或 bill 权限；范围负责人 manage、企业 Owner read／approve、财务 read，Owner 不得 manage，同一自然人不得批准自己创建或最后修改的规则版本。

### 2. 预算

1. 1.0 Token 额度继续在 Gateway 热路径原子预占并可硬拒绝。
2. 2.0 企业、成本中心、团队和项目的金额预算首发只做阈值、告警、预测和经营复盘，不进入 Gateway 金额硬拒绝。
3. 金额预算可以记录超额策略意图，但 2.0 运行态只执行 `NOTICE / WARNING / CRITICAL` 通知；不得把异步已结算金额伪装成请求前精确余额。
4. 后续要启用金额硬拒绝，必须单独证明预占、释放、重试、Attempt、跨层预算和故障恢复原子性，并走 Planning Change。

### 3. 请求归属

1. 原始事实只保存 Principal 和请求事实；经营归属使用版本化 `usage_attribution_snapshot`，不复制 Token 与金额。
2. 初始归属顺序：
   - `DIRECT`：认证项目 Principal 或服务端已确认的显式项目／对象映射；
   - `RULE`：请求发生时唯一命中的已发布规则版本；
   - `UNASSIGNED`：无规则、同优先级多规则冲突、对象失效或数据不足。
3. 系统不得用名称、邮箱、最近使用、同名组织或“看起来最像”猜测归属。冲突进入未归属桶和检查项。
4. 人工修正生成 `MANUAL_CONFIRMED` 新版本并记录理由、操作者和前后值；旧快照不更新。Statement 使用对应结账版本选择的最新已确认快照。
5. 调岗、团队或成本中心变化只影响生效时间后的请求，不重算历史。

### 4. 分摊与价值

1. API 实际费用按 Ledger 原值归集，不进入套餐费用分摊；Coding Plan／订阅固定采购费用单独使用管理分摊。
2. 每个成本项的已发布规则只能选择一种依据：实际扣减额度比例、Token 比例、请求次数比例、固定比例或企业公共成本。不存在静默级联 fallback；分母为 0 或输入不完整时进入未分摊。
3. 分摊使用 `numeric(24,8)`／十进制库；按 8 位小数最大余数法分配尾差，相同余数按稳定对象 ID 排序。`已分摊 + 未分摊 = 可分摊采购费用` 必须精确成立。
4. 币种分别结算，禁止无汇率版本时跨币种相加。厂商权益百分比、本地 Token、API 实际费用和套餐管理分摊分栏展示。
5. 分摊规则和结果 append-only、版本化；重开产生新版本，不改旧 Statement。
6. 业务价值只接受获授权负责人手工提报／确认，保存口径、来源和确认人；Token、费用或模型不得自动推断绩效、ROI 或价值。

## 后果

- 产品边界更清楚：Token 硬控继续可靠，金额预算先可解释告警；不为首发制造一套伪精确的资金拒绝。
- 未归属与分摊尾差不会消失，历史组织变化也不会重写旧账。
- W20-05、W20-11～14 必须用属性测试、并发测试、负向权限和 Statement 守恒证明实现。

## 被拒绝方案

| 方案 | 原因 |
| --- | --- |
| 团队负责人与成本中心负责人合并 | 成员管理与经营归集边界不同，会造成越权 |
| 金额预算首发直接硬拒绝 | 当前只有结算后金额，缺少多层原子预占证明 |
| 冲突时任选一个归属 | 会把未知问题静默写成确定事实 |
| 规则变化重算历史账期 | 破坏旧 Statement 和审计可复现性 |
| 用 Token 自动评价人员价值 | Token 是消耗事实，不是绩效或业务价值 |
