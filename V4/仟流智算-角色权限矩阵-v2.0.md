## 1. 权限记号

| 记号 | 含义 |
| --- | --- |
| `M` | 在角色允许范围内管理／写入 |
| `S` | 只在被授权组织、团队、成本中心、项目或本人范围内管理／查看 |
| `R` | 只读 |
| `A` | 审批或最终确认；不自动包含业务明细读取 |
| `—` | 默认拒绝 |

矩阵是服务端授权合同，不是页面显隐表。最终判定始终使用 `enterprise + actor + role_version + resource + action + scope + object_owner`；前端隐藏不能替代拒绝。

## 3. 角色与 typed scope 合法组合

| 系统角色 code | 合法 `scope_type` | `scope_id` 语义 | 可分配人 |
| --- | --- | --- | --- |
| `ENTERPRISE_OWNER` | `ENTERPRISE` | 必须等于 `enterprise_id` | 既有企业 Owner |
| `AI_ADMIN` | `ENTERPRISE`、`ORG_UNIT` | 企业 ID 或同企业组织单元 ID | 企业 Owner |
| `TEAM_MANAGER` | `TEAM` | 同企业 `team.id` | 企业 Owner；企业级 AI 管理员白名单 |
| `COST_CENTER_MANAGER` | `COST_CENTER` | 同企业 `cost_center.id` | 企业 Owner |
| `FINANCE_AUDITOR` | `ENTERPRISE`、`COST_CENTER` | 企业 ID 或同企业成本中心 ID | 企业 Owner |
| `EMPLOYEE` | `SELF` | 必须等于被授权 `person_id` | 企业 Owner；AI 管理员白名单 |
| `PROJECT_MANAGER` | `PROJECT` | 同企业 `project.id` | 企业 Owner；企业级 AI 管理员白名单 |

`PLATFORM_ADMIN` 只存在于平台身份域，不进入企业 `role_assignment`。`AI_ADMIN@ORG_UNIT` 只可为服务端确认在该组织树内的成员分配 `EMPLOYEE@SELF`；团队和项目是独立对象，不得从名称、成员关系或组织类型推断其后代关系。空 `scope_id`、`*`、跨企业对象、类型借位均拒绝。本表是 Schema、授权引擎、`AT-005` 和 W20-05 的测试 oracle。

## 4. 强制边界

1. 平台运营管理员不是企业超级管理员：默认不能读取企业请求、人员、费用、账单、导出和 Secret；支持访问必须走独立的申请、批准、到期与撤销合同。
2. 企业 Owner 不能读取厂商 Secret 或已生成 Key 明文。系统只允许一次性展示新 Key；后续只能轮换，不能回显。
3. AI 管理员不能创建或授予企业 Owner、财务／审计和平台角色，不能批准自己的支持访问，不能替企业 Owner 结账或重开。
4. 团队负责人、成本中心负责人和项目负责人是三个独立角色；范围只取授权对象及其有效后代／关联，不自动扩展到同名对象或其他范围。
5. 财务／审计保持只读：可查看和导出企业经营与审计证据，但不管理 Secret、成员、资源、预算规则、分摊规则或账期状态。最终结账／重开由企业 Owner 执行。
6. 普通员工只能查看本人接入、额度、用量和经营摘要；不能查看其他人员、团队、项目或企业级明细。
7. 多角色权限在同一企业内取允许集合，但显式安全边界不被角色叠加绕过；跨企业永远拒绝。
8. Provider Secret 与 Principal Key 是两类凭证：前者由 AI 管理员 step-up 后发起并写入待确认密文，另一名企业 Owner 独立 step-up 后确认，发起人不得自批且 Owner 不得读取明文；后者允许普通员工和项目负责人按本人／项目范围自助创建、轮换或撤销，只在创建／轮换响应中一次性展示，后续只能看前缀、状态和指纹。
9. 分摊采用“范围负责人起草／建议、企业 Owner 批准、财务／审计只读复核”的三权合同。Owner 没有 `allocation:manage`；同一自然人即使叠加范围负责人角色，也不得批准自己创建或最后修改的规则版本。
10. 业务价值只能由自然人手工提报。团队、成本中心和项目负责人只能确认本范围，企业 Owner 执行企业级最终确认，财务／审计只读；确认生成新版本和审计，不能由 Token、费用或模型自动生成，也不能覆盖旧确认。
11. 平台管理员、企业 Owner、AI 管理员必须启用 TOTP；任何角色执行 Provider Secret 管理、结账／重开、完整导出或支持访问批准时必须在最近 10 分钟完成 step-up。Owner 双 share 恢复的管理员 A 创建与管理员 B 批准也必须各自拥有最近 10 分钟平台 step-up。前端提示、二次确认和角色叠加均不能绕过服务端 MFA 状态。
12. AI 管理员没有任何 `support_access:*` 权限；既有或外部报障渠道不属于支持访问授权状态机，提交报障本身不能换取企业数据访问权。
13. 2.0 的 1 类平台角色与 7 类企业角色均为只读系统定义；企业只能管理 `role_assignment + scope`，不能创建角色或编辑权限集合。自定义角色必须走 2.1／Planning Change。
14. 平台管理员必须一人一号、独立密码和 TOTP；首装一次性 bootstrap 仅在没有 ACTIVE 平台管理员时可用。最终销毁执行人与复核人按不同 `platform_admin_id`、独立 Session 和独立 step-up 判定，部署职责清单声明两账号持有人不同；禁止停用最后管理员或破坏尚未完成销毁任务所需的双账号能力。
15. AI 管理员不能重置 Owner、平台身份或任何人的 MFA。所有已登录本人均可在 step-up 后修改自身凭证；企业 Owner 只可重置非 Owner。所有 Owner 目标统一要求两个不同平台账号各自在最近 10 分钟 step-up 下，于 30 分钟待批窗口内完成创建／批准并各自交付一份独立 share；部署职责清单声明两账号持有人与目标 Owner 互不重叠。单 share 无效，批准后双 share 另有 30 分钟。平台身份禁止 peer 重置，只能本人恢复码或环境 Owner 批准的离线灾难恢复。任何恢复都不能改角色、代设置凭证或让管理员取得目标 Session。
16. Principal Key 的新明文只允许所属自然人本人或获授权项目负责人接收。企业 Owner／AI 管理员只能查看元数据并强制撤销、通知所属人自助重建；团队负责人只读本范围元数据，任何管理员都不能代创建／轮换。
17. 平台／企业普通 Session、各自 bootstrap、凭证恢复和生命周期恢复使用不同的 `__Host-` Cookie 名称、realm 和 CSRF token；双登录并存时不得互相覆盖或接受错 realm Cookie。
18. 支持访问请求 24 小时过期；批准后默认 30／上限 60 分钟，从批准时点起算且首次激活不续时。两个 TTL 互不替代，任一过期都只能重新申请。
19. `period_check_item:resolve` 只允许 Owner 或 TEAM／COST_CENTER／PROJECT typed scope 精确匹配的负责人；处理记录 append-only，只引用通过权威业务 API 完成的修正，不得直接改基础账本，处理后必须重新 Check。AI 管理员和财务／审计只读，普通员工无权。
20. Owner 凭证恢复的平台权限拆为 `identity:recover_owner_request|approve|reject`。创建者只能 request；另一名具备对应独立权限且完成本人 step-up 的平台管理员才能 approve 或 reject。拒绝／过期原子使 share A 失效且绝不生成 share B，任何旧单重放都拒绝。
21. 支持访问申请绑定唯一 `support_actor_id`，只能由该平台账号激活／使用；批准、拒绝和撤销只允许企业 Owner 在企业 realm 以本人 step-up 执行，平台账号没有批准权限。部署职责清单声明支持账号持有人不兼任该企业 Owner。2.0 运行时只校验账号、realm、权限、MFA、时限和状态机，不建设实名或跨 realm 同人去重；未披露的同人多账号是明确接受的残余风险，不能在 Evidence 中宣称已技术证明“真人不同”。
22. 普通生命周期请求只允许企业 Owner 从企业 realm 发起，平台运营账号只从平台 realm 按原请求执行或拒绝；部署职责清单声明执行账号持有人不兼任该企业 Owner。运行时校验 realm、账号、权限、step-up、24 小时请求、状态和 expected version，不把账号分轨或职责清单冒充真人身份技术证明。

## 5. 生命周期与版本

- 角色授权保存 `valid_from / valid_until / role_version / scope_type / scope_id`；
- 登录 Session、Key 和 Worker Job携带授权版本，人员停用、离职、角色撤销或企业停用后立即失效；
- 调岗只改变生效时点后的权限，历史账期、请求归属和旧 Statement 不重写；
- 最后一个 ACTIVE 企业 Owner 不得被删除或停用，必须先完成受审计的 Owner 交接；
- 批量授权部分失败时，成功项和失败项分别记录；重试不得重复授权。

## 6. W20-05 必测负向矩阵

- 直接 ID、列表、搜索、聚合、批量、导出、缓存、Worker、通知和审计入口；
- 同企业跨团队／成本中心／项目；跨企业同 UUID 模式；已撤权 Session／Key；过期支持访问；
- AI 管理员自授 Owner、平台人员自批支持访问、财务写入分摊或重开、负责人访问相邻范围；
- 多角色叠加、角色版本并发变更、最后 Owner、企业停用与恢复；
- 逐一覆盖 9 个合法 role×scope 组合及全部非法交叉组合；`ENTERPRISE/SELF` scope_id 错值、空值、通配符、跨企业和对象类型借位；组织级 AI 管理员尝试授予 TEAM／PROJECT 或组织树外 SELF；
- 所有拒绝返回稳定 reason code，不泄露目标对象是否存在，并形成不含敏感数据的安全审计。
