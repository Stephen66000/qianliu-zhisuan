## 3. 项目与成员模型

### 3.1 保留现有项目身份，分开核算生命周期

本期复用 `principal.type = PROJECT` 的 ID，不迁移所有项目、不新造第二套项目主键。增加项目核算配置扩展；UI 中经营用途与“接入配置”分区展示。

- 仅用于经营核算的项目无需先生成 Key 或配置模型、额度即可维护成员。当前主体创建与接入配置已经分离，实施时以真实创建路径验证。
- 已有项目 Key 保持原有授权和行为。新增成员不会向成员发项目 Key，也不会继承项目模型权限。
- 新增“结束成员归集”操作和生效时点，限制成员权重可应用的区间；该操作不调用原有“停用主体”接口，不撤销任何 Key。
- 结束后仍发生的项目 Key 直接调用，继续保留并归入其直接来源，可标为“核算结束后直接调用”，不隐藏真实消耗。
- 原有停用/归档的调用权限效果不变。归集侧独立记录其处理：归档项目不接收新的成员配置；既有历史与迟到结算保留。若需终止自动归集，必须有可追溯的核算结束时点，不能用查询时的当前状态反推历史。
- 负责人不是默认成员；加入成员、设置权重均需显式操作。

### 3.2 成员关系

一名员工可以参加多个项目，一个项目可以有多名员工。参与关系至少记录项目、员工、加入时间、退出时间、操作人、记录时间、原因和版本。

规则：

1. 只选择同企业员工主体；不要求员工已绑定企业微信人员。
2. 同一员工在同一项目的有效参与区间不得重叠；允许退出后再加入，保留独立参与记录。
3. 区间采用 `[加入时刻, 退出时刻)`；退出为空表示尚未确定。允许预定未来加入/退出。
4. 人数动态计算：当前成员数、所选时点成员数、账期参与人数分别展示。账期参与人数按员工去重，不把多次加入算成多个人。
5. 成员数、发生用量人数和产生非零归集份额人数分开，不能互相替代。
6. 已有历史参与事实不能物理删除；误录通过修订/撤销版本留痕。旧计算批次仍能引用旧版本。
7. 员工停用不删除或自动关闭参与历史；员工恢复也不自动恢复已结束的参与关系。归集匹配仅依据源请求开始时有效的参与区间、权重区间和项目核算区间，不以查询时员工的 ACTIVE/DISABLED 状态筛除源事实。
8. 停用前已开始、停用后才完成/结算的请求仍按开始时点归集。开放参与关系继续存在，恢复后取得有效授权的新请求也按当时规则匹配；需要终止项目关系时单独记录退出时点，不能把停用等同于退出。
9. 停用后的新调用仍由原授权链拒绝，与剩余额度无关。当前 `principal-repository.ts` 的 `deactivate` 撤销有效 Key/Grant，`apps/gateway/src/auth/principal-auth.ts` 同时校验 Key 与主体状态。若存在异常记账事实，归集仍按其时间证据处理，另交既有异常流程核查，不默许越权调用或删除消耗。以上为代码核查，不代表本轮已运行停用回归。

### 3.3 权重规则

- 权重是企业设定的“用量归集比例”，不是系统测得的真实工时。
- 用整数基点 `weight_bps` 保存，10000 表示 100%，最小调整为 0.01%。单项目允许 0～100%。
- 对同一员工任意有效时刻，该员工所有带权重的项目关系中，同时满足参与区间、权重区间和项目核算区间的权重总和必须 ≤10000；小于 10000 时保留剩余，不自动归一化。该约束不包含项目主体直接调用或逐请求人工指定；二者不是员工权重关系。
- “权重规则 100%（专属规则）”指该时段某项目的 `weight_bps=10000`，仍属于自动执行的成员权重规则，走 §4.2 优先级 3。它不等于“人工指定”，也不能因为只剩一个成员关系而自动产生。
- 权重有自己的起止时间：员工继续参加项目但权重变化，必须形成新段。
- 权重有效区间必须落在参与区间和项目核算有效区间内；缩短参与区间或结束项目时，同一事务关闭/修订受影响权重，不改变其他项目权重。
- 缺少规则时不均分、不猜测、不阻断 AI 调用，进入未分配。
- **0% 规则段是显式、可审计、可展示的规则段**：`weight_bps=0` 合法保存、出现在规则时间线与审计记录中，不得折叠、删除或改写为"无规则"；计算结果仍全部进入未分配，其未分配原因码为权重余量（余量=10000），不得标注为"无生效规则"。
- 采用员工级规则集合版本：一次调整可原子提交 A、B 等多个项目的新份额，防止逐项保存产生中间超配。
- 两个管理员同时给同一员工增加项目权重时，数据库事务按企业＋员工串行校验，并校验预期版本；返回冲突区间和项目，不允许前端校验后直接写入。

1. 以既有经营账选取的实际消耗账本行为输入，不直接使用“仅成功请求”的用量概览代替；有实际消耗的失败 Attempt 沿用经营账原规则。
2. 逐 `ledger_line.id` 保留证据，原请求 ID、Attempt ID、员工/项目主体、资源、模型、币种、Token 类型、质量一并带入。
3. **匹配关系时间**沿用 `ai_request.started_at`。同一请求的各 Attempt 按同一开始时点匹配，不因重试跨越退出时刻而重新归属；本期不尝试拆分一次请求内部的真实使用时长。
4. **进入账期时间**沿用经营账当前有效的结算/兼容时间合同。跨月开始、次月结算时，以开始时点选规则、以既有入账规则选月份，并在明细同时展示两种时间。
5. 本期项目核算日期按现有经营账的 Asia/Shanghai 月份口径展示；接口保存带时区时间戳，不改全产品时区。企业时区不同须在界面和合同注明，不能隐式使用浏览器时区。
6. 日期型退出输入若表达“最后参与日 9 月 20 日”，后端转换为 9 月 21 日 00:00 排他边界；**该 00:00 一律按 Asia/Shanghai（UTC+08:00）自然日零点计算**，不使用服务器进程时区或浏览器时区。界面明确“参与至该日结束”。精确时刻输入保持其原意。
7. Token 总量沿用输入＋输出，不把缓存、推理细分或倍率扣减再加一次。源质量为估算、混合、未知时，结果保留质量；未知不伪装成实际值或 0。

### 4.2 归集优先级及防重复

术语固定：**项目直接调用**来自项目主体；**人工指定**是管理员对具体请求记录的项目归属；**成员规则分摊**是系统按生效权重计算的份额。成员规则由人配置不代表它属于“人工指定”；100% 专属规则仍属于成员规则分摊。

| 顺序 | 条件 | 处理 |
| --- | --- | --- |
| 1 | 源主体就是项目 | 100% 项目直接调用，不进入员工分摊池 |
| 2 | 员工请求已有有效人工项目指定 | 100% 归到指定项目；本次源行不再参与自动权重分摊 |
| 3 | 员工在请求开始时有有效参与关系和权重 | 按各项目比例归集，剩余进入未分配 |
| 4 | 无有效规则，或缺少可靠关系 | 保留未分配及原因，不阻断调用 |

已有人工指定按其有效归属版本读取；不能按“项目是否有部门”判断人工指定是否存在。缺项目部门不应丢失明确项目目标。历史来源间出现冲突时，输出冲突证据，不静默选一个。

原有人工指定入口和原有影响范围保持不变。本期不新增项目账内“改写原请求归属”的快捷编辑；项目归集明细只读。后续如增加修正入口，应写管理归集覆盖层，不能借此扩展原始事实修改权限。

项目直接调用即便无法识别真实员工，也必须保留“项目主体调用”来源，不根据负责人或成员列表猜调用者。

### 4.3 分段及守恒

对员工的所有参与边界、权重边界和项目核算结束边界求有序并集，生成规则恒定的半开时间段。账期内源行按请求开始时间匹配该段；匹配所需关系可跨账期读取，不能先裁掉账期之前的关系。

先从同一批次、同一账期的源行集合中划分三个互斥集合：项目直接调用、已有人工指定的员工请求、其余员工请求。其余员工请求构成员工待分配池，其中包含完全无规则的请求。直接调用和人工指定的源行不能再次进入待分配池。

```text
自动归集到项目 p 的 Token = Σ（待分配池内源行 Token × 该时点项目 p 的权重）
待分配池源行的未分配权重 = 1 − Σ（适用项目权重）

员工待分配池守恒：
所有项目的自动归集 Token + 未分配 Token = 员工待分配池可计量 Token

全来源守恒：
项目直接调用 Token + 人工指定 Token + 自动归集 Token + 未分配 Token
= 同一源行集合的可计量 Token 总量

单项目汇总：
项目 p 的归集 Token = p 的直接调用 Token + p 的人工指定 Token + p 的自动归集 Token
```

源行的优先级路径互斥；待分配池内允许同一源行产生多个项目及未分配份额，各份额不重复计量并完整覆盖该行可计量量。不能把“路径互斥”误解为一条源行只能有一个结果目标。除守恒外，同时校验每个源行的覆盖和去重，不能让“一行漏算＋另一行重复”恰好抵消。逐源行、逐项目、批次汇总均保存核对结果。未知用量的源行必须保留质量与覆盖证据，不把未知数值当 0 纳入“精确守恒已通过”。

计算底层按源行执行，展示层可以按“员工＋项目＋时间段＋规则版本”汇总。不能先用整月总量乘平均权重，也不能在成员午间变更时直接使用整日粗粒度桶。

### 4.4 Token、费用和次数

- 原始 Token 仍为整数。归集 Token 是管理份额，可保留 4 位小数；基点权重下可精确表达，不逐行取整丢失尾数。用 BigInt/Decimal 和数据库 numeric，禁止用浮点 Number 累加账务值。
- 输入、输出、缓存、推理细分分别分配，输入＋输出形成归集总 Token；列表格式化不改变存储精度。
- API 金额以原源行的已知费用和币种为依据乘权重，不重新定价、不使用跨模型平均价、不自行换汇。
- Coding Plan 先复用当前经营账的套餐成本分配到源行结果，再按项目规则分配。现有权威来源为 `provider_finance_event.cash_paid_cny`，因此本期 `package_line_cost` 是 CNY 成本事实，归集结果显式保存 `package_cost_currency='CNY'`。资源全月分母、既有月费口径不随项目筛选、分页或权重变化而改变。
- 费用采用既有账务精度；必要舍入对同一源行、同一费用种类、同一币种使用确定性最大余数法，项目 ID/未分配标识作为稳定平局顺序。只对非零份额目标分配尾差。
- 对同一源行集合内的已知金额，每个费用种类、每个币种分别满足“直接调用金额＋人工指定金额＋自动归集金额＋未分配金额＝相同精度的源金额”。API CNY、API USD 和套餐 CNY 分别守恒、分别展示，禁止跨币种直接求和；本期不存在套餐 USD 的隐式默认。员工待分配池内部另验自动归集与未分配之和；未知费用另列完整性缺口。源行成本尚未标准化精度时，在共享成本适配层明确精度和尾差规则，并证明不改变原员工账及总账。资源级无源行可承接的套餐待分配成本另表核对，不硬塞进这条源行公式。
- API 已知部分、未知费用笔数、套餐无法分配成本分别保留。不能把一笔没有 Token 的资源级套餐余额伪造为员工项目用量；若需展示，放入独立“资源级待分配成本”区，不混入成员余量。
- 请求次数按目标内 request ID 去重，不乘权重。一个请求可涉及多个项目，各项目“涉及请求数”不可相加当企业请求总数。
- 归集权重不是 Token 质量置信度；规则分摊与实报/估算等两类标签分别展示。

### 4.5 未分配与统计视角

本期默认将剩余放入“未分配”，原因区分：无参与关系、无生效规则、权重余量、历史关系未知、规则待修复等。不会把剩余自动解释成公共事务或其他工作。

公共事务/其他工作分类是可后续增加的管理标签，本期不新增公共成本分类体系。这样不妨碍保留全部余量，也不会把未知用途变成已知用途。

员工账与项目账是同一事实的不同维度，严禁相加。项目账必须分别给出源总量、已归集量、未分配量和完整性状态；按项目搜索后仍可解释筛选汇总与全局核对总数的区别。

员工所属部门与项目所属部门分别保留。本期不把项目分摊结果重新汇入部门账，也不重算首页“活跃项目”。首页或其他入口跳到项目账时，应标明原调用口径与新归集口径的差别，避免数字同名却含义不同。

## 6. 数据设计建议

以下为逻辑对象及建议命名，最终迁移序号按开工时仓库实际状态确定。避免把表名建议当作已有数据库结构。

| 逻辑对象 | 建议名称 | 核心字段与约束 |
| --- | --- | --- |
| 项目核算配置版本 | `project_accounting_profile_version` | enterprise、project principal、核算起止、配置版本、操作者、原因；与调用 status 分离 |
| 成员参与记录及修订 | `project_membership` / `project_membership_revision` | 稳定参与 ID、员工/项目、参与区间、revision、supersedes、修订状态；当前有效修订间不能重叠 |
| 员工归集规则集合 | `employee_project_allocation_policy` | enterprise、employee、policy version、当前版本指针/发布状态、审计字段；员工维度原子发布 |
| 规则集合内时间段与份额 | `employee_project_allocation_rule` | policy ID、member revision、project、valid_from/until、weight_bps；集合内各段守恒、关系覆盖 |
| 归集计算批次 | `project_allocation_run` | enterprise、month、schema/algorithm version、规则/关系/人工归属输入摘要、源事实标识、asOf、状态、计算耗时、完整性、结果 hash |
| 源行归集结果 | `project_allocation_line` | run ID、ledger line/request/Attempt、源主体、目标项目或未分配、来源、时间段、规则/关系版本、权重、各 Token/成本份额、`api_cost_currency`、固定为 CNY 的 `package_cost_currency`、质量、原因 |

实现要求：

1. 所有引用包含企业边界，数据库外键和服务端校验共同防跨企业引用。
2. 当前修订与历史修订分离；历史版本允许时间覆盖，但不能同时成为有效版本。禁止简单在所有历史行上加互斥约束，导致合法修订无法保存。
3. 发布员工规则集合时持有员工级锁并重验全部重叠区间。成员、核算终止时间变化必须与相关规则变更保持同一事务一致性。
4. 计算结果只追加，不覆盖已发布批次。源行＋目标＋批次设唯一约束；未分配目标使用明确唯一策略，不能因 NULL 唯一语义生成重复行。
5. 保存足以重放的输入引用和版本，不能只存最终合计。被引用的关系、规则、人工归属、源金额证据在保留期内不可清除。**保留策略（本期冻结）**：现场核验现有代码未发现针对 ledger/归属快照/账单版本的 TTL 或自动清理机制（仅有 append-only 触发器与迁移 down 数据守卫）；据此本期冻结为——不引入任何自动清理，被任何计算批次或账单版本引用的对象在引用存续期间绝不可删除；未来归档/清理另立独立方案（含保留期定义与迁移），不属于本期范围。
6. 一份源事实输入快照同时供总计和明细使用；不能分别查询时碰上新结算，形成“明细之和不等于列表”。
7. 索引覆盖企业/员工/有效区间、企业/项目/参与区间、批次/项目/源行、批次/未分配/分页。先用实际查询计划确定，不一次新增无用索引。
8. 新表是管理归集层，禁止把其多项目结果回写为多个原始 usage 或 ledger 行。

主体类型合同：沿用 `/principals/:id/...` 的既有路径风格，不为本功能改造旧路由；参数名 employeeId/projectId 本身不构成类型保证。新增路由使用统一服务端解析器，先按 `enterprise_id + id + type` 查询：员工规则接口要求 EMPLOYEE，成员/核算生命周期/项目明细接口要求 PROJECT；成员请求体中的员工 ID 也要求同企业 EMPLOYEE。GET、预览、写入及仓储入口均执行类型边界校验，不能仅校验 UUID。外部对不存在、跨企业或类型不匹配返回统一不可访问/不存在语义，避免泄露其他企业对象；内部日志记录具体原因，状态合法性另验。权限映射及静态/动态路由匹配在 WP01 一并验证。

权重编辑唯一合同：单项目页面不得读取后再提交员工完整规则集合。客户端只提交当前项目的修改意图：员工 ID、项目 ID（由路径锁定）、目标时间段/权重、`expected_policy_version`、原因和幂等键。服务端以“企业＋员工”取得锁，读取当前完整规则，替换当前项目对应部分，原样保留其他项目规则，执行全时间线校验后发布新完整版本。提交期间当前版本已变化时返回 `409 allocation_policy_conflict`，附最新版本和需重新预览标志，不自动覆盖。

预览按调用者权限脱敏：当前项目和有权查看的其他项目可返回名称、区间和占比；无权查看的项目只按冲突时间段返回 `hidden_project_count`、`hidden_weight_bps`、`available_bps` 和 `remaining_bps`，不返回项目 ID、名称、成员或费用。若隐藏规则导致超配，返回同样的匿名冲突段。只有具备企业级项目配置权限的独立管理入口才能读取/提交完整规则集合；该入口不是本期单项目页面的依赖。

预览汇总数字的精确口径（同一员工、同一参考时点 `t`，冻结定义）：

- `hidden_weight_bps(t)` ＝ 该时点无权查看项目生效权重之和。
- `available_bps(t)` ＝ `10000 − hidden_weight_bps(t)`：保留隐藏规则后，当前项目可占用的最大容量（即可见项目全部让渡时的上限）。
- `remaining_bps(t)` ＝ `available_bps(t) − current_project_weight_bps(t)`：应用当前项目意图（预览态）或当前生效权重（查看态）之后的剩余容量，供可见的其他项目继续分配；可见其他项目若继续占用，从该值中扣减并在可见明细中同步展示。
- 预览数字不替代校验：任何时刻的权重和 ≤10000 仍由服务端锁内全时间线校验兜底。

算例：隐藏项目合计 3000bps、当前项目意图 2500bps → `available_bps=7000`、`remaining_bps=4500`；若可见的 B 项目此时占 2000bps，则 B 展示在可见明细中，当前项目实际可再占用 `4500−2000=2500`bps。

项目列表、状态与明细 GET 均纯读，不创建计算任务；手工重建 POST 需要经营账操作权限。首次初始化及系统自动刷新见 §8.1。

接口实现时遵循仓库真实前缀、Schema、分页和错误风格；上述新增路径不是当前已存在接口。明细分页须稳定排序并固定 run ID，分页期间有新数据不能造成跳行和重复。

错误区分非法区间、权重超额、关系覆盖不足、跨企业、对象不存在、并发版本冲突、账期已关闭、计算未完成。返回结构化字段和具体冲突时间段，不把失败当空结果。

### 7.3 项目管理体验

- 现有项目行提供“成员与归集”入口；保持使用主体页原有员工功能。

## 8. 计算更新、历史修正与结账

### 8.1 更新机制

1. 项目/成员/权重写事务记录变更事件和受影响员工、时间区间；事务提交后触发有界重建，不同步扫描全企业历史。
2. 首次计算由管理员启用该企业/账期功能时在同一事务登记持久初始化任务；打开项目账、分页、刷新页面和状态 GET 均只读取数据，不创建任务。后续源事实变化由系统变更消费/有界补偿扫描登记待更新状态；识别接口在 WP01 核验，缺少可靠水位时补管理侧机制，不假设现成的完整变更序列。不得只依赖最大 settled_at，以免漏掉迟到插入和旧日期修正。有可用批次先显示并注明更新时间/过期状态，后台刷新完成后切换；无批次显示待计算状态，不返回假的 0。
3. 规则变更按请求开始时间查受影响源行，再映射到实际入账月份，包含跨月结算；不简单按规则变更月份失效一个缓存。
4. 计算使用固定输入快照，结果校验成功后原子切换当前批次。中途失败不发布部分结果。
5. 同一输入摘要与算法版本重复任务幂等**（幂等限定于当前发布：输入回到历史状态时确定性重发布为 current，`76-CONTRACT-AMENDMENT-01`）**；分页查询指定批次。标记过期、重建触发与原始 Gateway 请求解耦。
6. 多实例任务准入按“企业＋账期”去重，同一时刻至多一个 QUEUED/RUNNING 主任务；不同算法版本也不能并发发布同一账期当前结果。规则/事实事件合并到持久 dirty generation。运行中的新变更只推进待处理代次，完成后对比输入代次再安排一次补算，不因事件或用户数膨胀成多份任务。
7. 建议默认自动刷新最小启动间隔 30 秒（WP01 按负载确认），以 last_started_at 固定判断，不因每次事件滑动延后而永久饿死。首个初始化任务不受该间隔限制；已有任务时返回其状态。手工操作可使到期前的已合并任务提前就绪，但同一操作受服务端限频且不能绕过单任务约束、并发限制或版本校验。
8. 失败按有界指数退避重试，默认最多 3 次，超过后标为失败并保留 dirty 状态，由有权限的手工重试或新输入触发后续批次；GET 不重置失败计数。Worker 崩溃通过租约超时回收，发布校验任务/租约的执行者代次，避免旧 Worker 回来覆盖新结果。执行者代次与输入 dirty generation 是两个概念：合法执行者可发布其固定输入快照的完整批次；若计算期间已有新输入，发布后标记待更新并合并补算，不能要求其输入永远追平持续写入才允许展示首批结果，也不能将过期批次冒充最新。当前版本切换不得退回较旧输入结果。系统任务与管理员手工任务分别记录 actor。
9. 结账要求所锁定输入对应的最新可用批次；冷却中可等待或由有权限操作促发，但不能用旧批次结账。迟到数据在既有结账政策下处理；不得自动重开已关闭账单。

### 8.2 旧历史与规则回填

- 不从负责人、当前通讯录、当前成员反推出历史参与关系。历史无证据即保持旧口径或未分配。
- 首次启用不自动重算所有旧月份。选定一个未关闭试点账期和明确起始时点，录入关系后生成项目归集结果。
- 支持管理员给未关闭账期补录参与时间或权重，须填写原因并预览影响；结果形成新批次，旧结果可追溯。
- 对已关闭账期，保存当前/未来规则不应被历史冻结阻断；但不改冻结结果。若用户明确要更正该账期，沿用有权限、有原因的重开流程，生成新账单版本，保留旧版本。

### 8.3 结账兼容

- 结账冻结采用唯一方案：在 `operating_bill_version.snapshot.sourceFacts.projectAllocation` 保存不可变批次引用和小型核对摘要，不把逐源行归集明细复制进账单 JSON。冻结内容固定为 `run_id`、`schema_version`、`algorithm_version`、`input_digest`、`result_hash`、守恒汇总、完整性状态和生成时间；如需展示规则/关系版本，只保存版本摘要或 digest，不嵌入整套规则和关系。
- 逐源行明细继续保存在不可变的 `project_allocation_line`，关闭账期始终通过冻结的 `run_id` 读取。被任一账单版本引用的 `project_allocation_run` 及其明细禁止删除、改写或重新指向；回退和归档策略必须保留该引用可解析。若 JSON 引用无法用外键表达，数据库不可变/删除保护和结账读取完整性测试必须补足，不能依赖应用约定。
- 旧 `sourceFacts.accountFacts` 保持原意，继续支撑员工账和旧账读取；不得替换成一对多分摊行。
- 新功能已启用的账期结账前验证归集批次与锁定的源事实/规则版本一致。并发结算、规则修改、人工指定与结账按统一锁序或版本检查串行化；发现变化则重算或明确拒绝该次结账。
- “计算已完成但存在合法未分配”允许结账；“没有计算完成/守恒失败”不能冒充完整项目账冻结。事实质量不完整沿用既有允许不完整结账政策，并保留标识。
- 特性未启用的账期维持原结账路径。读取旧 schema 不要求重开才能查看原汇总；缺新增明细时给出历史能力说明。

## 9. 权限、审计与数据安全

本期复用现有模块级 view/operate 权限，**不新增任何权限实体/角色/码表**。权限映射冻结为现有 12 模块体系：项目成员/规则/核算生命周期写入属于 `principals`（使用主体）模块 operate；项目成员与成员历史读取属于 `principals` view；**"企业级项目配置权限"＝ `principals` 模块 operate**——企业级完整规则集合入口（读取 `GET /principals/:employeeId/project-allocation-policy` 与提交完整集合）一律要求该权限，无 operate 仅 view 的角色访问完整规则集合入口返回 403，跨企业/类型不符返回统一 404 语义（负例列入 A01）；项目账读取属于经营账查看权限（`billing` view），手工重建及账期修正按经营账操作权限（`billing` operate）检查；系统自动任务依据已授权启用范围执行，记录 SYSTEM actor，不借只读用户的页面请求取得写权限。规则预览若返回金额，另需经营账查看权限。

项目负责人不自动获权；参与项目也不授予 AI 模型或账单查看权限。所有 API 在服务端验证企业边界，不以客户端隐藏按钮代替授权。

审计至少包含操作者、记录时间、生效时间、对象、旧新版本、原因、幂等键和受影响账期。仅保存计量元数据，不引入提示词、回答正文、员工文件或工作内容采集。

## 12. 验证方法、性能和证据

### 12.1 检查顺序

1. 领域测试：时间边界、优先级、权重守恒、精度与稳定性；使用独立金标和性质验证，不只复制实现公式。
2. 隔离 PostgreSQL 集成测试：迁移、约束、锁、幂等、并发、旧 schema、结果与源账本对账。
3. Control API 集成测试：企业/权限、版本冲突、状态、分页与结账。
4. Web 与 E2E：项目成员管理到项目账的完整真实入口，以及员工/其他模块无回归。
5. 受影响类型检查、Lint、构建；再执行当前适用的覆盖率、架构、文件大小、重复率、依赖安全、canary 和变异检查。以开工时门禁要求为准，失败不能绕过或用其他历史 PASS 代替。

当前根目录提供 `corepack pnpm@11.11.0 run typecheck`、`lint`、`test`、`test:integration`、`test:e2e`、`build`、`quality`、`quality:mutation` 等入口。具体定向用例命令在 WP01 按实际测试配置记录，本计划不宣称这些命令已执行。

### 12.2 不变性核对

固定时钟和隔离测试数据，保存新增关系前后的原始表关键字段摘要、员工账、月度经营总览、部门账、资金账、首页指标、**用量总览（含其物化桶/覆盖度状态）**响应。只新增/修改成员和权重后对比，要求全部保持原值。项目账只在其新归集字段/投影发生预期变化。

另测共享查询重构前后响应一致；原有人工指定等既有操作按旧合同回归，不把其原有副作用混同于新增成员归集行为。

### 12.3 性能目标

WP01 在记录机器、数据库配置和现有基线后冻结指标。建议用合成数据覆盖 1000 员工、200 项目、单月 100 万源账本行及单员工多次规则变化；数据量不是对客户规模的承诺。

- 项目账已生成批次下首屏/分页 API p95 目标 ≤1 秒；规则保存/冲突预览 p95 目标 ≤1 秒，大范围历史影响扫描采用异步预览。
- 单月 100 万行完整重建建议目标 ≤5 分钟；单员工区间修改只重算受影响部分或账期，不触发全企业无界扫描。
- 记录峰值内存、查询计划、锁等待、批次大小和 Worker 重启恢复；列表不按每个项目分别扫描原账本，避免 N+1。
- 归集任务限并发、分批读取；压测对照 Gateway p95 延迟不应比同负载基线增加超过 5%，且不新增调用错误。超目标先优化/限流，不通过更改原计费路径解决。
- 若环境不足以验证规模目标，标记性能证据缺口，不能宣称生产规模已验收。

### 12.4 证据组织

建议证据目录：`V4/Evidence/PROJECT-ALLOCATION-20260919/<candidate>/`；实施前核对并记录其与现行 SOP 的对应关系，不改写其他工作包证据路径。

## 13. 迁移、启用与回退

1. 增量迁移建新表/索引，不批量修改原账本、既有项目 ID 或负责人关系，不猜测历史成员。
2. 正式迁移必须从重新冻结的 WP01 合同生成或逐项核对。现有 `0076_project_allocation.js` 是无效草稿，已知包含索引引用不存在列的错误；不得原样执行、补丁式续做或作为“迁移已建立”的证据。新候选的迁移编号按目标基线实际最新编号确定，不预占 0076。
3. 应用先具备新旧 schema 兼容读取，再按企业/明确起始账期开启项目归集；默认旧数据维持原路径。
