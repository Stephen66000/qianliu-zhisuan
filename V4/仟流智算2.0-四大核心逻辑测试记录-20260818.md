## 一、测试结论摘要

本次不是对页面“有没有”做静态检查，而是围绕企业真正关心的四个问题，使用已部署 2.0 的真实页面和请求数据进行查验：

1. 现在还能不能用、还能用多久；
2. 谁用了、用了多少、用在哪里；
3. 什么时候用更划算；
4. 为什么放行、切换或拒绝。

### 结果统计

| 结论 | 数量 | 说明 |
| --- | ---: | --- |
| 通过 | 11 | 页面、操作和数据口径均达到本次测试要求 |
| 待确认 | 21 | 页面或部分事实存在，但缺少真实样本、历史对比或下钻证据 |
| 暂未测试 | 6 | 线上没有对应事件，或缺少组织／并发／故障测试前置条件 |
| 不通过 | 2 | 已确认存在可复现的产品闭环问题 |
| P1 记录 | 3 | CP-02、UC-10、MD-10；问题池另有后续 P1 设计项 |

### 总体判断

- 2.0 的四条底层逻辑并没有被页面重做破坏，资源、用量、请求、路由、计量和账单事实基本能够看到。
- 真实可用链路已经跑通：资源正常、员工日／周／月用量可看、项目用量可看、请求可以下钻到 Attempt／Usage／计价证据。
- 当前主要问题不是“没有功能”，而是：部分场景缺少真实测试样本；部分管理页面把内部技术事实直接倾倒给用户；结账管理没有先把本月采购和花费列出来供负责人确认；策略和计价的生命周期、解释和恢复入口不完整。
- 结论不能写成“40 条全部通过”。准确结论是：**11 条已通过，21 条待确认，6 条由于前置样本不足暂未测试，2 条已确认不通过。**

## 二、统一测试口径

### 1. 每个场景检查五件事

`当前事实 → 发生原因 → 系统动作 → 执行结果 → 可追溯证据`

### 2. 结果分类

- `通过`：页面、数据、操作和证据闭环成立。
- `待确认`：页面有内容，但缺少真实事件、历史版本、组织数据或可比较样本。
- `暂未测试`：没有在生产制造故障，或当前没有对应业务样本。
- `数据缺口`：应该有数据，但缺失、过期或来源不清。
- `解释缺口`：结果存在，但用户无法知道为什么放行、切换、拒绝、归集或结账。
- `闭环缺口`：有输入框或状态，但缺少执行、恢复、确认或后续动作。

### 3. 安全边界

凭证失效、熔断、并发抢额度、额度耗尽、调度规则发布和账期冻结均没有在生产环境人为制造。能用历史事件或已存在的真实请求验证就验证，没有样本就记录“暂未测试”，不把演示操作冒充真实证据。

## 三、维度一：持续生产（CP-01～CP-10）

客户问题：**现在还能不能用？还能用多久？出问题后什么时候恢复？**

### CP-01 全部资源正常 —— 通过

- 入口：`运行保障`、`厂商资源 → 资源健康与异常`、`用量账本 → 请求明细`。
- 现场结果：运行保障显示活跃熔断 0、受阻资源 0、影响请求 0、降级资源 0；Kimi、DeepSeek、智谱均正常、允许请求；请求明细存在真实成功请求。
- 结论：资源健康、可用性和真实请求结果一致，CP-01 通过。

### CP-02 API 余额逐渐降低 —— 数据缺口／待确认／P1

- DeepSeek 经营快照显示：充值 `109.41 CNY`、当前余额 `68.00 CNY`、本期费用 `47.41 CNY`。
- 余额更新时间为 `2026-08-03 11:58`，距离本次测试日已经过期；累计费用和费用周期结束为空。
- 供给预测仍给出预计耗尽、覆盖时长和 `MEDIUM` 可信度，但不能确认预测使用的是当天余额。
- 结论：页面有余额快照，但不能稳定回答“现在还能用多久”。已登记 `POOL20-025`，建议按资源每日自动同步余额／费用，保留快照、同步状态、失败原因和数据时间。

### CP-03 消耗高峰后的预测变化 —— 展示有内容，行为待确认

- 供给预测是只读展示，不存在“点击刷新”操作。

- 当前页面没有历史速度对比，也不能在生产制造高峰验证前后变化。
- 结论：展示字段可查，预测自动刷新能力归入 `POOL20-025`，CP-03 暂不能证明预测会随高峰立即变化。

### CP-04 Coding Plan 五小时额度 —— 数据缺口／待确认

- 结论：Kimi 和智谱的窗口事实可见；智谱五小时重置时间缺失，但原因尚未归因给厂商、API、适配层或前端。

### CP-06 Provider 凭证异常 —— 暂未测试

- 资源健康页面中 Kimi、DeepSeek、智谱均正常，允许请求，无凭证失效、认证失败或连接失败样本。
- 未在生产环境故意修改 Key。
- 结论：当前没有可观察凭证异常事件，不能以“没有异常”代替测试通过。

### CP-07 主资源连续失败并熔断 —— 暂未测试

- `运行保障 → 熔断事件`勾选“显示历史事件”后仍为空。
- `可用性规则`页有新建草稿入口，但没有看到已发布生效规则。
- 结论：没有规则和历史事件，不能验证连续失败、切换备用资源和恢复链路。

### CP-08 厂商恢复正常 —— 解释缺口／待确认

- `异常中心`存在多条 `AUTO_RESOLVED` 运行保障预警，原因包括上游技术故障、上游配置错误。
- 同时存在一条 `主体额度使用异常 · OPEN`，额度使用率 119.8%，超额 1,971,477。
- `AUTO_RESOLVED` 卡片不能展开，无法查看事件时间、恢复时间、影响资源、影响请求和恢复后放行结果。
- 结论：有恢复状态，但缺少恢复过程和证据下钻。

### CP-09 厂商数据过期／不可计算 —— 通过展示核验

- Kimi、智谱显示 `CODING_PLAN_WEEKLY_STALE`；DeepSeek 显示 `MONTHLY_BUDGET_NOT_CONFIGURED`，数据时间可见。
- 过期、未知分母和预算未设置没有被伪造成 0%，也没有生成虚假精确日期。
- 结论：不可计算原因和数据时间的展示符合要求；自动同步的新鲜度问题另记 `POOL20-025`。

### CP-10 连续无调用与闲置事实 —— 待确认

- Kimi 连续 0 天无调用，DeepSeek 0 天，智谱 1 天；页面显示闲置状态“未判定”。
- 当前没有连续多日无调用资源，无法验证长期闲置样本。
- 结论：字段展示正确，但长期闲置行为尚未测试。

### UC-08 缺少组织关系 —— 待确认

- 待归属展示已在部门账中出现，但当前样本无法进一步验证完整守恒和修正流程。
- 组织同步后需要复测“全部部门合计＋待归属＝企业总成本”。

### UC-09 Token 子集不重复计算 —— 通过

- 请求输入 43,113、输出 1,119、缓存 42,752、计量质量 `PROVIDER_REPORTED`、Attempt 1、上游 HTTP 200。
- 真实 Token = `43,113 + 1,119 = 44,232`；缓存是输入子集，没有重复加入。
- 结论：Token 计量公式和上游 Usage 一致，UC-09 通过。

### UC-10 月度账单关闭与重开 —— 结账闭环不通过

- 2026-08 账期显示待结账，并提示 Kimi／智谱缺套餐费用或额度事实、DeepSeek 未知 API 成本。

- 结论：结账页把技术缺口直接泛化成“缺事实”，没有形成经营确认闭环；记录为 P1。正确流程应先列本月花费清单，再逐项确认。

## 五、维度三：峰谷差异（PV-01～PV-10）

### PV-02 时间边界 —— 通过配置核验

- 当前使用中未发现多条启用计价规则冲突。
- 调度策略和计价规则各自使用自己的优先级体系，数字越小在各自体系内越优先。

- 页面存在多个规则版本；请求明细中能看到 `deepseek-flash-base-v1` 和价格。
- 尚未找到同一模型新旧版本切换前后的真实请求进行历史不重算核验。

### PV-07 套餐是否优先 —— 待确认

- Kimi 请求确实使用 Coding Plan，套餐内、扣减额度 95,913、API 费用为套餐内。
- 但路由候选只有一个，调度为 `ALLOW_NO_POLICY`，无法证明系统在 API 与套餐同时可用时执行了“套餐优先”。

### PV-08 套餐耗尽后的用户提示 —— 暂未测试

- 当前没有 Coding Plan 额度耗尽样本。
- Owner 已确认：耗尽时只提示“该厂商额度已经用完，请等待额度重置”，等待还是切换由用户决定，系统不自动替用户切换。

### PV-09 调度节省 —— 待确认

- 首页本月调度节省显示 `0.00`。
- 当前没有实际执行且具备可比较成本证据的 `SWITCH` 样本。
- 当前算法应区分：已实现节省金额、潜在峰值节省估算、避免高峰额度扣减；不能把拒绝或少用直接当成节省金额。

### PV-10 价格与可用性取舍 —— 暂未测试

- 当前成功请求大多只有一个候选资源，没有多候选的价格、延迟、健康取舍样本。
- 系统应记录事实，不能自动判断便宜资源一定更好；经营判断由负责人完成。

## 七、已确认的产品问题与后续方向

以下问题不是测试人员“不会操作”，而是测试过程中确认的产品或解释层缺口：

1. `POOL20-025`：DeepSeek 经营余额依赖人工快照，缺少按日自动同步和新鲜度状态；
2. `POOL20-026`：结账页先报“缺事实”，没有先列本月采购／花费清单供负责人确认；
3. `POOL20-027`：调度策略停用后没有重新启用或复制为新版本入口；
4. `POOL20-028`：统一模型、Model Route、计价规则缺少归档生命周期；
5. `POOL20-029`：调度策略缺少发布时间、开始生效时间、停用时间，并且没有清楚说明策略先于计价规则执行；
6. `POOL20-030`：高峰拒绝缺少“高峰时段暂停使用”等明确业务提示，也缺少无 Attempt／无扣费的用户可读证据；
7. `POOL20-031`：请求详情没有独立的计价决策区块，调度策略和计价规则容易混淆；
8. `POOL20-032`：调度输入原始 JSON 直接铺开，造成溢出，且 `ALLOW_NO_POLICY` 时大部分内容没有阅读价值；
9. `POOL20-033`：Coding Plan 耗尽后的行为应是明确提示和重置时间展示，不自动替用户决定等待或切换；
10. `POOL20-034`：首页 6 张主卡和“1.0 经营补充”2 张卡应合并为 8 张本月概览卡；调度节省为 0 时必须显示原因；
11. `POOL20-035`：调度节省要区分已实现节省、潜在节省和避免高峰扣减，不能把拒绝或少用直接当成节省金额。

## 八、最终结论

### 已经证明的能力

- 资源正常状态和基础健康信息可见；
- 员工日／周／月用量聚合正确；
- 项目用量聚合正确；
- Token 真实口径为输入＋输出，缓存和推理没有重复计入；
- 请求能够下钻到结算、路由候选、上游 Attempt、调度决策和计价事实；
- Coding Plan 五小时／周窗口可展示；
- 供给预测、数据过期、预算未设置和闲置未判定状态有明确展示；
- 正常请求 HTTP 200、Attempt、Settlement、Usage 和费用链路可追溯；
- 调度策略优先于计价规则的执行顺序在代码和请求证据中成立：命中 REJECT 时不进入上游和计量。

### 目前不能宣称已经证明的能力

- DeepSeek 余额自动每日同步；
- 智谱五小时窗口重置时间字段的完整来源链路；
- 真实熔断、恢复和备用资源切换；
- 多资源同模型的候选竞争和实际 SWITCH；
- Coding Plan 耗尽后的用户提示；
- 调度节省的真实金额；
- 部门归属、调岗历史和唯一成本守恒（当前没有导入组织部门）；
- 并发抢最后额度；
- 无效 Key、模型未授权和额度不足的真实拒绝样本；
- 结账关闭、重开和版本冻结的完整写操作闭环。

### 当前最重要的工作顺序

1. 先修正结账管理：按月份列出采购、套餐、充值、API 实际费用和余额，逐项让负责人确认；
2. 修正请求详情：分开“调度决策”和“计价决策”，原始 JSON 放入可折叠技术详情；
3. 补策略生命周期：发布、开始生效、停用、重新启用/复制新版本、归档和时间线；
4. 冻结调度节省算法：已实现节省、潜在节省、避免额度三种指标分开；
5. 接入企业微信／飞书组织后，重新测试部门归属、调岗和成本守恒；
6. 用测试主体和测试资源补齐熔断、额度耗尽、切换、并发和授权拒绝样本。
