## 1. Review 定义与目标

2.0 Review 是一次项目收口工程，不是把现有文件复制到一个目录。它要把以下对象闭合为同一条可复核链：

```text
1.0 可用基线
→ 2.0 立项与范围决定
→ PRD／TRD／原型／计划
→ W20-01～W20-11 开发过程
→ FR2-001～007／AT-001～008 交付结果
→ 最终代码、迁移、制品和目标环境
→ 质量、安全、运维和恢复 Evidence
→ 真实客户业务验证
→ 遗留问题与下一版本输入
```

最终资产必须做到：

- **可审阅**：每个结论都有合同、候选、命令、原始结果和 Evidence；
- **可交付**：代码、迁移、制品、配置、说明和部署结果可以组成完整交付；
- **可升级**：能证明从真实 1.0 起点升级到 2.0，且 1.0 已有能力没有被削减；
- **可回退与恢复**：回退、Feature Flag、备份和恢复边界经过目标环境验证；
- **可接手**：新成员可以理解组织导入、用量、归属、预算、经营和资源复盘的职责与不变量；
- **可追溯**：FR、AT、W20、代码、测试、迁移、发布和运行结果能够双向定位；
- **可演进**：历史方案、明确 non-scope、遗留问题和下一版本输入各有去向。

### 2.1 启动时必须优先核对的事实差异

1. `W20-10` 原始 Evidence 中出现过 `candidate-lock.draft.json`，而后续执行基线记录 W20-10 已冻结唯一 Commit／Tree；Review 必须找到最终锁、复算指纹并解释状态演进。

3. `2.0` Tag 的创建晚于开发执行基线最后更新时间；必须单独记录 Tag object、目标 commit、创建者、时间和依据。
4. V4 早期平台运营／多企业生命周期 ADR、PoC 和角色矩阵已退出当前 2.0 首发合同；只能作为历史变更资料，不得自动成为验收 oracle。
5. 初始验收矩阵中的 AT 状态仍需用最终候选 Evidence 回写；“开发工作包 done”不能自动替代“最终 Review 通过”。

## 3. Review 范围

### 3.1 必须纳入

- 2.0 立项基线、PRD、TRD、确认原型、架构图、开发规划、验收矩阵、执行基线和工程规则；
- `PC-20260812-03`、`PC-20260812-04` 及所有影响 2.0 范围、接口、迁移、发布和验收的 Planning Change；
- `M20-0～M20-5`、`W20-01～W20-11`、`FR2-001～FR2-007`、`AT-001～AT-008` 及其 Evidence；
- 1.0 兼容回归清单和 2.0 对 1.0 页面、接口、数据、Gateway 与运维能力的全部影响；
- `apps/`、`packages/` 下参与 2.0 构建或运行的生产代码、测试、数据库迁移、Worker、脚本、配置、CI 和部署文件；
- 通讯录、Excel、使用主体衔接、周期用量、部门归属、预算、月账、资源利用和采购复盘的正常与负向链路；
- 最终 Commit／Tree、Tag、依赖锁、迁移头、构建制品、镜像 Digest、Release Manifest 和目标环境部署；
- 安装、升级、Feature Flag、回退、备份、恢复、监控、告警、故障处理和运维交接；
- 企业微信、飞书、Excel 和 1.0 已支持客户端／Provider 的集成及状态说明；
- 标准 100 人／100 项目／200 Principal／每月 100 万 Ledger 的验收 Evidence；
- 真实客户验证、运营反馈、遗留问题和下一版本输入。

### 3.2 必须登记但不得误作当前实现依据

- 当前 PRD／TRD 已明确取消的平台运营、多企业生命周期、支持访问、复杂角色矩阵和正式导出方案；
- 未被当前 PRD／TRD 引用的 Stage 01 旧 ADR、旧 PoC 和旧角色权限矩阵；
- `_quarantine/`、历史原型、废弃文档、参考资料和外部调研；
- `node_modules/`、缓存、临时测试结果和可再生成构建产物；
- 第三方依赖源码。

这些内容必须标记为 `HISTORICAL`、`CANCELLED`、`REFERENCE_ONLY` 或 `REGENERATABLE`，并说明是否进入构建、发布或许可证清单。

### 3.3 明确禁止的伪完成

- 用静态原型或页面存在证明真实业务闭环；
- 用 W20 摘要报告代替丢失的原始测试输出；
- 用本机通过代替标准目标环境安装、升级、TLS、备份和恢复；
- 用合成通讯录响应冒充企业微信／飞书真实接口已验收；
- 用 Tag、commit 或分支名称代替候选锁和发布 Evidence；
- 用 100 人合成样本宣称真实客户价值已经验证；
- 用前端隐藏代替服务端权限、企业隔离和 non-scope 控制；
- 把未知数据写成 `0`、把不可计算写成精确日期、把未判定写成闲置结论；
- 把 `Coming Soon` 的对账／导出页签写成已经交付的后端能力。

## 4. 总体门禁与封板状态

```text
冻结 Review 对象与审核尺子
→ 资产盘点和权威关系核对
→ 复原 1.0 继承基线与 2.0 开发过程
→ 产品兼容 Review＋2.0 增量 Review
→ 架构、数据、迁移和全量代码 Review
→ 语义标注补齐并形成新候选
→ 质量、安全、容量和外部集成复验
→ W20-11 标准目标环境交付、回退和恢复
→ Owner 工程封板、Final Tag 与不可变归档
→ 交付后真实客户业务验证
→ 业务验证收口与下一版本输入确认
```

### 4.1 两个正式封板状态

1. **2.0 工程交付封板**
   - `delivery_status=done`；
   - 允许在真实客户业务验证前完成；
   - 必须完成 W20-11、最终候选审核、目标环境交付、运维与恢复，不得用本地候选代替。
2. **2.0 业务验证收口**
   - `validation_status=done`，或由 Owner 明确签发 `cancelled/deferred` 及理由；
   - 必须使用真实客户、真实角色和约定观察周期；
   - 结果作为下一版本输入，不反向改写已经封存的工程交付档案。

`Review 候选冻结` 只是过程状态，不是第三种封板。候选变化时必须重新锁定并按影响范围复验。

### 4.2 工程交付封板通过条件

- R20-01～R20-16、R20-18～R20-19 全部完成；R20-17 可保持 `todo`，但状态和原因必须写入 Final Review；
- W20-01～W20-11 全部 `done`，且每个 `done` 都有可读取 Evidence；
- FR2-001～007、AT-001～008 在同一最终候选上通过，AT 状态已回写；
- 1.0 兼容回归通过率 100%，既有入口、字段、操作、下钻、账本和 Gateway 合同无未批准缺失；
- V1.4 功能／验收与代码质量审核针对最终候选完成，P0／P1 和阻断性 Evidence Gap 为零；
- 代码语义标注补齐后的候选重新完成受影响审核、测试、Hash 和制品构建；
- 部门成本守恒、月账守恒、重复结算、重复归集、账本丢失均满足冻结阈值；
- Secret、完整 Key、密码、令牌和请求正文明文泄漏为零；
- 100 人标准样本、100 万 Ledger、并发、导入时限和查询 P95 达到 TRD 包络；
- 从真实 1.0 起点升级、Feature Flag 回退、允许条件下数据库回退、读模型重建和目标恢复通过；
- 目标环境的安装、Secret 注入、TLS、健康检查、代表性导入、七项业务主链、监控、备份和恢复有原始 Evidence；
- 最终 Commit、Tree、Tag、迁移、依赖锁、配置、镜像 Digest、SBOM、审核报告和档案 Hash 可互相对应；
- 非阻断 P2/P3、豁免、未验证外部条件和下一版本输入都有 Owner、优先级、期限和去向；
- Owner 签发工程封板决定。

### 4.3 业务验证收口通过条件

- 客户、角色、样本、观察周期、数据授权、成功指标和退出条件已在验证前冻结；
- 真实人员／项目导入、接入、用量、部门归集、预算、月账、资源判断和采购复盘均有观察记录；
- 已区分“产品可用”“客户采用”“效率改善”“商业价值”四类结论，不用单一 Token 或费用数字替代；
- 用户反馈、缺陷、经营结果、未采用原因和支持成本有证据；
- 业务遗留和下一版本输入已确认；
- Owner 签发 `done`、`deferred` 或 `cancelled` 决定。

## 6. 2.0 专项 Review 标准

### 6.1 1.0 兼容是独立门禁

2.0 的新增能力通过，不能抵消 1.0 能力缺失。至少逐项复核：

- 首页旧字段的稳定落点、资源摘要 14 列、模型原地下钻和员工 Token；
- 使用主体、接入配置、Key、Grant 和批量模型授权；
- 厂商资源、额度窗口、供给预测、健康与异常；
- 统一模型、Model Route、计价规则、调度策略全生命周期；
- 请求明细筛选、URL、分页与 Attempt→Usage→Ledger→Settlement 下钻；
- 月度总览、员工账、项目账、快照导入、结账／重开和历史版本；
- 运行保障五个管理区；
- 管理员账号与密码生命周期、操作日志、升级日志；
- Gateway 协议、流式、额度、路由、计价、结算和正文零留存。

### 6.2 2.0 七项增量必须证明同一事实源

- 通讯录三入口必须使用同一导入合同，稳定匹配、幂等、部分失败和主体衔接可追溯；
- 周期用量与 1.0 请求明细使用同一请求／Usage／Ledger 事实；
- 员工账、项目账和部门账是不同视图，不能相加造成重复成本；
- `部门合计＋待归属＝企业总成本`，每条事实在部门维度只归属一次；
- 预算是金额预警，不替代 Gateway Token 硬额度；
- 现金采购、API 费用、套餐成本、分摊和厂商窗口分栏；
- API 无可靠分母时利用率为未知，不是 0%；
- Coding Plan 五小时和周窗口分开；
- 闲置状态在未冻结阈值时保持 `UNASSESSED`；
- 采购复盘只有确定性事实和人工备注，不自动下单或扩展成 BI。

### 6.3 历史方案退出检查

Review 必须证明当前产品代码、Schema、API、导航和交付承诺没有重新引入以下首发外内容：

- 仟流科技总控台和跨企业目录；
- 平台运营管理员、支持访问和企业生命周期；
- 新 Agent 服务或自动执行；
- 正式对账／导出后端；
- 自动采购、自动充值和后台固时任务；
- 复杂 RBAC、SSO、成本中心和大 BI。

如因底层通用字段或旧表仍存在，必须说明它们是否可达、是否启用、是否进入构建和是否产生外部承诺；不能只按关键字判定。

### 7.2 全量审核范围

- `apps/` 和 `packages/` 的全部在范围生产代码；

### 7.3 语义标注最低要求

文件／模块级至少说明：

- 业务职责和不处理范围；
- 输入、输出、权威数据源和副作用；

核心函数／类级至少说明：

- 状态变化与事务边界；
- 失败、重试、重放、回退和取消语义；
- 数据库、Redis、外部通讯录和 Provider 访问；
- 调用者不得破坏的业务不变量。

重点检查以下复杂逻辑的“为什么”和“不能破坏什么”：

- 通讯录匹配、冲突、部分成功和 Principal 初始化；
- 时区桶、聚合水位、stale 和读模型重建；
- 请求时点部门／项目归属及历史快照；
- 部门成本、Token、月账和分摊守恒；
- 预算、利用率、耗尽、未知和未判定状态；
- Feature Flag、迁移、升级、回退、备份和恢复；
- Secret、Key、个人信息和正文零留存。

语义标注修改源码后，旧候选结论失效；必须生成新候选并按影响范围重新完成审核、测试、制品和 Hash。

## 11. 状态、Findings 与豁免规则

### 11.1 状态词汇

Review 工作包只使用：

```text
todo / doing / blocked / failed / done / cancelled
```

`done` 必须同时具备完成内容、候选身份、Evidence 路径、实际结果和复核结论。外部条件尚未开始时使用 `todo`；只有依赖已到期且确实无法继续时才使用 `blocked`。

### 11.2 Findings

- Findings 只使用 `P0～P3`；
- P0／P1 和阻断性 Evidence Gap 不得带入工程封板；
- P2／P3 必须有 Owner、处理方式、期限和版本去向；
- 涉及权限、Secret、客户数据、账本守恒、迁移、恢复和目标环境的事实不清时，停止受影响动作；
- “没有发现”只适用于实际覆盖范围，必须同时写明未覆盖范围。

### 11.3 豁免

豁免不能替代 P0／P1 修复，也不能把未运行测试改写成通过。允许豁免的非阻断项至少记录：

- 具体对象和条款；
- 风险与最坏影响；
- 未完成原因；
- 补偿控制；
- Owner、批准时间、到期时间；
- 触发复查条件和目标版本。
