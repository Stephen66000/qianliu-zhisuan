### POOL20-025 DeepSeek API 经营数据依赖人工快照，无法持续回答“还能用多久”

- **来源**：2026-08-18 已部署 2.0 场景测试 `CP-02`；`厂商资源 → DeepSeek-仟流智算 → 更新经营数据` 截图及供给预测截图。
- **优先级**：`P1`；当前不直接阻断请求，但会使余额、覆盖时长和预计耗尽判断依赖过期快照，影响持续生产决策。
- **状态**：`open`；先进入测试问题蓄水池，不立即改写已封板 PRD／TRD。
- **现场事实**：页面保存的 DeepSeek 经营快照为：充值 `109.41 CNY`、当前余额 `68.00 CNY`、本期实际费用 `47.41 CNY`；余额更新时间为 `2026-08-03 11:58`，累计费用和费用周期结束为空。供给预测仍展示速度、预计耗尽、覆盖时长和 `MEDIUM` 可信度，但测试时数据已经不是当天更新值。
- **问题判断**：当前入口是人工“更新经营数据／追加快照”，没有被验证为按日自动调用厂商 API 获取余额、费用和额度快照；过期数据如果继续参与预测，页面虽然有时间字段，仍不能稳定回答“现在还能用多久”。
- **建议方向**：增加按资源配置的自动同步任务，默认每日至少执行一次；成功后追加不可变经营快照并更新当前指针；失败、厂商不支持或超过新鲜度阈值时显示 `STALE／NOT_SUPPORTED／SYNC_FAILED` 及原因，不把旧余额伪装成当前值。
- **待验收问题**：
  1. DeepSeek 是否提供可调用的余额／费用接口；
  2. 自动同步频率、超时、重试和失败告警；
  3. 快照更新时间、来源、同步状态和历史版本是否可查；
  4. 过期快照是否会阻止或降级预计耗尽计算；
  5. 余额不可获取时是否明确显示“厂商未提供／需人工更新”，而不是空白或 0。
- **Evidence**：部署测试截图由当前测试任务回填至 `V4/仟流智算2.0-四大核心逻辑场景测试表.xlsx` 的 `CP-02` 行。

### POOL20-026 结账管理先报“缺事实”，没有先列出本月采购与花费供人工确认

- **来源**：2026-08-18 已部署 2.0 `UC-10` 结账管理测试。
- **优先级**：`P1`；当前页面无法让负责人确认“本月到底花了什么、多少钱”，结账判断无法形成可操作闭环。
- **状态**：`open`；先记录产品问题，不立即改写已封板 PRD／TRD。
- **现场事实**：2026-08 账期页面只显示“Kimi／智谱缺少套餐费用或额度事实”“DeepSeek 存在未知 API 成本”等泛化提示，以及一块结账说明输入框；没有先展示本月采购／充值／套餐费用／API 实际费用的逐项清单，也没有逐项确认、补充或标记异常的入口。
- **问题判断**：用户已经在厂商资源页录入过采购金额、套餐费用和余额，但结账页没有把这些经营快照与账期花费清单关联展示，无法判断到底缺哪个资源、哪个字段、哪个请求成本。余额是资产，不等于本月花费；人工确认应确认支出事实或异常说明，不应被迫猜测“缺事实”。
- **建议方向**：结账页先展示“本月花了什么”清单，逐项列出资源、采购／充值、套餐费用、API 实际费用、服务周期、数据来源、快照版本／时间和确认状态；用户可逐项选择“已核对／待补充／不适用／标记异常”。系统仍保留未知值，不把人工确认伪造成 0 或已计算值；完成确认后再执行检查、说明缺口并允许结账冻结。
- **Owner 确认的业务口径**：
  1. `Coding Plan` 属于先付费套餐：本月采购／套餐金额已有录入时，结账页应如实展示该金额、服务周期、已用／剩余额度和确认状态，不再泛化提示“缺少套餐费用”；
  2. `DeepSeek API` 属于预充值扣费：结账页应分别展示月初／本月充值、当前余额、已结算 API 实际费用和数据时间；充值是现金流，余额是资产，API 实际费用是调用成本，三者不能互相替代；
  3. 每一行先由负责人确认“属实／待补充／异常”，确认动作记录操作者、时间和备注；确认不改写原始账本，也不把未知值强行变成 0；
  4. 页面应把“已录入但未确认”和“确实缺失”分开显示，明确指出缺少的资源、字段、快照版本或请求范围。
- **验收要点**：
  1. 每一项支出都能回到采购记录、经营快照或请求账本；
  2. 缺口提示明确到资源、字段、快照／请求范围和原因；
  3. 人工确认记录操作者、时间、备注和版本，不改写原始账本；
  4. 未确认项如何影响结账必须明确，不能只显示一句“缺少事实”。

### POOL20-027 调度策略停用后没有重新启用或基于历史版本恢复的入口

- **来源**：2026-08-18 已部署 2.0 峰谷调度策略测试；用户查看 `额度规则 → 调度策略`。
- **优先级**：`P1`；策略停用后无法恢复，已配置的高峰拒绝／切换策略只能重新手工录入，容易造成策略断档和历史维护成本。
- **状态**：`open`；当前页面只展示 `RETIRED`，操作列没有“重新启用”或“复制为新版本”。
- **现场事实**：`zhipu-peak-reject-v1` 和 `v2` 均为工作日 14:00～18:00、动作 `REJECT`、全部主体、状态 `RETIRED`；生命周期说明为草稿 → 校验通过 → 发布 → 停用，但停用后的操作入口缺失。
- **冻结方向**：停用版本不能原地改回 `PUBLISHED`，以免改写历史决策；页面应提供“重新启用／复制为新版本”，复制旧版本全部条件生成新版本草稿，随后走校验 → 发布，新版本进入 Gateway 热路径，旧版本继续保留为 `RETIRED` 历史。
- **验收要点**：复制后新版本号递增；模型／资源、时段、动作、主体范围、优先级和说明完整带入；发布前不影响请求；发布后新请求命中新版本；历史请求仍保留原版本证据。

### POOL20-028 统一模型、Model Route、计价规则缺少归档生命周期

- **来源**：2026-08-18 已部署 2.0 额度规则测试；用户复核统一模型、Model Route 和计价规则管理页。
- **优先级**：`P2`；不直接阻断当前请求，但停用对象会长期堆在管理列表，历史版本与当前可用配置混在一起，后续维护容易误操作。
- **状态**：`open`；用户明确提出需要归档。
- **现场事实**：统一模型可以管理路由、创建路由、停用路由，但没有归档；计价规则可以新建版本、停用，但没有归档；已停用／历史配置无法从默认管理视图收起。
- **确认口径**：
  1. `停用`：不再参与新请求，但仍保留在当前管理视图和历史查询中；
  2. `归档`：从默认管理视图隐藏，历史请求、路由决策、计价快照、版本和审计记录全部保留；
  3. 已归档对象不能被新建授权、Model Route、计价规则或调度策略引用；
  4. 需要“查看已归档”和“取消归档”入口；取消归档后仍不能绕过必要的校验和发布流程；
  5. 对版本化计价规则和调度策略，不原地把历史版本改回启用，应通过复制为新版本再校验、发布。

### POOL20-029 调度策略缺少生效/停用时间线，且策略与计价规则的先后关系没有在产品中说明

- **来源**：2026-08-18 已部署 2.0 调度策略与峰谷规则测试；用户复核 GLM 工作日高峰 `REJECT` 策略和智谱峰值 `×3` 计价规则。
- **优先级**：`P1`；当前影响策略审计、恢复和峰谷行为解释。
- **状态**：`open`；用户明确提出需要补充时间记录和执行优先级说明。
- **现场事实**：调度策略页面可展示匹配时段、动作、主体范围、优先级和状态，但没有明确的策略生效时间、发布时间、停用时间或关闭时间。GLM 的高峰 `REJECT` 策略与智谱峰值计价规则属于两个不同阶段，页面没有告诉用户为什么前者会阻止后者。
- **正确执行顺序**：
  1. 请求先经过已发布调度策略；调度动作是 `REJECT／RATE_LIMIT／SWITCH／ALLOW`；
  2. `REJECT` 时在 Gateway 前门终止，不访问上游，不产生 Attempt、Usage、Ledger 或 API 费用；
  3. 只有请求被允许并进入上游后，才按生效的计价规则匹配价格或套餐倍率；
  4. 调度策略的数值优先级只在调度策略内部比较，计价规则的数值优先级只在计价规则内部比较，不能把两个数字放在同一优先级体系里比较。
- **时间记录要求**：每个策略版本至少展示创建时间、草稿校验时间、发布时间、开始生效时间、停用/退休时间和操作人；历史 `dispatch_decision` 继续保留命中的策略版本和请求时点快照。
- **验收要点**：GLM 工作日高峰已发布 `REJECT` 时，不应出现对应的厂商请求和 `×3` 计价；策略停用后新请求不再命中，但历史请求仍保留原策略和时间证据；页面要能解释“拒绝优先于计价”。

### POOL20-030 高峰拒绝缺少明确业务提示和无扣费证据展示

- **来源**：2026-08-18 已部署 2.0 峰值拒绝策略测试及历史需求复核。
- **优先级**：`P1`；用户需要知道为什么不能用，也需要确认拒绝没有产生上游调用和费用。
- **状态**：`open`；当前没有找到用户指定的“高峰时段暂停使用”固定提示。
- **现场／代码事实**：当前 Gateway 对调度 `REJECT` 返回通用 `dispatch_rejected`／“经营调度拒绝”；搜索当前代码和原型没有发现“高峰时段暂停使用”这句业务提示。调度拒绝发生在 Attempt 创建和上游调用之前，按执行合同不应产生上游 Attempt、Usage、Ledger、扣减或 API 费用。

### POOL20-031 请求明细没有独立展示计价规则，调度策略与计价规则容易混淆

- **来源**：2026-08-18 已部署 2.0 请求明细下钻测试。
- **优先级**：`P1`；影响费用解释、历史版本核对和调度／计价责任边界。
- **状态**：`open`；用户在请求明细中能看到调度决策，但无法直观看到独立的计价规则区块。

- **验收要点**：无调度策略时明确显示“未命中调度策略，默认允许”，但仍单独显示已命中的计价规则；历史请求能按请求时点看到不可变的规则版本和价格快照。

### POOL20-032 请求详情“调度输入”直接倾倒原始 JSON，内容溢出且无策略时没有阅读价值

- **来源**：2026-08-18 已部署 2.0 请求详情下钻测试。
- **优先级**：`P1`；请求解释区出现横向溢出和文本重叠，核心调度证据无法正常阅读。
- **状态**：`open`；用户确认当前展示内容过长，且在 `ALLOW_NO_POLICY` 时没有实际决策价值。
- **现场事实**：调度决策区域显示 `ALLOW_NO_POLICY`、命中策略“未命中”，但下方仍整段展示 `dispatch_input` 原始 JSON，包括主体 ID、资源 ID、模型、倍率、额度比例、预测风险、价格证据、计价快照和反事实字段；没有换行、折叠、摘要或技术详情分层，文字冲出容器并覆盖其他字段。
- **问题判断**：内部审计原始 JSON 不能直接作为默认用户界面。无策略命中时，用户只需要知道“未命中策略，默认允许”；完整 JSON 应作为可选技术详情，而不是强制展示。

  1. 默认只展示人类可读摘要：最终动作、命中策略／未命中、理由、选中资源、候选数量、是否切换；

  3. 原始 `dispatch_input` 放入可折叠“技术详情”，支持代码换行、复制和完整查看；
  4. 技术详情不得出现横向溢出、字段覆盖或脱敏字段泄漏。
- **验收要点**：普通管理员无需阅读 JSON 即能理解决策；审计人员仍可展开获得完整不可变快照；不同屏幕宽度下布局不溢出。

- **来源**：2026-08-18 PV-08 场景讨论；当前尚未出现真实额度耗尽样本。
- **优先级**：`P1`；额度耗尽时如果没有明确提示，用户无法判断是等待重置、换模型还是人工处理。
- **状态**：`open`；用户明确确认首版只返回事实提示，不替用户决定等待或切换。

- **验收要点**：耗尽请求有稳定错误码、厂商名称、额度窗口、下一重置时间和不可计算原因；不产生重复扣费；没有配置明确的用户动作前，不自动切换候选资源。

### POOL20-034 首页本月概览不应拆成“6 张主卡 + 1.0 经营补充 2 张卡”

- **来源**：2026-08-18 已部署 2.0 首页走查。
- **优先级**：`P2`；不影响数据计算，但造成信息层级重复，用户无法把 8 个本月核心指标当成一个整体理解。
- **状态**：`open`；用户明确要求合并展示。
- **确认方向**：首页“本月概览”统一展示 8 张卡：真实 Token、本月总支出、套餐支出、API 支出、活跃人数、厂商接入账号、本月充值、本月调度节省；取消“1.0 经营补充”独立区块。旧字段可以保留来源说明或 tooltip，但不再单独制造版本层级。
- **补充要求**：调度节省为 0 时显示原因（例如“本月无可计算的实际切换”），不能只显示一个没有解释的 `0.00`。

### POOL20-035 调度节省算法需要区分已实现节省、潜在节省和避免高峰扣减

- **来源**：2026-08-18 用户讨论 DeepSeek 分时价格、智谱工作日下午拒绝和“削峰填谷”节省口径。
- **优先级**：`P1`；该算法直接影响首页“本月调度节省”、采购复盘和经营判断，不能把拒绝请求或少用 Token 直接冒充节省金额。
- **状态**：`open`；算法口径待 Owner 与产品／技术共同冻结。
- **讨论事实**：
  1. DeepSeek 高峰时段有不同 API 价格；如果同一业务请求被延迟到低谷或切换到更便宜资源，才有可比较的前后成本；
  2. 智谱工作日下午直接 `REJECT` 时，如果请求没有在其他时间或其他资源重新执行，不能仅凭“没有花钱”认定产生了现金节省；
  3. Coding Plan 的 `×3` 是额度扣减倍率，`raw_token × (3-1)` 表示避免的额度消耗，不等于人民币节省；
  4. 当前实现的 `counterfactual_cost - actual_cost` 只适用于实际执行了 `SWITCH` 且两端都有价格证据的场景，不能覆盖拒绝、延迟执行和无替代执行。
- **建议算法分层**：
  1. **已实现调度节省金额**：`基准路径成本（高峰规则）－实际执行路径成本（低谷／替代资源）`；必须关联同一请求或等价任务，且两端都有不可变价格／倍率快照；
  2. **潜在节省／峰值暴露**：`历史高峰 Token ×（高峰单价－低谷单价）`，仅用于分析，标记为“估算／潜在”，不计入已实现节省；
  3. **避免高峰扣减**：`原始 Token ×（高峰倍率－实际倍率）`，单位是 Token／额度点，单独展示，不伪装成 CNY；
  4. **纯拒绝或未执行**：显示“高峰请求被拒绝／未产生可核验节省”，不计入已实现节省；如果业务确认需求被放弃，可单独统计“避免支出”，但不能和实际调度节省混用。
- **待确认问题**：DeepSeek 是否按 API 金额计算已实现节省；智谱是否只展示避免扣减额度；延迟到低谷的同一请求如何关联；拒绝后未重试是否只记“避免请求”；采购复盘如何同时展示已实现、潜在和避免额度三种指标。
- **Owner 补充口径**：系统不自动判断“便宜资源一定更好”。无论是 DeepSeek 不可用、延迟高，还是用户主动切换，系统只记录候选资源、最终资源、切换原因、健康／延迟事实、请求／Token／费用结果和是否实际执行；后续按企业自身策略统计，采购和经营判断由负责人完成。

## POOL20-006 部门账与项目账归集关系不清，存在重复计算风险

- **来源**：2026-08-12 仟流智算 2.0 原型走查
- **状态**：`done`；原型已确认
- **问题**：项目有负责人，也会归属于负责人所在部门。如果部门账直接把“员工账合计＋项目账合计”相加，同一笔由员工发起且已归属项目的请求会被计算两次。
- **核心口径**：员工账、项目账、部门账是同一批账本事实的三个分析维度，不是三笔相互叠加的成本。
- **建议归集规则**：
  1. 员工请求已归属项目：员工账中按员工查看，项目账中按项目查看；部门账只计入该项目的归属部门一次；
  2. 员工请求未归属项目：部门账按该员工在请求发生时的部门计入“员工直接成本”；
  3. 项目主体直接发起请求：部门账按项目归属部门计入“项目成本”；
  4. 员工或项目缺少有效部门关系：进入“待归属”，不得猜测部门。
- **项目部门关系**：项目应有明确的负责人和归属部门；标准版可默认继承负责人所在部门，但要保存发生时点／账期快照，负责人调岗不能改写历史部门账。
- **部门账展示建议**：分别展示“员工直接成本”“项目成本”和“部门合计”，让用户看见项目账如何汇入部门账，而不是只给一个无法解释的总数。
- **守恒要求**：每条账本事实在部门维度只能归属一次；`全部部门合计 + 待归属 = 企业当月总成本`。
