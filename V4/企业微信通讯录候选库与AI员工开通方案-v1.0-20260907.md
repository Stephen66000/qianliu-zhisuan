# 企业微信通讯录候选库与 AI 员工开通方案 v1.0

日期：2026-09-07  
状态：评估稿，尚未实施、提交、推送或部署。  
本地勘察基线：`codex/quota-pricing-review-20260905@4cea87f2e5928d7486282a934c7c6c0084f241de`。该基线不代表当前生产版本，实施前必须重新核对。  

## 1. 结论

方案可实现，但必须拆成两层数据和三条能力链路：

1. **组织人员库**：首次上传企业微信导出的通讯录，保存全体员工的姓名、部门和稳定账号信息。例如企业有 1000 人，组织人员库保存 1000 人。
2. **AI 员工主体**：管理员从组织人员库批量开通实际使用 AI 的人员。例如只开通 300 人，只有这 300 人建立仟流员工主体、Key、额度、用量和项目关系。
3. **每日组织核对**：每天调用企业微信“获取成员 ID 列表”接口，获取成员和部门的稳定关系，与昨日完整快照比较。该接口一次最多取 10000 条，1000 人通常一页即可完成。[企业微信官方：获取成员 ID 列表](https://developer.work.weixin.qq.com/document/path/96067)
4. **少量人员补录**：一次新增一至数人，且管理员知道姓名时，通过官方 CLI 按姓名查找，展示姓名和部门，确认后加入组织人员库或开通 AI。
5. **批量资料更新**：新增人员较多，或者发生姓名、部门名称批量变化时，再上传一份最新导出文件，系统只预览和应用差异。
6. **图片日报**：向 300 名员工稳定、主动发送个人图片，不能依赖 CLI 的最近会话能力；应由仟流统一建设企业微信第三方应用，客户管理员一次授权可见范围，再走“发送应用消息”的图片消息能力。客户不需要逐个员工扫码，也不需要逐家开发自建应用。[企业微信官方：发送应用消息](https://developer.work.weixin.qq.com/document/path/90236)

这套方案不要求客户给 300 人逐个打“仟流 AI 用户”标签。是否开通 AI 完全由仟流内部状态管理。

## 2. 用户场景

以一家 1000 人的企业为例：

- 企业微信通讯录有 1000 人；
- 实际购买或获准使用仟流 AI 的有 300 人；
- 企业管理员希望首次批量导入，后续自动发现组织变化；
- 少量新增员工可以快捷处理；
- 管理员希望查看员工是否仍在职、是否换部门；
- 后续可能每天向内部群或每位 AI 员工发送用量图片。

目标是减少客户维护工作：首次准备一份导出文件，后续由系统每日核对；只有资料无法从接口补齐或出现歧义时，才需要管理员处理。

## 3. 产品模型

### 3.1 两层人员关系

```text
企业微信通讯录
      │
      │ 首次导出上传 + 每日稳定标识核对
      ▼
组织人员库（1000 人）
      │
      │ 管理员批量开通 / 停用
      ▼
AI 员工主体（300 人）
      │
      ├── Key 和登录
      ├── 模型权限与额度
      ├── 用量与经营账单
      ├── 项目负责人候选
      └── 图片日报接收范围
```

组织人员库中的人只表示“企业里有这个员工”，不表示其已开通 AI。未开通的 700 人：

- 不创建员工主体；
- 不生成 Key；
- 不继承模型授权和额度规则；
- 不进入 AI 用量与经营账单；
- 不接收个人用量日报；
- 可以被管理员搜索并批量开通。

### 3.2 身份对应

每名组织人员保存三类信息：

| 信息 | 来源 | 用途 |
| --- | --- | --- |
| 姓名、部门名称 | 首次或后续通讯录导出文件 | 页面展示、搜索和人工识别 |
| 企业微信成员稳定标识 | 导出文件中的账号字段，或每日成员接口 | 识别同一个人，避免改名后重复建人 |
| 企业微信部门稳定标识 | 每日成员接口及部门基线 | 识别调部门及组织关系变化 |

姓名用于展示，稳定标识用于系统关联。不能只按姓名自动合并同名员工。

首次实施前必须拿一份真实企业微信导出文件验证：

1. 导出表是否包含“账号”或同等稳定字段；
2. 该字段是否与每日成员接口返回的成员稳定标识属于同一标识体系；
3. 导出表是否包含部门稳定标识，还是只有部门名称；
4. 一人多部门在导出表中的表达方式；
5. 离职、禁用、未激活员工是否包含在导出结果中。

这五项没有通过真实样本验证前，不能承诺导出表与每日接口可以自动一一对应。

## 4. 首次接入流程

### 4.1 客户操作

客户管理员只需完成以下动作：

1. 从企业微信管理后台导出通讯录；
2. 在仟流上传导出文件；
3. 检查导入预览中的重复、缺失和格式冲突；
4. 通过搜索、勾选或上传开通名单，批量选定 300 名 AI 用户；
5. 确认开通结果。

客户不需要逐个员工打标签，也不需要每位员工扫码。

### 4.2 仟流处理

1. 识别企业微信原始导出格式，保留原文件摘要，不把未经确认的数据直接应用到正式主体。
2. 按稳定账号匹配已有组织人员；稳定账号缺失或冲突时进入待处理。
3. 创建或更新组织人员、组织部门和任职关系。
4. 导入 1000 人时只建立组织人员，不自动创建 1000 个员工主体。
5. 对管理员选中的 300 人执行“开通 AI”：建立员工主体并应用模型权限、额度及 Key 领取状态。
6. 返回本次新增、更新、未变化、冲突、跳过、已开通和未开通数量。

### 4.3 批量开通方式

产品提供三种方式，均在仟流中操作：

- 按姓名、部门搜索后多选；
- 按部门批量选择，再排除个别人；
- 上传一份仅包含待开通人员稳定账号或员工编号的名单。

无需依赖企业微信标签。若企业以后主动维护了“AI 用户”标签，可以作为可选输入，但不作为产品成立条件。

## 5. 每日自动核对

### 5.1 官方能力

[企业微信官方“获取成员 ID 列表”](https://developer.work.weixin.qq.com/document/path/96067)明确支持：

- 获取企业成员与部门的稳定关系；
- 游标分页；
- 单页数量范围 1～10000；
- 仅通过“通讯录同步 Secret”调用。

官方同时明确：该接口不返回姓名和部门名称。姓名和部门名称不能通过每日接口重新拉取。[企业微信官方：通讯录同步接口调整](https://developer.work.weixin.qq.com/document/path/96079)

因此，每日同步的准确名称是“组织身份核对”，不是“全量资料同步”。

### 5.2 每日任务流程

```text
获取企业微信当日完整成员—部门关系
                │
                ├── 拉取失败或分页不完整：整批失败，不改任何人员状态
                │
                ▼
与上一份成功快照比较
                │
                ├── 新成员
                ├── 已有成员部门变化
                ├── 已有成员消失
                └── 无变化
                ▼
生成待处理事项 + 自动更新允许更新的组织关系
```

任务必须先拉完全部分页并通过数量、重复及结构检查，才能发布为成功快照。半份数据不能触发离职或停用。

### 5.3 四类结果

#### A. 新增人员

出现新的成员稳定标识时：

- 新增到“待补充资料”列表；
- 不自动创建 AI 员工主体；
- 不自动分配 Key、权限或额度；
- 页面显示新增数量和发现时间。

每日接口没有姓名。少量新增且管理员知道姓名时，使用 CLI 搜索确认；批量新增时上传最新通讯录，只处理增量。

#### B. 部门人员变化

已知成员的部门稳定标识发生变化时：

- 记录旧关系和新关系；
- 保存任职变更时间；
- 已有部门标识能映射到名称时，自动更新可读部门；
- 出现未知部门标识时，标记“部门名称待补齐”；
- 不改变员工 Key、额度和历史用量。

每日接口不能发现“部门名称改了但稳定标识没变”。这种情况需要通讯录变更回调或再次上传导出文件。新配置的通讯录同步回调也只应按稳定成员和部门标识设计。[企业微信官方：成员变更通知](https://developer.work.weixin.qq.com/document/path/90970)、[部门变更通知](https://developer.work.weixin.qq.com/document/path/90971)

#### C. 在职状态

重点检查已开通 AI 的 300 人：

- 仍出现在成功快照中：保持正常；
- 未出现在成功快照中：进入“疑似离职／权限范围变化”队列；
- 保留其历史 Key、用量、账单和项目关系，不删除人员；
- 后续处置由企业选择安全策略。

建议提供两种策略供企业配置：

| 策略 | 第一次完整快照发现缺失时 |
| --- | --- |
| 严格模式 | 立即暂停新的 AI 调用，管理员确认后归档或恢复 |
| 审核模式 | 标记待确认，连续两次成功快照缺失或管理员确认后停用 |

无论选择哪种策略，接口调用失败、凭证失效或分页不完整都不能触发人员停用。

#### D. 未开通 AI 的人员

对其保留组织人员状态，用于未来搜索和开通。每日核对不会为其创建主体，也不会发送个人用量日报。

## 6. 少量变化使用 CLI

### 6.1 已确认能力

[企业微信官方 CLI 仓库](https://github.com/WecomTeam/wecom-cli)及其[联系人能力说明](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-contact/SKILL.md)显示，联系人搜索可以返回：

- 姓名；
- 部门路径；
- 英文名或别名；
- 职务；
- 成员稳定标识。

当前本地 CLI 1.1.0 的实时 Schema 已核实：一次可提交 1～10 个关键词，列表结果仍可能截断。它适合一至数名已知姓名人员的补录，不适合替代全企业通讯录同步。

### 6.2 使用流程

1. 管理员输入新增员工姓名；
2. CLI 返回同名候选及部门；
3. 管理员选择正确人员；
4. 仟流将该企微身份绑定到组织人员；
5. 管理员决定是否开通 AI。

CLI 当前文档没有证明可以只凭一个未知成员稳定标识反查其姓名。因此，日报发现“新增 5 人”以后，如果管理员不知道姓名，仍需要上传最新导出文件或使用企业微信受控展示能力补充识别。[企业微信官方：通讯录展示组件](https://developer.work.weixin.qq.com/document/path/91958)

受控展示组件只能在页面上显示姓名和部门，官方明确限制第三方直接获取和存储这些名称，所以它适合作为人工确认界面，不能冒充资料同步接口。

## 7. 再次导入与增量同步

管理员上传最新导出文件后，系统按稳定账号生成差异预览：

| 差异 | 默认处理 |
| --- | --- |
| 新账号 | 新增组织人员，默认不开通 AI |
| 姓名变化 | 更新显示名称，保留原身份和历史 |
| 部门变化 | 结束旧任职关系，建立新任职关系 |
| 文件中缺失 | 标记待确认，不直接删除或停用 |
| 同一稳定账号出现多行 | 按多部门规则处理；无法解释时冲突 |
| 同名不同账号 | 视为两个人，不自动合并 |
| 不同姓名同一账号 | 视为同一身份的资料变化，进入预览 |

重复上传同一文件必须幂等，不重复建人、重复开通或重复执行权限初始化。

## 8. 图片日报和消息能力

### 8.1 CLI 能做什么

[企业微信官方 CLI 消息说明](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-message/SKILL.md)确认：

- 可以给当前授权人发送图片；
- 可以给机器人最近互动过的有效单聊或群聊发送图片；
- 发送其他对象前，必须从当次可达会话列表选择目标。

当前实时接口定义最多返回最近 20 个会话，且不支持分页或过滤。因此 CLI 可以用于测试群、负责人和少量活跃会话，不能承诺每天覆盖 300 名员工。

### 8.2 稳定向 300 人发图片

稳定逐人发送每日用量图片，应使用[企业微信官方“发送应用消息”](https://developer.work.weixin.qq.com/document/path/90236)：

- 官方明确支持图片消息；
- 一次可指定最多 1000 名成员；
- 支持重复消息检查；
- 接收人必须处于应用可见范围并具有所需基础接口许可；
- 第三方服务商可以从企业授权信息取得应用实例信息。

产品路线应是：仟流统一开发和维护一个企业微信第三方应用，各客户管理员授权安装并设置可见范围。客户不需要开发自己的自建应用，也不需要 300 名员工逐一扫码。

对于每人不同的用量图，仟流逐人生成和发送；对于全员相同的企业汇总图，可以批量指定接收人。正式设计需要补充：

- 第三方应用上架与审核；
- 基础接口许可及费用；
- 企业授权、取消授权和可见范围变化；
- 图片生成、临时素材上传和过期处理；
- 幂等投递、失败重试和送达结果；
- 单人频率、单应用日发送量及错峰规则；
- 用量数据的员工可见范围和隐私策略。

日报发送属于后续独立功能，不应阻塞通讯录候选库和 AI 开通功能落地。

## 9. 已排除的企业微信接口

以下两份用户提供的官方文档属于“客户联系”，其中“客户”是外部联系人，不是企业内部员工，不能用于员工通讯录同步：

- [获取客户列表](https://developer.work.weixin.qq.com/document/path/92113)：返回指定内部员工添加的外部联系人。
- [添加企业客户事件](https://developer.work.weixin.qq.com/document/path/96361#%E6%B7%BB%E5%8A%A0%E4%BC%81%E4%B8%9A%E5%AE%A2%E6%88%B7%E4%BA%8B%E4%BB%B6)：在已有员工添加外部联系人时触发。

两者都不会在企业新增内部员工时提供所需姓名和部门资料。

## 10. 对当前仟流实现的改造

### 10.1 必须改造

当前 `packages/database/src/repositories/directory-import-apply.ts` 在导入人员时会同时创建内部人员和员工主体，并执行员工规则初始化。直接上传 1000 人会产生 1000 个员工主体，与本方案冲突。

需要拆成：

```text
导入组织人员
  └── Person + 外部身份 + 部门任职

开通 AI
  └── Principal + 接入配置状态 + 模型授权规则 + Key 待领取
```

具体改造：

1. 导入默认只创建或更新 `Person`、外部身份及组织任职。
2. 新增单人和批量“开通 AI”事务，只有该事务创建员工 `Principal`。
3. 新增单人和批量停用／恢复入口，保留历史用量和账单。
4. 组织人员列表展示“未开通、已开通、已停用、待核对”。
5. 员工主体列表只展示已建立主体的人员。
6. 项目负责人只能从有效 AI 员工主体中选择，或根据最终业务规则决定是否允许未开通 AI 的组织员工担任负责人；该点需要产品确认。

### 10.2 导入能力

当前仟流 Excel 模板不是企业微信原始导出格式，且要求员工编号、限制最多 1000 行。实施时需要：

1. 新增企业微信原始导出适配器，不要求客户手工改成仟流模板；
2. 将企微账号与仟流员工编号分开建模；
3. 提高安全容量并留出超过 1000 人的余量；
4. 保留现有文件大小、压缩包、宏及外链检查；
5. 先预览后应用，支持增量差异和幂等重放；
6. 原始文件不长期保存，只保留必要字段、摘要和审计结果。

### 10.3 每日连接器

当前 `apps/worker/src/directory/wecom-connector.ts` 依赖旧的部门列表和部门成员详情接口取得名称，不适合本方案。需要新增以官方成员 ID 列表为事实源的核对连接器：

- 完整分页；
- 按企业隔离凭证和快照；
- 每日调度和手工立即核对；
- 失败不发布快照；
- 差异预览与审计；
- 不因成员缺失直接删除人员；
- 不把稳定标识写入用户可见日志。

## 11. 页面建议

“组织通讯录”页面分成四块：

1. **连接状态**：凭证已配置、最近成功时间、最近失败原因、下次核对时间。
2. **组织概览**：全体人数、AI 已开通人数、未开通人数、待处理数量。
3. **变化中心**：新增人员、部门变化、疑似离职、未知部门和冲突。
4. **人员列表**：姓名、部门、在职状态、AI 开通状态；支持搜索、多选和批量开通。

主要操作：

- 上传首次／最新通讯录；
- 预览并应用差异；
- 立即核对企业微信；
- 批量开通 AI；
- CLI 查找新增人员；
- 处理疑似离职；
- 查看同步历史。

页面不展示内部机器标识，只显示姓名、部门、状态和可操作原因。

## 12. 验收标准

| 编号 | 场景 | 通过标准 |
| --- | --- | --- |
| A01 | 首次上传 1000 人 | 创建 1000 名组织人员，不自动产生 1000 个 AI 主体 |
| A02 | 批量选择 300 人 | 只创建 300 个有效员工主体，权限规则只应用一次 |
| A03 | 重复上传同一文件 | 不重复建人、建主体或执行授权初始化 |
| A04 | 同名不同账号 | 显示为不同人员，不自动合并 |
| D01 | 每日拉取 1000 人 | 完整分页后发布快照，数量和部门关系可复核 |
| D02 | 增加 5 人 | 显示新增 5 人，默认不开通 AI，资料不完整时明确提示 |
| D03 | 已有人员换部门 | 保留旧任职区间，更新当前关系，不改变 Key 和历史用量 |
| D04 | 300 名 AI 用户中有人消失 | 进入设定的停用策略，不删除历史事实 |
| D05 | 拉取超时或只得到半页 | 整批失败，不产生离职、部门变化或人员删除 |
| C01 | CLI 查询一至数名已知人员 | 显示姓名和部门，管理员确认后绑定，不依赖手机号 |
| C02 | CLI 结果截断或同名 | 显示限制和候选，不自动选择 |
| M01 | 给授权人或测试群发图片 | 当次可达目标实际收到，失败不盲目重复发送 |
| M02 | 第三方应用向测试员工发图片 | 管理员一次授权后员工无需逐一扫码；实际收图并记录结果 |
| B01 | 组织人员未开通 AI | 没有 Key、额度、AI 用量和个人日报 |
| B02 | 停用 AI 主体 | 新请求被阻止，历史账单、用量和项目关系仍可审计 |

## 13. 分阶段实施建议

### 阶段 0：真实样本验证

- 取得一份脱敏的真实企业微信导出文件；
- 核对账号和部门字段；
- 用测试企业验证每日成员接口；
- 证明导出账号与接口稳定标识能够一一对应；
- 形成字段映射和异常样本。

未通过此阶段，不进入正式数据迁移。

### 阶段 1：组织人员库与批量开通

- 拆分 `Person` 与 `Principal` 创建路径；
- 支持原始导出文件、增量预览和批量开通；
- 完成 1000／300 场景自动化与浏览器验收。

### 阶段 2：每日组织核对

- 接入成员 ID 列表；
- 建立成功快照、差异中心和失败保护；
- 增加每日调度及手工立即执行；
- 先观察差异，不自动停用正式员工。

### 阶段 3：CLI 少量补录

- 每企业独立授权和凭证隔离；
- 按姓名查找、候选确认和绑定；
- 验证重新授权后的身份稳定性及调用边界。

### 阶段 4：图片日报

- CLI 先验证授权人及测试群发送；
- 第三方应用完成授权、许可和测试员工逐人图片投递；
- 再决定企业汇总图、个人用量图、发送周期及接收范围。

每阶段分别记录开发完成、测试完成、提交、推送和生产部署状态。生产数据应用和部署需要单独授权。

## 14. 评估时需要决定的事项

1. 首次导入 1000 人是否只保存姓名、部门和企微账号，不保存手机号、邮箱及头像；建议只保存必要字段。
2. 300 名 AI 用户采用页面批量勾选，还是额外上传开通名单；可以同时支持。
3. AI 用户从成功快照中消失时，选择严格模式还是审核模式。
4. 未开通 AI 的组织员工能否担任项目负责人。
5. 日报先发企业汇总群，还是先做每人一张个人用量图。
6. 是否接受由仟流统一提供第三方应用，由客户管理员一次授权；这是稳定向 300 人主动发图片的前提路线。
