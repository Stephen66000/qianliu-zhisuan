# 异常中心收录范围与展示规则 · v1.1

日期：2026-09-08。根据本次反馈修订；本地实现已按此调整，尚未提交、推送或部署。

## 1. 页面只管实际故障

不再展示以下预警：主体额度接近上限、主体超额、费用超过关注线、预计资源耗尽、部门预算警戒线或超预算。原历史记录保留，但不再进入异常中心列表和历史筛选。

原列举清单里的“主体当月 API 费用超过关注线”也属于预警，因此按“不再显示预警”的总原则移除。真正的错误扣减、计量丢失、重复计量和账本不一致继续显示。

额度使用率高、超额不作为故障；上游明确返回额度耗尽或套餐过期，并实际导致调用失败时，仍保留该次故障。这两种情况分开处理。

## 2. 收录的故障

| 类型 | 收录范围 |
| --- | --- |
| 资源状态异常或连续失败 | 降级、不可用、限流、实际耗尽等状态异常，或连续调用失败达到配置阈值 |
| 调用、计量或账本不一致 | 已识别的对账差异，包括缺失、重复和结算汇总不一致 |
| 厂商资源凭证失效 | 凭证无效、过期、刷新失败等实际问题 |
| 路由无可用候选 | 无健康候选、路由失败、无可用资源或熔断等导致的请求失败 |
| 流式响应异常 | 输出中断、缺少结束信号、取消未正确传递等已记录的失败 |
| 调度执行结果不一致 | 策略动作与实际动作不同，或明确的节省基线异常 |
| 其他实际调用失败 | 已归属于企业、写入请求记录的最终失败，包括网络、上游服务、响应格式、授权和配置错误等 |
| 后台任务失败 | 厂商额度/经营数据同步、订阅自动续记、用量聚合、对账任务、通讯录任务等已经捕获的执行错误 |
| 基础服务健康检查失败 | Worker 运行时检查内部 Gateway、管理 API、Redis 和数据库，记录明确失败 |

正常按策略拒绝、普通主体额度不足以及用户主动取消，不按系统故障收录。实际请求失败与资源级持续故障是不同记录：请求级保留每次结果，资源级记录用于持续跟踪。

原来的七种上游信号保留为故障原因：上游要求稍后重试、上游额度耗尽、套餐过期、模型未获授权、上游维护、配置错误、技术故障。新产生的观察记录会明确标为“上游故障”，并按资源、信号和模型区分，不再一概称为预警。

## 3. 月份只按发生日期

使用北京时间的首次发生日期筛选，不按更新时间、处理时间或恢复时间改变所属月份。

例如：8 月 19 日发生，持续到 9 月 3 日，随后处理或恢复——这条记录仍属于 8 月，选 9 月不显示。

连续资源故障保留首次发现日期；可追溯到具体请求的故障使用原请求发生时间。真正恢复后再次发生的新故障，是新的事件，归入新事件发生的月份。

## 4. “未关联资源”的说明

截图中的主体额度告警移除后，那批“未关联资源”记录会退出异常列表；不需要再为已取消的额度告警补做授权、周期和单位字段。

其他实际故障仍可能没有资源：例如请求在选到资源前失败、后台任务本身失败。因此保留“未关联资源”，不强行填写厂商或资源。“系统级”仅表示这条记录没有具体主体关联，不代表所有员工都受影响。

## 5. 恢复必须有证据

| 故障 | 可以确认恢复的依据 |
| --- | --- |
| 资源或凭证故障 | 故障之后该资源实际调用成功，资源状态正常且没有仍生效的阻断 |
| 有明确模型范围的上游故障 | 同一资源、同一稳定模型 ID 的后续成功；缺少稳定 ID 时核对实际上游型号，不使用可变的模型别名替代身份 |
| 对账差异 | 对应差异已经完成处理，并有处理时间 |
| 资源同步或后台任务 | 后续对应同步或任务实际执行成功 |
| 基础服务故障 | 后续同一服务健康检查成功 |

单次请求失败、历史流式中断和历史调度决策不因其他请求成功而改写，显示“单次失败记录”，由管理员说明跟进结果。

没有证据的旧“自动恢复”记录不再直接标绿，显示“恢复待核实”。旧上游记录若缺少可靠模型范围，也不会用其他模型的成功推定恢复。

人工处理和系统恢复始终分开：填写说明不等于修好后台；系统有恢复证据也不代表管理员已经确认处理。前台页面每 30 秒刷新一次，后台页面不轮询。

## 6. 人工“已处理”必须配说明

操作流程：每条异常选择“是” → 打开详情并定位到处理说明 → 填写说明 → 保存。

- 空白或只有空格的说明不能保存，后端也会拒绝。
- 说明建议写清原因、采取的措施和核对结果；不要填写密码、密钥。
- 说明、处理人、处理时间与审计记录一起保存；审计写入失败不会留下半完成的处理状态。
- 取消不提交；保存失败保留已输入文本，可以重试。
- 系统已自动恢复的事件仍可由管理员填写处理结论。
- 历史人工处理记录若缺少说明，会提示补充，不自动编造说明。

示例：“已核对厂商配置并更新凭证，使用同一资源和模型重新调用成功。”

## 7. 详情放在一个右侧抽屉里

按七个分区纵向滚动，不要求同屏展示全部内容：

1. 基本信息：发生时间、最后出现、主体、厂商/资源、模型。
2. 异常原因：类型、信号、具体故障说明。
3. 影响范围：单次请求、资源故障或共享后台任务等已知范围。
4. 处理建议：按故障类别提供排查方向。
5. 处理情况：是否处理、必填说明、处理人和时间。
6. 恢复依据：实际证据、时间和证据编号；未知就明确说明未知。
7. 关联请求与事件记录：有请求时下钻，并保留检测、人工处理和验证恢复的记录。

已经使用本地真实浏览器配合模拟接口核对七分区、滚动、必填和保存交互；该检查不等于生产页面业务验收。

## 8. 能力边界

- 目前可汇总已写入请求记录、已识别信号和已捕获任务错误。尚未识别企业身份的非法 Key、到达应用前被代理拒绝的请求，不会被随意归给某个企业。
- 内部健康检查依赖 Worker 仍在运行。整机或 Worker 进程停机，仍需要独立的外部监控；此页面不能独立实时发现自身整体停机。
- 数据库暂时不可写时，存活的 Worker 进程会保留待补记信息，连接恢复后补记。若进程同时退出，内存信息不能保证保留，不伪称已完整落库。
- 共享后台任务故障只表达该任务异常，不表示本企业所有请求均已失败；具体归属可确认的请求和同步故障保留其主体或资源关联。
- 通知与人员继续暂缓，本次没有启用企微推送。
- 本地新增迁移 `0069_alert_recovery_evidence` 用于保存恢复依据；有恢复证据时禁止破坏性降级。正式发布脚本需在后续发布准备时单独绑定新候选，现有已发布 0068 脚本不适用于本轮。

本稿替代 v1.0 中关于阈值预警、跨月展示和无证据自动恢复的建议。
