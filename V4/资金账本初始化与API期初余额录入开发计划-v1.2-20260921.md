# 资金账本初始化与 API 期初余额录入开发计划 v1.2

> 日期：2026-09-21  
> 状态：`DISCUSSION_DRAFT / PLAN_NOT_APPROVED / IMPLEMENTATION_NOT_AUTHORIZED`  
> OpenSpec Change：`provider-finance-initialization`  
> 适用范围：仟流智算「厂商资源 → 充值与订阅」资金账本  
> 本文只锁定范围、合同、验收与上线边界，不授权代码开发、数据库迁移、生产部署、生产资金录入或资金账本激活。

## 0. v1.2 修订结论

v1.2 保留 v1.1 的核心方向：API 期初余额、Coding Plan 购买与周期、历史资金事实、用量归属、守恒校验和严格资金写激活必须形成一个不可拆分的初始化闭环。

本版补齐以下阻断项：

1. 使用 OpenSpec 的 `proposal → delta specs → design → tasks` 结构管理本变更。
2. 把切换时点后的历史 API 充值、Coding Plan 购买/续费和旧记录关闭结果纳入初始化候选，消除“充值接口尚未开放但预检要求充值已迁移”的死锁。
3. 明确预检是“财务事实只读”：允许保存非权威候选审计，但不得写入资金事件、订阅周期或修改用量事实。
4. 定义候选规范化、候选哈希、完整事实水位、有效期和企业级幂等语义。
5. 明确激活只能由一个外层 `SERIALIZABLE` 事务完成，内部写入原语必须接受同一个 `Transaction<Database>`。
6. 明确历史用量只允许修复四个字段，并用非目标字段哈希证明未发生越界修改。
7. 明确兼容期初接口不得绕过说明、证据和资源启用规则。
8. 明确严格写激活不可逆；异常停写通过 Control API 与 Worker 双端运行模式完成，不伪装成数据库回滚。
9. 明确 `SERIALIZABLE` 在语句或提交边界返回 `40001/40P01` 时整体回滚，并映射为可人工重试的 `409 ACTIVATION_RETRY_REQUIRED`；协调器内部禁止自动重试。
10. 把历史修复资格行集固定为候选中的 `ledger_line` 主键列表，逐行保存非目标字段基准哈希；新增行不进入该哈希比较。
11. 删除持久化 `ACTIVATING` 状态，候选只在成功提交时从 `PREVIEWED` 原子转为 `ACTIVATED`，避免进程崩溃留下僵死状态。
12. 候选 TTL 固定为 30 分钟，不因读取、提交失败或重放滑动续期。
13. 增加激活前企业级静默租约：暂停新 Gateway 请求和自动续订、排空在途结算后才能预检和激活。
14. 锁定 64 位咨询锁命名空间，避免与仓库其他咨询锁共用无前缀键空间。

当前结论仍为：`NO_GO_FOR_IMPLEMENTATION`。只有 OpenSpec 工件审查通过并收到 `PLAN_APPROVED` 与 `IMPLEMENTATION_AUTHORIZED` 后，才能创建独立 worktree 开发。

## 1. 背景与已确认事实

### 1.1 产品与代码现状

1. 前端现有“充值与订阅”提供 API 充值、Coding Plan 购买/续费、资金记录与订阅周期查看，但没有 API 期初余额入口。
2. 后端已有 `API_OPENING_BALANCE`、充值、订阅、期初更正、冲销、对账和资金余额合同。
3. 系统切换时点固定为：
   - UTC：`2026-08-31T16:00:00.000Z`；
   - Asia/Shanghai：`2026-09-01 00:00:00`。
4. 当前普通资金写接口同时受 `PROVIDER_FINANCE_MODE=ACTIVE` 和企业级 `strict_writes_enabled=true` 保护。
5. 当前切换预检只识别已落库的期初、购买和订阅周期；草稿不能直接成为 `GO_CANDIDATE`。
6. 当前历史用量回填会受控修改 `ledger_line` 的四个字段：
   - `settled_at`；
   - `api_cost_currency`；
   - `api_cost_status`；
   - `subscription_period_id`。
7. `provider_finance_runtime_state` 一旦激活即不可逆，不能把“停写”描述成把该状态改回 `false`。
8. 仓库已经存在多类事务级和会话级咨询锁；本变更必须使用独立命名空间和 64 位键，不能假定咨询锁键空间为空。

### 1.2 2026-09-21 生产只读基线

1. DeepSeek API 资源已产生真实请求及 Token，但没有 API 期初余额事实。
2. DeepSeek 在切换时点后可能存在需要确认并迁移的历史充值记录。
3. 智谱 Coding Plan 已产生真实请求及 Token，但购买金额、人民币实付和服务周期仍不完整。
4. 生产 `provider_finance_runtime_state` 尚无企业级激活记录。
5. Control API 与 Worker 未显式注入 `PROVIDER_FINANCE_MODE`；默认值不能替代部署回执。
6. 当前生产没有执行资金初始化或严格写激活。

## 2. 目标与非目标

### 2.1 目标

1. 为激活范围内的每个 API 资源及其必要币种账户建立唯一原始期初余额。
2. 迁移或明确关闭切换时点后的历史 API 充值和 Coding Plan 购买/续费记录。
3. 为需要归属的 Coding Plan 用量建立唯一有效订阅周期。
4. 对初始化草稿执行财务事实只读的假设投影、完整预检和守恒校验。
5. 使用一个事务原子写入资金事实、订阅周期、允许的用量修复、激活状态和操作审计。
6. 激活动作幂等、并发安全、可追溯，不产生半成功状态。
7. 激活完成后，日常充值、续费、自动续订和经营账单读取正常工作。
8. 对未来新增 API 资源提供受控的资源级期初登记，不允许先产生用量再补期初。

### 2.2 非目标

1. 不自动读取银行、支付宝、微信支付、发票或厂商敏感凭证。
2. 不猜测期初余额、实付金额、币种、订单号或订阅周期。
3. 不修改模型计价规则、资源凭证、模型路由或主体授权。
4. 不把充值伪装为期初余额，不把期初余额伪装为充值。
5. 不自动解决缺乏充分证据的 `UNKNOWN_COST`；证据不足时必须 `NO_GO`。
6. 不允许前端、运维或脚本直接修改资金事实表。
7. 不随代码部署自动执行生产初始化或激活。
8. 不把生产激活纳入 OpenSpec `/apply` 的自动执行任务。

## 3. 激活范围与事实集合

### 3.1 激活范围快照

每次预检必须生成不可变的 `activation_scope_snapshot`，至少包含：

1. 企业 ID：来自已认证管理员会话，不信任请求体提供的身份。
2. API 资源：预检时 `status <> 'DELETED'` 的全部 API 资源。
3. Coding Plan 资源：满足任一条件且 `status <> 'DELETED'`：
   - 切换时点后有 `ledger_line`；
   - 有当前或跨越切换时点的运营快照；
   - 有切换时点后的购买记录；
   - 管理员在候选中明确标记为在用。
4. 事实窗口：从固定切换时点开始，到预检事务的 `snapshot_at` 为止。
5. 所有资源、资金、购买、周期、用量、计价和旧费用处置的事实水位。

资源在预检后新增、删除、改模式、改状态或改变影响财务的配置，均使候选失效。

### 3.2 API 必要币种账户

每个 API 资源的必要币种集合为以下并集：

1. 切换时点运营快照中的币种；
2. 已存在资金事件中的币种；
3. 切换时点后已定价 API 用量的结算币种；
4. 切换时点后历史充值记录的币种；
5. 管理员在初始化草稿中明确新增并提供证据的币种。

若并集为空，管理员必须显式选择至少一个账户币种，并说明为何选择。不得仅因系统默认值而自动创建 CNY 或 USD 账户。

每个 `企业 + API 资源 + 币种` 只能存在一条原始期初余额。

### 3.3 初始化候选包含的事实

完整候选必须同时包含：

1. `api_opening_balances`：API 期初余额。
2. `historical_api_recharges`：切换时点后、尚未迁移的真实 API 充值。
3. `coding_plan_purchases`：切换时点后、尚未迁移的首次购买或续费。
4. `coding_plan_carryovers`：跨越切换时点的既有 Coding Plan 周期。
5. `legacy_purchase_resolutions`：每条旧购买记录的迁移或关闭决定。
6. `usage_repairs`：只允许的四类历史用量字段修复摘要。
7. `preflight_result`：缺口、守恒结果、候选哈希、事实水位和有效期。

每条 `resource_purchase_record` 必须且只能得到一种关闭结果：

- `MIGRATED`：生成对应资金事件/订阅周期并保存源记录引用；
- `ALREADY_REPRESENTED`：引用已有资金事件，证明不是漏记或重复；
- `REJECTED_WITH_EVIDENCE`：证明该记录不是实际资金事实，并记录管理员、原因和证据。

不允许仅通过忽略旧记录使预检通过。

## 4. 产品流程

### 4.1 初始化状态页

资金模式非 `OFF` 且企业严格写未启用时，显示初始化向导。页面展示：

- 运行模式；
- 严格写状态；
- 固定切换时点；
- 激活范围资源数和必要账户数；
- 历史购买记录关闭进度；
- 用量修复预估；
- 最近预检哈希、时间、过期时间和事实水位；
- `NO_GO` 缺口或 `GO_CANDIDATE` 结论。

### 4.2 API 期初余额

每个必要币种账户必须填写：

| 字段 | 规则 |
|---|---|
| 厂商资源 | 只读，显示厂商、资源和模式 |
| 币种 | 必要币种集合中的 `CNY` 或 `USD` |
| 期初余额 | 非负十进制，最多八位小数；`0` 必须显式填写 |
| 期初时点 | 固定为切换时点，不可编辑 |
| 事实说明 | 必填，1～1000 字 |
| 证据引用 | 必填，1～4000 字，不存敏感凭证明文 |
| 来源旧记录 | 可空；存在运营快照时显示引用 |

期初写入后只能通过 `API_OPENING_BALANCE_CORRECTION` 更正，不覆盖原记录。

### 4.3 历史 API 充值

切换时点后的每条真实充值至少登记：

- 资源、币种、到账金额；
- 人民币实付；
- 充值发生时间；
- 厂商订单号或外部引用；
- 说明与证据；
- 对应旧购买记录 ID；
- 记录级幂等键。

初始化候选中的历史充值必须参与余额投影：

```text
当前余额 = 期初余额 + 期初更正 + 充值 + 对账调整
         + 历史成本调整 + 冲销 - API 用量扣费
```

### 4.4 Coding Plan 购买与周期

每条购买或续费至少登记：

- 产品名称；
- 类型：首次购买或续费；
- 原币金额与币种；
- 人民币实付；
- 服务开始日；
- 服务结束日（页面为包含结束日）；
- 扣费时间；
- 自动续订选择；
- 外部引用、说明与证据；
- 对应旧购买记录或跨切换快照引用。

服务端统一转换为上海自然日的 `[period_start, period_end_exclusive)`。默认周期为“下个月同日前一日”；非默认周期必须说明。扣费日期必须等于服务开始日。

重叠周期只有在每条历史用量仍能唯一归属时才允许存在；否则 `NO_GO`。

### 4.5 财务事实只读预检

`POST /provider-finance/activation-preview` 接受完整草稿，执行：

1. 规范化草稿并计算候选哈希。
2. 在 `REPEATABLE READ + READ ONLY` 财务计算事务中加载激活范围和事实快照。
3. 把草稿作为虚拟资金事实和虚拟订阅周期参与投影，不写入资金表。
4. 模拟四类允许的用量修复并报告行数，不更新 `ledger_line`。
5. 对切换时点至 `snapshot_at` 的完整窗口检查：
   - 所有必要 API 账户均有期初；
   - 所有旧购买记录均已关闭；
   - 所有 API 用量费用状态明确；
   - 所有 Coding Plan 用量唯一归属周期；
   - Usage 与 Ledger Token 守恒；
   - 余额公式守恒且不为负；
   - 月度经营账单在涉及月份全部完整；
   - 非目标字段不会被历史修复修改。
6. 返回结构化缺口、`GO_CANDIDATE | NO_GO`、候选哈希、事实水位和过期时间。

预检不得写入资金事件、订阅周期、运行激活状态或修改用量事实。允许记录不具财务权威性的候选元数据和预检审计，但必须在 `READ ONLY` 事务成功结束后，由独立控制事务写入；不得在只读事务内部插入候选或审计记录。

### 4.6 原子激活

`POST /provider-finance/activate` 仅接受未过期的 `GO_CANDIDATE`。服务端必须：

1. 从认证会话取得企业与管理员身份。
2. 校验请求中的 `confirm_enterprise_id` 仅用于二次确认，必须等于会话企业。
3. 校验企业级静默租约仍有效、Gateway 新请求与自动续订已暂停、在途请求和结算已经排空；任一不满足返回 `409 ACTIVATION_NOT_QUIESCENT`。
4. 使用以下固定 64 位键获取企业级事务咨询锁；失败立即返回 `409 ACTIVATION_IN_PROGRESS`，不排队等待：
   ```sql
   pg_try_advisory_xact_lock(
     hashtextextended(
       'qianliu:provider-finance-activation:v1:' || enterprise_id::text,
       0::bigint
     )
   )
   ```
5. 在一个 `SERIALIZABLE` 外层事务中：
   - 锁定候选记录和运行状态；
   - 校验候选状态、有效期、哈希和激活幂等键；
   - 重算完整事实水位，任何变化均返回 `409 CANDIDATE_STALE`；
   - 写入 API 期初和历史充值；
   - 写入 Coding Plan 购买事件、跨切换周期和订阅周期；
   - 关闭每条旧购买记录；
   - 仅按候选中排序后的 `ledger_line` 主键列表锁定和修复资格行；
   - 仅修改允许的四个 `ledger_line` 字段；
   - 对候选固定行集逐行验证非目标字段基准哈希未变化；预检后新增行不进入该哈希比较，但会受完整事实水位和静默门禁约束；
   - 重新执行完整窗口守恒；
   - 写入 `strict_writes_enabled=true`；
   - 将候选从 `PREVIEWED` 原子更新为 `ACTIVATED`，保存激活结果、回执和操作审计。
6. 任一步失败则整体回滚；不得在主事务前单独提交 `ACTIVATING` 状态。
7. `40001 serialization_failure` 或 `40P01 deadlock_detected` 无论发生在事务语句还是提交边界，均在整个事务执行边界之外捕获并映射为 `409 ACTIVATION_RETRY_REQUIRED`、`retryable=true`。协调器、数据库仓储和 HTTP 层均不得自动重试；管理员重新提交同一幂等键前必须重新读取激活状态。
8. 重试时若事实水位不变，可继续使用原候选；若水位变化，再返回 `409 CANDIDATE_STALE` 并要求重新预检。
9. 若数据库已经提交但客户端未收到响应，同一幂等键必须返回已保存的 `ACTIVATED` 结果。

所有内部资金写入函数必须接收同一个 `Transaction<Database>`；禁止在激活事务中调用会自行开启新事务的公开方法。

## 5. 候选、哈希、事实水位与幂等

### 5.1 候选规范化

候选哈希输入至少包括：

- `schema_version`；
- 会话企业 ID；
- 固定切换时点；
- 排序后的资源与必要币种账户；
- 期初、充值、购买、周期和旧记录关闭决定；
- 金额规范化值：账户金额八位小数、人民币实付两位小数；
- UTC 时间和上海自然日边界；
- 说明与证据引用；
- 完整事实水位摘要。

候选哈希不得包括：展示名称、客户端管理员 ID、激活幂等键、生成时间、随机候选 ID或 UI 排序状态。

统一使用稳定 JSON 序列化和 SHA-256。数组必须按领域主键和时间排序，空值必须规范为 `null`，不得依赖对象属性插入顺序。

### 5.2 完整事实水位

`fact_watermark` 必须覆盖所有会影响预检结果的记录集合及其确定性摘要，至少包括：

- `provider_resource`；
- `provider_resource_operating_snapshot`；
- `resource_purchase_record`；
- `provider_finance_event`；
- `provider_subscription_period`；
- `provider_finance_legacy_cost_resolution`；
- `ledger_line`；
- `usage_event`；
- 生效计价规则或 `billing_rule_snapshot`；
- `provider_finance_runtime_state`。

激活时必须在企业锁内重新加载并计算相同摘要。仅比较“资源版本”不足以证明候选未漂移。

完整事实水位与历史修复非目标哈希是两个不同合同：

1. 完整事实水位负责发现候选范围内新增、删除或变化的事实集合。
2. 历史修复基准只覆盖预检时确定的修复资格行集。候选必须保存排序后的 `ledger_line_id`、允许修复字段及逐行 `non_target_hash_before`。
3. 激活时按主键稳定排序加锁；缺行、资格变化、目标字段预期不符或非目标哈希变化均使候选失效。

### 5.3 候选与激活记录

建议新增企业级控制表 `provider_finance_activation_attempt`，它不是资金事实表，至少保存：

- 企业、候选 ID、候选哈希、事实水位哈希；
- 预检结论、缺口摘要、创建者、创建时间、过期时间；
- 固定修复资格行 ID、允许修复字段和非目标字段基准哈希；
- 状态：`PREVIEWED | ACTIVATED | EXPIRED | REJECTED`；不得持久化 `ACTIVATING`；
- 激活幂等键和激活结果快照；
- 激活时间与激活管理员。

不得存储 API Key、订阅 Token、银行卡信息、支付密码或厂商登录凭证。

候选 TTL 固定为 `1800` 秒：`expires_at = preview_committed_at + 30 minutes`。读取候选、激活失败、锁竞争、`40001/40P01` 或幂等重放均不得延长有效期；过期后只能重新预检。

企业级静默租约固定最长 60 分钟，必须带管理员、开始时间、过期时间和解除审计。租约到期自动失效并恢复 Gateway 请求和自动续订；激活开始时租约剩余时间必须不少于 5 分钟，否则返回 `409 ACTIVATION_NOT_QUIESCENT` 并重新进入静默流程。

### 5.4 幂等语义

1. 同一企业、同一激活幂等键、同一候选哈希：返回第一次结果。
2. 同一企业、同一幂等键、不同候选哈希：`409 IDEMPOTENCY_CONFLICT`。
3. 企业已经激活后提交不同候选或不同幂等键：`409 ALREADY_ACTIVATED`，不得伪装成成功重放。
4. 记录级资金事件仍保留其资源级幂等键和唯一约束。

## 6. API 与权限合同

### 6.1 新增接口

1. `GET /provider-finance/activation-state`
   - 返回运行模式、严格写状态、激活范围摘要、最近候选元数据和激活回执。
2. `POST /provider-finance/activation-preview`
   - 接受完整草稿；返回结构化预检、候选哈希、水位和有效期。
3. `POST /provider-finance/activate`
   - 接受候选 ID、候选哈希、激活幂等键和 `confirm_enterprise_id`。

企业 ID、管理员 ID、角色和权限只能来自服务端认证会话。请求体中不得接受可覆盖会话身份的 `enterprise_id` 或 `admin_id`。

### 6.2 权限

1. 查看状态：`resources.view`。
2. 创建预检候选：`resources.operate`。
3. 执行激活：`resources.operate`，并通过生产侧独立授权门禁。
4. 未授权、跨企业、候选企业不匹配必须失败关闭并写失败审计。

### 6.3 现有接口

1. 充值、订阅、更正、冲销和对账继续要求 `ACTIVE + strict_writes_enabled`。
2. 原 `opening-balances` 接口不得成为初始化旁路。
3. 激活后未来新增 API 资源使用资源级启用流程：
   - 新资源初始状态为资金未就绪，不得承载生产流量；
   - 必须登记必要币种账户的期初余额；
   - 说明和证据引用强制必填；
   - 完成资源级守恒检查后才能进入可调度状态。

## 7. 数据库与领域设计

优先复用：

- `provider_finance_event`；
- `provider_subscription_period`；
- `provider_finance_runtime_state`；
- `provider_finance_idempotency`；
- `provider_finance_duplicate_candidate`；
- `provider_finance_reconciliation_case`；
- `operation_log`。

允许新增或扩展非资金事实控制结构，以保存企业级候选与激活幂等。不得把候选草稿加入经营账单或余额计算。

领域层必须拆分为：

1. 纯规范化与哈希函数；
2. 只读投影/预检函数；
3. 接受 `Transaction<Database>` 的资金写入原语；
4. 激活事务协调器；
5. 激活后的资源级资金启用服务。

## 8. 失败关闭规则

以下任一情况必须 `NO_GO` 或在激活时返回冲突：

1. 必要 API 账户缺少期初余额、说明或证据。
2. 旧购买记录没有唯一关闭结果。
3. 真实历史充值或订阅购买缺少金额、币种、实付或证据。
4. 存在未解释的 `UNKNOWN_COST`、缺币种或币种冲突。
5. Coding Plan 用量无法唯一归属周期。
6. Usage 与 Ledger Token 不守恒。
7. 余额公式不守恒或余额为负。
8. 任一涉及月份的经营账单不完整。
9. 候选过期、哈希不匹配或完整事实水位变化。
10. 企业锁获取失败。
11. 企业已经激活但请求不是同一幂等重放。
12. 会话企业、确认企业、候选企业不一致。
13. 历史修复会修改四个允许字段以外的任何 `ledger_line` 字段。
14. 企业静默租约无效、已过期、仍有在途请求或待结算事实。
15. `40001/40P01` 事务失败；本次回滚并要求人工重试，不得在服务端循环重跑。

禁止提供 `--no-verify`、直接改表、关闭触发器、跳过守恒或修改安全门禁等旁路。

`REJECTED_WITH_EVIDENCE` 只适用于证明某条旧购买记录不是实际资金事实，绝不能用于忽略、关闭或冲销 `UNKNOWN_COST` 用量行。未知用量成本仍必须通过既有计价事实或受控历史费用处置闭环，否则保持 `NO_GO`。

### WP00：OpenSpec 与候选基线

### WP01：合同、候选与迁移

- 新增企业级候选/激活幂等持久化。
- 加固期初说明与证据合同。

### WP02：事务原语与假设投影

- 抽取 transaction-aware 资金写入原语。

- 业务负责人确认全部金额、币种、周期、订单和证据；
- 启动目标企业静默租约，暂停新 Gateway 请求和自动续订；

- 验证资金余额、经营账单和新用量归属。
- 成功或失败后解除静默租约并验证流量恢复；若租约自动到期，必须重新开始预检流程。

## 10. 最低测试矩阵

### 10.1 候选与预检

- 草稿投影不写资金表、不改 `ledger_line`；
- 哈希与输入顺序无关；金额和空值规范化稳定；
- 任一事实表变化都会使候选失效；
- 候选过期、企业不匹配和非 `GO_CANDIDATE` 均拒绝激活。

### 10.2 历史事实

- 正数和零值期初、八位小数、错误切换时点；
- 历史充值迁移、重复订单、缺实付和旧记录三种关闭结果；
- Coding Plan 默认周期、自定义周期、重叠周期和自动续订冲突；
- 旧记录不得被静默忽略。

### 10.3 原子性与幂等

- 两管理员并发时仅一个取得锁；
- 任一步异常导致资金事实、周期、用量修复和激活状态全部回滚；
- 同键同候选重放；同键不同候选冲突；激活后不同请求冲突；
- 现有内部方法不得开启脱离外层事务的新事务；
- 在事务语句和提交边界分别注入 `40001`，验证返回 `ACTIVATION_RETRY_REQUIRED` 且服务端零次自动重试；
- 注入 `40P01`、进程中断和提交成功但响应丢失，验证回滚或幂等重放语义；
- 验证不存在可持久残留的 `ACTIVATING` 状态。

### 10.4 守恒与历史修复

- 切换时点至候选水位全部月份守恒；
- Usage 与 Ledger Token 一致；
- API 余额公式一致且非负；
- Coding Plan 用量唯一归属；
- 只修改候选固定主键行集的四个允许字段，逐行非目标哈希变化数必须为零；
- 新增行不进入固定修复哈希，但必须触发事实水位或静默门禁检查。

### 10.5 权限与运维

- `resources.view` 与 `resources.operate` 权限区分；
- 跨企业、伪造管理员 ID、伪造企业 ID 失败；
- `DARK/OFF` 时 Control API 和 Worker 都不产生新资金写入；
- 运行状态仍保持不可逆，恢复后继续从原激活状态运行；
- 企业静默租约阻止目标企业新 Gateway 请求和自动续订，并能排空在途结算；
- 静默租约到期自动恢复，候选固定 30 分钟过期且不滑动续期；
- 固定 64 位锁键与仓库其他咨询锁不串锁。

## 11. 验收标准

### 11.1 技术验收

1. OpenSpec 每项 Requirement 至少有一个可执行 Scenario。
2. 预检与激活共享同一套规范化、投影和守恒逻辑。
3. 激活为单事务、幂等、并发安全且失败零写入。
4. 候选完整绑定事实水位，不能仅依赖资源版本。
5. 所有历史购买记录有唯一关闭结果。
6. 不记录敏感凭证明文。

### 11.2 产品验收

1. DeepSeek 显示可解释的期初、历史充值、当前余额、本月充值和 API 成本。
2. 智谱显示购买金额、人民币实付、服务周期和套餐成本。
3. 经营账单区分 API 动态成本与 Coding Plan 固定成本。
4. 所有金额可回溯至期初、充值、购买、续费、更正、冲销、对账或用量事实。
5. `NO_GO` 必须精确到资源、账户、旧记录或用量行类别。

### 11.3 生产验收

1. 部署成功不等于资金账本激活。
2. 激活必须有候选回执、独立授权和操作审计。
3. 验证至少一笔 DeepSeek API 用量、一笔历史/后续充值和一笔智谱套餐用量归属。
4. 验证完整窗口资金、Token、周期和经营账单守恒。

## 12. 激活前静默、异常停写与恢复

### 12.1 激活前静默期

生产预检前必须为目标企业建立最长 60 分钟的审计静默租约：

1. Gateway 在 admission 阶段拒绝该企业的新请求并返回明确维护状态；不得中断已经提交到上游的请求。
2. Worker 跳过该企业的自动续订和其他会改变候选事实的资金任务。
3. 等待该企业 `IN_PROGRESS` 请求、未结束 Attempt、未配对 Usage/Ledger 和待结算事务全部归零。
4. 排空完成后才生成候选；候选 TTL 为 30 分钟。
5. 激活成功、明确放弃或租约到期后恢复流量。租约到期自动恢复时，旧候选不得继续激活。

静默门禁是生产激活的前置条件，不等于 `PROVIDER_FINANCE_MODE=DARK`；后者用于激活后的全服务资金停写，不能阻止 Gateway 生成新 `ledger_line`。

### 12.2 激活后异常停写

严格写激活不可逆。激活后发现异常时：

1. 将 Control API 与 Worker 的 `PROVIDER_FINANCE_MODE` 同时切换为 `DARK`；若需要完全关闭读取接口则使用 `OFF`。
2. 重启或替换两个服务，分别验证运行模式生效。
3. 停止新的充值、续费、自动续订和严格账本写入，但不修改 `strict_writes_enabled`。
4. 保留已写事实，通过更正、冲销和对账修复，不删除或覆盖原记录。
5. 修复后重新执行完整预检与业务确认，再恢复 `ACTIVE`。

运行手册必须提供 Control API、Worker、镜像、容器、路由和公开接口的独立验证证据。
