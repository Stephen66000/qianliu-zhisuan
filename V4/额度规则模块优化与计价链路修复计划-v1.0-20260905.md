## 2. 厂商、模型和资源的职责

厂商资源负责资源账号登记、凭证、官方模型同步、充值与订阅实付、余额及真实 Token。计价维护集中在“额度规则 → 计价”。本次不新增厂商资源计价编辑入口，也不新增此前误解产生的“只读计价状态”需求。

厂商代码已经存在于“登记资源 → 新建厂商”的“厂商代码”字段，对应数据库 `provider.code`：DeepSeek 为 `deepseek`，智谱为 `zhipu`，Kimi 为 `kimi`。显示名称与资源名称是另外的字段。资源表单中的“厂商”选项提交 `provider_id`，不改名为代码。

现有厂商代码下拉框只支持三个已适配厂商。新增同厂商账号复用代码；接入全新厂商需要扩展代码选项、请求适配和模型同步等能力。本次不新增千问等厂商，不把代码改为任意输入。

统一模型与路由的数据结构继续保留，一个模型可以对应多个具体资源。取消重复创建入口不等于删除模型、路由或历史关系。

## 3. 计价 Tab 与“新建规则”

### 3.1 操作流程

1. 选择模型：使用厂商资源同步并登记的模型目录，包含可配置的待配置模型。
2. 选择具体厂商资源：只列出该模型对应的已同步资源；展示厂商、资源名称及 API/Coding Plan 模式以区分账号。上游模型从选中候选自动带出。
3. 在同一表单填写路由优先级和权重，不要求再进入独立路由页面。
4. 在独立的计价区域填写价格，或选择符合条件的历史规则集沿用。
5. 一次“保存并启用”完成配置。未来生效的价格需明确显示待生效，不能宣称当前已可调用。

正常路径复用已有模型与路由候选，避免重复建路由。保留现有真实模型验证、企业隔离、资源状态、授权和计价就绪检查；减少点击不能绕过这些校验。模型真实验证会消耗厂商额度，继续使用现有明确确认流程。

后端以一次事务保存整套计价及相关路由配置、状态变更、审计；任何一项失败全部回滚。上游检测在事务外完成，最终事务复核验证状态和版本。提交具有幂等及并发版本检查，重复点击不能产生重复规则或半启用配置。

### 3.2 价格显示与版本管理

- API 明确显示币种、计价单位、缓存命中输入价、未命中输入价、输出价、适用时段、倍率及生效时间；未配置与明确零价需要区分。
- 用户价格展示优先使用“元/百万 Token”等可读单位；保存时按现有内部每 Token 单位准确转换，不把单价单位与金额混淆。
- 高峰/低谷配置展示时区、星期、时间窗口和最终有效单价，使用户能核对某时刻的实际费用。
- Coding Plan 明确显示真实 Token 对应的额度扣减倍率，不伪造每次请求的 API 现金费用。
- 保留版本化编辑、停用、归档和历史查看；修改价格生成新版本，历史账本使用原快照。
- 金额显示沿用现有格式；价格输入和价格证据保留必要精度。不能将厂商模块“最多两位小数”的展示要求扩展为单价或结算精度限制。

### 3.3 沿用同厂商历史价格

复用旧分支 `origin/codex/billing-rule-assist-v1.4-integration` 的整套计价复制思路，选择性移植相关功能和回归测试。该分支包含截图导入等其他能力，不整分支合入。本次不加入截图识别、模型识价或新的导入数据表。

复制约束在前后端同时实施：

- 必须同企业、同 `provider.code`、同资源模式。Kimi 只能复制 Kimi；DeepSeek 不能复制给千问；API 与 Coding Plan 不混用。
- 优先推荐同资源、同模型的可用规则；其他同厂商模型的价格只能作为明确标识的候选，由管理员检查差异。
- 没有合适候选时使用空白表单，不自动跨厂商填价。
- 复制整套基础价、时间窗口、倍率、币种和规则优先级；重新绑定目标资源/上游模型，并设置新版本和生效时间。
- 保存复制来源和新旧差异，源版本保持不变，整套创建原子提交。

旧复制接口要求路由已经启用。移植时需适配本次单次保存流程，在服务端统一校验并提交，不能恢复成先启用路由、再提交价格的两次操作。

## 4. Gateway 统一计价合同

### 4.1 当前代码事实与缺口

本地检查确认：Gateway 在调用上游前冻结适用规则，调用完成后按每个上游尝试计算并保存用量和账本。API 已使用 Token 分项价格；Coding Plan 已使用倍率扣减。

当前 API 分支只匹配 `API_PRICE` 并按其单价计算，独立 `TIME_WINDOW` 倍率没有叠加到 API 费用。带时间窗口的绝对 API 单价已经可以匹配，不能笼统判断所有高峰费用都没有生效。

生产用调度输入解析器 `resolveResourceOperatingInput()` 当前固定返回 `priceMultiplier: "1"`。依赖倍率条件的策略缺少真实输入；既有按明确时间窗口匹配的策略不因此等同于全部失效。

具体线上哪些规则受到影响，实施前通过只读规则及账本抽样核对，不能仅凭页面配置或模拟测试判断。

### 4.2 真实 Token 与逐次计算

真实 Token = 输入 Token + 输出 Token。缓存命中 Token 属于输入子集，推理 Token 按适配器规范化语义保存，不重复加到真实 Token 总量中。保留厂商原始计量质量；估算或未知不能标为厂商精确计量。

API 倍率模式下，定义 H 为缓存命中输入 Token、I 为总输入 Token、O 为输出 Token，各分项价格均换算成每 Token 单价：

```text
本次基础费用 = H × 命中输入单价 + (I − H) × 未命中输入单价 + O × 输出单价
本次 API 费用 = 本次基础费用 × 本次命中的时段倍率
Coding Plan 本次扣减额度 = (I + O) × 本次有效扣减倍率
```

以上计算适用于所有时段。API 未配置时段加价且有有效基础规则时倍率为 1；Coding Plan 继续使用已配置的基础/档位倍率，不能将既有非高峰倍率一律改为 1。套餐有效倍率按既有规则优先级唯一确定，不默认把档位倍率与时间倍率再相乘。

API 用 Decimal/numeric 计算，中间乘加不提前舍入，最终按现有入账精度冻结。套餐扣减保留现有整数舍入合同，并测试小数倍率边界。真实 Token 不因倍率改变。

### 4.3 兼容既有价格，避免重复加价

API 支持现有“按时段配置绝对单价”和新增“基础单价 × 时段倍率”两种表达，规则集需明确其计算模式。

同一次计算只能执行一种模式：绝对高峰价格不再叠加倍率；新增倍率模式明确关联基础价格和窗口规则。旧规则保持现有语义，不能部署后自动套上新倍率。对混合配置、无基础规则和相互冲突的窗口，保存/发布时明确校验并给出原因。

复用现有规则优先级、时区、多窗口及版本边界；窗口按左闭右开处理，覆盖跨午夜和跨生效版本场景。倍率模式无法取得完整价格时不得回退成免费或静默按 1 倍。

### 4.4 调度与结算共用计价解析

建立共用的价格解析结果，包含资源、上游模型、资源模式、适用时刻、基础规则、窗口、有效倍率、币种和版本证据，供就绪校验、调度和 Gateway 结算复用。

调度先解析候选在当前时刻的价格，再执行允许、切换、限流或拒绝。实际调用前按选中资源和本次尝试时刻复核，并冻结最终规则；跨越窗口边界或规则更新导致倍率变化时，重新核对相关调度条件，不能高峰前放行、进入高峰后绕过策略。

切换与重试按实际资源及各次调用时刻分别解析、冻结、结算。保留原候选的决策证据，实际费用使用实际调用资源的规则。费用节省等现有消费者需复用完整价格证据，避免仍用不含倍率的旧计算路径。

固定绝对价格模式没有可推导的统一倍率时，不自行推算“3 倍”；继续支持明确时间条件的策略，并将倍率条件的适用性在配置与校验中说明。不得把未知倍率伪装为已核实的 1 倍。

## 5. 成功、失败与数据库账本

结算单位是每个上游尝试（Attempt），一次用户请求可能包含多个尝试。是否记录消耗取决于实际用量证据，不仅取决于最终请求状态。

| 情况 | 处理 |
| --- | --- |
| 访问厂商前拒绝 | 不产生上游消耗；若已创建 Attempt，沿用明确零消费事实；尚无 Attempt 时保留拒绝记录即可 |
| 成功且用量可计量 | 按冻结规则逐次计算并保存 |
| 流中断或最终失败，但已有可计量消耗 | 保存已发生的 Token、费用及质量标记 |
| 已访问厂商但用量不明 | 保存未知状态，费用未知不能当成免费 |
| 重试或切换 | 各次实际消耗分别记账，再按请求汇总；同一 Attempt 重复持久化不得重复计费 |

数据库 PostgreSQL 继续作为账本事实来源：`billing_rule` 保存配置；`usage_event` 保存用量；`ledger_line` 保存逐次费用、扣减和冻结证据；`ledger_transaction` 保存请求汇总；厂商资金账本保存充值、订阅等实付事实。

新增倍率结算证据至少包含基础规则 ID/版本、窗口规则 ID/版本、计算模式、时区与命中窗口、适用时刻、分项单价、有效倍率、币种、最终费用和计量质量。优先扩展现有快照结构，并兼容旧请求详情和历史账本读取。

经营账本读取已结算数据库事实进行归集、对账和既有套餐分摊；API 请求费用不在报表查询时按最新价格重算。Coding Plan 固定实付来自资金事实，倍率影响扣减及既有分摊权重，不增加厂商实付金额。

历史资金记录、既有账本和冻结报表不自动改写。若抽样发现旧请求漏算，单独记录差异及影响范围；历史纠正需另行明确处理方案。

## 9. 测试与验收标准

### 9.1 计价与数据库

- 同样 Token 在普通时段按基础价、高峰按配置倍率计费；多个高峰窗、窗口起止、跨午夜、时区及版本切换均可复算。
- 示例：输入 1,000,000，其中命中缓存 200,000，输出 100,000；命中价 1 元/百万、未命中价 2 元/百万、输出价 4 元/百万，基础费为 2.20 元，3 倍时为 6.60 元。这只是测试数据，不是厂商实际价格。
- 已有绝对高峰价格保持原结果，不重复乘倍率；Coding Plan 3 倍只改变扣减，不改变真实 Token 或订阅实付。
- 小额费用、中间精度、大 Token 值、币种、无价格、未知用量及明确零费用均正确处理。
- 上游前拒绝、成功、流中断、失败有消耗、失败用量未知、重试和切换均核对逐次行与请求汇总。
- 重复持久化不重复扣费；并发改价不改变已冻结调用的结算结果；历史账本和冻结账单保持原值。
- 汇总与现有资金投影一致，未知费用继续暴露缺口，不被已知部分合计掩盖。

### 9.2 调度与配置

- 使用数据库真实规则和正式输入解析器，验证倍率条件确实触发允许、切换、限流或拒绝，不能仅注入模拟的 `priceMultiplier: "3"`。
- 验证调度判断后跨峰谷边界、规则更新、目标切换与重试时的决策/结算一致性。
- 无基础价、冲突窗口、模式混用、跨企业引用、未验证路由、失效资源及并发更新能被正确阻止。
- “保存并启用”失败全部回滚；复制多条规则部分失败时无残留启用状态；同厂商同模式过滤在 API 层也不可绕过。

### 9.3 页面与生产业务

- 页面仅有计价、调度策略两个 Tab；部门预算和独立新建模型/路由入口已移除。
- 从已同步模型开始，选择资源、填写优先级权重及价格，一次提交完成配置；现有配置的编辑和恢复路径仍可用。
- Kimi 复制候选来自 Kimi，API 与 Coding Plan 不混用，无候选可空白创建；价格单位、生效时段和最终单价可核对。
- 策略停用后可单独存档，默认列表隐藏，“查看存档”仍能找到历史和审计。
- 在隔离测试数据库完成完整浏览器和 Gateway 流程，运行受影响类型检查、Lint、构建及相关集成回归。
- 部署后由用户在 Mac Mini 验证现有三家厂商正常调用、真实 Token、逐次费用、倍率和汇总一致。真实调用产生费用时按既有确认范围执行。
- 实际高峰样本未取得前，该项标为待验收；健康检查成功不等于高峰计价业务通过。
