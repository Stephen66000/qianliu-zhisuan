> 日期：2026-10-03（Asia/Shanghai）
> 状态：`REQUIREMENTS_CONFIRMED / PLAN_PREPARED / IMPLEMENTATION_NOT_AUTHORIZED / DEPLOYMENT_NOT_AUTHORIZED`
> 分析基线：`7f3557f7afabcd6665aea39932895899272e318b`。本文件是开发与验收方案，本轮仅新增计划文档。

## 1. 已确认目标与范围

适用于 Kimi、智谱的 `CODING_PLAN` 资源。5 小时或周额度耗尽时，Gateway 向使用现有 Key 的用户返回对应窗口、预计恢复时间和自动恢复说明；厂商窗口恢复后自动允许新请求，无需管理员执行同步、验证、更新凭证或恢复操作。

本次不追查 Kimi 历史 403，不修改历史状态或请求事实，不新增首页区块、管理页面、告警平台或独立调度服务。真实凭证失效、管理员停用、套餐过期、主体授权撤销保持各自语义。本次不把所有 401/403/429 都解释成额度耗尽。

额度耗尽时不自动换模型、换到付费 API、使用已购余额或额外付费额度，也不在后台重跑用户已失败的请求。额度同步使用既有查询接口，不发起消耗生成额度的 Chat 探针。

## 2. 当前证据与待补点

用户在 2026-10-02 提供的生产只读查询显示：

- Kimi 的 5 小时及周额度同步成功，资源为 `ACTIVE`；智谱两个窗口同步成功，资源为 `DEGRADED`。
- Kimi 在 2026-09-26、智谱在 2026-09-28 有 `QUOTA_SYNC_RECOVERED / system` 记录，证明现有自动恢复实际运行。
- Kimi 2026-09-28 的凭证隔离由管理员 Chat 验证解除；本次不继续调查该历史请求。
- 智谱的当前 5 小时窗口没有 `reset_at`。恢复时间未知是必须覆盖的真实边界。

当前源码已具备：5 小时和周窗口解析、重置时间存储、额度类隔离自动恢复、恢复后有效 Key 模型集合刷新。需要补齐：

1. 首次耗尽提示只写“厂商额度已用完”，没有明确区分 5 小时与周窗口，也没有统一按北京时间展示。
2. 已隔离资源的后续请求走 `sendNoEligibleResponse()`，通常返回泛化冷却或无可用资源提示，丢失窗口原因。
3. 恢复时间读取函数默认取最早未来时间，未检查该窗口是否耗尽；不能用它计算两个耗尽窗口的整体恢复时间。
4. 普通 429 可能表示并发或频率限制，需要与窗口耗尽分开；现有 5 小时分类还进入通用失败切换路径，需落实本次停止请求的约定。
5. Worker 在资源恢复后仍需与其他额度类阻断、Key 模型集合保持一致，防止资源有余量但原 Key 仍无法调用。

以上为源码分析与用户提供的历史生产快照，不是本计划实施后验收结果。

## 3. 用户提示与接口合同

### 3.1 文案

有可信恢复时间时，模板为：

> Kimi 厂商 5 小时额度已用完，预计 10 月 3 日 01:16（北京时间）恢复，系统将自动恢复服务，请届时重试。

> Kimi 厂商周额度已用完，预计 10 月 5 日 11:16（北京时间）恢复，系统将自动恢复服务，请届时重试。

智谱使用同一模板，替换厂商名称。两个窗口均耗尽时：

> Kimi 厂商 5 小时和周额度均已用完，预计 10 月 5 日 11:16（北京时间）恢复，系统将自动恢复服务，请届时重试。

没有可信时间时：

> 智谱厂商 5 小时额度已用完，恢复时间暂未知，系统将自动检查并恢复服务，请稍后重试。

两个窗口均耗尽但其中一个恢复时间未知时，说明两项耗尽及整体时间暂未知，不拿已知窗口的时间冒充整体可用时间。上游只明确“套餐额度耗尽”、未指出窗口且无可信窗口快照时，使用“套餐额度已用完”，不猜为周额度。

### 3.2 时间与证据

1. 优先读取上游明确属于该阻断窗口的重置时间；`Retry-After` 只有在该响应已明确识别为窗口耗尽时，才作为该次窗口恢复的预计时间。
2. 上游未提供时，读取同企业、同资源、同窗口的可信成功快照。不能读取其他资源、未耗尽窗口、失败保留快照或已过期时间来填充预计恢复时间。
3. 两项均耗尽且两个时间都已知，整体预计恢复取较晚值；只耗尽一项，使用这一项时间。不能取所有窗口的最早时间。
4. 快照有效性结合 `sync_status`、`last_success_at`、当前时刻及既有 5 分钟同步节奏判定；初始实施采用 10 分钟展示有效期，超过则显示未知。恢复判断使用当次厂商查询，不依赖这个展示有效期。
5. 不使用“报错时刻 + 5 小时”或“报错时刻 + 7 天”推算。时间仅用于预计与安排检查，到时仍需确认余量。
6. 中文按 Asia/Shanghai 展示；机器字段保持 ISO 时间。跨年时补全年份。
7. 对多候选资源按已经授权、对应模型且未归档的范围取证；首次失败提示描述实际失败资源，隔离期只在证据明确的范围内说明额度阻断，不能让一个耗尽账号代表所有候选。

### 3.3 北向协议

- 对明确的窗口耗尽，未提交响应时返回 HTTP 429、兼容的 `error.message` 及请求 ID，不伪装为成功模型正文。
- 保留既有错误码兼容性，明确提供厂商、阻断窗口集合、`next_reset_at`；时间未知返回 null 和稳定不可计算原因。新增窗口字段与 Outcome 扩展需在 Contracts 中统一定义，不让前端自行猜测。
- 有可信预计时间时提供 `Retry-After`，支持时间到后再次请求；它不是让客户端持续自动重试或后台重放的指令。
- Chat Completions、Messages、Responses 在适用错误路径中使用同一语义。已提交流保持既有流内错误与关闭规则，不重写 HTTP 状态、不追加其他模型输出。
- 首次耗尽、隔离期间再次请求、准入阶段发现窗口耗尽，均使用相同的窗口提示规则；普通并发限制、主体本地额度耗尽与管理员策略阻断保持独立提示。
- Gateway 能保证返回正确错误内容；第三方客户端是否展示该内容，需要单独验证，不能仅凭 API 测试声明用户实际看到提示。

## 4. 自动恢复合同

1. 明确窗口耗尽后结束本次请求，记录额度类状态与安全证据，不进入凭证验证流程。
2. 按厂商实际恢复时间安排检查；没有时间或查询失败时沿用既有 5 分钟重试间隔。运行依赖现有 Worker，不新增定时服务。
3. 5 小时与周额度同时耗尽时，可按较早重置点先更新窗口事实，但用户整体预计可用时间取较晚点；只要仍有一个阻断窗口耗尽，就继续等待。
4. Kimi 恢复要求当次返回的 5 小时、周窗口都可知且有余量。智谱必须确认 5 小时窗口有余量；返回周窗口时同样必须有余量。
5. 如果已确认周窗口耗尽，后续缺失、UNSUPPORTED、STALE 或 FAILED 不能作为该窗口恢复证据；应保留既有阻断事实并继续查询。优先复用现有窗口历史和状态事件，不新建存储平台。
6. 恢复后自动进入可调用状态，沿用 `QUOTA_SYNC_RECOVERED` 审计及 Key 模型集合刷新；下一次成功调用变为 `ACTIVE`。成功后的管理员文案可表达“额度已恢复，可使用，待成功调用确认”。
7. 若还有相同资源和模型范围的额度类 availability 阻断，必须随可信额度恢复协调解除，不能要求人工处理第二道额度阻断。鉴权、配置、计划停用、管理员停用等其他阻断不得被这次恢复清除。
8. 整条路径不得要求重新保存资源、重发 Key、点击“立即同步”或管理员验证。恢复延迟按 Worker 扫描和厂商查询延迟描述，不承诺精确在重置秒点恢复。
9. 恢复事务与状态复核沿用现有并发保护；查询期间若管理员停用或轮换凭证，不得用旧查询结果恢复新状态。

## 5. 最小开发工作包

| 工作包 | 主要落点 | 交付 |
|---|---|---|
| WP1 窗口证据与提示 | `packages/contracts`、`provider-adapters/src/upstream-failure.ts`、Gateway `runtime-controls.ts`、`upstream-error-diagnostic.ts` | 明确窗口集合、可信恢复时间和统一中文提示；识别只针对新合同，不追查旧 403 |
| WP2 请求路径闭环 | Gateway `pipeline-admission.ts`、`pipeline-response.ts`、`pipeline-settlement.ts`、`pipeline-attempt-execution.ts` | 首次与隔离期请求一致提示；窗口耗尽停止追加 Attempt；不使用付费回退 |
| WP3 自动恢复闭环 | Worker `coding-plan-quota/runner.ts`、数据库额度窗口／资源恢复仓储及适用 availability 事件 | 各阻断窗口确认恢复后同 Key 可调用，已确认耗尽窗口的缺失不能误解封 |
| WP4 验证与交付 | 定向单测、真实 PG 集成、Gateway 注入或受控 HTTP、必要的管理员状态文案 | 绑定候选版本的技术证据及待部署、待业务验收状态 |

复用现有接口、Worker 与窗口表；默认不新增数据库迁移。若实施发现可靠记录阻断窗口必须增加持久化字段，应先把原因和最小迁移补入本计划，不扩大为新模块。首页重设计、套餐财务及管理员凭证恢复流程均不纳入本次。

## 6. 验收矩阵

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A1 | Kimi／智谱仅 5 小时耗尽，响应含时间 | 429 提示厂商、5 小时、正确北京时间、自动恢复；不新增失败切换 Attempt |
| A2 | 仅周额度耗尽，响应或快照含周重置时间 | 提示周额度，禁止误用 5 小时重置时间 |
| A3 | 两项耗尽且时间不同 | 提示两项；整体预计时间取较晚值；先恢复一项仍禁止普通准入 |
| A4 | 全部未知或任一阻断窗口时间未知 | 明确整体时间未知，字段为 null，不造日期，不使用现在加周期 |
| A5 | 可信快照兜底，过期／FAILED／STALE 快照 | 前者按同窗口兜底；后者不用于确定的恢复时间或自动解封 |
| A6 | 冷却期间同 Key 再次请求 | 保留具体窗口提示，不退化为泛化无可用资源；不发起上游生成请求 |
| A7 | 普通并发／频率 429、主体额度、未授权模型 | 不误报厂商窗口耗尽；权限门禁保留 |
| A8 | 重置点到达但厂商仍返回零、超时或错误 | 保持阻断、安排下一检查；不要求人工操作 |
| A9 | 所有阻断窗口确认有余量 | Worker 自动恢复；原有效 Key 不修改即可成功调用；后续状态变正常 |
| A10 | 已确认周耗尽，下一响应不含周窗口 | 不凭 5 小时余量解除周额度阻断；后续查询确认周恢复后才能解封 |
| A11 | 额度类 availability 事件仍 OPEN | 可信恢复解除同范围额度阻断，其他类型阻断保持，调用路径可用 |
| A12 | 同步恢复重复执行或管理员并发变更 | 幂等、不清除新故障、停用或凭证轮换状态，不扩大 Key 授权 |
| A13 | 失败、预占及付费回退边界 | 无后台重放、无额外付费资源 Attempt；保留真实用量，预占和租约正常释放 |
| A14 | 三种北向协议与真实客户端 | API 错误语义一致；至少一个实际使用客户端确认提示可见，未验证的入口明确列出 |

使用合成厂商响应和隔离 PG 覆盖耗尽—重置—恢复，不消耗真实厂商生成额度制造故障。执行受影响包定向回归、typecheck、lint 和 build；既有全仓失败单列，不扩大本次测试与改造范围。

## 7. 发布与授权边界

1. 本轮交付计划文档，代码修改、提交推送、部署和生产状态调整尚未进行。
2. 开发开始时重新核对当前版本及改动归属，使用适合的隔离工作区，候选以当时已确认版本为基线。
3. 技术验证完成后提供候选差异、测试证据、原镜像及回滚步骤；部署单独授权，服务器操作延续一步一条指令。
4. 发布后的完成标准是同 Key 从耗尽提示到恢复可调用全程无需管理员操作，同时确认实际客户端看到正确提示。部署健康检查不能替代这条业务验收。
