## 2. 已冻结的代码 Finding

### CQA-01 / P2：同一行的真实 Token 与利用率分子不一致

位置：`apps/control-api/src/resource-insights/routes.ts:35-38,49-51`。

原因与影响：

1. 资源利用接口分别执行旧 `listResourceUtilization` 与新 `loadResourceTokenUtilization`，然后直接拼接结果。
2. 旧查询 `query.ts:139-140` 只限制自然月起止，没有截止当前时刻的条件；新查询 `token-utilization.ts:40` 限制 `settled_at/created_at <= now`。
3. 前端主表读取 `row.realTokens`，利用率及悬停读取 `row.tokenUtilization.currentMonthTokens`。同一行因此可能出现两份不同的“当月真实 Token”。
4. 此外，两条查询没有共享数据库快照；并发结算或登记资源时，存在拼接不同时间点结果的静态风险。本轮确定性复现针对截止时间差异，不声称已经复现并发时序。

隔离 PostgreSQL 17 复现：

- 资源具备完整三个月历史，基线总 Token 为 300，月均为 100。
- 查询时刻为 `2026-09-05T04:00:00Z`。
- 9 月已到查询时刻的 Token 为 100，另有 9 月 20 日结算时间的 900 Token。
- 调用实际的两个查询函数，得到：

```json
{"displayTokens":"1000","numerator":"100","average":"100.00000000","rate":"1.00000000"}
```

断言主表 Token 等于利用率分子失败：`expected '1000' to be '100'`。此场景使用测试数据，未读取或修改正式公司账本。

违反点：V1.4 类型/数据边界与测试语义要求，以及本计划“所选当月累计到当前、分子可与真实 Token 核对”的规则。

最小修复建议：厂商资源接口统一截止时刻，并使主表 Token 与利用率分子来自同一份已结算事实；必要时使用同一数据库快照。不要改变采购复盘原有合同。补接口级断言 `realTokens === tokenUtilization.currentMonthTokens`，覆盖未来记录和并发新结算/新资源。

测试遗漏：当前组件夹具本身就同时放入 `realTokens="1000"` 和 `currentMonthTokens="9000000"`（`ResourceUtilizationPanel.test.tsx:33-35`），但只断言百分比。建议同步修正夹具并添加一致性断言。

处置：未修复，待进入整改执行；本报告不自行接受残余风险。
