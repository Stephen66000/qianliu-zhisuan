## 3. 原 Findings 逐项结论

### F-01：CLOSED

`alert-event-request-derivations.ts` 删除按全部 request ID 构造大 IN 的查询。最新 Attempt 现在由 `latestAttemptResource` 相关子查询取得；`deriveDispatchAlerts` 在 SQL WHERE 中筛选动作不一致或无法解释基线的异常，正常历史不再进入应用层集合。

独立运行真实 PG17 容量测试，65,535 条正常决策返回 `[]`，没有 08P01。子查询的参数数量不随历史 request ID 数量增长。证据：[node-regression.log](./node-regression.log)，`alert-event-dispatch-scale.integration.test.ts` 的真实代码与执行结果。未断言生产当前流量规模。

### F-02：CLOSED

`alert-event-operational-derivations.ts:19–26` 为调用/扣减异常取得同企业、同请求的最新资源。派生结果与 0066 的补全方向一致，后续 evaluate 重新赋值时保留实际资源。

独立 PG17 回归验证：迁移至 0065 → 种入真实对账差异/请求/Attempt/告警 → 0066 补全 → evaluate → resource_id 仍为原资源 → 0066 down 仍保留资源；存在已归档管理员时 0065 down 仍拒绝。上述场景全部通过。

### F-03：CLOSED

AlertsPanel 对主体、资源、厂商三种查询的 error 分别取值；显示“关联信息加载失败”的告警与重试入口；关联缺失时使用失败标签或未知 ID 回退。资源查询失败时跳过依赖资源映射的厂商过滤，并禁用不可靠的选择器；主体筛选仍依据告警自身 principalId，未依赖失败的名称映射。

独立 Web 测试验证三种辅助请求失败后原异常仍显示、“主体信息加载失败/资源信息加载失败”可见、相应筛选禁用、重试调用全部 refetch。既有列表、详情、人工处理等直接测试一并通过。

### F-04：CLOSED（原 6 项）

成功审计测试改为按 `action=admin.cleanup + target_id + result=SUCCESS` 找到准确记录，逐字段断言 target_type、target_id、result、username、status、archived_at、sessions_revoked。
