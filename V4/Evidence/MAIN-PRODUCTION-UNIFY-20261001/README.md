用户于本会话明确同意“核对线上修复 → 修复首页加载错误 → 合回 main → 验证统一候选 → 本地和服务器同步到同一个提交”。原项目目录及其他工作区的未提交改动保留。部署分 prepare、build、deploy、verify；镜像构建在替换服务之前完成，切换前等待 Gateway 已建立连接排空。任何切换后核验失败，恢复此前四个应用镜像和有效配置。PostgreSQL、Redis 与 Nginx 不替换。

## 发布启动等待返修

首次切换因 Bash ERR trap 继承到 curl 的命令替换，在进程尚未监听时触发了回退。发布脚本已将暂时连接失败作为一次未就绪检查，同时仍要求三个 HTTP 入口 200 与 Worker healthy；到期仍失败则保存诊断并回退。三项脚本回归覆盖首次连接失败后正常启动、端点始终不可达、Worker 始终未就绪。应用源码与 280 项回归绑定的候选保持一致。

## Worker Linux 原生依赖构建返修

第二次切换时三个 HTTP 入口已就绪，但 Worker 因缺少 Canvas Linux musl 原生二进制持续重启，严格健康门禁据实回退。pnpm 将下载失败的可选平台包省略，安装步骤仍返回成功。Worker Dockerfile 现显式应用编排已有的 NPM_REGISTRY，并在镜像导出前加载 Canvas、渲染一个 PNG；缺少原生依赖将直接阻止构建。lockfile 及供应链策略不放宽，应用源码保持不变。

镜像源设置使用 pnpm 11 的 project scope：global scope 需要额外全局 bin PATH，与容器内项目依赖安装无关。已在独立临时项目验证 project scope 正确写入项目 .npmrc，原工作区和用户的 registry 设置保持不变。
