零自动重试的失败映射实现（唯一分支）：

```ts
// packages/database/src/repositories/provider-finance-activation-coordinator.ts:708-728（逐字）
function sqlStateOf(error: unknown): string | null {
  if (error === null || typeof error !== "object") return null;
  const code = (error as { code?: unknown }).code;
  return typeof code === "string" ? code : null;
}
export function mapActivationFailure(error: unknown): unknown {
  const state = sqlStateOf(error);
  if (state === "40001" || state === "40P01") {
    return new ProviderFinanceActivationError(
      "ACTIVATION_RETRY_REQUIRED", "激活事务与并发写入冲突，请重读激活状态后再提交",
      { sqlstate: state, retryable: true }, true);
  }
  if (error instanceof ProviderFinanceError) {
    return new ProviderFinanceActivationError(
      "CANDIDATE_STALE", `初始化事实写入失败：${error.message}`, { code: error.code }, false);
  }
  return error;
}
```

### 1.3 `40P01` 注入闭环（v1 披露 G-1 已撤回）

**v1 披露的事实（如实保留为历史）**：`provider-finance-activation-apply.integration.test.ts` 第 868 行用例
**标题**为「`40001/40P01` 在语句与提交边界都映射为 `ACTIVATION_RETRY_REQUIRED`…」，但**函数体只注入了
`40001`**（语句边界真实 `40001`；提交边界用 DEFERRABLE 触发器 `ERRCODE='40001'`）。全仓检索确认：`40P01`
在 `apps`/`packages` 中共 6 处，其中 4 处为 `pool039-lock-order.test.ts` 的「**不得出现**死锁」负向断言
（消费域），另 2 处是该用例的标题与文档注释——**无任何一处实际注入 `40P01`**。该口径在 WP03 → WP04 → WP05
三份报告中被继承性引用，属**证据链层面的措辞夸大**；因本轮授权第 1 条明确要求「实际注入 `40P01`」，
其未被实际注入即构成 **6.1 未完成**，故 WP06 曾被 HOLD。

**本次补正（最小改动，仅测试文件）**：在同一用例内新增一次真实注入，并修正口径。

```ts
// 语句边界 · 死锁（40P01）：另一条 class 40 的真实 SQLSTATE，必须独立注入并单独断言，

// 同上：消息文本来自本条 DO 块，证明 40P01 注入确实执行（而非仅被 grep 到）。

// 且 detail.sqlstate 必须回带各自的原始 SQLSTATE（证明是逐码映射而非巧合）。
for (const [error, sqlstate] of [
```
