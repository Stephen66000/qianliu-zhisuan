# 全平台流式空闲 300 秒与超时提示开发计划 v1.1

> 日期：2026-09-22
> 状态：`DISCUSSION_APPROVED / OPENSPEC_REVIEWED / IMPLEMENTATION_NOT_AUTHORIZED`
> 用户已认可方案方向和 OpenSpec 审核修订；尚未授权代码实施、部署或生产配置变更。

## 0. 修订说明

v1.1 替代 v1.0，并关闭 OpenSpec 计划级审核发现：

1. 将 Undici 底层 `bodyTimeout` 纳入设计，要求它晚于业务 300 秒空闲计时器触发，避免相同门限竞争后被误记为网络中断。
2. 按 Chat Completions、Messages、Responses 的真实输出行为分别核验下游等待；不再用单一“330 秒”覆盖全部协议。
3. 将“只有一次 Attempt”修正为“发生 `STREAM_IDLE_TIMEOUT` 后不再新增 Attempt”，允许此前已发生的合法切换。
4. 把零长度原始块过滤写入解析器任务和验收，防止无数据活动无限续期空闲窗口。
5. 将 Coding Plan 并发租约时限绑定到总请求时限与安全余量，避免五分钟等待期间被过期回收。

## 1. 目标与验收口径

所有经过仟流 Gateway 的正式流式模型调用，统一使用 300,000 毫秒的上游流式空闲门限。连续 300 秒未收到上游有效数据时终止本次请求，向客户端返回：

> 上游模型响应中断，等待超时。请稍后重试，或切换其他模型。

目标是增加长推理请求的恢复等待窗口，并给出可理解、可操作的失败提示；不承诺修复上游停顿或保证原请求恢复。本次不实现自动换模型、自动重放、断点续写或 Agent 任务恢复。

“全平台”指正式模型调用链，覆盖已接入厂商、通用 OpenAI-compatible 资源、API 与 Coding Plan 模式，以及 Chat Completions、Messages、Responses 接口。模型发现、凭证探针、健康检查等管理操作保留其独立时限；非流式请求不改为等待 300 秒。

## 2. 当前证据与基线边界

- 曹磊 2026-09-22 17:22:57 发起的请求 `b0724f1b-b7f4-43e7-9d91-4a9304c355c1`，账本显示首字节 5.3 秒、耗时 221.2 秒，失败层为 `STREAM_IDLE_TIMEOUT`，响应已提交；后续同模型请求成功。
- 该证据确认网关等待上游新数据超时，不能单凭它区分厂商生成停顿和上游网络停滞，也不能证明多等到 300 秒一定成功。
- 本地策略默认为全局 45 秒，智谱 Coding Plan 独立默认 120 秒；厂商和模式级配置可覆盖全局。仅修改一个环境变量不足以统一门限。
- `@qianliu/provider-adapters` 当前使用 Undici 7.29.0，其客户端默认 `bodyTimeout=300000`；若不显式协调，底层与业务计时器可能竞争。
- Chat 和 Messages 可逐块北向提交，Messages 已有 5 秒协议 ping；Responses 当前聚合上游流后再生成北向 SSE，可能在上游持续输出时仍长期没有下游字节。
- Coding Plan 并发租约当前默认 60 秒，正式调用没有续租路径；虽然现有活跃计数依赖 `released_at`，仍需把 TTL 与长请求合同一致，消除未来或外部回收提前释放的风险。
- 生产此前只读观察到全局空闲配置 45 秒、上游请求总时限 600 秒；实施前必须重新核对生产提交、镜像、运行容器、资源模式和实际反代。
- 计划编写基线是分支 `codex/wecom-activation-release-20260911`、提交 `2b33719`，仅用于代码影响分析，不等于生产或开发候选基线。当前工作区有其他任务改动，后续实施必须使用隔离工作区。

## 3. 行为合同

### 3.1 空闲计时与分层超时

1. 第一个上游有效非空原始数据块到达后，启动空闲计时；此后每个有效非空原始数据块重置计时。
2. 包含文本、推理、工具调用片段的 SSE 事件以及合法上游 SSE 注释／心跳可作为上游活跃证据；无需产生可展示正文。
3. 零长度 TCP 块、空读取、网关发给客户端的心跳、客户端自身活动不得刷新上游空闲计时。
4. 连续空闲达到 300,000 毫秒时触发业务层取消和终止；299 秒内恢复则重置完整窗口。计时器清理后不得残留回调或重复结算。
5. 上游明确断开、异常 EOF、损坏事件或其他确定失败立即按原规则结束，不等待满 300 秒。
6. 首字节等待策略保持现状；总调用时限继续独立生效。总时限先到时返回 `REQUEST_TIMEOUT` 对应结果，不套用空闲超时文案。
7. 底层 HTTP headers/body 超时必须晚于对应业务层计时器并留出确定余量；不得与 300 秒设为相同值。底层意外抢先终止必须在测试中可识别为失败。

### 3.2 配置统一

正式调用链采用一个全局空闲配置：`GATEWAY_UPSTREAM_STREAM_IDLE_TIMEOUT_MS=300000`，代码默认值同为 300000。

- 取消智谱 Coding Plan 空闲特例和正式调用中厂商／模式级空闲覆盖的生效逻辑；首字节策略保留既有差异。
- 旧 `GATEWAY_*_STREAM_IDLE_TIMEOUT_MS` 厂商／模式变量仅产生一次脱敏弃用提示，部署时清理，不得静默覆盖全局值。
- 全局配置保留正整数毫秒校验和空值默认行为；所有正式资源的解析结果必须为 300000。
- 通用 Caller 默认空闲值与正式生产装配保持一致。模型发现、权限探针、模型验证等显式管理调用继续使用自己的独立时限。
- 不新增管理后台页面、数据库配置表或数据库迁移。

### 3.3 下游连接与三协议

- Messages 保留现有协议 ping；ping 只能维持下游连接，不能刷新上游空闲计时。
- Chat Completions 和 Responses 由可控反向代理提供足以覆盖业务窗口与错误发送的等待时间；若需要协议保活，必须先用真实客户端验证 SSE 注释或事件兼容性，再作为实施设计的一部分。
- Responses 因当前聚合转换，客户端／代理等待必须覆盖整个 600 秒总调用时限及错误发送余量，推荐可控链路不低于 660 秒，而不是 330 秒。
- Chat／Messages 已提交后的空闲窗口至少覆盖 300 秒并留出错误发送余量；仍须以实际代理指令语义和客户端测试为准。
- 第三方客户端存在无法调整的更短时限时，明确记录不支持的入口，业务验收不得标记完整通过。

### 3.4 错误提示、Attempt 与计量

- 仅 `failureLayer=STREAM_IDLE_TIMEOUT` 使用本计划文案；首字节、总时长、客户端取消、限流、鉴权和普通网络断开保持独立含义。
- 保留 `upstream_timeout`、`STREAM_IDLE_TIMEOUT`、真实请求 ID和已提交后的中断分类，不把错误伪装为模型正文。
- 已提交：使用协议内错误并关闭流；不重写已经发送的 HTTP 状态。未提交：使用兼容错误包和 HTTP 504。Responses 聚合路径必须覆盖未提交空闲超时。
- 一旦某个 Attempt 以 `STREAM_IDLE_TIMEOUT` 结束，本请求不再启动新 Attempt。该规则不否定空闲超时之前已经完成的合法 Attempt。
- WorkBuddy 是否保留中文文案、是否追加自身 3003 包装，以实际客户端验证为准。
- 沿用事实计量：已收到的用量按既有质量标记处理，缺失用量保持未知／估算语义；超时后释放连接、额度预占和租约，原请求失败事实不被后续成功覆盖。
- Coding Plan 并发租约 TTL 至少覆盖总调用时限和结算／释放余量，并由正式运行时同源派生；不得继续依赖 60 秒默认值。

## 5. 验收矩阵

| 编号 | 场景 | 预期 |
|---|---|---|
| A1 | 已接入厂商、API／Coding Plan、通用兼容资源 | 正式调用有效空闲值均为 300000 |
| A2 | 无全局值、空值、旧厂商／模式值、非法全局值 | 默认 300000；旧值不生效并提示弃用；非法值启动失败 |
| A3 | 首块后静默 299 秒再恢复并完整结束 | 不提前失败，恢复后重置空闲窗口 |
| A4 | 连续有效空闲达到 300 秒 | 触发 `STREAM_IDLE_TIMEOUT`，返回规定提示和真实 ID；此后不新增 Attempt |
| A5 | 此前已有一次合法失败并切换，第二次 Attempt 空闲超时 | 总 Attempt 可为 2，但空闲超时后不再发起 Attempt 3 |
| A6 | 多次块间间隔小于 300 秒，总历时超过 300 秒 | 不把累计时长误当连续空闲；仍受总调用时限约束 |
| A7 | 上游心跳／注释、推理或工具片段；零长度块、下游 ping | 前者刷新上游空闲窗口；后者不刷新；零长度块不能续期 |
| A8 | Undici 默认边界附近的真实 HTTP 慢流 | 业务层先产生 `STREAM_IDLE_TIMEOUT`；不得被底层 body timeout 抢先变成网络中断 |
| A9 | Chat、Messages 已提交和未提交 | 合法流内错误或 HTTP 504；Messages ping 不改变上游计时 |
| A10 | Responses 上游持续输出但下游聚合等待超过 330 秒 | 可控代理／客户端不断开；成功时返回完整响应，空闲时返回 504 兼容错误 |
| A11 | 首字节、总时长、客户端取消、异常 EOF、损坏事件 | 按各自原因及时结束，不套用空闲超时提示 |
| A12 | Coding Plan 请求跨越 300 秒空闲窗口 | 并发租约不被提前回收；结束后释放，无重复放行和结算 |
| A13 | 部分用量或缺少最终用量的失败流 | 保留既有计量质量，额度预占和连接正常清理 |
| A14 | WorkBuddy 5.5.6 经等效公网反代访问受控慢流 | 300 秒前可控链路不断开，超时后用户实际看到约定提示或记录客户端包装缺口 |

计时边界使用假时钟确定性测试；Undici 竞争和三协议使用受控真实 HTTP 慢流；至少执行一次 300 秒真实时间链路验证。测试使用合成内容和隔离环境，不以生产用户请求充当试验。

执行相关包定向回归、typecheck、lint、build；遵守实施基线要求。既有全仓失败单独记录，不扩大本次修复。测试结果必须绑定候选提交和镜像。

## 6. 发布、回滚与完成标准

发布前保存原镜像、全局及旧覆盖值、HTTP Dispatcher 配置、并发租约派生值和实际代理配置。确认代码、镜像、容器环境和代理生效值一致；部署窗口处理在途长请求。

发布后分别报告代码验证、配置生效、链路验证和真实客户端验收。A1—A14 的适用项通过后才能进入业务接受；第三方客户端不展示提示时，不能声明端到端完成。

回滚恢复原镜像、原超时和代理配置，并核验有效门限、健康状态和租约释放。本次无数据库迁移，不修改历史失败事实。

部署后使用现有账本和异常中心观察断流比例、等待时长、并发占用、清理和新成功请求；不新建监控平台，也不把失败延后误报为稳定性改善。
