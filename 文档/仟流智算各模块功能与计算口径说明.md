# 仟流智算各模块功能与计算口径说明

2026年9月9日更新版

仟流智算用于统一管理企业的 AI 使用主体、厂商供给、调用规则、实际用量与经营支出。管理者可以沿着“谁在用、用什么、如何控制、用了多少、花了多少、哪里异常、谁能管理”的顺序理解系统。

### 模块索引

| 模块 | 主要解决的问题 |
| --- | --- |
| 首页看板 | 老板一眼看本月 Token、费用、活跃员工与活跃项目，及接入资源是否正常 |
| 使用主体 | 谁可以调用模型，额度和费用归属到谁 |
| 厂商资源 | 接入哪些 API 和套餐，供给、额度与资金是否正常 |
| 额度规则 | 调用怎样计价，何时放行、切换或限制 |
| 用量账本 | 每次调用发生了什么，实际消耗多少 |
| 经营账单 | 按月看支出，并按员工、项目和部门分析 |
| 运行保障 | 发现异常、追踪处理并核实恢复 |
| 系统设置 | 维护企业信息、管理员权限、登录安全和审计记录 |

### 阅读方式

每个模块按管理功能、重点指标、计算或判断规则、注意事项介绍。配置型模块的“算法”主要是权限和状态判断，不强行编造经营指标。示例中的金额、Token 和比例仅用于解释计算方式。

首页看板章节已按标准版首页（2026-09-10）更新，见下节。当前模块名称和行为以应用版本 7245669、数据库迁移 0072 为基准。文末列出子功能边界及实现索引，便于后续维护。

## 0 首页看板（标准版）

### 管理范围与功能

面向企业负责人的月度概览与资源健康入口，分两个分区：本月概览（本月 Token 消耗、本月费用、本月活跃员工、本月活跃项目四张卡片）与接入资源（按厂商列出资源数量、形态、调用状态与一句话关注信息）。每张卡片与区块右上角入口跳转到对应明细页。

### 重点指标与权威来源

| 指标 | 权威来源与口径 | 点击去向 |
| --- | --- | --- |
| 本月 Token 消耗 | 与厂商资源 / 用量总览同源：成功请求（不筛结算状态）的账本行，输入 + 输出合计（北京自然月） | 厂商资源 / 用量总览 |
| 本月费用 | 与经营账单月度总览同源：本月总花费（资金模式或余额桥接口径，多币种分别展示） | 经营账单 / 月度总览 |
| 本月活跃员工 | 与用量账本 / 用量概览同源：成功且已结算请求的去重员工数（企业时区自然月） | 用量账本 / 用量概览 |
| 本月活跃项目 | 与经营账单项目账同源：当月有用量归属的去重项目数（排除未归属请求） | 经营账单 / 项目账 |

### 同期比较与状态规则

- 每卡提供上月同期参照：上月 1 日至同一日同一时刻（半开区间）；上月无对应日期时截止上月月末，并在脚注写明。同期为真实聚合，不按天数折算。
- 上期为 0、未知或不可比（多币种、缺口）时不输出正常增长百分比；员工与项目显示数量差。Token 卡为页面唯一青色焦点，变化量保持中性色。
- 接入资源区调用状态按厂商内最差资源状态展示（正常 / 局部异常 / 异常 / 待确认）；额度或余额同步失败、同步数据过期与调用状态分别判断，正常厂商完整列出；凭证失效等异常以固定模板给出关注信息与范围。“管理资源”进入厂商资源 / 供给与健康。

### 需要注意

- 首页 Token 与首页费用的统计集合不同：Token 只算成功请求，经营费用含确有消耗的失败请求，两卡数字不构成同一集合，分别跳各自明细页。
- 活跃员工与活跃项目分别去重、分别统计，不可相加；项目账分页中的“未归属项目”行不计入活跃项目数。
- 数据来自服务端聚合接口（GET /dashboard/home），前端只格式化；刷新按钮重新拉取，失败时保留错误态与重试，不清零。

## 阅读前先区分四类数据

### Token 用量与额度扣减

总 Token 通常按输入 Token 加输出 Token 汇总。缓存命中 Token 是输入的分项，推理 Token 是独立展示的细分字段；不能看到四个字段就全部相加。上游未完整提供用量时，应同时看数据质量标记。

套餐扣减按原始计量值乘命中倍率计算。倍率改变的是额度消耗，不会改变模型实际生成了多少 Token。例如原始计量 100、倍率 3，扣减是 300；不能据此说真实用量也是 300。

### API 消耗与现金付款

API 消耗是请求结算产生的费用；充值是向厂商账户增加可用余额；实付人民币是采购付款事实；套餐费用是已登记的订阅费用。这几个数可能在不同时间发生，也可能使用不同币种。充值金额不应直接当成当月 API 消耗。

不同币种分别汇总。默认币种设置不能把美元自动折算为人民币。已有“实付人民币”记录时，可据此看现金支出；不能自行用一个汇率补出系统没有记录的付款。

### 时间范围与数据完整性

经营账单按北京时间自然月统计，范围为月初零点至下月月初零点，包含起点、不包含终点。用量概览按企业时区划分日、周、月。选择相同日期前，先核对时区、主体维度、请求状态和结算时间。

“0”表示已知没有发生；“—”、未知、不完整表示不能给出完整结论。存在部分已知金额时，可以保留已知部分并提示缺口，但不能把部分合计视为完整账单。

### 为什么两个页面可能对不上

用量概览主要统计成功且已结算请求；经营分析会排除没有消耗的失败记录，但保留确有 Token、费用、扣减或已输出响应的失败记录。请求明细还保留失败和拒绝等审计事实。比较时必须统一筛选条件，不能直接用总行数互相核对。

## 1 使用主体

### 管理范围与功能

管理真正调用 AI 的员工和项目，包括新建、改名、启用、停用、归档或符合条件时删除，以及 Key、模型授权、额度和核算归属。组织通讯录提供人员与组织资料，批量模型授权用于统一配置多名员工的模型使用范围。

### 重点指标与字段

| 指标或字段 | 如何理解 |
| --- | --- |
| 主体类型与状态 | 员工或项目；在用、停用、归档 |
| 模型授权和有效期 | 允许使用的模型，以及授权开始和截止时间 |
| 授权额度与已用额度 | 按有效规则记录的额度上限和周期扣减 |
| Key 状态 | 用于业务调用的凭证是否仍有效 |
| 部门与项目负责人 | 用于核算归属，项目部门随负责人所属部门确定 |

### 计算与判断规则

调用前先检查主体启用、Key 有效、模型已授权、授权处于有效期。额度剩余 = 授权额度 − 当前周期已用额度；预计剩余 = 额度剩余 − 本次预估扣减。预计剩余不足且不允许超额时拒绝；允许超额时记录超额事实。

放行后先预占额度，请求结算后校正：新已用额度 = 预占后的已用额度 − 本次预估值 + 本次实际扣减值，最低为 0。这样可减少并发请求同时看到足额余额的问题。

### 需要注意

主体账号与后台管理员是两套身份：员工能调用模型，不代表能登录管理后台。通讯录里有人，也不代表已为其开通 AI 主体或完成模型授权。

停用主体会撤销其 Key；重新启用不能假定旧 Key 自动恢复。清理前先判断历史引用，已有使用和核算事实的主体应保留历史或归档。变更部门、项目负责人时，需要区分当前归属与已经冻结的历史账单。

## 2 厂商资源

### 管理范围与功能

管理厂商的 API 与 Coding Plan 资源，包含资源接入、模型发现、凭证维护、额度同步、供给健康、充值和订阅登记。这里回答“企业现在有什么资源、还能用多久、钱和额度从哪里来”。

| 子页面 | 主要内容 |
| --- | --- |
| 资源利用 | 资源清单、接入状态、可用模型及资源详情 |
| 用量总览 | 按厂商、资源或模型查看成功调用的消耗 |
| 额度窗口 | 厂商提供的不同额度窗口、剩余量、重置时间和同步状态 |
| 供给与健康 | 资源状态、消耗速度、耗尽预测和恢复情况 |
| 充值与订阅 | API 资金事件、套餐服务周期、自动续订和历史记录 |

### 重点指标

API 重点看账户币种、期初余额、充值、已结算消耗、当前余额、资金缺口和对账状态。Coding Plan 重点看套餐费用、服务周期、总额度、已用额度、剩余额度及下一重置时间。共同关注最近同步时间、资源健康、凭证状态与预测可信度。

### 计算与判断规则

额度使用率 = 同一窗口已用额度 ÷ 同一窗口总额度 × 100%；剩余比例 = 剩余额度 ÷ 总额度。分母必须大于 0，单位和窗口必须一致。厂商提供多个窗口时分别展示，不把日额度、周额度和月额度相加。

新的 API 资金账本按事件推算余额：期初余额 + 期初修正 + 充值 + 对账调整 + 历史费用调整 + 冲销净额 − 已计价消耗。调整项使用记录自身的正负号。缺期初或存在未计价请求时，余额状态会提示不完整；余额为负时需要对账。

### 需要注意

平台资金账本是根据登记与结算事实计算的结果，不等同于厂商官网实时余额。厂商额度、平台实际 Token 和平台资金余额各有数据来源；应先核对同步时间、窗口、币种和完整性。

### 厂商资源的预测与订阅规则

#### 供给预测怎样计算

系统分别计算近 1 小时、24 小时、7 天的消耗速度。单窗口速度 = 窗口消耗量 ÷ max（已覆盖小时数，1）。没有数据点，或覆盖不足窗口长度的四分之一时，该窗口不参与预测。

综合速度 = 各有效窗口“速度 × 权重”的合计 ÷ 有效权重合计。近 1 小时、24 小时、7 天的权重依次为 0.5、0.3、0.2。剩余可用小时 = 剩余额度 ÷ 综合速度；预计耗尽时间 = 当前时间 + 剩余可用小时，且不会晚于资源失效时间。

示例：三个窗口速度为 100、80、50 单位/小时，全部有效，则综合速度为 84。剩余 840 单位时约可覆盖 10 小时。这是按近期行为外推的估计，不是厂商承诺。

剩余额度未知时不输出精确耗尽日期；速度缺失或为 0 时也不强行给日期。程序以窗口数据点数量和覆盖情况判断可信度：数据点合计不足 10 时为低；达到门槛且 1 小时、24 小时均有效时为高，否则为中。

#### 充值与订阅怎样记录

API 充值分别记录账户入账金额、账户币种和实付人民币，避免把到账额度与真实付款混在一起。套餐订阅记录产品、服务起止、付款及对应周期；当月费用与跨月服务周期是两个口径。

自动续订是平台按照已登记信息延续订阅记录的功能。取消后保留本期及历史记录。它不代表平台已向厂商完成扣款，也不能代替在厂商后台取消实际自动扣费。

#### 恢复资源时需要注意

凭证失效需要更新授权并验证真实调用。额度查询或同步成功，只能证明该查询通路恢复，不能直接证明模型调用凭证可用。不要仅因为额度数字重新出现，就把资源视为已经全面恢复。

充值与订阅入口受资金模式控制。资金模式未开启时仍可能使用旧的经营快照口径；新旧口径的差别见经营账单说明。

## 3 额度规则

### 管理范围与功能

管理模型计价与调度策略。计价解决“本次请求按哪个单价或倍率结算”；调度策略解决“在当前条件下允许、切换、限流、拒绝还是允许超额”。主体可用模型与个人额度仍由使用主体中的授权配置负责。

### 重点指标与字段

| 字段 | 管理含义 |
| --- | --- |
| 资源及模型范围 | 规则适用于哪些资源与上游模型 |
| 生效时间与时间窗 | 何时开始、何时结束，是否按星期或时段区别 |
| 输入命中价 输入未命中价 输出价 | API 三类 Token 的单价 |
| 倍率与计价模式 | 直接单价，或冻结基础单价后乘倍率 |
| 优先级和版本 | 数值较小优先；保留本次实际命中的规则版本 |
| 策略状态和动作 | 草稿与已发布不同，只有已发布策略参与调度 |

### 计价公式

API 费用 = 缓存命中输入 Token × 命中单价 +（输入 Token − 缓存命中 Token）× 未命中单价 + 输出 Token × 输出单价。界面显示每百万 Token 单价时，应将该价格除以 1,000,000 后代入。

倍率计价模式下，上述基础费用再乘该版本倍率；直接单价模式不额外乘倍率。费用以十进制定点精度计算，避免浮点误差；套餐扣减 = 原始计量值 × 命中倍率，按整数扣减值结算。套餐已包含不应被解释为“真实成本为零”。

示例：输入 1,000，其中缓存命中 200，输出 500；每百万 Token 单价依次为 1、2、4 元，费用为 0.0038 元。若使用 2 倍计价模式，费用为 0.0076 元。

### 需要注意

价格与倍率必须对应资源形态，不能用 API 价格冒充套餐额度规则。规则变更影响其生效范围内的新结算；已有账本保存原规则版本和命中证据，不应被当前价格覆盖。

### 额度规则的匹配与调度

#### 多条计价规则如何确定唯一结果

先按资源、模型、生效期和时间窗筛选，再依次比较：较小优先级、更具体的资源与模型范围、有时间窗的规则、较新的生效版本，最后按 ID 稳定排序。一次计价选中确定版本，不能把所有命中的倍率叠乘。

时间范围包含开始、不包含结束。跨午夜窗口归属于开始日，例如“周一 23:00 至 02:00”包含周二凌晨 01:00。同一规则内多个窗口重叠时，按配置顺序记录第一个命中窗口。

#### 技术路由与经营策略怎样配合

技术路由先过滤不满足调用条件的资源，排除本请求已尝试的资源，选取最小优先级的候选组，再在组内评分。当前评分为 0.4 × 归一化静态权重 + 0.4 × 健康因子 + 0.2 × 会话亲和因子。

健康因子：正常资源为 1、降级资源为 0.6、半开探测为 0.3；会话亲和因子在命中最近成功资源时为 1，否则为 0。最高分中选，同分按资源 ID 稳定选择。它不是随机轮询，也不是单纯选择最低价格。

经营调度再按模型、资源、主体范围、时段、价格倍率、剩余比例或耗尽风险匹配已发布策略，执行对应动作。自动切换只允许在配置的等价资源组内进行，并仍需满足可调用性约束。

#### 调度节省如何理解

可计算的调度节省 = 已发布基线在同一请求条件下的可比成本 − 实际执行动作后的成本。必须确实执行了动作，并有可比价格或倍率证据；只是提示、没有执行或基线不可比时，不应宣称实现节省。

#### 需要注意

保存草稿不等于已经发布。给策略配置切换目标后，还要确保目标资源、模型授权和计价可用。允许超额也不等于可以绕过凭证失效、主体停用或资源硬性不可用等约束。

## 4 用量账本

### 管理范围与功能

保留请求级使用事实，用来查消耗、解释费用和排查失败。用量概览提供周期指标、趋势与主体排名；请求明细支持按主体、项目、Agent、厂商、资源、模型、状态和时间组合筛选，并下钻查看路由、上游尝试与结算证据。

### 重点指标

| 指标 | 统计口径 |
| --- | --- |
| 活跃主体 | 所选维度和周期内有统计用量的不同主体数 |
| 请求数 | 概览统计成功且已结算请求，明细依筛选状态展示 |
| 真实 Token | 输入加输出，另列缓存与推理细分 |
| API 费用 | 相应请求结算费用，需同时关注未知金额 |
| 套餐扣减 | 按命中倍率折算后的额度消耗 |
| 数据质量 | 上游实报、估算、账户聚合、混合或未知 |

### 计算与判断规则

概览先按企业时区确定日、周或月范围，再选成功且已结算事实，按员工或项目归属聚合。趋势按小时或天分桶，消耗排名按相应主体用量排序。已结算请求的统计时间不能简单理解为页面打开时间。

一条用户请求可能包含多个上游尝试。请求数按请求标识统计，费用和细分用量根据对应结算记录汇总；不能把一次重试当成另一名用户发起的新请求。详情保留当次实际路由和计价版本，便于解释“为什么用了这个资源、为什么这样扣减”。

### 需要注意

概览和请求明细的状态范围不同，明细中的失败或拒绝不会自动进入成功用量概览。员工视角与项目视角也不是互斥的数据集合，不能将两者总量直接相加。

“真实 Token”是页面指标名称，仍要结合实报或估算等质量字段。未知不是零。查看排名和趋势时，应注意数据时间；接口刷新失败不能被当作“本周期无消耗”。

涉及多币种的费用核对优先使用经营账单或资金账本中的币种分组，不能仅凭用量页面的金额符号推断已经完成汇率转换。

## 5 经营账单

### 管理范围与功能

按北京时间自然月汇总 AI 投入与使用，支持月度总览、员工账、项目账、部门账、套餐利用率与采购复盘。它帮助管理者判断费用去了哪里、哪些主体在使用、购买的资源是否匹配实际需求。

### 重点指标

| 指标 | 含义 |
| --- | --- |
| 本月总 Token | 当月经营分析口径下的输入与输出合计 |
| 期初余额 本月充值 期末余额 | 资源资金在本月的变动情况，按币种区分 |
| API 花费 | 资金模式启用时来自请求已计价费用 |
| 套餐费用 | 资金模式启用时来自当月登记的套餐付款净额 |
| 本月总花费 | 同币种 API 花费加套餐费用，不等于现金支出 |
| 活跃主体与人均用量 | 分别看实际使用主体，以及公司用量相对员工规模 |
| 已确认金额价值 | 已确认价值记录的金额，不等于系统自动识别的收益 |

### 计算与判断规则

资金模式已启用时：API 花费按对应账户的当月计价消耗汇总；套餐费用按当月资金事件的套餐现金记录汇总；总花费按币种合计。未计价请求会形成缺口，页面可展示已确认部分并提示不完整。

资金模式未启用时，旧口径仍可能使用“期初余额 + 本月充值 − 期末余额”推算 API 花费，以及经营快照中的套餐费用。缺余额、币种不一致或桥接结果为负时不能正常推算。核对历史月报时必须先确认使用了哪种口径。

### 需要注意

套餐可能跨月服务，但当前现金口径按付款记录发生月份计入，不能自行解释成按服务天数摊销。不同维度和新旧资金模式可能使用不同统计时间或来源，月报对比应保留版本与口径。

### 经营账单的员工账项目账与部门账

#### 各子账管理什么

员工账回答“哪个员工用了多少”；项目账回答“哪些使用归属于这个项目”；部门账回答“费用归属于哪个部门”。项目通过已保存的负责人关系确定部门，已有请求归属快照和已关闭账单优先保留历史含义。

#### 重点指标

关注输入、输出、总 Token、API 费用、套餐分摊、合计费用、请求数、活跃天数、最后使用时间、用量占比和数据质量。部门账还需要看未归属部分；没有归属不能擅自分给一个部门。

#### 计算与分摊规则

总 Token = 输入 + 输出；活跃天数 = 当月有使用的不同日期数；请求数按请求标识去重。主体用量占比 = 该主体总 Token ÷ 同口径全部主体总 Token × 100%，分母为 0 或未知时不给比例。

部门费用按有效归属汇总相应请求的 API 费用和套餐分摊。部门总费用 = 已归属该部门的 API 费用合计 + 套餐分摊合计；未归属记录单独保留，不在多个部门重复计费。

新资金口径的套餐分摊按“同资源、同自然月”的原始输入加输出 Token 占比分配：主体分摊费用 = 该资源当月套餐费用 × 主体当月 Token ÷ 资源当月总 Token。不能把不同资源混成一个分母，也不能把倍率扣减直接当成原始 Token。

示例：某资源本月套餐费 300 元，甲使用 100 万 Token，乙使用 200 万，则分别分摊 100 元和 200 元。金额取整后出现尾差时，按最大余数法补齐：先向下取整，再将剩余最小金额单位依小数余数从大到小分配，保证分摊合计守恒。

同资源分母中存在未知用量，或本月没有用量时，相关套餐费保留为未分摊，不强行平均。旧快照口径的套餐分摊可能按倍率后的扣减占比分配，因此跨版本比较时应保留该差别。

#### 需要注意

员工账、项目账、部门账是不同分析维度，不是三类可以相加的独立支出。员工请求归属于项目后，两个视角都可能看到相关使用。账单已关闭时读取冻结版本；修改当前负责人不能直接重写已关闭月份。

### 经营账单的利用率与采购复盘

#### 管理范围与重点指标

套餐利用率观察厂商套餐用量的月度变化；采购复盘观察每月与年内的现金投入、充值和 API 消耗。重点关注历史峰值、月度利用率、综合利用率、年内总付款、平均每月付款、最高付款月份和资金账户完整性。

#### 当前套餐利用率公式

单厂商月利用率 = 该厂商当月 Coding Plan Token ÷ 该厂商已有历史记录中的最高月 Coding Plan Token × 100%。峰值基准来自历史使用数据，不是购买额度；峰值也不保证仅限选定年度。没有正数峰值或当月用量未知时，不能计算。

当前综合利用率取 Kimi 与智谱两项月利用率的算术平均，要求两项都可计算。它不是按采购金额加权，也不代表全部厂商的综合利用率。

示例：某厂商历史峰值为 1,000 万 Token，本月 600 万，则该页面显示 60%。这不能推出厂商套餐“还剩 40%”。厂商真实额度使用比例应回到厂商资源的对应额度窗口查看。

#### 采购与趋势计算

年内付款合计按选定年份的 1 月至所选月份累计；平均每月付款 = 年内累计付款 ÷ 所选月份序号。例如选择 9 月，则除以 9，不是只除以发生付款的月份数。未来月份不填成已发生付款。

年内平均月 Token 从该年度中不早于首次记录用量月份的期间计算；人均 Token = 公司当月总 Token ÷ 该月统计截止时仍存在且未归档的员工主体数量（包含停用但未归档主体），当前月用统计时点人数。此处员工数量不是“活跃员工数”，也不是企业全体通讯录人数。

环比变化 =（本期值 ÷ 上期值 − 1）× 100%；上期值为 0 或缺失时不给正常百分比。API 充值账户金额与实付人民币单独保留，不能直接当成同一个币种数相减。

#### 需要注意

当前“对账与导出”“价值确认”在经营账单主页面保留入口，但对应区域仍为空，不能按已有完整操作流程介绍。已确认价值指标的存在，也不证明页面已具备完整的录入、确认或 ROI 计算功能。

## 6 运行保障

### 管理范围与功能

异常中心集中查找调用、路由、流式请求、后台同步、凭证及调用扣减等异常，支持按月份、主体、厂商、关键词筛选，查看详情、登记处理结果并追踪恢复证据。通知与人员目前明确暂缓。

### 重点指标与字段

| 字段 | 如何使用 |
| --- | --- |
| 异常类型与严重度 | 判断影响范围和处理顺序 |
| 首次发生 最近发生 发生次数 | 区分单次事件、持续问题和再次发生 |
| 关联主体 资源 请求 | 定位实际受影响对象，不臆造归属 |
| 是否处理与处理记录 | 反映人工处理状态和备注 |
| 恢复时间与恢复证据 | 反映后续客观成功事实，独立于人工处理 |

### 判断与合并规则

系统从明确的请求失败、调度差异、未闭合扣减对账差异、凭证状态和后台任务失败等事实生成异常。普通额度限制、策略主动拒绝和正常客户端取消等情形会按分类排除，避免把正常控制动作全部报成故障。

异常使用稳定标识匹配历史记录，保留发生时间、重复发生与处理情况。按月查询需要考虑异常时间与月份的交集，不能只查“本月新建记录”，否则跨月未结束的问题会消失。

自动恢复需要后续证据：例如同资源相关模型后续调用成功，或对应后台任务随后成功，或对账差异已关闭。恢复证据包含时间与关联记录；异常暂时没被本轮扫描查到，不足以证明已经恢复。

### 需要注意

“已处理”表示有人进行了处理或确认，不代表底层服务恢复；“自动恢复”表示出现恢复证据，不等于人工已核查，也不保证以后不再故障。再次失败应保留新的发生事实。

凭证异常与额度同步异常要分别判断。查看历史故障时，要区分那次故障后的成功证据与资源当前状态。当前版本不应承诺完整通知送达、自动联系人同步或已覆盖所有业务告警场景。

## 7 系统设置

### 管理范围与功能

包含企业信息、账号与安全、审计日志、关于版本四个页签。企业信息维护名称、联系人、邮箱、时区和默认币种，不再包含企业 Logo 上传。账号与安全管理真实管理员、自定义岗位、密码、登录策略及有效会话。

### 重点字段

企业信息关注时区与币种；管理员关注启停和归档状态、角色、岗位名称及查看和操作权限；登录安全关注失败次数、失败计数窗口、会话有效期和首次改密；审计关注时间、动作、对象、操作人、结果和变更详情；关于版本关注当前应用版本与已有升级记录。

### 权限与安全判断规则

超级管理员拥有全部模块权限。自定义角色以岗位名称加权限勾选定义：查看需要 view 开启；操作需要 view 与 operate 同时开启。账号授权、登录策略修改和发布类操作仍仅限超级管理员，不能依靠勾选绕过。

当前每个企业保存一套自定义岗位配置，所有 CUSTOM 管理员共享；不是可创建无限多个不同岗位的角色管理系统。修改岗位权限会影响使用这套岗位的账号。系统保护最后一名有效超级管理员，避免管理入口被全部锁死。

新建或重置密码使用 Argon2id 哈希保存，登录通过哈希校验，不提供读取原密码的功能。新密码要求为 12 至 128 位，并包含大写、小写、数字和特殊字符。失败计数窗口内达到设置次数后限制继续登录；次数范围 3 至 10，窗口范围 5 至 60 分钟。会话有效期范围 15 至 1,440 分钟；缩短策略会限制现有会话，延长策略不会自动延长旧会话。

### 审计与版本规则

审计按企业时区将单日或日期段转换成时间范围，记录 ADMIN、SYSTEM 或 UNKNOWN 来源及变更前后内容。保存配置时检查版本号；多人同时修改发生冲突时要求刷新，避免静默覆盖。关于版本读取部署提供的 APP_VERSION，升级历史展示已有记录，不代表点击页面即可升级。

### 需要注意

自己改密码、为其他管理员重置密码、结束其他设备会话是不同操作。历史审计操作人未记录时保留未知，不自动猜成人名。集成与同步、通知设置、数据管理不属于本轮交付功能。
