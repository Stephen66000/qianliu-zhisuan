## 标准发布入口

参考 `V3/Evidence/Production-Release/20260810-pool039043-integration/run-release.sh`：

1. 传入完整 40 位 `CANDIDATE_COMMIT`，核对 GitHub main 精确 SHA；
2. 核对当前 Release、数据库基线和迁移阻断项；
3. 冻结旧应用镜像；
4. 构建 migrate／control-api／gateway／worker／web；
5. 停写，执行 `pg_dump -Fc`，用 `pg_restore -l` 校验并记录 Hash；
6. 按迁移链执行并核对列、索引、外键和最新迁移号；
7. 启动服务，检查健康、镜像来源、RestartCount 和数据库；
8. 原子更新 current release 指针，保存日志。

## 回滚／恢复边界

- 迁移前失败：恢复冻结镜像并启动上一 Release；
- 迁移后失败：保持停写，不允许旧应用在新 Schema 上继续写；
- 数据恢复：从本次 `pg_dump -Fc` 使用 `pg_restore --clean --if-exists --no-owner --exit-on-error` 恢复，再核对迁移号并启动旧应用；
- 当前脚本故意不自动执行破坏性 `pg_restore`，必须由运维人员确认目标数据库和备份 Hash；
- 本地真实 PG17 已有 migrate→rollback→migrate round-trip；生产发布备份均验证可列目录，但本轮未再做生产全库覆盖恢复。

## 运行检查

- 外部：Gateway `/health`、管理 Web、Control API；
- 容器：PostgreSQL、Redis、Worker 健康和 RestartCount；
- 业务：请求成功率、429／503、资源健康、熔断、额度窗口、账本完整性；
- 安全：不要求用户提交正文或完整 Key，故障定位使用时间、模型、状态码和 request ID；
- 变更：迁移、模型 alias、计费规则和 Key／Grant 操作必须保留操作日志和 Evidence。
