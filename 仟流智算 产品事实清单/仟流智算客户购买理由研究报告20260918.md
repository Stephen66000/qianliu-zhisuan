**版本说明：在 V1.0 基础上，纳入五项补访回答与“价值体现”页面截图。本版完成本轮内部访谈的研究整理；外部市场验证与未确定商务事项单独列示。**

## 一、研究结论

### 1. 本轮最重要的结论

对 Stephen 所经营的科技公司而言，AI 已经从少数员工零散使用的工具，发展为团队持续使用的工作资源。原先分别购买、多人共用账号的方式，出现了使用归属不清、额度闲置与集中耗尽并存、部门及个人成本难以统一核算等问题。

仟流智算的购买理由，可以归纳为：

> **企业已经在持续购买和使用 AI，就需要把这些投入管理起来。仟流智算把模型、Token、人、钱连接起来，让老板看清使用与成本，按员工、部门和项目核算，并据此调整采购、额度和资源使用方式。**

Stephen 在本轮补访中，将老板最重视的价值明确表述为两项：

**成本管控：**买了多家厂商的资源，既要满足员工工作需要，也要知道钱花在哪里，怎样减少不必要的重复采购、闲置与资源不足。

**效果评估：**买来的算力究竟使用得怎么样，需要有工具把使用、覆盖、利用与成本呈现出来，为管理判断提供依据。这里保留受访者“效果评估”的用词；现有证据支持的是算力使用和采购效果的评估，不等于仅凭 Token 就能计算员工业务贡献、工作质量或新增收入。

他的管理目标是鼓励员工使用 AI，而不是为了让账单下降而限制正常工作。

### 2. 本轮新增了哪些有分量的证据

**有实际后果。**一次共用资源额度不足后，同事没有立即补买账号，而是等待额度恢复，再继续用 AI 完成相关工作，实际等了一天多。这证明问题曾影响具体工作的推进。它不等于已经证明该员工整天没有工作，或整个项目延期了一天多。

**有管理用途。**Stephen 明确表示，看到数据后能够主动管理和调整资源。他举出智谱使用多、Kimi 使用少的场景，讨论资源是否保留、高峰时段是否路由至 Kimi，同时把任务所需的模型质量作为前提。这个回答说明了数据如何进入管理决策；具体路由方案是否已经实施及其结果，本轮没有取得记录。

**有量化页面。**补充截图显示了两种不同的比较：当月账号等效少购节约 **1,863.30 元**，以及 Coding Plan 相对页面 API 基准的等效采购降本 **7,993.39 元**。两者的基准不同，不能相加为一个总节省金额。具体公式见第七部分。

**有商业化方向。**Stephen 当前倾向采用 SaaS 方式，但明确这仍是想法；正式价格与标准交付未定。本轮无需为了写完研究文档，强行把设想变成已经确定的商业条款。

### 3. 文档完成范围

本轮已经可以完成一份有过程、有原始表达、有案例和初步数量依据的内部购买理由研究文档。七个访谈问题均已覆盖，回答深度在下文逐项标明。

这不等于七项研究工作全部完成了外部验证，也不等于所有潜在客户都会认可或购买。科技公司内部案例已有依据；教育等其他行业、外部付费意愿、厂商价格与授权条件仍未在本轮独立验证。

## 四、候选客户与筛选共识

### 1. 五类候选客户

| 客户类别 | 本轮选择依据 | 优先级及证据状态 |
|---|---|---|
| 科技开发公司 | Stephen 的公司已有 AI Coding、多人使用、账号分配和用量核算问题 | 优先；有内部实际案例 |
| 在线教育企业 | Stephen 认为知识与文字处理场景较多，可能持续使用 AI | 优先；目前是待验证行业假设 |
| 广告营销、内容代运营公司 | 多客户、多项目、密集文字内容工作可能产生资源管理需求 | 后续候选；由讨论形成的假设 |
| 电商、跨境电商团队 | 商品内容、多语言等任务可能产生持续使用和成本归属需求 | 后续候选；尚无本轮真实案例 |
| 专业服务机构 | 咨询、财税、法律等文字工作较多 | 后续候选；尚无本轮真实采购案例 |

### 2. 两项优先条件

**已经高频使用 AI。**本轮不以完全不使用 AI、还需要从零普及使用价值的企业为优先对象。

**已经需要多家 AI 厂商的资源。**企业同时使用不同厂商时，统一入口、权限、资源分配和核算的价值更容易展开。多人、多部门、多项目会进一步增加管理需求。

保留这些条件作为优先筛选逻辑，但不写成“只用一家就一定不需要”或“只要高频、多厂商就一定会买”。

### 3. 角色区分

老板关心投入和成本、资源是否被合理使用、能否按组织核算；技术管理者负责提出需求、配置与调整；员工关心正常工作、可用模型和剩余额度。

本轮已经明确的本公司既往采购链是：**技术总监提出需求与方案 → Stephen 拍板。**它不等于所有外部企业都采用同一流程。

## 五、七个访谈重点问题及回答

### 问题一：问题是否真实存在？

**状态：已问清主要情境，有具体亲历。**

公司原来同时购买 Coding Plan 类账号和 API 资源。初期人数较少，一个账号可能供两三个人使用；随着团队更多地使用 AI Coding，共用方式的管理问题逐渐显现。

多人知道同一套账号凭证，谁登录谁使用，管理者难以知道每个人用了什么、用了多少。使用也不均衡：Stephen 回忆，有一次七天周期已经到第六天，还剩约 95% 的额度；另一次则是集中使用后，其他同事需要时发现额度不足。

他还描述过一次对高峰扣减规则注意不足，一个下午消耗约 30% 的额度，后续团队使用变得谨慎。具体厂商时段、倍率与现行价格没有在本轮核验，应记录为亲历陈述，不能作为统一现行价格事实对外发布。

**研究结论：**本公司的需求来自实际使用中的归属、供给和核算问题，不是仅从功能表推导出的痛点。

### 问题二：这个问题是否值得解决？

**状态：价值已说明，新增具体工作影响；尚未形成完整损失统计。**

Stephen 表示，AI 已经是其团队完成开发工作的重要资源。额度不足时，要继续使用，就需要再购买资源，或者等待额度恢复。

本次进一步确认：**所述那一次，同事选择等待，等了一天多，额度恢复之后才继续用 AI 完成相关工作。**

这表明问题不仅是“账不好看”，还曾影响实际工作的推进。但本轮没有证据支持把这一天多全部计为无工作时间、人工损失或整个项目的延期。

额度闲置则对应另一类问题：已经购买的资源没有被充分利用，下一轮怎样购买、保留和分配缺少依据。

> “我们是鼓励员工用的。”

这句话决定了本轮价值方向：企业希望提供足够、可管理的 AI 资源，而不是简单减少员工使用来压低支出。

**研究结论：**对本公司，问题值得解决，涉及工作推进、资源利用和管理透明。本轮已补上具体后果，未统计总损失，也不据此编造金额。

### 问题三：现有办法为什么不够？

**状态：主要替代办法及局限已问清；竞品比较不在已完成范围内。**

**少量账号供多人使用：**采购数量少，但使用归属、额度分配和剩余情况不清，可能出现闲置或抢额度。

**每人单独购买：**Stephen 认为不同员工使用程度不同，低使用者可能用不完，高使用者仍可能不够。对话不足以证明公司曾长期全面实行过每人独立购买。

**分别登录厂商后台：**需要逐个平台查看，信息有限，也难以形成员工、部门、项目和财务之间的统一关系。

**只看花了多少钱：**不能解释哪些人员、模型和用量构成了费用。

仟流智算希望补上的，是把“模型—Token—人—钱”连接起来，并让这种关联进入授权、额度、资源选择及经营核算。

**研究结论：**更换理由不是单纯增加账号，而是把分散采购和使用变成可以统一管理、按组织归集的资源。

**排除无来源内容：**Stephen 没有讲过原来靠 Excel 汇总、手工台账、复杂报销或财务追问解决问题。这些不能作为访谈事实。S1 页面 DeepSeek 行含“杜绝分散报销”的界面文案，也不能倒推成公司确实发生过分散报销。

### 问题四：为什么现在需要买？

**状态：自研与使用的触发条件清楚；外部正式采购时点未给定。**

早期使用人数少、频次不高，少量账号先用着尚能应付。随着 AI Coding 在团队中持续使用，使用者和消耗增加，额度不足、闲置与核算不清的问题开始同时出现。

Stephen 在补访中进一步指出，他预期企业完成实际业务时会越来越多地购买算力，对费用和使用情况的管理会越来越重要。这是他的未来判断；本轮没有以外部市场资料验证需求或价格走势。

**本公司触发条件可以写为：**AI 从个别人使用的工具，变成团队持续依赖的工作资源；原有管理办法已不足以支持资源供给和成本判断。

没有必要凭空设定“达到多少 Token”“多少员工”“多少支出”就必须购买。本轮没有获得这些阈值，也没有外部客户预算周期或采购期限的证据。

### 问题五：客户真正重视什么结果？

**状态：定性目标充分，核心价值在补访中进一步明确；有量化比较入口。**

#### 1. 成本管控

Stephen 要知道企业买了什么资源、谁在用、用了多少、花了多少钱。他并不满足于知道一个月的总账单，还希望理解造成账单的模型、Token 和使用主体。

#### 2. 效果评估

保留受访者原词，具体指向：买来的算力是否有人用、哪些模型用得多、哪些资源利用少、各部门使用与成本怎样，以及采购方式是否经济。

P1 明确说明，不承诺通过 Token 推导员工创造的业务价值。因此本报告不把效果评估扩写成员工绩效自动评价、产出质量判定或新增收入测算。

#### 3. 组织层面的经营账

访谈反复强调员工账、部门账和财务账；P1 同时列有项目账，合计四本经营账：员工、部门、项目、财务。

“某部门二十个人、九个人使用 AI，这个月用了多少 Token、花了多少钱”是受访者用来说明需求的例子，不是经确认的本公司部门人数。

#### 4. 从看到数据到主动管理

Stephen 本次明确表示：

> “实现了主动管理，我们会去进行调整。”

他以智谱用得多、Kimi 用得少为例，提出对资源保留与高峰时段路由进行考虑。同时强调，是否转向 Kimi，还要看其算力质量能否满足任务要求。

记录原意时，不擅自把他提到“是否保留”的对象改成另一个厂商，也不把“考虑是否路由”改写成已经成功完成切换。

**可以形成的管理链条：**看到资源使用差异 → 判断差异原因与任务质量要求 → 评估采购、保留和路由安排 → 根据决定调整资源。

此链条来自其管理思路；本轮未取得某一次具体调整的执行日志及前后结果。

#### 5. 员工更关心剩余可用资源

Stephen 转述员工反馈：使用量和剩余额度都应该清楚，但员工更关注还剩多少，以便安排接下来的工作。

“像连接公司 Wi-Fi 一样使用公司的算力”是他对统一供给方式的比喻，不是完整技术描述。

**研究结论：**老板购买的价值是把投入和使用管清楚，员工获得的价值是清晰、可用的工作资源。这两者应一起表达。

### 问题六：谁能够把采购推动起来？

**状态：本公司的角色关系已明确，不需要重复问。**

既往 AI 账号和 API 资源采购由技术总监提出，Stephen 最终批准。技术总监强调先够用、尽量不浪费，不是直接购买最高档。

本轮仟流智算是自研自用，因此没有实际经历外部软件供应商议价、采购验收和合同付款全过程。

**研究结论：**本公司可以明确“技术负责人推动、老板拍板”；不能直接把这写成已有仟流智算对外成交案例。

### 问题七：什么会阻止购买？

**状态：内部采用情况和价格判断已问到；外部反对证据仍为空。**

Stephen 表示，自研自用没有明显接入顾虑。对将来客户采购，他目前最重视价格与收益的匹配。

他举例：买工具花三万元、节省四五万元，可以考虑；如果只能省一万元却收费两万元，就不符合其判断。这些是解释接受逻辑的假设金额，不是实际报价、客户预算或已实现节省。

本次访谈的初步收费设想为每人每年 199 元或 299 元，再结合约 20%—30% 的节省分成；尚未决定计费范围、是否叠加、分成底稿、上限和结算方式。

补访进一步确认：**商业化目前倾向 SaaS，但仍属于当前想法，不是已上线公共 SaaS 的事实。**

Stephen 认为主要是用量、请求等信息，隐私问题相对可控，尚未想到明确法务或财务阻力。本文保留为受访者判断，不写成已经确认不存在敏感性、合规或采购障碍。

**研究结论：**内部暂无明显阻力；对外采购的主要预判条件，是价格与客户认可的管理、使用和节省价值匹配。本轮没有独立证明外部客户的购买意愿。

#### 计算逻辑

这里的比较基准是：**同样四个人，如果每个人都分别购买 Kimi 和智谱各一个同档账号，需要八个账号；截图方案为两家各一个，共两个账号。**

```text
= 4 ×（199.00 + 422.10）
= 2,484.40 元

页面当前两家套餐的计入月费
= 199.00 + 422.10
= 621.10 元

等效少购节约
= 2,484.40 − 621.10
= 1,863.30 元

也可分项计算：
Kimi：（4 − 1）× 199.00 = 597.00 元
智谱：（4 − 1）× 422.10 = 1,266.30 元
合计：597.00 + 1,266.30 = 1,863.30 元
```

**可以写入案例的表述：**

> 在本次截图所示用量范围内，Kimi、智谱各一个套餐账号被四名员工使用。按四人分别购买两家同档套餐的比较基准，等效少购六个账号，月度采购费用差额为 1,863.30 元。

这与 Stephen 举的“六个人原来可能要六个账号，现在两到三个就能使用”的原理一致，但人数不能混在一起：**六人是他的示意例子；四人、两家各一个账号才是本张截图的具体数据。**

#### 口径边界

本轮没有确认公司过去实际每月支付过八个账号的费用，也没有确认每个外部客户原本都会给每人购买两家套餐。公式支持的是该基准下的等效少购额，不自动证明已经相对历史账单减少了 1,863.30 元支出。

页面使用了“月度净节省”一词，本文保留来源但不直接采用为客户最终净收益结论：软件费、托管或新增服务成本没有在这张表里呈现。

页面“可满足 6～8 人使用”属于界面承载评价。本轮看到的实际人数是四人，未取得六至八人负载验证，也不把“四人使用”写成“四人必然能同时满负荷使用”。

### 3. 口径 B：Coding Plan 相对页面 API 基准的等效采购降本

| 套餐 | 页面计入月费 | 当月 Token（页面显示） | 实际摊薄单价 | 页面标注的同级 API 基准单价 | 等效 API 采购成本 | 页面降本金额 |
|---|---:|---:|---:|---:|---:|---:|
| Kimi Coding Plan | ¥199.00 | 162.26 M | ¥1.23／M | ¥12.00／M | ¥1,947.18 | ¥1,748.18 |
| 智谱 Coding Plan | ¥422.10 | 444.49 M | ¥0.95／M | ¥15.00／M | ¥6,667.31 | ¥6,245.21 |
| 合计 | **¥621.10** | **606.75 M** | **约 ¥1.02／M** | 汇总栏另见口径备注 | **¥8,614.49** | **¥7,993.39** |

M 在本节沿用页面含义，即百万 Token。底层 Token 可能比展示值更精细，不用已四舍五入的 M 值倒推各行应精确到分的差额。

```text
页面等效 API 采购成本合计
= 1,947.18 + 6,667.31
= 8,614.49 元

页面计入的套餐月费合计
= 199.00 + 422.10
= 621.10 元

相对页面 API 基准的等效成本差额
= 8,614.49 − 621.10
= 7,993.39 元

按页面展示的总 Token 计算套餐摊薄成本
= 621.10 ÷ 606.75

```

**可以写入案例的表述：**

> 截图当月累计展示约 6.0675 亿 Token，页面计入两家套餐月费合计 621.10 元，摊薄约 1.02 元／百万 Token。按该页面采用的 API 单价基准折算，等效采购成本为 8,614.49 元，两者差额为 7,993.39 元。

#### 口径边界

这里的基准是“按页面 API 价格采购同等用量”，不是“给每个人购买独立套餐”。“官方同级 API 市价”是页面字段名称，本文没有验证其是否为当期真实、适用、可比的厂商价格，也未审计模型、输入输出、缓存与计费周期是否逐项可比。

这个差额包含套餐与 API 两种采购方式之间的价格差别。不能直接将全部差额归因于仟流智算单独创造，更不能称为新增收入或已经节省的现金净额。

### 4. 两种结果不能相加

```text
不采用的汇总方式：
1,863.30 元 + 7,993.39 元 = 总节省
```

两者分别是在“每人独立买套餐”和“按 API 购买用量”两种替代方案下，对当前套餐方式作比较。它们不是已经证明彼此独立的两笔收益。

研究文档可同时展示两种对比，帮助说明采购价值；对外报价、节省分成或客户净收益计算，必须明确采用哪个基准，不能重复记账。

### 5. 对购买理由的意义

本次补充后，已经不能再把证据状态写成“完全没有节省金额或计算方法”。正确状态是：

> **已有来自系统页面的数量、金额及可复算的比较公式；尚未完成原始账单、实际替代采购方案、全部新增费用与可比计费规则的核对。**

这使本轮研究从“只表达希望省钱”，推进到“能够展示怎样核算采购价值”。

## 八、可直接用于内部策略对齐的购买理由文字

### 1. 按原定模板整理

**这类客户：**已经高频使用多家 AI 服务、多人或多个部门共同使用资源的科技企业。科技与在线教育是本轮确定的优先方向，但本案例的实际证据来自科技公司。

**在什么情况下产生需求：**AI 从少数人的工具变成团队持续依赖的工作资源，账号、用量、费用与管理要求随之增加。

**要完成什么：**向员工持续提供工作资源，明确谁能用什么、能用多少，并按组织理解费用和使用情况。

**目前如何解决：**分别采购 Coding Plan 和 API 资源，少量账号多人共用，或考虑每人分别购买，再到各厂商后台查看。

**主要问题：**使用归属不清、额度闲置与集中耗尽并存、总量及部门成本难以统一核算。

**真实后果：**某一次额度不足后，同事等待一天多才恢复相关 AI 工作；其他总体损失没有统计。

**可能选择仟流智算的理由：**把模型、Token、人、钱关联起来，让成本管控和使用效果评估有依据；通过看到资源差异，进一步考虑采购、分配和路由调整，而不是只看到账单总额。

**目前能够提供的证明：**本公司持续内部使用经历；本轮访谈；组织经营账与调用记录等产品资料；S1 中账号复用、套餐月费、用量及两种等效采购比较。

**决策链：**本公司既往资源采购由技术总监推动、Stephen 拍板。

**主要购买条件：**价格与客户认可的价值匹配；资源使用能够支撑工作，调整路由时仍需考虑任务质量。正式收费、外部验收与交付尚未确定。

### 2. 完整叙述版

公司已经在买 AI、员工已经在用 AI，但管理者不一定知道谁用了什么、用了多少、费用属于哪个部门或项目。少量账号共用可能出现归属不清和额度冲突；给每个人单独购买又可能产生闲置。

在 Stephen 的公司，这种矛盾真实出现过：有的账号临近周期结束仍有大量额度，另一次却因额度不足，使同事等待一天多后才继续使用 AI 完成相关工作。

他希望解决的，不只是某个账号贵不贵，而是公司怎样持续供给并管理这笔投入。仟流智算把模型、Token、人员和费用关联起来，提供员工、部门、项目及财务视图，帮助管理者看清使用与成本，再决定资源是否保留、怎样分配、是否调整使用路线。

“价值体现”页面进一步给出了采购比较：在截图的四人使用场景下，两家各一个套餐，相对每人分别购买两家同档套餐，等效少购六个账号；同一批套餐的累计用量也可以与页面 API 价格基准作比较。它们是两套不同的采购对照，而不是可相加的收益。

因此，本轮购买理由可以表达为：**在鼓励员工持续使用 AI 的同时，让企业对投入实现成本管控，对使用实现效果评估，并据此主动管理资源。**具体客户能实现多少净节省，仍须结合其真实采购基准、使用情况及软件交付成本计算。

### 3. 一句话工作表达

> **仟流智算把企业分散的 AI 资源和使用成本连接到人、部门与项目，让老板看清用了什么、用了多少、花了多少，并有依据地管好这笔投入。**

这是本轮研究归纳，不是已经定案的广告语。

### A2. 汇总标签需要核对，保留原值

页面“合计／加权平均”中的 API 单价显示 **13.50 元／M**。该数等于两个显示单价 12 与 15 的算术平均；如果用页面等效成本合计除以 Token 合计，则约为：

```text

```

这表示“加权平均”可能采用了不同口径，需确认后台公式；本文不把 13.50 静默替换成 14.20，也不据此认定所有明细有误。

```text

折数 = 10 × 621.10 ÷ 8,614.49 ≈ 0.721 折
降幅 = 1 − 621.10 ÷ 8,614.49 ≈ 92.79%
```

上述结果与汇总标签不完全一致。可能涉及口径或数据时点，现有材料不足以判断具体原因。研究正文因此采用可以复算的金额差额，不把汇总折扣率作为已经核验的宣传结论。

### A2 后续（2026-09-19）：已核对闭环
